# データベース連携

*[English](database.md) | 日本語*

QuickER は、稼働中のデータベースからスキーマを取り込んで図に起こし、図とデータベースの差分を検出して同期スクリプトを適用し、図から DDL を生成します。図とデータベースはどちらの向きにも往復できるため、取込と差分同期を実行することで、図と実 DB の乖離を把握して解消できます。

## 対応 DBMS

| DBMS | スキーマ取込 | 差分同期 | DDL 生成 | 方言切替 | 備考 |
|---|:-:|:-:|:-:|:-:|---|
| SQL Server | ✅ | ✅ | ✅ | ✅ | 説明は拡張プロパティ（MS_Description）と同期 |
| PostgreSQL | ✅ | ✅ | ✅ | ✅ | 13 以降。説明は `COMMENT ON` と同期 |
| MySQL | ✅ | ✅ | ✅ | ✅ | 8.0 以降（MariaDB は対象外）。説明は `COMMENT` 句と同期 |
| Oracle | ✅ | ✅ | ✅ | ✅ | 19c 以降。説明は `COMMENT ON` と同期 |
| SQLite | ✅ | ✅ | ✅ | ✅ | ファイル DB。列の変更・削除・FK 変更を含む差分同期はテーブル再構築方式。説明の機構なし |

実データベースを使う取込・同期には、実 DB 統合テスト（SQL Server / PostgreSQL / MySQL / Oracle は Testcontainers のコンテナ、SQLite は実ファイル DB）を用意しています。コンテナを使うテストは Docker のある環境でのみ実行され、CI では自動的にスキップされます。また検証は各 DBMS の代表 1 バージョンで行っており、表のサポート範囲全体を網羅するものではありません。

## スキーマ取込（DB → 図）

ツールバーの「DB取込」ボタンから、接続ダイアログ「データベースから取込」を開きます。

### 接続の指定

- **サーバー型 DBMS** — 対象 DB、ホスト、ポート（空欄で方言の既定値）、データベース名、ユーザー名、パスワードを指定します。SQL Server では認証方式（Windows 認証 / SQL Server 認証）と「サーバー証明書を信頼する (TrustServerCertificate)」も選べます。Oracle にはサービス名の欄があります
- **SQLite** — ファイルパスを「参照」から指定します（取込では既存ファイルのみを指定できます）
- **タイムアウト** — 「接続タイムアウト」は接続そのものが確立するまでの待ち時間（サーバー型 DBMS のみ）、「コマンドタイムアウト」はスキーマ取込・同期の SQL 1 文が実行できる時間です。コマンドタイムアウトの既定は 60 秒で、SQLite を含む全方言に効きます。`0` は無制限（ADO.NET の規約）を意味し、負値は確定時に拒否されます。どちらも接続プロファイルごとに保存され、この設定が無かった頃のプロファイルは既定値で読み込まれます
- **接続テスト** — 実際にスキーマの取得を試行し、検出したテーブル数を表示します

> **注意:** 「サーバー証明書を信頼する (TrustServerCertificate)」は、自己署名証明書のローカル・コンテナ環境の SQL Server へそのまま接続できるよう既定でオンです。この設定はサーバー証明書の検証を省略するため、正規の証明書を持つ本番・リモートサーバーへ接続する場合はチェックを外し、なりすまし検知を有効にしてください。設定は接続プロファイルごとに保存されます。

### 接続プロファイル

入力内容は名前を付けて保存でき、次回から「保存済み接続」で呼び出せます。プロファイルは `%AppData%\QuickER\connections.json` に保存され、パスワードは本体とは分離した別ファイルへ **Windows DPAPI（CurrentUser スコープ）で暗号化**して保存されます（「保存」チェックを付けた場合のみ。既定の設定では平文で保存されることはありません）。最後に使った接続内容は自動的に記憶され、次回起動時に復元されます。

### 取り込まれる内容

- テーブル（ビューは対象外）と列（型・長さ・精度・NULL 可否）
- 主キー（複合キーの列順序を保持）
- 外部キー（制約名と ON DELETE / ON UPDATE の参照アクションを含む）。FK を持つ側の列集合が、そのテーブル自身の主キーまたは一意制約と一致する場合は 1 対 1 と判定されます。複数列で構成される外部キーはリレーションとしては取り込まれますが、列同士の対応付けは復元されません（1 本のリレーションが持てる列の対応は 1 組のため）。SQLite は FK 制約名を永続化しないため、取込時に制約名が合成されます
- テーブル・列の説明（SQL Server の MS_Description 拡張プロパティ、PostgreSQL の `obj_description` / `col_description`、MySQL の `TABLE_COMMENT` / `COLUMN_COMMENT`、Oracle の `user_tab_comments` / `user_col_comments`）。SQLite は説明の機構がないため対象外です

取り込まれるのはここまでです。境界の全体と、それが DDL 生成にとって何を意味するかは[図がモデル化する範囲](#図がモデル化する範囲)を参照してください。

取込結果は現在の図へマージされます。テーブル名・列名で現在の図と照合し、一致した要素は現在の図の要素の同一性を引き継ぐため、レイアウト・幅・色・メモと、それらを参照する名前付きクエリが温存されます。空き領域へ配置されるのは新しく取り込まれたテーブルだけで、現在の図に一致する要素が 1 件もない完全な新規取込のときにだけ、図全体が自動整列されます。確認ダイアログは、現在の図と構造的な差分がある場合に加えて、取込によって壊れる名前付きクエリがある場合にも表示され、削除対象のクエリ名が列挙されます。

取り込んだ後、手元の既存エンティティ資産と生成コードをどう付き合わせるかは、[生成コードの使い方の「既存コードベースとの共存」](code-generation.ja.md#既存コードベースとの共存)を参照してください。

## 図がモデル化する範囲

図はデータベースの複製ではなく設計モデルです。往復できるのは、図がモデル化している次の範囲だけです。

- テーブルと列（型・長さ・精度・NULL 可否）
- 主キー（複合キーの列順序を含む）
- 外部キー（列ペア・制約名・参照アクション）
- UNIQUE 制約
- テーブル・列の説明

これ以外はモデルの外です。取り込まれず、生成 DDL にも出ず、差分同期も検出・変更の対象にしません。

| スキーマ要素 | 取込 | 生成 DDL | SQLite のテーブル再構築 |
|---|---|---|---|
| `DEFAULT` | 取り込まない | 出力しない | 失われる |
| `CHECK` 制約 | 取り込まない | 出力しない | 失われる |
| `COLLATE` | 取り込まない | 出力しない | 失われる |
| 生成列（計算列） | 通常の列として取り込む（式は失われる） | 通常の列として出力 | 失われる |
| `IDENTITY` / `AUTO_INCREMENT` / `AUTOINCREMENT` | 取り込まない | 出力しない | 失われる（`INTEGER` の主キーは rowid 別名のままなので暗黙の自動採番は保たれる） |
| 非 UNIQUE インデックス | 取り込まない | 出力しない | 温存（`CREATE` 文の全文を保持して再作成） |
| トリガー | 取り込まない | 出力しない | 温存（同上） |
| ビュー・ストアドプロシージャ・関数・シーケンス | 取り込まない | 出力しない | 対象外 |

SQLite のテーブル再構築を除けば、これらのオブジェクトはそのまま放置されます。差分同期は検出すらしないため、手で作ったインデックスや `DEFAULT` はデータベースに残り続けます。図の定義からテーブルを作り直す再構築だけが例外で、だからこそ図が表現できないものを落とし得ます（QuickER は対象テーブルで見つかった属性を実行確認に列挙します。[SQLite の差分同期](#sqlite-の差分同期テーブル再構築方式)を参照）。

**DDL 生成は設計から新しいスキーマを作るための機能であり、取り込んだ既存データベースの再現には使えません。** 元のデータベースが上記のモデル化範囲だけで出来ていない限り、生成される `CREATE` 文は別物のスキーマです（テーブル・列・キー・制約は同じでも、既定値・CHECK・照合順序・自動採番・インデックス・トリガーは 1 つもありません）。既存データベースの移送にはそのデータベース自身のツールを使い、QuickER の DDL は設計から新規に立ち上げる用途に使ってください。

## 差分同期（図 → DB）

ツールバーの「DB同期」ボタンから、差分ダイアログ「DB スキーマ同期 (差分実行)」を開きます。データベースの現状と図の内容を突き合わせ、差分の一覧と生成 SQL のプレビューを確認したうえで、選択した項目だけを実行できます。

### 検出される差分

- テーブルの追加・削除
- 列の追加・変更（型・NULL 可否）・削除
- 外部キーの追加・削除
- 主キーの変更（付与・解除・キー列構成の変更）
- テーブル・列の説明の設定・更新・削除（SQLite は対象外）
- 列の並び順の変更（同期できるのは SQLite / MySQL）

同名の要素を同一とみなして比較するため、リネームは「削除＋追加」として検出されます。

列の並び順は、追加・削除を除いた共通列の相対順序で比較されます。SQLite と MySQL では選択可能な差分項目（既定では未選択）として同期でき、SQLite はテーブル再構築に畳み込み、MySQL は `ALTER TABLE ... MODIFY ... AFTER` で移動する列を最小限にします。他の 3 方言では案内として表示されるのみで、同期の対象外です。

### 実行の安全設計

- **破壊的な差分（削除・型変更）は既定で選択されず**、実行時には破壊的変更を含む旨の確認が表示されます
- 生成スクリプトは依存関係順（テーブル追加 → 列追加 → FK 削除 → 旧主キー解除 → 列変更 → 新主キー付与 → 列削除 → テーブル削除 → FK 追加 → 説明）に並び、種別ごとの見出しコメントが付きます
- FK 列を解決できない外部キー追加は、不正な DDL を出さずスキップコメントとして出力されます
- 複数列で構成される外部キー（複合外部キー）は正式に対応しています。リレーションは列ペアの順序付きリストを保持するため、取込・DDL 生成・同期のいずれも構成列をすべて運びます。主キー変更に伴う暗黙の解除・再作成や SQLite のテーブル再構築も同様で、複合外部キーが単一列へ静かに縮むことはありません
- SQL Server・PostgreSQL・SQLite ではトランザクションで実行され、失敗時はロールバックされます。MySQL / Oracle は DDL が暗黙コミットされる仕様のため、途中で失敗した場合は部分適用となる可能性がある旨が警告されます
- SQLite の再構築を含む実行では、再構築されるテーブルを列挙した専用の確認が表示されます
- 最初の差分検出で差分が 1 件もない場合は、その旨を表示したままダイアログは開いています。同期を適用したあとの再読込で差分がゼロになった場合は、自動で閉じます。実行が失敗した場合も差分を自動で再読込するため、部分適用後の状態が一覧に反映されます（MySQL / Oracle で意味を持ちます）

### 主キーの同期

図でテーブルの主キーを変更（付与・解除・キー列構成の変更）すると、テーブル単位の差分項目 1 件として検出されます（既定では未選択）。旧主キーの制約名は実行時にデータベースのカタログを逆引きして特定するため、任意の制約名を持つ取込済みデータベースでもそのまま動きます。スクリプトは「旧主キーの解除 → 選択した列変更 → 新主キーの付与」の順に実行されるため、旧キー列を NULL 許容へ変える変更も 1 回の同期で成立します。

変更対象の主キーを参照している外部キーは、変更の前後で自動的に「外して→作り直す」処理が入ります（SQL Server では外部キーに関わる列の変更でも同様です）。参照先の列が新しい主キーに含まれなくなる場合は、外部キーの再作成が失敗する可能性がある旨が実行確認に表示されます。失敗時、SQL Server・PostgreSQL ではスクリプト全体がロールバックされますが、MySQL / Oracle では外部キーが外れたままの部分適用になり得ます。

### 説明の同期

テーブル・列の説明は、説明の機構を持つ 4 方言で同期されます。SQL Server は MS_Description 拡張プロパティ、PostgreSQL と Oracle は `COMMENT ON`、MySQL は `COMMENT` 句を使います。既存の有無を判定して追加と更新を使い分けるのは SQL Server の拡張プロパティのみで、PostgreSQL と Oracle は `COMMENT ON`、MySQL は `COMMENT` 句を再実行します（いずれもそれ自体が冪等です）。図側で説明を空にすると削除されます。SQLite は説明の機構がないため、差分検出も同期も行われません。

### SQLite の差分同期（テーブル再構築方式）

SQLite は `ALTER TABLE` でできる変更が限られているため、列の変更・削除などを含む同期はテーブル再構築方式で行います。「データベースの現状＋選択した差分」を合成した新しい定義のテーブルを作成し、データを移送してから旧テーブルと入れ替え、インデックスなどの補助オブジェクトを再作成します。再構築はトランザクション内で実行され、コミット前に外部キー整合を検査（`PRAGMA foreign_key_check`）して、違反があればロールバックのうえ違反テーブルを報告します。

再構築後のテーブルは図の定義から作成されるため、[図がモデル化する範囲](#図がモデル化する範囲)の外にあるものは再現されません。`AUTOINCREMENT`・`DEFAULT`・`CHECK`・`COLLATE`・生成列は現在の DB にあっても**再現されず黙って失われます**（QuickER の外で設定した既定値が再構築後に消えるのはこのためです）。インデックスとトリガーは `CREATE` 文の全文を保持して再作成するため失われません。暗黙の自動採番も、`INTEGER` の主キーは再構築後も rowid 別名のままなので保たれます。喪失を見えるようにするため、QuickER は再構築対象テーブルの現在の `CREATE TABLE` 文を読み取り、見つかった属性を実行確認ダイアログに列挙します。その属性が必要なテーブルでは、同期後に手動で付け直してください（あるいはその変更自体を手書き SQL で実行してください）。

同期先の SQLite ファイルは、接続ダイアログの「新規作成」ボタンで新しく作ることもできます。空のデータベースへ図全体を適用して、新規構築に使えます。

## 方言切替

ツールバー右の「対象DB:」コンボで、図のターゲット DBMS をいつでも切り替えられます。

- 各列の型は「元方言 → 中立の正規型 → 新方言」の経路で自動変換を試みます
- 変換できなかった列は元の型を保持したまま、警告ダイアログに一覧表示されます
- 切替と型変換は 1 回の Undo でまとめて戻せます
- SQL Server の `rowversion` / `timestamp` は SQLite では通常の `BLOB` になり、同時に NOT NULL が解除されます（SQLite には採番する主体がいないため、ローカルで作った行は同期が書き込むまで版を持ちません）。この変換は非可逆で、その `BLOB` を SQL Server へ戻しても `varbinary(max)` にしかなりません（行バージョンには戻りません）。両者で列の意味がどう変わるかは [マルチターゲット Repository](code-generation.ja.md#マルチターゲット-repositorysqlserver--sqlite) を、2 つのデータベースを同期させるコードの生成は[双方向同期の支援](code-generation.ja.md#双方向同期の支援--generate-sync-support)を参照してください。他の方言には対応する型が無いため、`rowversion` 列は変換不能として警告に載ります

## DDL 生成

ツールバーの「出力」から SQL DDL を選ぶと、図の対象 DBMS の方言で CREATE 文一式を出力します。テーブル・列の説明も DDL に含まれます（SQL Server は sp_addextendedproperty、PostgreSQL / Oracle は COMMENT ON、MySQL は COMMENT 句、SQLite はコメント行）。エクスポート全般の操作は[インポートとエクスポート](import-export.ja.md)を参照してください。
