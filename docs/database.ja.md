# データベース連携

*[English](database.md) | 日本語*

QuickER は、稼働中のデータベースからスキーマを取り込んで図に起こし、図とデータベースの差分を検出して同期スクリプトを適用し、図から DDL を生成します。
図とデータベースはどちらの向きにも往復できるため、取込と差分同期を実行することで、図と実 DB の乖離を把握して解消できます。

## 対応 DBMS

5 つの方言のすべてで、スキーマ取込・差分同期・DDL 生成・方言切替ができます。
差分同期での方言ごとの違いは[検出される差分](#検出される差分)にまとめています。

| DBMS | 対応版 |
|---|---|
| SQL Server | 2016 以降 |
| PostgreSQL | 13 以降 |
| MySQL | 8.0 以降（MariaDB は対象外） |
| Oracle | 19c 以降 |
| SQLite | ファイル DB |

実データベースを使う取込・同期には、実 DB 統合テスト（SQL Server / PostgreSQL / MySQL / Oracle は Testcontainers のコンテナ、SQLite は実ファイル DB）を用意しています。
コンテナを使うテストは Docker のある環境でのみ実行され、CI では自動的にスキップされます。
また検証は各 DBMS の代表 1 バージョンで行っており、表のサポート範囲全体を網羅するものではありません。

## スキーマ取込（DB → 図）

ツールバーの「DB取込」ボタンから、接続ダイアログ「データベースから取込」を開きます。

### 接続の指定

- **サーバー型 DBMS**：対象 DB、ホスト、ポート（空欄で下の表の既定のポート）、データベース名、ユーザー名、パスワードを指定します。
  ポートは空欄だけが既定値の意味で、数値でない値や 1〜65535 の範囲外の値は、OK・「接続テスト」・プロファイルの保存で拒否されます（打ち間違いで既定ポートの別のインスタンスへつながることはありません）。
  SQL Server の Microsoft Entra ID 認証（旧称 Azure AD）は、ユーザー名を入れると対話式のサインインになり、空欄にすると既定の資格情報の連鎖（環境変数・マネージド ID など）を使います。
  Oracle の接続は EZConnect 形式 `host:port/service` で組み立てられます
- **暗号化 (SSL Mode)**：PostgreSQL・MySQL で、接続に TLS をどこまで要求するかを指定します。
  既定は「Unspecified」で、接続文字列へキーワードを載せずドライバ既定に委ねます（下の注意を参照）。
  接続プロファイルごとに保存され、この設定が無かった頃のプロファイルは「Unspecified」で読み込まれます
- **コマンドタイムアウト**：スキーマ取込・同期の SQL 1 文が実行できる時間です。
  既定は 60 秒で、SQLite を含む全方言に効きます（`0` は ADO.NET の規約どおり無制限）。
  空欄・数値でない入力・負値は、OK・「接続テスト」・プロファイルの保存のどれでも拒否されます（黙って既定値で動くことはありません）。
  接続プロファイルごとに保存され、この設定が無かった頃のプロファイルは既定値で読み込まれます
- **接続テスト**：実際にスキーマの取得を試行し、検出したテーブル数を表示します。
  テストの実行中は OK を押せません（テストは途中で取り消せないため、確定して閉じるとテストだけが接続を掴んだまま走り続けます）

#### 方言ごとの通信路の暗号化

この接続には DB の資格情報が乗るため、何も設定しなかったときに各方言がどう振る舞うかを把握しておいてください。

| 方言 | 何も設定しないときの既定 | 証明書の検証まで求めるには |
| --- | --- | --- |
| SQL Server | 暗号化されるが**証明書は検証しない**（TrustServerCertificate がオン） | 「サーバー証明書を信頼する」のチェックを外す |
| PostgreSQL | Npgsql の既定。サーバーが対応していれば暗号化するが**証明書は検証しない** | **暗号化 (SSL Mode)** を `VerifyCa` / `VerifyFull` にする |
| MySQL | MySqlConnector の既定。同じく暗号化はするが**検証しない** | **暗号化 (SSL Mode)** を `VerifyCa` / `VerifyFull` にする |
| Oracle | **平文 TCP** | ダイアログでは指定できません（後述） |
| SQLite | 該当なし（ローカルファイル） | — |

**暗号化 (SSL Mode)** の各値の意味は次のとおりです。

- `Unspecified`：キーワードを一切書かず、判断をドライバへ委ねます（既定。この設定が無かった頃と接続内容が同一になります）
- `Disable`：暗号化しません
- `Prefer`：サーバーが対応していれば暗号化します（証明書は検証しません）
- `Require`：暗号化できなければ接続を拒否します（証明書は検証しません）
- `VerifyCa`：暗号化を必須にし、証明書が信頼できる CA から発行されていることを検証します
- `VerifyFull`：`VerifyCa` に加えて、証明書が接続先のホスト宛であることも検証します

`Require` が防げるのは盗聴だけです。
検証を伴わない以上、中間者は任意の証明書を提示できます。
正規の証明書を持つサーバーが相手なら `VerifyFull` を選んでください。

**Oracle** をこの選択肢の対象外にしているのは、管理対象ドライバの TLS がこの形をしていないためです。
切り替えは接続文字列のキーワードではなくデータソースのプロトコル接頭辞（`tcps://host:2484/service`）で行い、あわせてリスナーのポートも変える必要があります。
また TCPS は常に証明書チェーンを検証するため `Require` に当たる形が無く、交渉による切り替えも無いため `Prefer` に当たる形もありません。
Oracle へ TLS で接続する必要がある場合は、接続文字列をそのまま渡す `quicker scaffold --connection` を使ってください。

```
quicker scaffold --connection "Data Source=tcps://db.example.com:2484/ORCLPDB1?ssl_server_dn_match=true;User Id=app;Password=***" --out ./Generated --provider oracle
```

Windows では信頼する CA をホスト自身の証明書ストア（Microsoft 証明書ストア）から取るため、Oracle ウォレットは不要です。
他のプラットフォームではシステムの OpenSSL トラストストアが使われ、ホストの構成によってはウォレットが必要になる場合があります。
`ssl_server_dn_match=true` は「証明書が接続先のサーバー宛か」を検証させる指定です。
この既定値はドライバの版によって異なってきた経緯があり（確認した版ではオフ＝素の `tcps://` は `VerifyFull` より `VerifyCa` に近い状態）、既定に頼らず明示することと、実際に使うドライバの版で挙動を確認することをおすすめします。
Oracle の*ネイティブネットワーク暗号化*は接続文字列の外で設定する別機構で、サーバーの認証を行わないため代用にはなりません。

PostgreSQL・MySQL を `quicker scaffold` から使う場合も専用のオプションはありません。
`SSL Mode` は通常の接続文字列キーワードなので `--connection` に含めてください（`...;SSL Mode=VerifyFull`）。

### 接続プロファイル

入力内容は名前を付けて保存でき、次回から「保存済み接続」で呼び出せます。
プロファイルは `%LOCALAPPDATA%\QuickER\connections.json` に保存され、パスワードは本体とは分離した別ファイルへ **Windows DPAPI（CurrentUser スコープ）で暗号化**して保存されます（「保存」チェックを付けた場合のみ。既定の設定では平文で保存されることはありません）。
最後に使った接続内容は自動的に記憶され、次回起動時に復元されます。
DB 同期のダイアログは対象 DB が図の方言に固定されるため、前回接続がそれと違う方言だったときは復元しません（ホスト・ファイルパス・サービス名は方言ごとに意味が違い、そのまま入れても接続できないためです）。
「保存」チェックを付けたままパスワードを空欄で保存すると、チェックも外れた状態で保存されます（保存するものが無いため。「保存済みと表示されるのに復元するものが無い」状態は作りません）。
保存済みパスワードの暗号ファイルを読めないとき（他のプログラムが一瞬掴んでいる、別のユーザーや端末で暗号化された、など）は、パスワード欄を空欄にしてステータス行で知らせます。
そのプロファイルを、パスワード欄が空欄のまま「保存」のチェック付きで上書きしようとすると、保存を断ります（そのまま保存すると、読めなかっただけのパスワードが消えるためです）。
パスワードを入力し直すか、「保存」のチェックを外してから保存してください。
保存は「保存名」がキーです（前後の空白は除いて照合します）。
同じ保存名・同じ DB 種別のプロファイルがあればそれを上書きし、無ければ新しいプロファイルになります。
上書き先が一覧で選んでいるものと違うときは、実行前に確認します（接続先と保存済みパスワードが置き換わり、元に戻せないためです）。
読み込んだプロファイルをそのまま上書きする場合は確認しません。
名前だけを変えたいときは「名前の変更」ボタンを使ってください。
保存名の欄の値へ、選択中のプロファイルの名前だけを変更します（接続の設定値と保存済みパスワードはそのまま引き継がれます。パスワードの暗号ファイルには触れません）。
保存名を打ち替えて「保存」を押すと、名前の変更ではなく別のプロファイルとして保存されます。
保存・名前の変更・削除は、いずれも `connections.json` を読み直してから書き戻します。他のプログラムがこのファイルを掴んでいるなどで読み取れなかったときは、**何も書かずに中止**してステータス行で知らせます（登録済みのプロファイルは無傷のまま残ります。少し待ってからやり直してください）。
書き込みの途中で失敗したとき（ディスクの空き不足、パスワードの暗号ファイルの書き込み・削除の失敗など）は、一部だけ反映された可能性があるため、ステータス行で知らせて一覧をファイルから読み直します。
一部だけ反映されても、プロファイルに別の接続先の保存済みパスワードが付くことはありません。
古いパスワードの暗号ファイルは `connections.json` を書く前に消し、新しいものはその後に書きます。
そのため `connections.json` を書けなかったときは、プロファイルは保存済みのパスワードの無い元の設定のまま残り、パスワードを入力し直すことになります。
OK での前回接続の記録に失敗したときも接続はそのまま進み、記録できなかったことをメッセージで知らせます。
ファイルが壊れていた場合は、上書きする前に一度だけ `connections.json.corrupt` へ退避します。

### 取り込まれる内容

- テーブル（ビュー・マテリアライズドビュー・外部テーブル・子パーティション・一時表・マテリアライズドビューのコンテナ表とログ表は対象外）と列（型・長さ・精度・NULL 可否）
- 主キー。複合キーは制約自身の列順序ごと取り込みます。
  `PRIMARY KEY (b, a)` はそのまま `(b, a)` として図に入り、生成 DDL も制約が宣言していた順序で出力されるため（テーブルでの列の並びとは独立）、裏付けインデックスの列順が往復で保たれます
- 外部キー（制約名と ON DELETE / ON UPDATE の参照アクションを含む）。
  FK を持つ側の列集合が、そのテーブル自身の主キーまたは一意制約と一致する場合は 1 対 1 と判定されます。
  複数列で構成される外部キーも、列同士の対応付けを宣言順にすべて取り込みます。
  SQLite は FK 制約名を永続化しないため、取込時に制約名が合成されます
- テーブル・列の説明（方言ごとの取込元は[説明の同期](#説明の同期)の表）
- 列の 2 つの印：計算列（生成列）と、値を指定させない自動採番の列（式と採番の定義は取り込みません）

取り込まれるのはここまでです。
境界の全体と、DDL 生成への影響は[図がモデル化する範囲](#図がモデル化する範囲)を参照してください。

#### 取込が見ている範囲

方言ごとに取込の対象範囲は 1 つで、その外にあるオブジェクトは取込からは見えません。

| DBMS | 取込の対象範囲 |
|---|---|
| SQL Server | 接続先データベースの全スキーマ |
| PostgreSQL | `public` スキーマのみ |
| MySQL | 接続先データベース（MySQL の「スキーマ」はデータベースそのもの） |
| Oracle | 接続ユーザーの自スキーマ（`USER_*` ビュー） |
| SQLite | 接続した単一のデータベースファイル |

Oracle では、利用者が `INVISIBLE` にした列も取り込みます（意図して隠した列であって、存在しない列ではないためです）。
ただし Oracle 側で列の順番を持たない扱いになるため、図では可視列の後ろに並びます（複数あるときは作った順です）。
`INVISIBLE` という属性そのものは図が持たないため、図から生成した DDL では通常の可視列として宣言されます。
関数インデックスがテーブルへ足すシステム生成列（`SYS_NC…$`）は取り込みません。

この範囲の外を参照する外部キーは、親テーブルが図に無いためリレーションにできません。
黙って消さず、除外したことを報告します（次項）。
SQLite は `CREATE TABLE` のときに参照先テーブルの実在を検査しないため、存在しないテーブルを参照する外部キーがデータベースに残っていることがあります。
これも同じ扱いで、取り込まずに報告します。
MySQL で、接続先のデータベースに無いテーブルを参照する外部キー（`FOREIGN_KEY_CHECKS = 0` で作った・そうして参照先を落とした）も同じです。
名前に `.` を含むテーブルは、SQLite でもほかの方言と同じく取り込みません（図はテーブル名の最初の `.` をスキーマ修飾と読み、SQLite では添付したデータベースの名前になるため）。
詳しくは次項の取込の警告を参照してください。

無効化された制約も取り込みません（Oracle の `DISABLE`、SQL Server の `NOCHECK CONSTRAINT`）。
無効化された制約は実際には何も強制しないため、取り込むと図がデータベースには無い保証を宣言することになるからです。
`WITH NOCHECK` で追加されたが現在は有効な SQL Server の外部キーは、以後の書き込みには強制が効くので取り込みます。

#### 取込の警告

取込そのものは常に成功しますが、スキーマの一部は宣言どおりの形では図へ写し取れません。
その場合は完了ダイアログが対象を一覧します（`quicker scaffold` は同じ内容を標準エラーへ出力します）。
差が黙って生まれないようにするためです。

表は種類をすべて挙げ、下の箇条書きは表のセルに書けないことを補います。

- PostgreSQL の**ドメイン型**の列は基底型として取り込みます。
  図はドメイン型を持たないため、ドメインの `CHECK` 制約は失われます
- SQLite の**型を宣言していない列**は `BLOB` として取り込み、列ごとに名指しします。
  SQLite はこうした列にどの型の値も入れられますが、生成コードは `byte[]` で読むので、ほかの種類の値を持つ行は読み取りで失敗します
- 列の**既定値**は取り込まず、既定値ごとに列を名指しします。
  図は既定値を持たないため、生成 DDL は `DEFAULT` なしで列を作ります。
  値が `NULL` の既定値は既定値が無いのと同じ意味なので告げません。
  空文字列が `NULL` になる Oracle では、`DEFAULT ''` と、`DEFAULT (NULL)` のように括弧で包んだ `NULL` や `''` もこれに含めます
- **指定した値も受け付ける自動採番**は取り込みません。MySQL の `AUTO_INCREMENT`、PostgreSQL の `serial` と `GENERATED BY DEFAULT AS IDENTITY`、Oracle の `GENERATED BY DEFAULT AS IDENTITY`、SQLite の `AUTOINCREMENT` です。
  その列は自動採番として 1 回だけ名指しし、既定値として重ねて告げません
- MySQL では、列の**照合順序**（テーブルの既定と違うとき）・**`INVISIBLE`**・**`ON UPDATE`**・**`SRID`** を取り込まず、列ごとに名指しします
- **前後に空白のある名前**（テーブル名・列名・外部キー名・一意制約名）は空白を除いて取り込み、名前ごとに告げます。
  MySQL は末尾の空白を許さないので、出るのは先頭の空白だけです
- **取込範囲の外を参照する外部キー**は取り込みません（SQLite と MySQL では、存在しないテーブルを参照する外部キーがこれに当たります）
- **大文字小文字または前後の空白だけが違う同名テーブル**は片方だけを取り込みます（図は両者を区別できないため。PostgreSQL と Oracle は引用識別子で、MySQL は `lower_case_table_names` が 0 なら、SQL Server は大文字小文字を区別する照合順序のデータベースなら、ASCII の英字しか畳まない SQLite は `Äpfel` と `äpfel` のような名前なら両方を共存させられます）
- **名前に `.` を含むテーブル**は取り込まず、そのテーブルを名指しします。
  図はテーブル名の最初の `.` をスキーマとテーブルの区切りと読むので、`Order.Lines` はスキーマ `Order` のテーブル `Lines` と読まれます。
  そのまま取り込むと QuickER のほかの機能からは別のテーブルになり、生成した QuickER 版 Repository はテーブルが無いエラーになり、DDL と同期は別のテーブルを作ります（そのスキーマが無ければ失敗します）。
  SQL Server では、`dbo` のテーブルで名前に `.` を含むものと、名前に `.` を含むスキーマのテーブルすべてが対象です。
  `dbo` 以外のスキーマのテーブル名に含まれる `.` は同じテーブルとして読み戻せる（`a.b.t` はスキーマ `a` のテーブル `b.t`）ので、取り込みます
- 同じように、テーブルの中で**大文字小文字または前後の空白だけが違う同名の列**は、宣言順で後のほうを取り込みません。
  取り込まなかった列の主キー印・説明・一意制約・外部キーは、取り込んだ列へは付きません（取り込まなかった列を含む一意制約と外部キーは取り込みません）
- **計算列・生成列**（SQL Server の計算列、MySQL / PostgreSQL / SQLite の `GENERATED ALWAYS AS`、Oracle の仮想列）は、式を持たない読み取り専用の列として取り込みます。
  図は式をモデル化しないため、生成 DDL は普通の列を作ります（DDL には手で式を足すよう促すコメントが付きます）。
  生成コードはその列を INSERT / UPDATE から外します（[生成コードの説明](code-generation.ja.md#計算列生成列)を参照）
- **値を指定させない自動採番**（SQL Server の `IDENTITY`、PostgreSQL と Oracle の `GENERATED ALWAYS AS IDENTITY`）の列は、採番の定義（開始値・増分）を持たない「DB が採番する列」として印を付けて取り込み、列ごとに名指しします。
  図は採番の定義を持たないため、生成 DDL は普通の列を作ります（採番の指定を手で足すよう促すコメントが付きます）。
  生成コードは主キーでないその列を INSERT / UPDATE から外します（[生成コードの説明](code-generation.ja.md#db-が採番する列)を参照）
- SQLite の**仮想テーブル**（FTS5 / R*Tree など）は取り込みません。
  通常テーブルの形で写し取れないためで、付属表（シャドウテーブル）も一緒に除外し、仮想テーブル 1 つにつき 1 件で報告します
- **図が持たないオブジェクト**は取り込まず、名前を並べて告げます。
  外部テーブルは PostgreSQL の外部テーブル、Oracle の `ORGANIZATION EXTERNAL` の表、SQL Server の外部テーブルで、PostgreSQL の子パーティションは属する親テーブルの名前つきで並べます（親は下のとおり取り込みます）。
  データベースや拡張が持つもの（システム表・マテリアライズドビューのコンテナ表とログ表・拡張が入れる表）は告げずに外します
- SQL Server の**テンポラルテーブル**は、現在の値を持つ本表だけを取り込みます。
  履歴表はシステムが管理する本表の付属物で、それ自体が独立したエンティティではないためです。
  本表の期間列（`GENERATED ALWAYS AS ROW START / END`）は、データベースが値を作る列なので計算列と同じ扱いになります。
  `HIDDEN` 修飾でも同じように取り込みます。
  生成コードはこの列を書き込みから外すため、本表への追加・更新はそのまま行えます（[計算列の説明](code-generation.ja.md#計算列生成列)を参照）
- **SQL へ安全に書き出せない型**の列は、型の表記ごと名指しします。
  取込は成功しますが、直すまで DDL 生成とスキーマ同期は**図全体**を拒否します（型は識別子でも文字列リテラルでもなく、クォートで包む場所がないためです。[列の型に置ける表記](#列の型に置ける表記)を参照）。
  SQLite は宣言された型のテキストをそのまま保持し、PostgreSQL は引用が要る型名を引用込みで返すため、どちらからも出ます
- **パーティションテーブル**は親テーブルとして取り込み、パーティション自体はモデル化しません。
  生成 DDL はパーティションなしで作成します
- SQLite の **NULL を許す主キー**は NOT NULL へ補正して取り込み、補正した列を名指しします。
  rowid テーブルでは、宣言型がちょうど `INTEGER` の単一列主キー以外は NULL を許せてしまうためです（図と GUI は主キーを常に NOT NULL として扱います）。
  名指しするのは実際に補正した列だけで、構成列が最初から `NOT NULL` と宣言されている主キーは報告しません。
  既存の行に NULL の主キーがあると、この図からの同期（テーブル再構築）でデータの移送に失敗することがあります

対象が 1 件も無ければ、従来どおり 1 行の完了メッセージになります。

#### 取り込んだ型の表記

取込は各列の宣言型をデータベース自身のカタログから読み、QuickER の短い語彙で書き出します。
変わるのは表記だけで、型は変わりません。

<!-- dialect-table: imported-type-spelling -->

| 方言 | 宣言 | 取込の表記 |
| --- | --- | --- |
| SQL Server | `datetime2(7)` / `datetime2(3)` | `datetime2` / `datetime2(3)` |
| PostgreSQL | `character varying(50)` / `timestamp(3) with time zone` | `varchar(50)` / `timestamptz(3)` |
| MySQL | `decimal(12)` | `decimal(12,0)` |
| Oracle | `INTEGER` / `SMALLINT` / `NUMBER(*,0)` | `NUMBER(*,0)` |
| SQLite | `VARCHAR(50)`（宣言のまま） | `VARCHAR(50)` |

以前のバージョンで取り込んだ図では、表記が変わった列が次の差分同期で型の変更として 1 度だけ現れます。
図を取り込み直すか、図の型をデータベースに合わせてください。

取込結果は現在の図へマージされます。
テーブル名・列名で現在の図と照合し、一致した要素は現在の図にある要素をそのまま引き継ぐため、レイアウト・幅・色・メモと、それらを参照する名前付きクエリが温存されます。
大文字小文字だけ違う名前も、大文字小文字を無視して両側で 1 つに決まるなら一致とみなし、名前の表記は取り込んだ側に変わります（たとえば Windows の MySQL はテーブル名を小文字で返します）。
大文字小文字だけ違う名前が並んでいるときは完全に一致するものを先に組み、それでも 1 つに決まらない名前は新しいテーブル・列として扱います。
空き領域へ配置されるのは新しく取り込まれたテーブルだけで、現在の図に一致する要素が 1 件もない完全な新規取込のときにだけ、図全体が自動整列されます。
確認ダイアログは、現在の図と構造的な差分がある場合に加えて、取込によって壊れる名前付きクエリがある場合にも表示され、削除対象のクエリ名が列挙されます。

取り込んだ後、手元の既存エンティティ資産と生成コードをどう付き合わせるかは、[生成コードの使い方の「既存コードベースとの共存」](code-generation.ja.md#既存コードベースとの共存)を参照してください。

## 図がモデル化する範囲

図はデータベースの複製ではなく設計モデルです。
往復できるのは、図がモデル化している次の範囲だけです。

- テーブルと列（型・長さ・精度・NULL 可否）
- 主キー（複合キー自身の列順序を含む）
- 外部キー（列ペア・制約名・参照アクション）
- UNIQUE 制約
- テーブル・列の説明
- 列の 2 つの印：計算列（生成列）と、値を指定させない自動採番の列（式と採番の定義は持ちません）

これ以外はモデルの外です。
取り込まれず、生成 DDL にも出ず、差分同期も検出・変更の対象にしません。

<!-- dialect-table: modeling-fidelity -->

| スキーマ要素 | 取込 | 生成 DDL | SQLite のテーブル再構築 |
| --- | --- | --- | --- |
| `DEFAULT` | 取り込まない（名指しで告げる） | 出力しない | 失われる |
| `CHECK` 制約 | 取り込まない | 出力しない | 失われる |
| `COLLATE` | 取り込まない（MySQL は名指しで告げる） | 出力しない | 失われる |
| 生成列（計算列） | 式を持たない読み取り専用の列として計算列の印を付けて取り込み、告げる | 普通の列として出力（注意コメント付き） | 失われる（注意コメント付きの普通の列として作り直す） |
| 値を指定させない自動採番 | DB が採番する列の印を付けて取り込み、告げる（SQL Server・PostgreSQL・Oracle。採番の定義は失われる） | 普通の列として出力（注意コメント付き） | 対象外（SQLite には無い） |
| 指定した値も受け付ける自動採番 | 取り込まない（名指しで告げる） | 出力しない | 失われる（宣言型が `INTEGER` の主キーは rowid 別名のままなので暗黙の自動採番は保たれる＝下記の注記） |
| 非 UNIQUE インデックス | 取り込まない | 出力しない | 温存（`CREATE` 文の全文を保持して再作成） |
| トリガー | 取り込まない | 出力しない | 温存（同上） |
| 列リストの後ろのテーブルオプション（`WITHOUT ROWID`・`STRICT`） | 取り込まない | 出力しない | 失われる |
| 制約の句（`ON CONFLICT`・`DEFERRABLE INITIALLY DEFERRED`） | 取り込まない | 出力しない | 失われる |
| ビュー | 取り込まない（名指しで告げる） | 出力しない | 温存（作り直した表を指し続ける） |
| ストアドプロシージャ・関数・シーケンス | 取り込まない | 出力しない | 対象外 |

**rowid 別名が成立するかは「整数列かどうか」ではなく宣言型のつづりで決まります。**
SQLite が主キーを rowid 別名として扱うのは、宣言型がちょうど `INTEGER` のときだけです。
表制約の形かどうかは関係なく（`x INTEGER, PRIMARY KEY (x)` も、QuickER が出力する `x INTEGER NOT NULL, CONSTRAINT PK_t PRIMARY KEY (x)` も別名になります）、`INT` は別名になりません。
SQLite から取り込んだ図は宣言型をそのまま保持するため上記の保証が成立しますが、QuickER で新規作成した図や、方言を切り替えて SQLite へ戻した図は 32 ビット整数に `INT`・64 ビット整数に `BIGINT` を出力します。
そう宣言された主キーはただの列で、暗黙の自動採番はそもそも存在せず、キーを与えない INSERT は NULL を入れます（生成される Repository はアプリ側でキーを採番する前提なので、この違いは生成コードの動作には影響しません）。

SQLite のテーブル再構築を除けば、これらのオブジェクトはそのまま放置されます。
差分同期は検出すらしないため、手で作ったインデックスや `DEFAULT` はデータベースに残り続けます。
図の定義からテーブルを作り直す再構築だけが例外で、だからこそ図が表現できないものを落とし得ます（QuickER は対象テーブルで見つかった属性を実行確認に列挙します。[SQLite の差分同期](#sqlite-の差分同期テーブル再構築方式)を参照）。

**DDL 生成は設計から新しいスキーマを作るための機能であり、取り込んだ既存データベースの再現には使えません。**
元のデータベースが上記のモデル化範囲だけで出来ていない限り、生成される `CREATE` 文は別物のスキーマです（テーブル・列・キー・制約は同じでも、既定値・CHECK・照合順序・自動採番・インデックス・トリガーは 1 つもありません）。
既存データベースの移送にはそのデータベース自身のツールを使い、QuickER の DDL は設計から新規に立ち上げる用途に使ってください。

## 差分同期（図 → DB）

ツールバーの「DB同期」ボタンから、差分ダイアログ「DB スキーマ同期 (差分実行)」を開きます。
データベースの現状と図の内容を突き合わせ、差分の一覧と生成 SQL のプレビューを確認したうえで、選択した項目だけを実行できます。

### 検出される差分

- テーブルの追加・削除
- 列の追加・変更（型・NULL 可否）・削除
- 外部キーの追加・削除・作り直し（参照アクション・構成列・参照先だけが変わった外部キー）
- 一意制約の追加・削除・作り直し（構成列だけが変わった名前付きの一意制約）
- 主キーの変更（付与・解除・キー列構成または列順序の変更）
- テーブル・列の説明の設定・更新・削除
- 列の並び順の変更

同名の要素を同一とみなして比較するため、リネームは「削除＋追加」として検出されます。
データベースと大文字小文字だけ違う名前のテーブル・列も、大文字小文字を無視して両側で 1 つに決まるなら同じ要素とみなし、スクリプトにはデータベース側の綴りを書きます。
引用した名前が大文字小文字を区別する方言のためです（Oracle は引用符なしで作った表を `ORDERS`、PostgreSQL は `orders` として持つので、図の `Orders` のままでは存在しない表を指します）。
図にしか無いテーブル・列は、図の綴りで作ります。
名前の無いリレーションの外部キーは、DDL が付けるのと同じ既定名（`FK_{子テーブル}_{親テーブル}`）で照合されます。

列の型は、データベースが保存する表記へそろえてから比較します。
データベースは宣言の綴りをそのまま覚えるとは限らず、`numeric(18,0)` と宣言しても `numeric(18)` として返します。
そのため同じ型の別の綴りは差分になりません。

<!-- dialect-table: same-type-spellings -->

| 方言 | 同じ型とみなす | 差分のまま |
| --- | --- | --- |
| SQL Server | `numeric(18,0)` と `numeric(18)`、`datetime2(7)` と `datetime2`、`float(24)` と `real`、`float(53)` と `float`、`rowversion` と `timestamp` | `datetime2(3)` と `datetime2` |
| PostgreSQL | `timestamp` と `timestamp(6)`、`numeric(18,0)` と `numeric(18)` | |
| MySQL | `decimal(12)` と `decimal(12,0)`、`decimal` と `decimal(10,0)` | |
| Oracle | `TIMESTAMP` と `TIMESTAMP(6)`、`INTEGER` と `NUMBER(*,0)` | |
| SQLite | （宣言のまま比べる） | |

そろえるのは既定値の省略と、データベースが覚えていない別名だけで、意味の違う型（`datetime2(3)` と `datetime2`）は従来どおり差分になります。

PostgreSQL では、型の系統をまたぐ変更（`varchar` から `integer`、`text` から `date`、`integer` から `boolean` など）に `USING 列::新しい型` を付けて書くので、すべての値が変換できれば通ります。
文字列型への変更には付けないので、短くした `varchar(n)` に収まらない値があると、切り詰めずに同期が失敗します。
取込が分類できない型（PostGIS の型・ユーザー定義型）にも付けません。

<!-- dialect-table: referential-actions -->

| 方言 | `ON UPDATE` | `SET DEFAULT` | 差分での比べ方 |
| --- | --- | --- | --- |
| SQL Server | ✅ | ✅（NOT NULL の子の列には DEFAULT 制約が要る） | 宣言のまま |
| PostgreSQL | ✅ | ✅ | 宣言のまま |
| MySQL | ✅ | —（受け付けるが効かない。句を省いて注記） | `SET DEFAULT` を `NO ACTION` として比べる |
| Oracle | —（句を省いて注記） | —（句を省いて注記） | `ON UPDATE` と `SET DEFAULT` を `NO ACTION` として比べる |
| SQLite | ✅ | ✅ | 宣言のまま |

表で無い・効かないとするアクションは、差分で `NO ACTION` として比べ、DDL と同期スクリプトは句を省いて外部キーを作り、注意のコメントを添えます。
MySQL（InnoDB）は `ON DELETE` / `ON UPDATE` の `SET DEFAULT` を受け付けますが効かせません（親の行を消すと `NO ACTION` と同じく失敗します）。
SQL Server は、NOT NULL の子の列に DEFAULT 制約が無いと `SET DEFAULT` の外部キーを作れません（エラー 1762）。
図は列の既定値を持たないため、DDL はそうした外部キーの前に注意のコメントを添え、同期は追加・作り直す外部キーを実行確認で名指しします。
データベースの列に DEFAULT 制約があれば通るので、実行は止めません。

<!-- dialect-table: column-alteration -->

| | SQL Server | PostgreSQL | MySQL | Oracle | SQLite |
| --- | :-: | :-: | :-: | :-: | :-: |
| 列の変更で照合順序を読み直して書き添える | ✅ | ✅（型の既定と違うときだけ） | ✅（実定義から） | — | —（再構築で失われる） |
| 列の変更で `DEFAULT` を保つ | ✅（外して同じ名前で付け直す） | ✅（DB が保つ） | ✅（実定義から） | ✅（DB が保つ） | —（再構築で失われる） |
| 既定値のある列の型の種類の変更を実行確認に表示する | ✅ | ✅ | ✅ | ✅ | — |

列定義の変更で、新しい型が文字列型のときに照合順序を書き添えるのは上の表のとおりで、書かないとデータベースの既定の照合順序へ戻るためです。
SQL Server で型が変わるときに DEFAULT 制約を外して付け直すのは、残したままだとエラー 5074 で断られるためです。
SQL Server で列を削除するときも、同じ理由で先に DEFAULT 制約を外します。
その列を参照する CHECK 制約や、利用者が作った索引は外しません。図がそれらを持たないためで、残っていると列の削除はエラー 5074 で断られ、同期は巻き戻ります。
既定値のある列の型の種類を変える同期は、上の表のとおり実行確認に表示されます。
既定値が新しい型に合わないと、PostgreSQL と Oracle では同期が失敗し、MySQL ではエラー 1067 で同期が失敗し、SQL Server では既定値を使う行の追加が失敗します。
MySQL と Oracle の同期の失敗では DDL が巻き戻らないので、それより前の文は適用されたまま残ります。
外部キーの作り直しは削除と追加を 1 つにまとめた差分項目で、既定では選択されません（同じ名前の外部キーを外してから付け直すため、MySQL / Oracle では付け直しに失敗すると外部キーが外れたまま残り得ます）。
一意制約の作り直しも同じで、名前（または生成される名前 `UQ_{テーブル}_{列}` がデータベースの名前と同じ）を保ったまま構成列だけが変わった一意制約は、削除と追加を 1 つにまとめた差分項目になり、既定では選択されません。
データベースが使っている名前で制約を足すと失敗し、付け直しは重複した値で失敗し得るためです。
一意制約は 2 段で組み合わせます。
先に、図で名前を付けた一意制約を、データベースの同じ名前の制約と組みます。構成列が同じなら差分にならず、違えば作り直しになります。
残りの一意制約は構成列の集合で組むので、図で名前の無い一意制約は、名前に関わらず同じ列のデータベースの制約と一致します。
名前の無い制約に生成される名前は、先の段では使いません。
データベース側に名前の無い制約（SQLite）は、構成列だけで組みます。
複合外部キーの列ペアの並びだけの違いは、どの方言でも差分にしません（列ペアは親の列と子の列の対応で、並びは意味を持ちません。Oracle は宣言した並びを残さずに参照先のキーの並びで返します）。
SQL Server と MySQL は参照する列の並びが参照先のキーの並びと一致することを求めるので、DDL は列ペアを参照先のキー（主キー、合わなければ一意制約）の並びへ並べ替えて出します。
同期で足す・作り直す外部キーは図の並びのまま出すため、図の並びが参照先のキーと違うと SQL Server と MySQL では失敗します（実行確認に表示されます）。
SQLite は `a.b` のようにドットを含む表名を「添付したデータベース a の表 b」と読むため、そのデータベースを添付していなければ、その表の DDL と同期は失敗します。
DDL は表の前に注意のコメントを添え、同期は対象の表を実行確認に表示します。

列の並び順は、追加・削除を除いた共通列の相対順序で比較されます。
そのため、真ん中へ列を足しただけでは並び順の差分にならず、足した列はテーブルの末尾に付きます（次の同期で並び順の差分として出ます）。
既存の列の並べ替えも同時にあるときは、1 回の同期で足した列の位置まで反映されます。
下の表で列の並び順を同期できる方言では、選択可能な差分項目（既定では未選択）として同期でき、MySQL は移動する列を最小限にします。
MySQL の `MODIFY` は列定義を実 DB のカタログから組み立て直すため、列を動かしても属性と説明はそのまま残ります（[MySQL の `MODIFY COLUMN` が再指定するもの](#mysql-の-modify-column-が再指定するもの)を参照）。
ほかの方言では案内として表示されるのみで、同期の対象外です。

計算列の NULL 許容は比較しません（データベースは NULL 許容を式から決め、図は式を持たないためです）。
計算列の型の変更は下の表で選べる方言でだけ選べ（PostgreSQL の `ALTER COLUMN ... TYPE` は式を保ちます）、選んでも列の NULL 許容は変えません。
ほかの方言では案内として表示されるのみです（式なしでは型を変えられないためです。SQL Server は変更を断り、SQLite の再構築は式を落とします。MySQL も案内として表示するだけです）。
下の表で主キーとちょうど同じ列の一意制約を持てない方言では、そうした一意制約は比較せず、差分項目にしません。
SQLite はそうした制約を保持せず、Oracle は断るためです（一意性は主キーが保証します）。
DDL と同期で作る表からもその一意制約を省き、注意のコメントを添えます。
Oracle で、データベースにある一意制約と同じ列へ主キーを付け替える同期は、ORA-02261 で失敗します。
図からその一意制約を外して削除の差分も選ぶか、データベースで先に外してください。

### 実行の安全設計

- **破壊的な差分（削除・型変更）は既定で選択されず**、実行時には破壊的変更を含む旨の確認が表示されます
- 生成スクリプトは依存関係順（FK 削除 → 一意制約削除 → テーブル削除 → テーブル追加 → 列追加 → 旧主キー解除 → 列変更 → 新主キー付与 → 列削除 → 一意制約追加 → FK 追加 → 説明）に並び、種別ごとの見出しコメントが付きます。
  テーブルの削除を追加より前に置くので、図で名前を変えたテーブルが古いテーブルの一意制約の名前を引き継いでも通ります。
  DDL が暗黙コミットされる方言（MySQL・Oracle）では、表の削除の後の作成が失敗すると古い表は消えたまま残ります。同期をやり直すと作成されます。
  SQLite はテーブルを作り直す方式なので、独自の順序で並びます
- FK 列を解決できない外部キー追加は、不正な DDL を出さずスキップコメントとして出力されます
- テーブル・列を削除すると、その削除で表・列を失う外部キーも、その外部キーの削除を選んでいなくても外します（SQLite では残る子テーブルを作り直して外します）。
  そのため、親と子のテーブルを一緒に削除しても、並び順に関係なく通ります
- 列を削除すると、その列を使う一意制約も、その一意制約の削除を選んでいなくても外し、確認ダイアログで 1 つずつ名指しします。
  残りの列で一意制約を作り直すことはしないので、必要なら図に一意制約を足してください
- 選んだ変更が、選んでいない変更（表・列の追加、または主キーの変更）を前提にするときは、その変更をスクリプトから外し、確認ダイアログで前提にするものと一緒に名指しします。
  主キーの列の削除は、その列を主キーから外す主キーの変更を前提にします。
  追加・変更する外部キーが親の新しい主キーを参照し、その主キーの変更が無ければ参照先が主キーにも一意制約にもならない場合は、主キーの変更を前提にするものとして扱います（MySQL で、列の並びだけを変える主キーの変更を実行しない場合も同じです）。
  前提にする変更を QuickER が代わりに選ぶことはありません
- 複数列で構成される外部キー（複合外部キー）は正式に対応しています。
  リレーションは列ペアの順序付きリストを保持するため、取込・DDL 生成・同期のいずれも構成列をすべて運びます。
  主キー変更に伴う暗黙の解除・再作成や SQLite のテーブル再構築も同様で、複合外部キーが単一列へ静かに縮むことはありません
- SQL Server・PostgreSQL・SQLite ではトランザクションで実行され、失敗時はロールバックされます。
  MySQL / Oracle は DDL が暗黙コミットされる仕様のため、途中で失敗した場合は部分適用となる可能性がある旨が警告されます
- Oracle のスクリプトと DDL は SQL*Plus で手で流すこともできます。
  通常の文は `;` で終わり、`/` 行は PL/SQL ブロックの後ろにだけ置くので、各文はちょうど 1 回だけ実行されます（SQL*Plus は `/` 行で直前の文をもう一度実行します）
- SQLite の再構築を含む実行では、再構築されるテーブルを列挙した専用の確認が表示されます。
  再構築するテーブルの一覧や外部キーの再作成などの注意事項は、確認ダイアログのスクロールできる詳細欄に全件表示されます
- 最初の差分検出で差分が 1 件もない場合は、その旨を表示したままダイアログは開いています。
  同期を適用したあとの再読込で差分がゼロになった場合は、自動で閉じます。
  実行が失敗した場合も差分を自動で再読込するため、部分適用後の状態が一覧に反映されます（MySQL / Oracle で意味を持ちます）。
  再読込そのものが失敗した場合（回線断など）は、差分とスクリプトを空にし、再計算に成功するまで実行できません（取り直せなかった古いスクリプトを流さないためです）
- 差分の再計算や実行の最中は、「差分を再計算」・「実行」・「全選択」・「全解除」を押せません。
  同期スクリプトを実行している間はダイアログも閉じられません（閉じると実行がダイアログの外で続くためです）。再計算の最中は閉じられます

### 主キーの同期

図でテーブルの主キーを変更（付与・解除・キー列構成または列順序の変更）すると、テーブル単位の差分項目 1 件として検出されます（既定では未選択）。
旧主キーの制約名は実行時にデータベースのカタログを逆引きして特定するため、任意の制約名を持つ取込済みデータベースでもそのまま動きます。
スクリプトは「旧主キーの解除 → 選択した列変更 → 新主キーの付与」の順に実行されるため、旧キー列を NULL 許容へ変える変更も 1 回の同期で成立します。
新しい主キーに加わる列は、その列自体の変更を選んでいなくても、主キーの変更の一部として `NOT NULL` になります（型はデータベースのままです）。

変更対象の主キーに支えられた外部キー（旧主キーと同じ列を参照するもの）は、変更の前後で自動的に「外して→作り直す」処理が入ります。
一意制約を参照する外部キーには触れません。

<!-- dialect-table: foreign-key-rebuilds -->

| | SQL Server | PostgreSQL | MySQL | Oracle | SQLite |
| --- | :-: | :-: | :-: | :-: | :-: |
| 列の変更で、その列の外部キーを外して付け直す | ✅ | — | ✅ | — | —（表を作り直す） |
| キーの列の変更で、主キー・一意制約を外して付け直す | ✅ | — | — | — | —（表を作り直す） |
| 外す主キー・一意制約の索引に乗る外部キーも付け直す | — | — | ✅ | — | — |
| 参照する列の並びを参照先のキーに合わせる | ✅ | — | ✅（並びだけの変更は実行しない） | — | — |
| 長さだけ違う文字列型を両端に許す | —（エラー 1753） | ✅ | ✅ | ✅（単位語が同じとき） | ✅ |
| 付け直しの失敗で外部キーが外れたまま残り得る | — | — | ✅ | ✅ | — |

キーの列の変更で外して付け直した主キーの名前は `PK_{テーブル}` になります（上の表）。
MySQL では、主キーを変える表自身の外部キーのうち、旧主キーの先頭の列に乗るものも外して作り直します（旧主キーがその外部キーを支える唯一の索引だと、主キーを外せないためです）。
外部キーを支える唯一の索引が一意制約の索引のとき、その一意制約を消す場合も同じです（外さないと MySQL がエラー 1553 で断ります）。
外部キーの片側の列だけ型を変えるなど、同期後に外部キーの両端の列の型が一致しなくなる変更では、外部キーを外し直さず、列の変更はそのまま失敗します（DB は変わりません）。
付け直しが必ず失敗し、MySQL / Oracle では外部キーが外れたまま残るのを避けるためです。
長さだけが違う文字列型（`varchar(50)` と `varchar(100)` など）は、上の表で両端に許す方言では食い違いとみなしません。
Oracle では、長さの単位（`CHAR` / `BYTE`）が両端で同じときだけです。
片側の長さだけを変えても、通常どおり外部キーを外して付け直します。
SQL Server は長さも一致しないと外部キーを作れない（エラー 1753）ため、DDL はそうした外部キーの前に注意のコメントを添えます。
実行確認がそうした外部キーを表示するので、両端の列を同じ型へ揃えてください。
このときはほかの外部キーも外し直しません（列の変更がどのみち失敗し、付け直しまで届かないためです）。
参照先の列が新しい主キーに含まれなくなる場合は、外部キーの再作成が失敗する可能性がある旨が実行確認に表示されます。
失敗時はスクリプト全体がロールバックされますが、上の表で外れたまま残り得る方言では、外部キーが外れたままの部分適用になり得ます。
追加・変更する外部キーが、同期後の主キーにも一意制約にもちょうど一致しない列を参照する場合も、同じく実行確認に表示されます。
上の表で参照する列の並びを参照先のキーに合わせる方言では、参照される複合キーの並びだけを入れ替える変更や、外部キーの列の並びだけをキーと合わなくする変更も表示されます。
MySQL ではこうした変更は実行しません（外部キーを外した後の付け直しが失敗し、外部キーが外れたまま残るためです）。
実行しなかった変更は実行確認に表示されます。
適用するには、その外部キーの削除も選んで先に外すか、手で付け替えてください。
本来は付け直しが通る構成でも実行しません。
MySQL 8.0 系、または 8.4 で `restrict_fk_on_non_standard_key=OFF` の環境で、参照する列を外部キーと同じ並びで先頭に持つ一意でない索引を手で作っている場合です（QuickER は一意でない索引を取り込まないため区別できません）。

### 説明の同期

テーブル・列の説明は、説明の機構を持つ 4 方言で同期されます。

<!-- dialect-table: descriptions -->

| 方言 | 取込元 | 書き方 | 基本多言語面の外の文字 |
| --- | --- | --- | --- |
| SQL Server | `MS_Description` 拡張プロパティ | `MS_Description` 拡張プロパティ（同期は既存の有無で追加と更新を使い分ける） | ✅ |
| PostgreSQL | `obj_description` / `col_description` | `COMMENT ON` | ✅ |
| MySQL | `TABLE_COMMENT` / `COLUMN_COMMENT` | `COMMENT` 句 | —（`?` として保存） |
| Oracle | `user_tab_comments` / `user_col_comments` | `COMMENT ON` | ✅ |
| SQLite | —（説明の機構が無い） | —（DDL はコメント行で書く。差分も同期もしない） | |

表が `COMMENT ON` または `COMMENT` 句とする方言では、同期は文や句を再実行するだけで、それ自体が冪等です。
図側で説明を空にすると削除されます。
空白だけの説明は「説明なし」として扱います（DDL は書かず、差分は空と同じとみなし、同期すると DB の説明を削除します）。
説明を書くのは説明の項目だけなので、列を追加しても、その列の説明の項目を選ばなければ説明は入りません（MySQL を含むすべての方言で同じです）。
表で基本多言語面の外の文字（絵文字など）を `?` として保存する方言では、比較は図の説明のそうした文字を `?` にした形で DB の説明と比べるので、同期や DDL の適用の後に差分が残りません。
同期の確認ダイアログはそうした説明を 1 つずつ名指しし、DDL はその説明の前に注記を書きます。

SQL Server では、スキーマを付けないテーブル名は `CREATE TABLE` と同じく接続ユーザーの既定スキーマを指し、説明も同じテーブルに付きます（スキーマは `SCHEMA_NAME()` で求めます）。
取込は `dbo` 以外のテーブルをスキーマ付き（`app.Widget`）で書くため、既定スキーマが `dbo` でないユーザーで使うときは、図のテーブル名にもスキーマを書いてください（書かないと、次の差分で `Widget` と `app.Widget` が別のテーブルになります）。

#### MySQL の `MODIFY COLUMN` が再指定するもの

MySQL には、列の説明だけを変える文も、位置だけを変える文もありません。
どちらも `ALTER TABLE ... MODIFY COLUMN` を通り、この文は列定義を**まるごと**言い直します。
新しい定義に書かなかったものは、その列から消えます。
MySQL の DDL は暗黙にコミットされるため、取り消しもできません。

そこで QuickER は、実行時に `information_schema.COLUMNS` から列定義を組み立て直し、変える部分だけを差し替えます。

- **説明の同期と列順の同期**は末尾の句（説明、または `AFTER` / `FIRST`）だけを、**列定義の変更**（型・NULL 制約の変更）は型と NULL 制約だけを差し替えます。
  図が表現しないもの（`DEFAULT`〔リテラル・式の両方。`BIT` とバイナリ系のリテラルを含む〕、`AUTO_INCREMENT`、照合順序とそれに伴う文字集合、`ON UPDATE CURRENT_TIMESTAMP`、`INVISIBLE`、空間参照系の `SRID`、生成列〔`VIRTUAL` / `STORED`〕）はそのまま引き継がれます。
  列順の同期と列定義の変更では、その列に付いている説明も保たれます（説明を変えるのは説明の同期の項目です）。
- **列定義の変更**で、照合順序は新しい型が文字列型のときだけ書き添えます（`JSON` 型などは `COLLATE` を受け付けないためです）。
  保った属性が新しい型に合わない（既定値 `'abc'` のまま `int` へ変える等）と、その変更は MySQL のエラーで失敗します。
  この差分は既定で未選択です。
- **主キーの変更**では、旧主キーの列に `AUTO_INCREMENT` があると主キーを外せない（エラー 1075）ため、その列から `AUTO_INCREMENT` だけを外してから主キーを外します。
  `AUTO_INCREMENT` は図で表現できないため付け直しません（説明・既定値などの他の属性は実定義から引き継ぎます）。
- **外部キーの削除**では、外部キーと同じ名前の一意でない索引を、ほかの外部キーが必要としていなければ一緒に外します。
  MySQL は使える索引の無い外部キーにこの索引を作り、外部キーを外しても残すため、残すと同じ名前の外部キーを別の列へ作り直すときに失敗します（エラー 1061）。
  外部キーと同じ名前で手で作った索引も、カタログでは区別できないため外れます。
  一意の索引はこの処理では外しません。
  先頭の列が同じ外部キーを 2 本とも外すと、2 本が共有する索引が残ることがあります（1 本目を外す時点では、もう 1 本がまだ使っているためです）。
  その索引と同じ名前の外部キーを別の列へ作り直すと、エラー 1061 で失敗することがあります。

次の 2 つは組み立て直しを通りません。
いずれもカタログが書いたとおりには記録していないためです。

- `COLUMN_FORMAT` と `STORAGE`（NDB Cluster）は `information_schema` に対応する列が無く、読み出せないため引き継げません。
- 生成列の式に含まれる文字列リテラルの文字集合導入子（`_latin1'x'`）は、接続の文字集合で読み直されて書き戻されます（`_utf8mb4'x'`）。
  式の意味は変わらず、カタログが記録する文字列だけが動きます。

説明の同期と列順の同期では、スクリプトの実行時点で列が無くなっていれば、その文は no-op に畳まれます。
何も失敗していないため、同期は成功として報告されます。
列定義の変更は、列が無ければ失敗させます（選んだ変更が黙って何もしないのは誤りだからです）。
列は在るのに定義を組み立て直せなかった場合は、逆にその文が失敗します。
中途半端に適用された列順が成功として報告されることはありません。

同期はスクリプトの実行前に、自分のセッションの `sql_mode` から `NO_BACKSLASH_ESCAPES` を外します（グローバルの設定には触れません）。
QuickER が書き出すリテラルは MySQL 既定の規則でエスケープされており、このモードのままでは同じ文字列がバックスラッシュを二重にしたまま格納されるためです。

この「実 DB からの組み立て直し」は、MariaDB を対象外としている理由のひとつでもあります。
MariaDB は `COLUMN_DEFAULT` の記録の意味論が異なるため、カタログから組み立て直した定義が元の列を再現する保証がありません。

### SQLite の差分同期（テーブル再構築方式）

SQLite は `ALTER TABLE` でできる変更が限られているため、同期が表の列を変更・削除する、主キーを変える、一意制約か外部キーを足す・外す、列の並び順を変えるときは、その表を作り直します（テーブル再構築方式）。
列の追加は、同じ同期でその表を作り直すほかの変更が無ければ `ALTER TABLE ADD COLUMN` で行い、あれば作り直しの中で列を足します。
「データベースの現状＋選択した差分」を合成した新しい定義のテーブルを作成し、データを移送してから旧テーブルと入れ替え、インデックスなどの補助オブジェクトを再作成します。
再構築はトランザクション内で実行され、コミット前に外部キー整合を検査（`PRAGMA foreign_key_check`）して、同期前より違反が増えていればロールバックのうえ違反テーブルを報告します。
SQLite は既定で外部キーを検査しないため、親の無い子行を抱えたデータベースは珍しくなく、同期前から在る違反だけでは失敗にしません。
作り直すテーブルを参照するビューがあっても再構築は通り、ビューは作り直したテーブルを指し続けます（`PRAGMA legacy_alter_table` を一時的に有効にします）。
削除した列を参照するビューのように同期で壊れるビューがあると、そのビューを名指ししてロールバックします。

再構築後のテーブルは図の定義から作成されるため、[図がモデル化する範囲](#図がモデル化する範囲)の外にあるものは再現されません。
そこの表が再構築で失われるとする要素は、現在の DB にあっても**再現されず失われます**（QuickER の外で設定した既定値が再構築後に消えるのはこのためです）。
暗黙の自動採番も、図の宣言型が `INTEGER` である限り保たれます（そうした主キーは再構築後も rowid 別名のままです。`INT` と宣言された主キー＝QuickER で新規作成した図や方言変換を経た図が持つ形は、もともと別名ではありません。[図がモデル化する範囲](#図がモデル化する範囲)を参照）。

喪失を見えるようにするため、QuickER は再構築対象テーブルの現在の `CREATE TABLE` 文を読み取り、見つかった属性を実行確認ダイアログに列挙します。
その属性が必要なテーブルでは、同期後に手動で付け直してください（あるいはその変更自体を手書き SQL で実行してください）。
`WITHOUT ROWID` か `STRICT` に依存しているテーブルは、再構築後に通常の rowid・非 STRICT のテーブルに戻るため、再構築を伴う同期に掛けず、その変更を手書き SQL で適用してください。
`NOT DEFERRABLE` と `DEFERRABLE INITIALLY IMMEDIATE` は既定と同じ即時検査なので、失われても意味が変わらず列挙しません。

同期先の SQLite ファイルは、接続ダイアログの「新規作成」ボタンで新しく作ることもできます。
空のデータベースへ図全体を適用して、新規構築に使えます。

## 方言切替

ツールバー右の「対象DB:」コンボで、図のターゲット DBMS をいつでも切り替えられます。

- 各列の型は「元方言 → 中立の正規型 → 新方言」の経路で自動変換を試みます
- 変換できなかった列は元の型を保持したまま、警告ダイアログに一覧表示されます
- 切替と型変換は 1 回の Undo でまとめて戻せます

次の表の列は、一部の方言へしか変換できないか、セルに書いた変更を伴って変換されます。
✅ の列は変換し（切替先と同じ方言の列はそのまま残る）、それ以外は変換不能として一覧に載ります。

<!-- dialect-table: unconvertible-types -->

| 元の図の列 | SQL Server | PostgreSQL | MySQL | Oracle | SQLite |
| --- | :-: | :-: | :-: | :-: | :-: |
| 負のスケール（PostgreSQL の `numeric(10,-2)`、Oracle の `NUMBER(10,-2)`） | — | ✅ | — | ✅ | — |
| 長さを書かない文字列・バイナリ（PostgreSQL の `varchar`、SQLite の `VARCHAR` / `VARBINARY`） | — | ✅ | — | — | ✅ |
| 精度の無い `decimal`（Oracle の `NUMBER`、PostgreSQL の `numeric`） | — | ✅ | — | ✅ | ✅ |
| 精度は上限なし・スケールは 0 以外（Oracle の `NUMBER(*,2)`） | — | — | — | ✅ | ✅ |
| 精度は上限なし・スケールは 0（Oracle の `INTEGER`、`SMALLINT`、`NUMBER(*,0)`） | ✅（`decimal(38,0)`・38 桁まで） | ✅（`numeric(38,0)`・38 桁まで） | ✅（`decimal(38,0)`・38 桁まで） | ✅ | ✅ |
| 行バージョン（SQL Server の `rowversion` / `timestamp`） | ✅ | — | — | — | ✅（`BLOB`・NOT NULL を解除） |

- 負のスケールは値を丸めます（`-2` なら 100 の倍数）。
  SQL Server と MySQL はそもそも受け付けず、SQLite の `DECIMAL` は丸めを持たないアフィニティなので、実行できない DDL を書き出す代わりに変換不能として報告します
- MySQL と Oracle は長さの無い `varchar` / `VARCHAR2` を受け付けず、SQL Server は長さを省くと**黙って 1 文字の列**を作ります。
  切り替えたい場合は、元の図で長さを書いてください
- 素の `decimal` は SQL Server では `decimal(18,0)`、MySQL では `decimal(10,0)` で、小数部を黙って丸める列になります
- Oracle の `INTEGER` と `SMALLINT` は `NUMBER(*,0)`（精度は上限なし・スケールは 0 の整数）です。
  精度を書かずに宣言できない方言では 38 桁の decimal になり、38 桁を超える値が入らなくなるため、確認ダイアログにその列が挙がります
- PostgreSQL の `numeric` は精度なしでスケールだけを宣言できず、素の `numeric` へ写すとスケールの宣言が落ちます

移行先の上限を超える長さ・精度は、そのまま書き出すと DDL の適用で失敗するため、変換不能として一覧に載ります。

<!-- dialect-table: target-limits -->

| 方言 | 文字列・バイナリ | decimal の精度 | decimal のスケール | 小数秒 |
| --- | --- | --- | --- | --- |
| SQL Server | `nvarchar` / `nchar` 4000・`varchar` / `char` / `binary` / `varbinary` 8000 | 38 | 0〜精度 | 7 |
| PostgreSQL | `varchar` / `char` 10,485,760 | 1000 | -1000〜1000 | 6 |
| MySQL | `char` / `binary` 255・`varchar` 16,383・`varbinary` 65,532 | 65 | 0〜30 | 6 |
| Oracle（`MAX_STRING_SIZE = STANDARD`） | `NVARCHAR2` 2000・`VARCHAR2` 4000・`NCHAR` 1000・`CHAR` / `RAW` 2000 | 38 | -84〜127 | 9 |

- PostgreSQL は 6 桁を超える小数秒（`timestamp(7)`）を受け付けますが 6 桁へ丸めるため、これも一覧に載ります
- MySQL の `varchar` の上限は `utf8mb4` の値（16,383 文字）で、行全体の上限（65,535 バイト）は適用時に MySQL が判定します
- Oracle の文字列と `RAW` の上限は `MAX_STRING_SIZE = STANDARD`（既定）の値です。
  QuickER は接続先の設定を知らないため、`MAX_STRING_SIZE = EXTENDED` のデータベースでも、この上限を超える列は変換不能として一覧に出ます

MySQL の整数は、符号を含めて持てる値の範囲で変換します。
符号つきの `tinyint`（-128〜127）は 16 ビット整数になります（他の方言と共通の 8 ビット整数は SQL Server の `tinyint` と同じく符号なしの 0〜255 のため）。
`tinyint(1)` は MySQL が真偽値を宣言するときの慣習なので、真偽値として読みます。

<!-- dialect-table: mysql-integers -->

| MySQL | 中立の型 | SQL Server |
| --- | --- | --- |
| `tinyint unsigned` | 8 ビット整数（符号なし） | `tinyint` |
| `tinyint` | 16 ビット整数 | `smallint` |
| `smallint unsigned` | 32 ビット整数 | `int` |
| `mediumint`、`mediumint unsigned` | 32 ビット整数 | `int` |
| `int unsigned` | 64 ビット整数 | `bigint` |
| `bigint unsigned` | `decimal(20,0)` | `decimal(20,0)` |
| `tinyint(1)` | 真偽値 | `bit` |

- 切替先の方言が受け付けない名前（上限より長い、保存できない文字を含む）は、切替では変わりません。
  DDL の生成と同期はそうした名前の変更まで止まるため、確認ダイアログには上のカラムと並べて、場所と理由つきで一覧に載ります。
  詳しくは[識別子の長さの上限](#識別子の長さの上限)を参照してください
- SQLite では SQL Server の `rowversion` / `timestamp` の NOT NULL が解除されます（SQLite には採番する主体がいないため、ローカルで作った行は同期が書き込むまで版を持ちません）。
  この変換は非可逆で、その `BLOB` を SQL Server へ戻しても `varbinary(max)` にしかなりません（行バージョンには戻りません）。
  両者で列の意味がどう変わるかは [マルチターゲット Repository](code-generation.ja.md#マルチターゲット-repositorysqlserver--sqlite) を、2 つのデータベースを同期させるコードの生成は[双方向同期の支援](code-generation.ja.md#双方向同期の支援--generate-sync-support)を参照してください
- DB が採番する列の印（値を指定させない自動採番）は、切替先の方言がその種類の列を持てないと外れます。
  確認ダイアログにはその列が挙がり、1 回の Undo で印も戻ります。
  詳しくは[DB が採番する列](code-generation.ja.md#db-が採番する列)を参照してください

## DDL 生成

ツールバーの「出力」から SQL DDL を選ぶと、図の対象 DBMS の方言で CREATE 文一式を出力します。
テーブル・列の説明も DDL に含まれます。
使う機構は方言ごとに違い、SQL Server は sp_addextendedproperty、PostgreSQL / Oracle は COMMENT ON、MySQL は COMMENT 句、SQLite はコメント行です。
エクスポート全般の操作は[インポートとエクスポート](import-export.ja.md)を参照してください。

### 列の型に置ける表記

列の型は、図が持っている文字列がそのまま SQL へ書き出されます（型は識別子でも文字列リテラルでもなく、クォートで包む場所がないため）。
そのため DDL 生成も差分同期も素の型表記だけを受け付け、それ以外を含む列があると出力全体を拒否して「テーブル.列」と型文字列を名指しします。
型に置けるのは次のものです。

- 単一スペース区切りの語（英字・各国語の文字・数字・`_`・`$`）の並び：`int`・`double precision`・`LONG RAW`・`UNSIGNED BIG INT`
- 各語の直後に置く括弧引数。引数は数値・語（文字・数字・`_`）・`*` のいずれかを 1 つか 2 つで、後ろに Oracle の単位語を置けます。
  `nvarchar(max)`・`decimal(10,2)`・`decimal(10,-2)`・`NUMBER(*,2)`・`VARCHAR2(50 CHAR)`・`TIMESTAMP(6) WITH LOCAL TIME ZONE`・`INTERVAL DAY(2) TO SECOND(6)`・`decimal(10,2) unsigned`・PostGIS の `geometry(Point,4326)` / `geography(MultiPolygon)`
- PostgreSQL の配列を表す末尾の `[]`（多次元のため繰り返せます）：`integer[]`・`integer[][]`
- MySQL の値リスト：`enum('a','b')`・`set('x','y')`

型の長さは 200 文字までです。
MySQL の値リストだけは長さを問いません（値の多い `enum` は 200 文字を超えることがあり、実在の宣言だからです）。

5 方言の型カタログが提供する表記も、スキーマ取込が実 DB から組み立てる表記も、すべてこの範囲に収まります。
外れるのは次のものです。

- `;`・引用符・バッククォート・バックスラッシュ・コメント記号（`--`・`/*` と MySQL の `#`）・改行を含む型。
  いずれもどの方言にも不要で、列ではなく文そのものを変えてしまいます（`#` は MySQL の行末コメント開始で、`MODIFY COLUMN` で型の後ろに続く `NOT NULL` / `COMMENT` / `AFTER` を黙って飲み込みます）
- 前後に空白・改行が付いた型。
  検証した文字列と書き出す文字列は一致していなければならず、先に Trim するとそれが崩れます（`"\nGO\n"` は Trim すると語 1 つの `GO` に見えますが、書き出されれば SQL Server のバッチ分割を誤作動させ得ます）。
  空・空白のみは従来どおり「型が未設定」として通ります
- 2 語目以降が列定義の句のキーワード（`NOT`・`NULL`・`DEFAULT`・`PRIMARY`・`KEY`・`REFERENCES`・`CHECK`・`GENERATED`・`IDENTITY`・`COLLATE`・`UNIQUE`・`ON`・`AS`・`AUTO_INCREMENT`・`AUTOINCREMENT`・`INVISIBLE`・`VISIBLE`・`CONSTRAINT`）である型。
  型は列定義の途中へ補間されるため、`int NOT NULL` や `varchar(50) COLLATE Latin1_General_BIN` はそのまま有効な DDL になり、NULL 許容・既定値・照合順序が図の宣言と食い違ったまま通ります（構文エラーが出ないので気付けません）。
  `int AS (price)`（生成列の省略形）や `int AUTO_INCREMENT` も同じで、図が計算列でも自動採番でもないと言う列が、データベースでは生成列・自動採番の列になり、生成コードの INSERT が実行時に失敗します。
  これらの語は、型カタログにも取込が組み立てる実在表記にも現れません

実 DB が生み出し得るものとして 2 つ明記しておきます。
PostgreSQL の 1 バイト `"char"` 型（引用符込みで、書き出す先の SQL がそれを運べません）と、取込が型名を解決できなかったときのフォールバック `user-defined` は通りません。
どちらもそのまま出しても DDL として失敗する表記で、生成時に列名つきで分かるようになったという違いです。

もう 1 つの端は SQLite です。
SQLite は任意の語の並びを宣言型として受理し、取込はそれを verbatim に持ち帰るため、SQL Server 流の DDL で作られた SQLite DB には `INT IDENTITY(1,1)` のような宣言が残り得ます。
2 語目の `IDENTITY` は上記の句キーワードに当たるため拒否されます。
これも生成時に列名つきで分かります。

これは QuickER が型を**解釈**できるかどうかとは別です。
方言カタログが解析できない型もそのまま保持され、中立の型トークンが付かない（＝方言切替で変換されない）だけです。

### 名前に含まれる改行・制御文字

テーブル名・列名・制約名に改行や制御文字が含まれていると、DDL 生成もスキーマ同期スクリプト生成も、場所（`TABLE 'x'`・`COLUMN 'x'.'y'`）を名指しして拒否し、何も出力しません。
対象は C0 制御文字・DEL と、Unicode の行区切り 3 種（U+0085・U+2028・U+2029）です。
C# コード生成も同じ名前を生成前診断のエラーとして報告します。

クォート文字は意図的に通します（`"`・`'`・`]`・バッククォートは実 DB に存在し得る名前で、書き出す箇所でエスケープされます）。
説明も拒否しません（説明の改行は正当で、`--` コメント行へ載る箇所で空白へ畳まれます）。

### 識別子の長さの上限

方言ごとに、テーブル名・列名・制約名の長さに上限があり、数える単位も違います。

<!-- dialect-table: identifier-length-limits -->

| 方言 | 上限 | 数える単位 | 保存できない文字 | 長すぎる名前を DB は |
| --- | --- | --- | --- | --- |
| SQL Server | 128 | UTF-16 コード単位 | — | 断る |
| PostgreSQL | 63 | UTF-8 バイト | — | 黙って切り詰める |
| MySQL | 64（テーブル名はさらにファイル名として 251 バイトまで。下を参照） | 文字 | 基本多言語面の外（`?` に置き換わる） | 断る |
| Oracle | 128（12.2 以降） | UTF-8 バイト | — | 断る |
| SQLite | なし | | — | |

- **QuickER が付ける名前**（`PK_{テーブル}`・`FK_{子}_{親}`・`UQ_{テーブル}_{列…}` と、それらを一意にする番号つきの名前）は、対象の方言の上限に収めます。
  上限内の名前は変わりません。
  超えるときは途中で切り、末尾に `_` と、元の名前から求めた 16 進 8 桁を付けます。
  切ったあとでだけ違う 2 つの名前も、別の名前のままです。
  結果は何度作っても同じです
- **利用者が入力した名前**は縮めません。
  DDL 生成とスキーマ同期スクリプトの生成は、上限を超える名前を場所と上限を示して断り（`TABLE 'x' is longer than the limit of 63 UTF-8 bytes`）、何も出力しません。
  この検査が無いと、DDL の適用で失敗するか、上の表で黙って切り詰める方言では、取り込み直すと別の名前のテーブルになります。
  切り詰めた位置より後ろでだけ違う 2 つの名前は、1 つに潰れてしまいます
- **編集画面と AI のツールは、そうした名前を入力した時点で警告します。**
  対象の方言が受け付けないテーブル名・列名・外部キー名・一意制約名を確定すると、ステータスバーにメッセージが出ます。AI と MCP のツールは応答に注意文を添えます。
  名前は入力のまま受け付けるので、あとで直せます。
  元に戻す・やり直す、ファイルの読込では警告しません
- **MySQL は基本多言語面の外の文字（絵文字や一部の珍しい漢字）を保存できません。**
  QuickER は長すぎる名前と同じに扱い、上の警告と、生成時の拒否の対象にします
- **MySQL のテーブル名には、ファイル名としての上限がもう 1 つあります。**
  InnoDB はテーブルごとにテーブル名のファイルを作り、ASCII の英数字と `_` 以外の文字はエスケープで書きます（`Ä` のような文字は 3 バイト、漢字を含むほとんどの文字は 5 バイト）。
  ファイル名は 251 バイトまでなので、漢字だけのテーブル名は 50 文字までです（列名は 64 文字まで）。
  `innodb_file_per_table` が有効（既定）のときの制約で、QuickER は常にこの上限で検査します
- **Oracle の 12.2 より前**（`COMPATIBLE` が 12.2 未満のデータベース）は、名前を 30 バイトに制限します。
  QuickER は接続先の設定を知らず 128 バイトで検査するため、そうしたデータベースでは名前を自分で短くしてください

#### 以前の版で作ったデータベース

既定名が 63 バイトを超える PostgreSQL の外部キーは、PostgreSQL が黙って切り詰めるため、以前の版では切り詰められた名前で作られていました。
差分同期は、そうした外部キー（利用者が名前を付けていないもの）を図の外部キーと同じものとみなすので、追加も削除も出ません。
