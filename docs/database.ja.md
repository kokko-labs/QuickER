# データベース連携

*[English](database.md) | 日本語*

QuickER は、稼働中のデータベースからスキーマを取り込んで図に起こし、図とデータベースの差分を検出して同期スクリプトを適用し、図から DDL を生成します。図とデータベースはどちらの向きにも往復できるため、取込と差分同期を実行することで、図と実 DB の乖離を把握して解消できます。

## 対応 DBMS

| DBMS | スキーマ取込 | 差分同期 | DDL 生成 | 方言切替 | 備考 |
|---|:-:|:-:|:-:|:-:|---|
| SQL Server | ✅ | ✅ | ✅ | ✅ | 説明は拡張プロパティ（MS_Description）と同期 |
| PostgreSQL | ✅ | ✅ | ✅ | ✅ | 13 以降。説明は `COMMENT ON` と同期 |
| MySQL | ✅ | ✅ | ✅ | ✅ | 8.0 以降（MariaDB は対象外）。説明は `COMMENT` 句と同期 |
| Oracle | ✅ | ✅ | ✅ | ✅ | 19c 以降。説明は `COMMENT ON` と同期 |
| SQLite | ✅ | ✅ | ✅ | ✅ | ファイル DB。列の変更・削除・FK 変更を含む差分同期はテーブル再構築方式。説明の機構なし |

実データベースを使う取込・同期には、実 DB 統合テスト（SQL Server / PostgreSQL / MySQL / Oracle は Testcontainers のコンテナ、SQLite は実ファイル DB）を用意しています。コンテナを使うテストは Docker のある環境でのみ実行され、CI では自動的にスキップされます。また検証は各 DBMS の代表 1 バージョンで行っており、表のサポート範囲全体を網羅するものではありません。

## スキーマ取込（DB → 図）

ツールバーの「DB取込」ボタンから、接続ダイアログ「データベースから取込」を開きます。

### 接続の指定

- **サーバー型 DBMS** — 対象 DB、ホスト、ポート（空欄で方言の既定値）、データベース名、ユーザー名、パスワードを指定します。SQL Server では認証方式（Windows 認証 / SQL Server 認証）と「サーバー証明書を信頼する (TrustServerCertificate)」も選べます。Oracle では「データベース名」欄の値がサービス名として使われます（接続は EZConnect 形式 `host:port/service` で組み立てられます）
- **暗号化 (SSL Mode)** — PostgreSQL・MySQL で、接続に TLS をどこまで要求するかを指定します。既定は「Unspecified」で、接続文字列へキーワードを載せずドライバ既定に委ねます（下の注意を参照）。接続プロファイルごとに保存され、この設定が無かった頃のプロファイルは「Unspecified」で読み込まれます
- **SQLite** — ファイルパスを「参照」から指定します（取込では既存ファイルのみを指定できます）
- **コマンドタイムアウト** — スキーマ取込・同期の SQL 1 文が実行できる時間です。既定は 60 秒で、SQLite を含む全方言に効きます。`0` は無制限（ADO.NET の規約）を意味します。空欄・数値でない入力・負値は、OK と「接続テスト」のどちらでも拒否されます（黙って既定値で動くことはありません）。接続プロファイルごとに保存され、この設定が無かった頃のプロファイルは既定値で読み込まれます
- **接続テスト** — 実際にスキーマの取得を試行し、検出したテーブル数を表示します

> **注意:** 「サーバー証明書を信頼する (TrustServerCertificate)」は、自己署名証明書のローカル・コンテナ環境の SQL Server へそのまま接続できるよう既定でオンです。この設定はサーバー証明書の検証を省略するため、正規の証明書を持つ本番・リモートサーバーへ接続する場合はチェックを外し、なりすまし検知を有効にしてください。設定は接続プロファイルごとに保存されます。

#### 方言ごとの通信路の暗号化

この接続には DB の資格情報が乗るため、何も設定しなかったときに各方言がどう振る舞うかを把握しておいてください。

| 方言 | 何も設定しないときの既定 | 証明書の検証まで求めるには |
| --- | --- | --- |
| SQL Server | 暗号化されるが**証明書は検証しない**（TrustServerCertificate がオン） | 「サーバー証明書を信頼する」のチェックを外す |
| PostgreSQL | Npgsql の既定。サーバーが対応していれば暗号化するが**証明書は検証しない** | **暗号化 (SSL Mode)** を `VerifyCa` / `VerifyFull` にする |
| MySQL | MySqlConnector の既定。同じく暗号化はするが**検証しない** | **暗号化 (SSL Mode)** を `VerifyCa` / `VerifyFull` にする |
| Oracle | **平文 TCP** | ダイアログでは指定できません（後述） |
| SQLite | 該当なし（ローカルファイル） | — |

**暗号化 (SSL Mode)** の各値の意味は次のとおりです。

- `Unspecified` — キーワードを一切書かず、判断をドライバへ委ねます（既定。この設定が無かった頃と接続内容が同一になります）
- `Disable` — 暗号化しません
- `Prefer` — サーバーが対応していれば暗号化します（証明書は検証しません）
- `Require` — 暗号化できなければ接続を拒否します（証明書は検証しません）
- `VerifyCa` — 暗号化を必須にし、証明書が信頼できる CA から発行されていることを検証します
- `VerifyFull` — `VerifyCa` に加えて、証明書が接続先のホスト宛であることも検証します

`Require` が防げるのは盗聴だけです。検証を伴わない以上、中間者は任意の証明書を提示できます。正規の証明書を持つサーバーが相手なら `VerifyFull` を選んでください。

**Oracle** をこの選択肢の対象外にしているのは、管理対象ドライバの TLS がこの形をしていないためです。切り替えは接続文字列のキーワードではなくデータソースのプロトコル接頭辞（`tcps://host:2484/service`）で行い、あわせてリスナーのポートも変える必要があります。また TCPS は常に証明書チェーンを検証するため `Require` に当たる形が無く、交渉による切り替えも無いため `Prefer` に当たる形もありません。Oracle へ TLS で接続する必要がある場合は、接続文字列をそのまま渡す `quicker scaffold --connection` を使ってください。

```
quicker scaffold --connection "Data Source=tcps://db.example.com:2484/ORCLPDB1?ssl_server_dn_match=true;User Id=app;Password=***" --out ./Generated --provider oracle
```

Windows では信頼する CA をホスト自身の証明書ストア（Microsoft 証明書ストア）から取るため、Oracle ウォレットは不要です。他のプラットフォームではシステムの OpenSSL トラストストアが使われ、ホストの構成によってはウォレットが必要になる場合があります。`ssl_server_dn_match=true` は「証明書が接続先のサーバー宛か」を検証させる指定です。この既定値はドライバの版によって異なってきた経緯があり（確認した版ではオフ＝素の `tcps://` は `VerifyFull` より `VerifyCa` に近い状態）、既定に頼らず明示することと、実際に使うドライバの版で挙動を確認することをおすすめします。Oracle の*ネイティブネットワーク暗号化*は接続文字列の外で設定する別機構で、サーバーの認証を行わないため代用にはなりません。

PostgreSQL・MySQL を `quicker scaffold` から使う場合も専用のオプションはありません。`SSL Mode` は通常の接続文字列キーワードなので `--connection` に含めてください（`...;SSL Mode=VerifyFull`）。

### 接続プロファイル

入力内容は名前を付けて保存でき、次回から「保存済み接続」で呼び出せます。プロファイルは `%LOCALAPPDATA%\QuickER\connections.json` に保存され、パスワードは本体とは分離した別ファイルへ **Windows DPAPI（CurrentUser スコープ）で暗号化**して保存されます（「保存」チェックを付けた場合のみ。既定の設定では平文で保存されることはありません）。最後に使った接続内容は自動的に記憶され、次回起動時に復元されます。

### 取り込まれる内容

- テーブル（ビュー・一時表・マテリアライズドビューのコンテナ表は対象外）と列（型・長さ・精度・NULL 可否）
- 主キー。複合キーは制約自身の列順序ごと取り込みます。`PRIMARY KEY (b, a)` はそのまま `(b, a)` として図に入り、生成 DDL も制約が宣言していた順序で出力されるため（テーブルでの列の並びとは独立）、裏付けインデックスの列順が往復で保たれます
- 外部キー（制約名と ON DELETE / ON UPDATE の参照アクションを含む）。FK を持つ側の列集合が、そのテーブル自身の主キーまたは一意制約と一致する場合は 1 対 1 と判定されます。複数列で構成される外部キーも、列同士の対応付けを宣言順にすべて取り込みます。SQLite は FK 制約名を永続化しないため、取込時に制約名が合成されます
- テーブル・列の説明（SQL Server の MS_Description 拡張プロパティ、PostgreSQL の `obj_description` / `col_description`、MySQL の `TABLE_COMMENT` / `COLUMN_COMMENT`、Oracle の `user_tab_comments` / `user_col_comments`）。SQLite は説明の機構がないため対象外です

取り込まれるのはここまでです。境界の全体と、DDL 生成への影響は[図がモデル化する範囲](#図がモデル化する範囲)を参照してください。

#### 取込が見ている範囲

方言ごとに取込の対象範囲は 1 つで、その外にあるオブジェクトは取込からは見えません。

| DBMS | 取込の対象範囲 |
|---|---|
| SQL Server | 接続先データベースの全スキーマ |
| PostgreSQL | `public` スキーマのみ |
| MySQL | 接続先データベース（MySQL の「スキーマ」はデータベースそのもの） |
| Oracle | 接続ユーザーの自スキーマ（`USER_*` ビュー） |
| SQLite | 接続した単一のデータベースファイル |

この範囲の外を参照する外部キーは、親テーブルが図に無いためリレーションにできません。黙って消さず、除外したことを報告します（次項）。Oracle では DISABLE された制約も取り込みません。DISABLE された制約は実際には何も強制しないため、取り込むと図がデータベースには無い保証を宣言することになるからです。

#### 取込の警告

取込そのものは常に成功しますが、スキーマの一部は宣言どおりの形では図へ写し取れません。その場合は完了ダイアログが対象を一覧します（`quicker scaffold` は同じ内容を標準エラーへ出力します）。差が黙って生まれないようにするためです。

- PostgreSQL の**ドメイン型**の列は基底型として取り込みます。図はドメイン型を持たないため、ドメインの `CHECK` 制約は失われます
- **取込範囲の外を参照する外部キー**は取り込みません
- **列を 1 つも読み取れなかった**テーブルは、列なしで取り込みます
- **大文字小文字だけが違う同名テーブル**は片方だけを取り込みます（取込は両者を区別できないため。PostgreSQL と Oracle は引用識別子で、MySQL も `lower_case_table_names` が 0 なら両方を共存させられます）
- **SQL へ安全に書き出せない型**の列は、型の表記ごと名指しします。取込は成功しますが、直すまで DDL 生成とスキーマ同期は**図全体**を拒否します（型は識別子でも文字列リテラルでもなく、クォートで包む場所がないためです。[列の型に置ける表記](#列の型に置ける表記)を参照）。SQLite は宣言された型のテキストをそのまま保持し、PostgreSQL は引用が要る型名を引用込みで返すため、どちらからも出ます
- **パーティションテーブル**は親テーブルとして取り込み、パーティション自体はモデル化しません。生成 DDL はパーティションなしで作成します

対象が 1 件も無ければ、従来どおり 1 行の完了メッセージになります。

#### 取り込んだ型の表記

取込は各列の宣言型をデータベース自身のカタログから読み、QuickER の短い語彙で書き出します。PostgreSQL の正準表記 `character varying(50)` ではなく `varchar(50)`、`timestamp(3) with time zone` ではなく `timestamptz(3)` です。変わるのは表記だけで、型は変わりません。

PostgreSQL では、これにあわせて**従来は誤った表記で取り込まれていた型**も正されます。以前の情報源では一部の修飾を表現できなかったためです。`numeric(10,-2)` と宣言した列は `numeric(10,2046)` として取り込まれていました。これは PostgreSQL 自身が受け付けない表記で、その図からは DDL すら生成できませんでした。`bit(8)` と `bit varying(16)` は長さを、`interval day to second(3)` は単位を、`time(3) with time zone` は精度を失い、配列は `_int4` のような内部名に、`varchar(20)[]` に至っては長さごと落ちて `_varchar` になっていました。これらの列は、実際の宣言型で取り込まれるようになりました。

**古いバージョンで作った図へ PostgreSQL を取り込み直すと、初回だけ差分が出ます。**上記に当たる列は、図が古い壊れた表記を、データベースが正しい表記を持つため、差分同期に列の変更として 1 度だけ現れます。健全な列は影響を受けません（表記は変わりません）。

取込結果は現在の図へマージされます。テーブル名・列名で現在の図と照合し、一致した要素は現在の図の要素の同一性を引き継ぐため、レイアウト・幅・色・メモと、それらを参照する名前付きクエリが温存されます。空き領域へ配置されるのは新しく取り込まれたテーブルだけで、現在の図に一致する要素が 1 件もない完全な新規取込のときにだけ、図全体が自動整列されます。確認ダイアログは、現在の図と構造的な差分がある場合に加えて、取込によって壊れる名前付きクエリがある場合にも表示され、削除対象のクエリ名が列挙されます。

取り込んだ後、手元の既存エンティティ資産と生成コードをどう付き合わせるかは、[生成コードの使い方の「既存コードベースとの共存」](code-generation.ja.md#既存コードベースとの共存)を参照してください。

## 図がモデル化する範囲

図はデータベースの複製ではなく設計モデルです。往復できるのは、図がモデル化している次の範囲だけです。

- テーブルと列（型・長さ・精度・NULL 可否）
- 主キー（複合キー自身の列順序を含む）
- 外部キー（列ペア・制約名・参照アクション）
- UNIQUE 制約
- テーブル・列の説明

これ以外はモデルの外です。取り込まれず、生成 DDL にも出ず、差分同期も検出・変更の対象にしません。

| スキーマ要素 | 取込 | 生成 DDL | SQLite のテーブル再構築 |
|---|---|---|---|
| `DEFAULT` | 取り込まない | 出力しない | 失われる |
| `CHECK` 制約 | 取り込まない | 出力しない | 失われる |
| `COLLATE` | 取り込まない | 出力しない | 失われる |
| 生成列（計算列） | 通常の列として取り込む（式は失われる） | 通常の列として出力 | 失われる |
| `IDENTITY` / `AUTO_INCREMENT` / `AUTOINCREMENT` | 取り込まない | 出力しない | 失われる（宣言型が `INTEGER` の主キーは rowid 別名のままなので暗黙の自動採番は保たれる＝下記の注記） |
| 非 UNIQUE インデックス | 取り込まない | 出力しない | 温存（`CREATE` 文の全文を保持して再作成） |
| トリガー | 取り込まない | 出力しない | 温存（同上） |
| ビュー・ストアドプロシージャ・関数・シーケンス | 取り込まない | 出力しない | 対象外 |

**rowid 別名が成立するかは「整数列かどうか」ではなく宣言型のつづりで決まります。** SQLite が主キーを rowid 別名として扱うのは、宣言型がちょうど `INTEGER` のときだけです。表制約の形かどうかは関係なく（`x INTEGER, PRIMARY KEY (x)` も、QuickER が出力する `x INTEGER NOT NULL, CONSTRAINT PK_t PRIMARY KEY (x)` も別名になります）、`INT` は別名になりません。SQLite から取り込んだ図は宣言型をそのまま保持するため上記の保証が成立しますが、QuickER で新規作成した図や、方言を切り替えて SQLite へ戻した図は 32 ビット整数に `INT`・64 ビット整数に `BIGINT` を出力します。そう宣言された主キーはただの列で、暗黙の自動採番はそもそも存在せず、キーを与えない INSERT は NULL を入れます（生成される Repository はアプリ側でキーを採番する前提なので、この違いは生成コードの動作には影響しません）。

SQLite のテーブル再構築を除けば、これらのオブジェクトはそのまま放置されます。差分同期は検出すらしないため、手で作ったインデックスや `DEFAULT` はデータベースに残り続けます。図の定義からテーブルを作り直す再構築だけが例外で、だからこそ図が表現できないものを落とし得ます（QuickER は対象テーブルで見つかった属性を実行確認に列挙します。[SQLite の差分同期](#sqlite-の差分同期テーブル再構築方式)を参照）。

**DDL 生成は設計から新しいスキーマを作るための機能であり、取り込んだ既存データベースの再現には使えません。** 元のデータベースが上記のモデル化範囲だけで出来ていない限り、生成される `CREATE` 文は別物のスキーマです（テーブル・列・キー・制約は同じでも、既定値・CHECK・照合順序・自動採番・インデックス・トリガーは 1 つもありません）。既存データベースの移送にはそのデータベース自身のツールを使い、QuickER の DDL は設計から新規に立ち上げる用途に使ってください。

## 差分同期（図 → DB）

ツールバーの「DB同期」ボタンから、差分ダイアログ「DB スキーマ同期 (差分実行)」を開きます。データベースの現状と図の内容を突き合わせ、差分の一覧と生成 SQL のプレビューを確認したうえで、選択した項目だけを実行できます。

### 検出される差分

- テーブルの追加・削除
- 列の追加・変更（型・NULL 可否）・削除
- 外部キーの追加・削除
- 主キーの変更（付与・解除・キー列構成または列順序の変更）
- テーブル・列の説明の設定・更新・削除（SQLite は対象外）
- 列の並び順の変更（同期できるのは SQLite / MySQL）

同名の要素を同一とみなして比較するため、リネームは「削除＋追加」として検出されます。

列の並び順は、追加・削除を除いた共通列の相対順序で比較されます。SQLite と MySQL では選択可能な差分項目（既定では未選択）として同期でき、SQLite はテーブル再構築に畳み込み、MySQL は `ALTER TABLE ... MODIFY ... AFTER` で移動する列を最小限にします。MySQL の `MODIFY` は列定義を実 DB のカタログから組み立て直すため、列を動かしても属性と説明はそのまま残ります（[MySQL の `MODIFY COLUMN` が再指定するもの](#mysql-の-modify-column-が再指定するもの)を参照）。他の 3 方言では案内として表示されるのみで、同期の対象外です。

### 実行の安全設計

- **破壊的な差分（削除・型変更）は既定で選択されず**、実行時には破壊的変更を含む旨の確認が表示されます
- 生成スクリプトは依存関係順（テーブル追加 → 列追加 → FK 削除 → 旧主キー解除 → 列変更 → 新主キー付与 → 列削除 → テーブル削除 → FK 追加 → 説明）に並び、種別ごとの見出しコメントが付きます
- FK 列を解決できない外部キー追加は、不正な DDL を出さずスキップコメントとして出力されます
- 複数列で構成される外部キー（複合外部キー）は正式に対応しています。リレーションは列ペアの順序付きリストを保持するため、取込・DDL 生成・同期のいずれも構成列をすべて運びます。主キー変更に伴う暗黙の解除・再作成や SQLite のテーブル再構築も同様で、複合外部キーが単一列へ静かに縮むことはありません
- SQL Server・PostgreSQL・SQLite ではトランザクションで実行され、失敗時はロールバックされます。MySQL / Oracle は DDL が暗黙コミットされる仕様のため、途中で失敗した場合は部分適用となる可能性がある旨が警告されます
- SQLite の再構築を含む実行では、再構築されるテーブルを列挙した専用の確認が表示されます
- 最初の差分検出で差分が 1 件もない場合は、その旨を表示したままダイアログは開いています。同期を適用したあとの再読込で差分がゼロになった場合は、自動で閉じます。実行が失敗した場合も差分を自動で再読込するため、部分適用後の状態が一覧に反映されます（MySQL / Oracle で意味を持ちます）

### 主キーの同期

図でテーブルの主キーを変更（付与・解除・キー列構成または列順序の変更）すると、テーブル単位の差分項目 1 件として検出されます（既定では未選択）。旧主キーの制約名は実行時にデータベースのカタログを逆引きして特定するため、任意の制約名を持つ取込済みデータベースでもそのまま動きます。スクリプトは「旧主キーの解除 → 選択した列変更 → 新主キーの付与」の順に実行されるため、旧キー列を NULL 許容へ変える変更も 1 回の同期で成立します。

変更対象の主キーを参照している外部キーは、変更の前後で自動的に「外して→作り直す」処理が入ります（SQL Server では外部キーに関わる列の変更でも同様です）。参照先の列が新しい主キーに含まれなくなる場合は、外部キーの再作成が失敗する可能性がある旨が実行確認に表示されます。失敗時、SQL Server・PostgreSQL ではスクリプト全体がロールバックされますが、MySQL / Oracle では外部キーが外れたままの部分適用になり得ます。

### 説明の同期

テーブル・列の説明は、説明の機構を持つ 4 方言で同期されます。SQL Server は MS_Description 拡張プロパティ、PostgreSQL と Oracle は `COMMENT ON`、MySQL は `COMMENT` 句を使います。既存の有無を判定して追加と更新を使い分けるのは SQL Server の拡張プロパティのみで、PostgreSQL と Oracle は `COMMENT ON`、MySQL は `COMMENT` 句を再実行します（いずれもそれ自体が冪等です）。図側で説明を空にすると削除されます。SQLite は説明の機構がないため、差分検出も同期も行われません。

#### MySQL の `MODIFY COLUMN` が再指定するもの

MySQL には、列の説明だけを変える文も、位置だけを変える文もありません。どちらも `ALTER TABLE ... MODIFY COLUMN` を通り、この文は列定義を**まるごと**言い直します。新しい定義に書かなかったものは、その列から消えます。MySQL の DDL は暗黙にコミットされるため、取り消しもできません。

そこで QuickER は、変更の目的に応じて列定義の出どころを 2 つに分けています。

- **説明の同期と列順の同期**は、実行時に `information_schema.COLUMNS` から列定義を組み立て直し、変えるべき末尾の句（説明、または `AFTER` / `FIRST`）だけを差し替えます。図が表現しないもの——`DEFAULT`（リテラル・式の両方。`BIT` とバイナリ系のリテラルを含む）、`AUTO_INCREMENT`、照合順序とそれに伴う文字集合、`ON UPDATE CURRENT_TIMESTAMP`、`INVISIBLE`、空間参照系の `SRID`、生成列（`VIRTUAL` / `STORED`）——はそのまま引き継がれます。列順の同期では、その列に付いている説明も保たれます。
- **列定義の変更**（型・NULL 制約の変更）は図から再指定します。その変更が表しているものが図そのものだからです。したがって上に挙げた属性は**落ちます**——いずれも図では表現できないものです。この差分は既定で未選択です。

次の 2 つは組み立て直しを通りません。いずれもカタログが書いたとおりには記録していないためです。

- `COLUMN_FORMAT` と `STORAGE`（NDB Cluster）は `information_schema` に対応する列が無く、読み出せないため引き継げません。
- 生成列の式に含まれる文字列リテラルの文字集合導入子（`_latin1'x'`）は、接続の文字集合で読み直されて書き戻されます（`_utf8mb4'x'`）。式の意味は変わらず、カタログが記録する文字列だけが動きます。

スクリプトの実行時点で列が無くなっていれば、その文は no-op に畳まれます。何も失敗していないため、同期は成功として報告されます。列は在るのに定義を組み立て直せなかった場合は、逆にその文が失敗します。中途半端に適用された列順が成功として報告されることはありません。

同期はスクリプトの実行前に、自分のセッションの `sql_mode` から `NO_BACKSLASH_ESCAPES` を外します（グローバルの設定には触れません）。QuickER が書き出すリテラルは MySQL 既定の規則でエスケープされており、このモードのままでは同じ文字列がバックスラッシュを二重にしたまま格納されるためです。

この「実 DB からの組み立て直し」は、MariaDB を対象外としている理由のひとつでもあります。MariaDB は `COLUMN_DEFAULT` の記録の意味論が異なるため、カタログから組み立て直した定義が元の列を再現する保証がありません。

### SQLite の差分同期（テーブル再構築方式）

SQLite は `ALTER TABLE` でできる変更が限られているため、列の変更・削除などを含む同期はテーブル再構築方式で行います。「データベースの現状＋選択した差分」を合成した新しい定義のテーブルを作成し、データを移送してから旧テーブルと入れ替え、インデックスなどの補助オブジェクトを再作成します。再構築はトランザクション内で実行され、コミット前に外部キー整合を検査（`PRAGMA foreign_key_check`）して、違反があればロールバックのうえ違反テーブルを報告します。

再構築後のテーブルは図の定義から作成されるため、[図がモデル化する範囲](#図がモデル化する範囲)の外にあるものは再現されません。`AUTOINCREMENT`・`DEFAULT`・`CHECK`・`COLLATE`・生成列は現在の DB にあっても**再現されず黙って失われます**（QuickER の外で設定した既定値が再構築後に消えるのはこのためです）。インデックスとトリガーは `CREATE` 文の全文を保持して再作成するため失われません。暗黙の自動採番も、図の宣言型が `INTEGER` である限り保たれます（そうした主キーは再構築後も rowid 別名のままです。`INT` と宣言された主キー＝QuickER で新規作成した図や方言変換を経た図が持つ形は、もともと別名ではありません。[図がモデル化する範囲](#図がモデル化する範囲)を参照）。喪失を見えるようにするため、QuickER は再構築対象テーブルの現在の `CREATE TABLE` 文を読み取り、見つかった属性を実行確認ダイアログに列挙します。その属性が必要なテーブルでは、同期後に手動で付け直してください（あるいはその変更自体を手書き SQL で実行してください）。

**テーブルオプション** `WITHOUT ROWID` と `STRICT` も同様に失われますが、**警告は出ません**。これらは列リストの閉じ括弧より後ろに置かれ、上記の確認を支える検出器は括弧の内側しか読まず、検出語の一覧にもこの 2 語は入っていないためです。再構築後のテーブルは、何も告げられないまま通常の rowid・非 STRICT のテーブルに戻ります。どちらかのオプションに依存しているテーブルは、再構築を伴う同期に掛けず、その変更を手書き SQL で適用してください。

同期先の SQLite ファイルは、接続ダイアログの「新規作成」ボタンで新しく作ることもできます。空のデータベースへ図全体を適用して、新規構築に使えます。

## 方言切替

ツールバー右の「対象DB:」コンボで、図のターゲット DBMS をいつでも切り替えられます。

- 各列の型は「元方言 → 中立の正規型 → 新方言」の経路で自動変換を試みます
- 変換できなかった列は元の型を保持したまま、警告ダイアログに一覧表示されます
- 切替と型変換は 1 回の Undo でまとめて戻せます
- `numeric(10,-2)` / `NUMBER(10,-2)`（100 の倍数へ丸めるスケール）の列は、PostgreSQL と Oracle の間でしか変換できません。SQL Server と MySQL は負のスケールをそもそも受け付けず、SQLite の `DECIMAL` は丸めを持たないアフィニティなので、この 3 方言では実行できない DDL を書き出す代わりに変換不能として報告します
- SQL Server の `rowversion` / `timestamp` は SQLite では通常の `BLOB` になり、同時に NOT NULL が解除されます（SQLite には採番する主体がいないため、ローカルで作った行は同期が書き込むまで版を持ちません）。この変換は非可逆で、その `BLOB` を SQL Server へ戻しても `varbinary(max)` にしかなりません（行バージョンには戻りません）。両者で列の意味がどう変わるかは [マルチターゲット Repository](code-generation.ja.md#マルチターゲット-repositorysqlserver--sqlite) を、2 つのデータベースを同期させるコードの生成は[双方向同期の支援](code-generation.ja.md#双方向同期の支援--generate-sync-support)を参照してください。他の方言には対応する型が無いため、`rowversion` 列は変換不能として警告に載ります

## DDL 生成

ツールバーの「出力」から SQL DDL を選ぶと、図の対象 DBMS の方言で CREATE 文一式を出力します。テーブル・列の説明も DDL に含まれます（SQL Server は sp_addextendedproperty、PostgreSQL / Oracle は COMMENT ON、MySQL は COMMENT 句、SQLite はコメント行）。エクスポート全般の操作は[インポートとエクスポート](import-export.ja.md)を参照してください。

### 列の型に置ける表記

列の型は、図が持っている文字列がそのまま SQL へ書き出されます（型は識別子でも文字列リテラルでもなく、クォートで包む場所がないため）。そのため DDL 生成も差分同期も素の型表記だけを受け付け、それ以外を含む列があると出力全体を拒否して「テーブル.列」と型文字列を名指しします。型に置けるのは次のものです。

- 単一スペース区切りの語（英字・各国語の文字・数字・`_`・`$`）の並び — `int`・`double precision`・`LONG RAW`・`UNSIGNED BIG INT`
- 各語の直後に置く括弧引数。引数は数値・語（文字・数字・`_`）・`*` のいずれかを 1 つか 2 つで、後ろに Oracle の単位語を置けます — `nvarchar(max)`・`decimal(10,2)`・`decimal(10,-2)`・`NUMBER(*,2)`・`VARCHAR2(50 CHAR)`・`TIMESTAMP(6) WITH LOCAL TIME ZONE`・`INTERVAL DAY(2) TO SECOND(6)`・`decimal(10,2) unsigned`・PostGIS の `geometry(Point,4326)` / `geography(MultiPolygon)`
- PostgreSQL の配列を表す末尾の `[]`（多次元のため繰り返せます） — `integer[]`・`integer[][]`
- MySQL の値リスト — `enum('a','b')`・`set('x','y')`

5 方言の型カタログが提供する表記も、スキーマ取込が実 DB から組み立てる表記も、すべてこの範囲に収まります。外れるのは次のものです。

- `;`・引用符・バッククォート・バックスラッシュ・コメント記号（`--`・`/*` と MySQL の `#`）・改行を含む型。いずれもどの方言にも不要で、列ではなく文そのものを変えてしまいます（`#` は MySQL の行末コメント開始で、`MODIFY COLUMN` で型の後ろに続く `NOT NULL` / `COMMENT` / `AFTER` を黙って飲み込みます）
- 前後に空白・改行が付いた型。検証した文字列と書き出す文字列は一致していなければならず、先に Trim するとそれが崩れます（`"\nGO\n"` は Trim すると語 1 つの `GO` に見えますが、書き出されれば SQL Server のバッチ分割を誤作動させ得ます）。空・空白のみは従来どおり「型が未設定」として通ります
- 2 語目以降が列定義の句のキーワード（`NOT`・`NULL`・`DEFAULT`・`PRIMARY`・`KEY`・`REFERENCES`・`CHECK`・`GENERATED`・`IDENTITY`・`COLLATE`・`UNIQUE`・`ON`）である型。型は列定義の途中へ補間されるため、`int NOT NULL` や `varchar(50) COLLATE Latin1_General_BIN` はそのまま有効な DDL になり、NULL 許容・既定値・照合順序が図の宣言と食い違ったまま通ります（構文エラーが出ないので気付けません）。これらの語は、型カタログにも取込が組み立てる実在表記にも現れません

実 DB が生み出し得るものとして 2 つだけ明記しておくと、PostgreSQL の 1 バイト `"char"` 型（引用符込みで、書き出す先の SQL がそれを運べません）と、取込が型名を解決できなかったときのフォールバック `user-defined` は通りません。どちらもそのまま出しても DDL として失敗する表記で、生成時に列名つきで分かるようになったという違いです。もう 1 つの端は SQLite で、SQLite は任意の語の並びを宣言型として受理し取込はそれを verbatim に持ち帰るため、SQL Server 流の DDL で作られた SQLite DB には `INT IDENTITY(1,1)` のような宣言が残り得ます。2 語目の `IDENTITY` は上記の句キーワードに当たるため拒否されます——これも生成時に列名つきで分かります。

### 名前に含まれる改行・制御文字

テーブル名・列名・制約名に改行や制御文字が含まれていると、DDL 生成もスキーマ同期スクリプト生成も、場所（`TABLE 'x'`・`COLUMN 'x'.'y'`）を名指しして拒否し、何も出力しません。対象は C0 制御文字・DEL と、Unicode の行区切り 3 種（U+0085・U+2028・U+2029）です。C# コード生成も同じ名前を生成前診断のエラーとして報告します。

クォート文字は意図的に通します（`"`・`'`・`]`・バッククォートは実 DB に存在し得る名前で、書き出す箇所でエスケープされます）。説明も拒否しません（説明の改行は正当で、`--` コメント行へ載る箇所で空白へ畳まれます）。

これは QuickER が型を**解釈**できるかどうかとは別です。方言カタログが解析できない型もそのまま保持され、中立の型トークンが付かない（＝方言切替で変換されない）だけです。
