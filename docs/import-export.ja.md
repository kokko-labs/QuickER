## インポート

「取込」ボタンからファイルを選ぶと、取込内容が図に反映されます。
DBML と Mermaid は図全体を置き換え、取込後に自動整列が適用されます。
**Excel 定義書はマージ取込**で、一致したテーブル・列は現在の図にある要素をそのまま引き継ぎます。
そのため名前付きクエリ定義や手で配置したレイアウトが温存され、自動整列も行われません。
DBML と Mermaid は、空でない図を置き換える前に確認します。テーブルを作り直して配置し直すため、構造が同一でも手で配置したレイアウト・色・メモ（Mermaid では説明も）と元に戻す履歴が失われるからです。
Excel 定義書は、現在の図が空の場合と、構造が同一で説明・メモの上書きも壊れる名前付きクエリも無い場合に、確認なしで続行します。

### DBML（.dbml）

`Table` ブロックと `Ref` 行からなる DBML を取り込みます。
対応範囲は QuickER の DBML エクスポートが書き出すサブセットで、構文だけでなく関係の列対応も往復します（`Ref` 行に書かれた列名をそのまま端点として使うため、ファイルが名指しした列がそのまま結ばれます）。

- 列設定: `pk`（`primary key` も可）/ `unique` / `null` / `not null` / `note: '...'` と、インライン参照（`ref: > users.id`。後述）。
  それ以外の設定は、参照先の無い `ref` も含めて読み飛ばします。外部キーの印は設定でなく、リレーションの子側の列であることから立てます
- テーブルの説明: `Table` ブロック内の `Note: '...'` 行（DBML 標準の書き方。他ツールが書いたファイルからも説明を復元します）
- 一意制約: 列設定の `unique`（その 1 列の制約）と、`Indexes` ブロックの `unique` 索引（`(列, …) [unique, name: '…']`＝複合・名前付き）。
  `unique` でも `pk` でもない索引は読み飛ばします
- 主キー: 列設定の `pk` と、`Indexes` ブロックの `pk` 索引（`(列, …) [pk]`）。後者は主キー自身の列順序も表します。
  `pk` 索引から一意制約は作らず（主キーはそれ自体が一意です）、索引の名前は捨てます（図は主キーの制約名を持ちません）。
  他のツールがこの書き方で主キーを宣言したファイルも読めます。
  列に `pk` を付けたうえで `pk` 索引も持つテーブルは、両者が同じ列を指していなければならず、順序は索引が決めます。
  列の集合が違う・`pk` 索引が 2 つある・索引の中で同じ列が 2 回出る、のいずれかは推測で合わせず、その行を示して取込を断ります
- 関係: DBML の短縮形 `Ref: Parent.a < Child.x` と、名前付きの `Ref 名前: Parent.a < Child.x`。
  記号は `-`（1 対 1）、`<`（1 対 多）、`>`（多 対 1。左右を入れ替えた 1 対 多として読みます）、`<>`（多 対 多）。
  1 対 1 の行では、2 つ目の列が外部キーです。
  端点は単一列（`Parent.a`）と複合 Ref 構文（`Parent.(a, b)`）の両方に対応し、複合外部キーは構成ペアが順序どおりに復元されます。
  両端の列数が食い違う行や、テーブルに無い列名を含む行は、リレーション自体は残したうえで列対応だけを捨てます（プロパティパネルで補えます）
- 制約名と参照アクション: 制約名は名前付き `Ref` の名前（`Ref FK_name: …`。引用が要る名前は `Ref "FK name": …`）から、参照アクションは端点の後ろの設定ブロック（`[delete: cascade, update: set null]`）から復元します。
  DBML の `restrict` は QuickER に対応する値が無いため `NO ACTION` として取り込みます。
  名前の無い `Ref` は名前を持たないまま取り込まれ、DDL が既定名 `FK_{子}_{親}` を付けます。
  同じ 2 テーブル間の名前の無い 2 本目のように既定名が既に使われているときは、子の外部キー列の名前を足し、それも使われていれば番号を足した名前を付けます
- インライン参照: 列設定の `ref: 記号 テーブル.列` は、その列を左辺に置いた `Ref` 行として読みます（`user_id integer [ref: > users.id]` は `Ref: posts.user_id > users.id` と同じ）。
  例外は 1 対 1（`-`）で、DBML の規則どおり `ref` を書いた列を外部キーとします。`Ref` 行とは逆です。
  インライン参照は名前と参照アクションを持ちません。
  スキーマ修飾の `ref: > public.users.id` のように読めない参照は、行番号つきの取込エラーにします
- 引用識別子: `"Order Details"` のように書かれたテーブル名・列名は引用符を外して読みます。型も同じ書き方（`"double precision"` / `"integer[]"`）に対応します。引用符の中の `\"` と `\` は復元します
- コメント: `//` から行末までと、複数行にまたがるものを含む `/* ... */`。どちらも文字列リテラルの中ではコメント扱いしないため、説明に URL を書けます
- キーワードは大文字小文字を区別しません（`Table` と `table`、`Ref:` と `ref:` のどちらでも読みます）
- 読み飛ばすもの: `Project` / `Enum` / `TableGroup` / `TablePartial` / `Note` / `records` の各ブロックと、テーブル名の後ろに書かれたテーブル設定（`Table users [owner: 'x'] {`）。QuickER が表せない情報しか持たないため、ブロックごと読み飛ばしてファイルの残りを取り込みます
- 未対応（読み飛ばさず、行番号つきで取込エラーにするもの）: ブロック形式の `Ref { ... }` / `Ref name { ... }` と、設定ブロックを端点の前に置いた `Ref` 行（どちらも読み飛ばすとリレーションが消えるため）・テーブルの別名（`Table t as U {`）・`~partial` の注入・`Table` ブロック内の複数行 `Note`・その他の解釈できない行

`Ref` 行とインライン参照は参照先の `Table` ブロックより前に書いても構いません（テーブルをすべて読み切ってから解決し、リレーションは書かれた順に並びます）。
どこにも定義されていないテーブルを参照する行は、従来どおり行番号つきの取込エラーになります。

列を持たないテーブルには既定の PK 列（`ID int`）が補われます。
DBML は方言情報を持たないため、図の対象 DB は取込前のまま維持されます。

### Mermaid（.mmd / .mermaid）

`erDiagram` 記法を取り込みます。
DBML と同じく方言情報を持たないため、対象 DB は維持されます。
キー標識 `UK` は、その 1 列だけの一意制約として取り込みます（Mermaid には複数列をまとめる構文が無いため、複合の一意制約は表現できません）。
列名に空白や記号は書けません（属性行は「型 名前 標識」を空白で区切る記法のため）。
書き出しでは `_` へ畳み、畳んだ列があることを完了時の内訳で告げます。
畳んだ結果が同じテーブルの別の列とぶつかるときは、畳む必要のない名前が元の綴りを保ち、畳んだほうに連番（`_2`, `_3`, …）が付きます。
空白や括弧を含むテーブル名のように Mermaid が素で書けない名前は二重引用符で囲んで書き（`"Order Details"`）、取込はリレーション行でも引用符を外して読みます。
引用の中にも書けない `"`・`%`・`\` は `_` へ畳んで告知し、畳んだ結果が別のテーブルとぶつかるときは番号を付けます。
型は Mermaid の型の語として書き、`-`・`[`・`]`・`.`・`*` 以外の空白と記号を `_` へ畳みます。
取込は末尾の `_10_2` を `(10,2)` へ戻します。
`nvarchar(max)` や `double precision` のように取込で元へ戻らない型は告知します。
型の無い列は型 `_` で書き、取込は型の無い列として読みます。
リレーション行にはラベルが必須のため、書き出しは制約名を、名前の無いリレーションには `relates` を書きます。
空白や記号を含むなど Mermaid が素で書けない名前は二重引用符で囲み、`"` は `_` へ畳みます。
取込でラベルを制約名にするのは、引用符の無い 1 語で、`relates` でなく、ほかのリレーションに付いておらず、主キー・一意制約の名前とも重ならないときだけです。
そのため、他のツールが繰り返し使う `has` のようなラベルは名前にならず、実際に `relates` という名前の制約も名前を失います。
こうして取込で同じ名前に戻らない制約名があれば、書き出し時に告知します。
名前にならなかったリレーションは名前を持たないまま取り込まれ、DDL が既定名 `FK_{子}_{親}` を付けます。
同じ 2 テーブル間の 2 本目のように既定名が既に使われているときは、子の外部キー列の名前を足し、それも使われていれば番号を足した名前を付けます。

### Excel 定義書（.xlsx）

QuickER がエクスポートした定義書を再取込できます。
キー欄の `UQ{n}` は同じ番号が同じ一意制約を表すため、同番の列をまとめて 1 件の制約として復元します（制約名は定義書に載らないため未設定＝DDL 生成時に合成されます）。
定義書は制約の構成列の順序も計算列の指定も載せないため、マージ取込はこれらを現在図から引き継ぎます。
構成列の集合が現在図の制約と同じ一意制約はその制約の列順を、現在図に名前があれば名前も引き継ぎ、一致した列は計算列の指定を引き継ぎます。
リレーション一覧の制約名欄が空のリレーションは名前を持たないまま取り込まれ、DDL が既定名 `FK_{子}_{親}` を付けます。
同じ 2 テーブル間の 2 行目のように既定名が既に使われているときは、子の外部キー列の名前を足し、それも使われていれば番号を足した名前を付けます。
シートの役割は非表示の定義タグで判定するため、シート名を変更・翻訳しても取り込めます。
ただし、**他のアプリで作成した Excel は直接取り込めません**（手元の定義書資産を移行する場合は、いったん QuickER の定義書形式に転記してください）。
定義書には対象 DBMS が埋め込まれており、取込時に方言ごと復元されます。
この情報が落ちた定義書（別のアプリで保存し直すと落ちることがあります）では、現在の図の対象 DBMS を保ちます。
書式のバージョンも埋め込まれており、この版が対応するより新しい定義書は取り込まずに案内します（読めない情報を落としたまま図にしないためです）。バージョンを持たない古い定義書は従来どおり取り込みます。
件数の不一致や重複、未定義のテーブル参照は取込エラーになります。
リレーション行が重複と見なされるのは、テーブルの組が同じで**構成列も同じ**ときだけです。
同じ親子の間に複数の外部キーを持つ図（配送先と請求先が同じテーブルを指す、など）も往復します。
1 対 1・1 対多の行で参照元列・参照先列のセルが両方とも空のものは、列の対応を持たないリレーションとして読み（出力はこうした行を書きます）、重複とは見なしません。
片方だけが空の行は取込エラーです。
列の行が 1 つも無い詳細シートは、列の無いテーブルとして読みます。

取込側に規模の上限はなく、2 つの役割シート以外のワークシートはすべてテーブル詳細シートとして読み、行は最初の空行まで走査します。
処理は UI スレッドで実行されるため、極端に大きなブックでは終わるまでウィンドウが応答せず、中断する手段もありません。

### C# コード（.cs）

コード生成ツールバーの「コード取込」ボタンから、QuickER が **`IncludeDataAnnotations` ON で生成した、エンティティを含む `.g.cs`**（分割出力・層別出力では `Entities.g.cs`、非分割ではその出力ファイル）を選びます。
取込は Roslyn の構文解析のみ（コンパイル・アセンブリ読込なし）で図を復元し、現在の図へマージします。
対象は `[Table]` を持つクラスだけで、Repository・EditModel・Mapper などのインフラクラスには `[Table]` が付かず、手書き POCO も無視されます（対象クラスが 0 件のときは、エンティティを含む `.g.cs` を選ぶよう案内するエラーになります）。

復元元は次のとおりです。

- **テーブル名**：`[Table]`
- **列名**：`[Column]`
- **列の型と説明**：`[DbColumnMeta]`
- **テーブルの説明**：`[DbTableMeta]`
- **主キー**：`[Key]`
- **複合主キーの順序**：`[DbTableMeta]` の `PrimaryKeyOrder`（宣言順と食い違うときだけ書き出されます）
- **NULL 可否**：プロパティ型が `?` かどうか（`[Required]` は一切使いません）
- **UNIQUE 制約**：クラスレベルの `[UniqueConstraint]`
- **リレーション**：`[NavigationReference]`

**失われるもの・変わるものはすべて警告として通知します**（取込完了時に内訳を表示）。
`[DbColumnMeta]` の付いていない列プロパティはスキップされ、それが主キー列のときは「テーブルが主キーを失う」ことまで伝える専用の警告になります。
列を 1 つも復元できなかったテーブルは、落とさずに **列ゼロのテーブル**として取り込みます（落とすと、そのテーブルを端点に持つリレーションまで道連れで消えるため）。
端点の列を解決できなかったリレーションは **列ペアなし**で復元し（DDL 生成・スキーマ差分の対象外になります）、名指しで警告します。
端点のテーブルがファイルに無いリレーション、引数を読み取れない `[NavigationReference]`（引数不足・文字列リテラルでない・`name:` 形式で並びが違う）も同様に名指しで警告します。
同名のテーブル・同名の列はそのまま受け入れたうえで通知します。
1 つのクラスが**同一ファイル内で**複数の `partial` 宣言に分かれている場合は `[Table]` を持つ部分だけを読むため、他の部分に残った列プロパティの件数を通知します（`[Table]` を持つ部分へ移してください）。

**UNIQUE 制約と FK メタデータも往復します。**
制約は `[UniqueConstraint("PropA", "PropB", Name = "UQ_...")]` の各プロパティ名を `[Column]` へ逆写像して復元し、構成列の並びは宣言順、`Name` が無ければ「DDL 生成時に合成」を意味します。
復元できない列を参照する制約（構成 0 件の制約も同様）は、別の意味の制約へ縮めないよう **制約ごと** スキップし、警告で通知します。
FK 制約名と参照アクションは `[NavigationReference]` の名前付き引数 `ConstraintName` / `OnDelete` / `OnUpdate` から復元します（既定値と異なるときだけ出力され、解釈できないアクションのトークンは警告のうえ未指定として扱われます）。

**複合主キー自身の列順序も往復します。**
キーの順序がキー列のプロパティの宣言順と食い違うとき、コード生成はそれを `[DbTableMeta(PrimaryKeyOrder = new[] { "B", "A" })]` として書き出します。
値はプロパティ名で、`[UniqueConstraint]` と同じく `[Column]` へ逆写像して復元します。
キーが宣言順どおりのテーブルにはこの引数を出さないため、生成コードは変わりません。
キー列とちょうど一致しない順序（知らないプロパティ・キーでない列・重複・キー列の過不足）は採らず、テーブルを示して警告し、キーは宣言順で取り込みます。
`[DbTableMeta]` を書き出すのは説明と同じくデータアノテーションを生成するとき（`IncludeDataAnnotations`）だけなので、それを外して生成したコードは順序を運べません。

列型は方言中立トークンから、現在の図が使う方言のネイティブ型へ展開します（展開できないトークンは警告のうえそのまま採用）。
トークンは型の「意味」だけを運ぶため、同じ意味の複数表記（`numeric` と `decimal`・`ntext` と `nvarchar(max)`・`datetime` と `datetime2`）は 1 つの代表表記へ畳まれます。
そこで、綴りが変わってしまう列についてはコード生成が元の表記も `[DbColumnMeta]` へ記録し（`NativeType`）、対象の列を情報診断で名指しします。
取込側は、記録された表記を現在の方言で解析した型がトークンと一致するときだけそれを採用するため、**`datetime` 列は `datetime` のまま戻ります**（`datetime2` へ化けて次の DB 同期が `ALTER COLUMN` を出す、ということが起きません）。
手編集や別方言向けの生成物で両者が食い違うときは、トークン側を採って警告します。
**コードは方言中立のため、取込後も図の対象 DB は取込前のまま維持されます**。

多対多リレーションはコードに存在しないため、既存図へのマージ取込では両端が生存する多対多を現在図から温存します（コードで消えた通常のリレーションは図からも消えます）。
FK メタデータの温存は **未指定分だけの fallback** で、端点（両端テーブル名・列名）が一致するリレーションについて、コードが指定していないフィールドだけを現在図から補完します（指定があればコードが勝ちます）。
旧バージョンで生成したコード（名前付き引数を持たない）も、この規則で全フィールドが未指定＝現在図の値がそのまま温存されます。
複合主キー自身の列順序も同じ規則です。
コードが順序を書いていないとき（旧バージョンで生成したコードは書けません）は、キーが同じ列で構成されている限り現在図の順序を保ちます。
一方で **UNIQUE 制約はコードが正本** で、現在図からの温存は行いません（属性が無いことは「制約を持たないテーブル」と区別できず、温存するとコード上で削除した制約を消せなくなるため）。
他の取込と同様、構造差分や壊れる名前付きクエリがあるときは置換確認が出ます。

**コードが語れないもの。**
複数行の説明は、コード生成の時点で空白へ畳まれます（`///` の summary と属性のリテラルに改行を載せられないため）。
取込は畳まれた文面をそのまま復元するので、元の改行は戻りません。
FK 制約名と参照アクションは既定値と異なるときだけ出力されるため、「名前なし・両方 `NO ACTION`」は「未指定」と区別できません。
マージ取込ではそれらのフィールドに現在図の値がそのまま残り、CLI のリバースでは既定値になります。
同じ 2 テーブル間に名前の無い外部キーが 2 本あると既定名が重なるため、取込はほかの取込と同じく、既定名が使われている側に子の外部キー列の名前を足し、それも使われていれば番号を足した名前を付けます。
`record` 宣言のエンティティは解析対象外です（生成エンティティは常に `class`）。
また `[Table]` の `Schema` 引数は読みません（生成側が出力せず、スキーマ修飾はテーブル名自体に含まれるため）。

CLI の `quicker reverse` は、同じ解析でマージなしの新規図（スキーマのみ JSON）を書き出し、`--out` の親ディレクトリが無ければ作成します（[CLI リファレンス](cli.ja.md) を参照）。

## エクスポート

「出力」ボタンから形式を選びます。
形式を問わず、いま開いている図ファイルは出力先にできません（何も書かずに案内します。図そのものは上書き保存で保存してください）。

### SQL DDL（.sql）

図の対象 DBMS の方言で CREATE 文一式を出力します。

### スキーマ JSON（.json）

図の保存形式（[ER 図の編集](er-editor.ja.md) を参照）から配置情報（座標・色などの layout）を除いた、スキーマ定義と名前付きクエリ定義だけの JSON を出力します（`{ "Version": 1, "Schema": { ... } }`。キーは大文字始まりで、大文字小文字を区別します）。
配置情報を持たないため差分が安定し、テーブル定義そのものをレビュー・バージョン管理したいときに向きます。
このファイルは QuickER で「開く」と読み込め、配置情報がないため全体が自動整列されます（スキーマと名前付きクエリ定義については可逆ですが、座標・色は復元されません）。
通常保存（layout 込みの `.json`）とは別に、配置の揺れを含めずスキーマだけを共有したい場合に使います。

### DBML / Mermaid

テキスト形式へ書き出します。
DBML の出力は上記インポートと同じサブセット（`Table` ブロック＋ `Ref` 行）で、DBML 標準の構文だけを使います。
書き出したファイルは関係の列対応を保ったまま再取込できます。
複合外部キーは DBML 標準の複合 Ref 構文（`Ref: Parent.(a, b) < Child.(x, y)`）で書き出します（単一列の外部キーは従来どおり `Parent.a < Child.x` 形式のまま）。
制約名は名前付き `Ref` の名前（`Ref FK_Child_Parent: Parent.a < Child.x`）として、`NO ACTION` 以外の参照アクションは端点の後ろの設定ブロック（`[delete: cascade]`）として書き出します。
列の外部キーの印は、その列が子側になる `Ref` 行だけが運びます（DBML には列に単独で印を付ける設定がありません）。
列の対応を持たない 1 対 1・1 対 多のリレーションと、対応がテーブルに無くなった列を指すものは書き出しません。
DBML はリレーションを列でしか表せず、代わりの列を書くと、再取込で定義していない外部キーができるためです。
多 対 多のリレーションは各テーブルの先頭列で書き出し（取込はこの列を読みません）、列の無いテーブルにつながるものは書き出しません。
一意制約は、名前なしの単一列制約を列設定 `unique` として、複合制約と名前付き制約を `Indexes` ブロック（`(列, …) [unique, name: '…']`）として書き出します。
複合主キー自身の列順序がテーブルの列順と食い違うときは、キーを列設定 `pk` でなく `Indexes` ブロック先頭の `(列, …) [pk]` 索引として書き出すため、順序も往復します（キーが列順どおりのテーブルは従来どおりです）。
ASCII の英数字とアンダースコア以外を含むテーブル名・列名・制約名は DBML の引用識別子（`"Order Details"` / `"受注"`）で、空白・角括弧・二重引用符を含む型（`"double precision"` / `"integer[]"` / `"\"MyType\""`）も同様に囲んで書き出します。
囲まないと読み戻せず、日本語を含むそれ以外の文字の名前を素で書くと DBML のツールが構文エラーにするためです。
Mermaid はキー欄が 1 列 1 標識のため `PK` > `FK` > `UK` の優先度で 1 つに畳み、**`UK` を出力するのは単一列制約の構成列だけ**です（複合制約を列ごとに分解すると、取込時に「単一列制約 × N」という別の意味になるため出力しません）。

どちらも dbdiagram.org などの DBML 対応ツールや、Mermaid を表示できる GitHub / ドキュメントツールとの連携に使えます。
ただし Mermaid は複合主キー自身の列順序を表現できず（キー列それぞれに `PK` の標識が付くだけ）、順序が列順と食い違うキーは再取込で列順に戻ります。

DBML はテーブルの説明を `Note:` 行、外部キーの参照アクションを `Ref:` 行の設定ブロック（`delete` / `update`。既定の `NO ACTION` は書きません）としても出力するため、これらも往復します。

出力形式が構造的に表現できない情報は、出力完了のダイアログに内訳が出ます（うるさくならないよう、同じ形式ではセッション中 1 回だけ）。
Mermaid は説明・メモ・NULL 許可・複合 UNIQUE 制約・UNIQUE 制約名・外部キーの列対応・参照アクション・名前付きクエリ・計算列・外部キー列の単一列 UNIQUE 制約（その列の標識は `FK` の 1 つになります）と、列順と食い違う複合主キーの順序を表現できないため、図にそれらが入っていれば、書き換えた列名・型・テーブル名と、取込で同じ名前に戻らないリレーションの制約名とあわせて告知されます。
DBML で告知されるのはテーブルのメモ・名前付きクエリ・計算列（再取込で通常の列になります）と、どのリレーションの子側の列でもない列に付いた外部キーの印と、列を書けないために書き出さないリレーションだけです（`Note` は説明に使うため、メモを載せるには独自拡張が必要になり、他ツールとの交換を優先して見送っています）。
SQL DDL や定義書は「その形式では出さないのが正しいもの」しか落ちないため、告知しません。

### Excel 定義書（.xlsx）

テーブル一覧、リレーション一覧、テーブル別の詳細シート（列の型・必須・キー・説明）からなる定義書を出力します。
キー欄は `PK` / `FK{n}` に加えて一意制約を `UQ{n}`（`PK/UQ1` や `FK1/UQ2` のような併記あり）で表します。
`PK` に序数は付かないため、複合主キー自身の列順序はこの定義書にも載りません（再取込では列順に戻ります）。
`n` は制約の登場順で、**同じ番号は同じ制約**を意味するため、複合制約は構成列すべてに同じ番号が並びます（複合外部キーの `FK{n}` も同じ流儀です）。

リレーション一覧は 1 行 1 リレーションを保ち、複合外部キーは参照元列・参照先列のセルへ構成列を宣言順のカンマ区切りで並べます（`TenantRef, RegionRef` / `TenantId, RegionCode`）。
再取込時はこれを分割して列ペアへ戻します（両側の列数は一致している必要があります）。
対象 DBMS がファイルに埋め込まれるため、この定義書は QuickER への再取込で図に戻せます。

セルはすべて値（テキスト）として書き出し、QuickER が数式を書くことはありません。
そのため `=` で始まるテーブル名・列名もブック内では文字列のままで、Excel で開いても評価されません。
QuickER に CSV 出力はありませんが、定義書を自分で CSV へ変換する場合は注意が要ります。
表計算ソフトは CSV を開くときに先頭の `=` / `+` / `-` / `@` を数式の始まりとして読むため、変換時に引用符で囲んでください。

### HTML 定義書（.html）

外部参照も JavaScript も含まない自己完結の単一 HTML を出力します。
中身は次のとおりです。

- サイドバーのナビゲーション
- 概要（対象 DBMS・テーブル数・リレーション数）
- テーブル一覧
- リレーション一覧（ON DELETE / ON UPDATE を含む）
- テーブル別詳細

ブラウザだけで閲覧できるため、開発者以外の関係者への配布に向きます。

図を修正したら定義書を再出力するだけで最新化できます。
再出力を手順に組み込んでおけば、「ドキュメントだけ古い」状態を避けやすくなります。

### PNG / SVG（画像）

図全体を画像として出力します。
どちらの形式も画面のズーム倍率の影響は受けません。
SVG は図のモデルから直接描くため選択枠や方眼背景を含みません。
PNG はキャンバスの描画をそのまま写すため、選択状態（選択枠や関連ハイライトによる減光）と方眼背景も反映されます。
PNG を出力する前には選択を解除しておいてください。

大きすぎる図は、ラスタライズの前に縮小されます。
PNG の総画素数（幅 x 高さ）は 1 億画素を上限とし、これを超える図は縦横比を保ったまま上限内へ縮小して保存します。
完了のダイアログには、実寸と実際に保存した画素サイズを表示します。
上限を設けているのは、ラスタライザ自身の限界を超えると出力そのものが失敗するためです。
上限がなければ、一定以上に大きな図はまったく書き出せません。
SVG には同じ上限がないため、実寸の解像度が必要なときは SVG で出力してください。

SVG に載る名前・説明はすべて XML エスケープされるため、図に書いた内容がマークアップを破ることはありません。
XML が本文に認めない文字（Word から貼り付けた改行などの制御文字）は空白で書くため、ファイルは必ず開けます。

### 印刷 / PDF

ツールバーの「印刷」（Ctrl+P）で印刷オプションダイアログが開きます。

- **図のタイトル**：ヘッダに印字するタイトル
- **印刷サイズ**：「用紙 1 ページに縮小して印刷」（既定）/「原寸大で印刷」（用紙サイズを図の実寸に合わせる・PDF 出力向け）
- **印刷日時をヘッダに印字する**：既定 ON。システムの地域設定に依らず、西暦の `yyyy/MM/dd HH:mm` で印字します

Microsoft Print to PDF などの PDF プリンタを選べば、そのまま PDF 出力になります。

原寸大では用紙が図の実寸そのものになるため、大きな図では用紙も大きくなります。
用紙は 1 辺 200 インチを上限とし（PDF・XPS が扱える上限です）、これを超える図では実寸を示して「縮小して 1 ページに収めて印刷するか」を確認します。
取りやめれば何も印刷しません。
自動整列した図なら 1,000 テーブルでも 100 x 61 インチなので、上限に掛かるのはテーブルを遠くへ離した図です。
