# QuickER の設計思想

*[English](overview.md) | 日本語*

業務アプリケーションのコードベースには、同じ知識が繰り返し現れます。たとえば「顧客」を 1 つ定義すると、その列とキーと関連の知識は、DDL に、エンティティクラスに、画面にバインドするモデルに、そして設計ドキュメントに現れます。同じ知識を、形を変えて 4 回書き写しているわけです。ER 図から設計を始める現場でも、コードから書き始めるコードファーストの現場でも、この繰り返し自体は変わりません。マイグレーションが DDL を肩代わりしてくれても、バインド用モデルとドキュメントは残ります。そして書き写された知識は、変更のたびにそろえて直せるとは限らないため、少しずつずれていきます。

問題は、正本をどこに置くかです。コードファーストは「正本はコード」と答えました。これで DB との同期は片付きます。エンティティを変えればマイグレーションが追従します。では、スキーマのレビューはどうでしょうか。正規化の崩れや関連の張り忘れといった設計の誤りは、クラス定義の行を追う目では見つけにくいものです。人間がスキーマを一望して確かめるための表現は、昔から決まっています。ER 図です。テーブルが箱、関連が線、キーはひと目でわかります。

だからといって「図を正本にすればいい」と言うのは早計です。図を正本に据えた開発はこれまで何度も試みられ、そのたびに同じ理由で敗れてきました。図が現実から置き去りになり、誰も信じない絵に退化するのです。

QuickER は、この退化が起きない条件を作ることで、ER モデルを正本（single source of truth）に据え直した Windows 用の開発支援ツールです。条件は 2 つ。図がテキストとも DB とも双方向に行き来できること。そして、図から先のコードと DDL と定義書がすべて自動で出てくることです（書き写しがなければ、ずれは起きません）。狙いは、業務アプリケーションをより速く、少ないコストで、最小の手書きコード量で作ることにあります。

## 図とテキストと DB の往復

図を正本にすると言うと、「スキーマ定義はテキストで書いて git で管理したい」と考える開発者は多いはずです。もっともな要求で、QuickER もそれを妨げません。

QuickER の図は 1 つの JSON ファイルで、テーブル定義（意味）と座標や色（見た目）を分けて持ちます。git で差分が読めるので、図をソースコードと同じようにバージョン管理し、プルリクエストでレビューできます。DBML や Mermaid との相互のインポートとエクスポートも備えているため、テキストで書きたい人は DBML で書いて取り込み、図で確かめる、という分担ができます。

DB との間も同じように往復できます。稼働中の DB（SQL Server / PostgreSQL / MySQL / Oracle / SQLite の 5 方言）からスキーマを取り込んで図に起こせますし、図と DB の差分を検出して同期スクリプトを生成することもできます。コードファーストで育ててきたシステムなら、いま動いている DB を読ませれば、最初の図はすぐに手に入ります。白紙から描き直す必要はありません。そして図と現実がずれても、差分検出がずれを表に出します。置き去りは、起きたとしても見えるところで起きます。

ドキュメントの側も往復に含まれています。Excel の定義書で設計を受け渡しする現場では、手元の定義書から図を起こすことも、図から定義書を出力することもできます。開発者以外の関係者に配るなら、HTML の定義書としてエクスポートすればよいのです。図を直せば定義書が追従するので、「ドキュメントだけ古い」という状態そのものがなくなります。

図を直して DB に反映する。DB 側の変更を図に取り込む。DBML で受け取った設計を図で確かめ、DDL と定義書にして返す。どこから始めても、どの向きにも進められるこの輪の中心に、図があります。

## AI との分業

既存の DB もコードもない、まっさらな新規開発ではどうでしょうか。白紙のキャンバスに数十のテーブルを起こす作業は、それ自体が軽くありません。

そこを AI が受け持ちます。「EC サイトの受注管理のテーブルを設計して」と AI チャットに話しかければ、たたき台の図が生成され、続きの会話で修正できます。接続先は OpenAI / Anthropic の API キーのほか、ローカルで動く LLM（Ollama・LM Studio など OpenAI 互換 API）、Codex や Claude Code のアカウント認証も使えます。ER 図から Web 画面のモックアップを起こす機能もあります。画面ごとの HTML と共有スタイルをまとめた「モックフォルダ」としてライブ保存され、会話しながら複数画面を作り込み、プレビューで遷移を確かめ、単一 HTML にまとめて関係者と共有できます。画面のイメージまで含めて、設計の早い段階で目線を合わせられます。

この分業は、AI にアプリを丸ごと書かせる開発とは構造が違います。AI が 1 から書く場合、確率的な出力がコードベースの全層に広がり、人間の確認はコードレビューという形で後から追いかけることになります。QuickER の流れでは、確率的な工程は「図の下書き」までで終わります。人間は図を見て、箱と線の水準でスキーマを確かめます。レビューを通った図から先は、決定的な生成器が毎回同じコードを出します。生成器そのものは Roslyn によるコンパイル検証と実 DB を使った統合テスト（[tests/QuickER.Tests](../tests/QuickER.Tests)）で継続的に検証されているため、図さえ確かなら、その下の層が日によって崩れることはありません。自然言語から始めて、人間の目を 1 枚の図に集中させ、その先を機械に任せる。AI に任せる範囲を減らすのではなく、AI の出力を人間が確かめられる場所に集める、という分業です。

## 生成コードが引き受ける範囲

レビューを通った図から、何が出てくるのでしょうか。QuickER の線引きは、スキーマから機械的に決まるものはすべて生成し、アプリケーション固有のものは生成しない、です。

生成側に入るのは次の 3 層です。

- **スキーマ定義**：エンティティクラスと、列ごとの値オブジェクト（オプション）。値オブジェクトを使うと顧客 ID と商品 ID が別の型になり、ID の取り違えがコンパイルエラーで落ちます。最大長や小数精度の検証コードも列定義から生成されます
- **データ操作**：Repository を 2 方式から選べます。軽量で依存最小の QuickER 版（式木クエリ、Include、グラフ保存、楽観排他、生 SQL の逃げ道）と、EF Core 版（EF Core に慣れた開発者は、いつもの DbContext と LINQ をそのまま使えます）。両者は同じインターフェイスを実装しており、DI 登録の 1 行を替えるだけで交換できます。図に保存した検索条件（名前付きクエリ）は、どちらの方式でも型付きメソッドとして生成されます
- **UI バインディング用モデル**：画面にそのままバインドできる EditModel と、エンティティとの相互変換を行う Mapper

DDL も 5 方言で出ます。図の対象 DB はいつでも切り替えられ、型は自動変換されます。

冒頭の 4 回の書き写しは、これで行き先が決まりました。DDL とエンティティとバインド用モデルの 3 回はコード生成が、設計ドキュメントの 1 回は定義書エクスポートが引き受けます。手で書き写すものは残りません。開発者が書くのは、画面とビジネスロジックです。

## 生成コードの独立性

コード生成ツールには定番の不安があります。生成されたコードが生成器の都合に縛られていて、少し外れたことをしようとすると行き止まりになる、というものです。

QuickER の生成コードは、この不安に対して次の設計を取っています。

- **UI フレームワーク非依存**：特定の UI ライブラリに依存せず、デスクトップアプリでも Web アプリでも使えます
- **クロスプラットフォーム**：QuickER 本体は Windows 用ですが、生成コードは Windows / Mac / Linux の .NET 上で動きます。作るアプリケーションはツールの動作環境に縛られません
- **自己完結**：既定では必要なランタイムがコードにインラインで含まれ、追加パッケージなしでビルドが通ります（NuGet パッケージ参照に切り替えるモードもあります）
- **partial クラスによる拡張**：検証の追加や表示名の変更は、生成ファイルに触れずに書けます
- **3 層構成への拡張**：リモート用インターフェイスと HTTP + JSON のクライアント / サーバーを追加生成でき、直接 DB 接続との切り替えもやはり DI の 1 行で済みます

そして、生成されたコードはライセンス上も利用者の成果物であり、制限なく利用、改変、再配布できます。行き止まりに見えた場所には、生 SQL の実行口と partial の拡張点が常に開いています。

## 守備範囲とこれから

QuickER は .NET 向けの Windows 用ツールとして開発しており、コード生成の対象は現在 C# です。

ただし、コード生成を使わなくても、ER 図の作成ツールとしてそのまま役に立ちます。描いて、DDL と定義書を出して、画像でエクスポートする。その使い方だけでも、5 方言の DDL 生成と、DB やテキスト形式との往復はすべて付いてきます。

図が持っているのは、言語に依存しない意味モデル（テーブル、列、関連）です。C# への変換はその上に載った 1 つの生成器にすぎないため、他の言語への対応は、生成器を足していく問題として残されています。ここは今後の開発で広げていきたい領域です。

冒頭の「顧客」の定義に戻りましょう。あの知識は、これからは図の中に 1 回だけ書けばよいのです。DDL も、エンティティも、バインド用モデルも、定義書も、図から出てきます。変更も同じで、図を直せば全部が追従します。書き写しのずれを探して直す時間は、画面とビジネスロジックという、アプリケーションの本体に返されます。

リポジトリには、設計から生成、実行までを一巡した動くサンプル（[samples/ec-order](../samples/ec-order)）が同梱されています。SQLite のファイル DB を使うので、.NET 10 SDK さえあればクローン直後にそのまま動きます。まずはこのサンプルで、1 回だけ書く開発を試してみてください。
