# QuickER が ER モデルを正本にする理由

*[English](overview.md) | 日本語*

QuickER は、データ中心の業務アプリケーションを .NET で作るチーム向けの Windows 用ツールです。レビューした 1 つの ER モデルから、DDL と DB 差分、C# データアクセスコード、リモート API、設計ドキュメント、画面モックを再生成します。

なぜすべてを ER モデルに集めるのか。業務アプリケーションが同じスキーマ知識を繰り返し書いているからです。「顧客」を 1 つ定義すると、その列とキーと関連の知識は、DDL に、エンティティクラスに、画面にバインドするモデルに、そして設計ドキュメントに現れます。どの写しも手で書かれ、手で書かれた写しは、変更がすべてに届くとは限らないため、少しずつずれていきます。

コードファースト開発は、正本をコードに置くことでこれに答えました。DB との同期は保てますが、スキーマのレビューは難しいままです。正規化の崩れや関連の張り忘れは、クラス定義の行を追う目では見つけにくいものです。スキーマを一望して確かめるための表現は昔からあります。テーブルが箱、関連が線、キーがひと目でわかる ER 図です。

ただし、図を正本と宣言するだけでは足りません。失敗の型はよく知られています。実装側の変更を図へ取り込む手順がなければ、図は現実から置き去りになり、信頼されなくなります。QuickER はこの失敗の型に、2 つの条件で対処します。モデルがテキストとも DB とも双方向に行き来できること。そして、モデルから先の成果物を手で書き写さず生成することです。生成された成果物は、手直しで散らばっていく代わりにいつでもモデルから再生成でき、それでもモデルの外で起きる変更は、差分検出を実行すれば表に出せます。

## モデルとテキストと DB の往復

QuickER が保存しバージョン管理するのは、意味を持つ ER モデルです。1 つの JSON ファイルがテーブル定義（意味）と座標や色（見た目）を分けて持ち、git で差分が読め、ソースコードと同じようにプルリクエストでレビューできます。テキストで書きたい人のために、DBML や Mermaid との相互のインポートとエクスポートも備えています。

スキーマは稼働中の DB とも往復できます。稼働 DB（SQL Server / PostgreSQL / MySQL / Oracle / SQLite の 5 方言）からスキーマを取り込めますし、モデルと DB の差分を検出して同期スクリプトを生成することもできます。コードファーストで育ったシステムは取り込みで最初のモデルが手に入り、その後のずれは、気付かれないままではなく差分として現れます。

ドキュメントも往復します。Excel の定義書からモデルを起こし、モデルから定義書を出力し、開発者以外の関係者には自己完結した HTML の定義書を配れます。定義書はモデルから再生成できるため、古くなったドキュメントの更新は、文章の中を探して直す作業から再出力へと縮みます。

## レビューを通ったモデルから出てくるもの

決定的なコード生成について、QuickER の線引きはこうです。スキーマから機械的に決まるものは生成し、アプリケーション固有のものは生成しません。

- **スキーマ定義**：エンティティクラス、列ごとの値オブジェクト（オプション。顧客 ID と商品 ID が別の型になり、取り違えがコンパイルエラーで落ちます）、列定義に由来する検証コード
- **データ操作**：同じインターフェイスを実装する 2 方式の Repository（軽量な QuickER 版＝現在は SQL Server と SQLite、または EF Core 版）。インターフェイスに依存させたコードなら、交換は DI 登録の 1 行で済みます。モデルに保存した名前付きクエリは、どちらの方式でも型付きメソッドになります。Repository 生成は単一列の主キーとアプリ側採番を前提とします
- **UI バインディング用モデル**：画面にそのままバインドできる EditModel と、エンティティとの相互変換を行う Mapper

DDL も 5 方言で出ます。モデルの対象 DB は切り替えられ、変換可能な型は自動変換し、できない型は警告します。冒頭の 4 つの写しはこれで出どころが決まり、開発者が手で書くのは本番の画面とビジネスロジックです。

## AI との分業

新規開発には取り込む DB がなく、白紙のキャンバスに数十のテーブルを起こす作業はそれ自体が軽くありません。そこを AI チャットが受け持ちます。「EC サイトの受注管理のテーブルを設計して」と話しかければ、たたき台のモデルが生成され、続きの会話で修正できます（API キーからローカル LLM、Codex、Claude Code までの接続方式は [AI チャットの設定](ai-chat.ja.md)を参照してください）。

AI は ER モデルから Web 画面のモックも生成します。成果は画面ごとの HTML と共有スタイルからなる「モックフォルダ」としてライブ保存され、各画面が遷移先と、読み書きするエンティティを宣言します。プレビューで遷移をたどり、単一 HTML にまとめて関係者と共有できるほか、QuickER はフォルダから AI を使わずに設計ドキュメント（画面一覧、遷移図、画面とエンティティの CRUD 表）を生成します。

さらに任意の第 2 段階として、モックフォルダから Blazor Web App または WPF のモックプロジェクトを生成できます。データ層はモデルから決定的にスキャフォールドされ、画面の UI は AI が実装し、最後に QuickER 自身が `dotnet build` を実行して結果を確かめます。ビルドは仮定ではなく検証です（エージェント型の接続はビルド失敗を反復修正しますが、API キー方式の修正は 1 回までのため、失敗が残ることがあります）。

つまり、確率的な工程はモデルで終わるわけではなく、モックやその UI も AI の出力です。この流れが制御しているのは出力の行き先です。AI の各工程は結果を検査して残せる成果物に落とし、人間はモデルそのものを図として、箱と線の水準でレビューします。レビューから先は、決定的な生成器が同じ入力から毎回同じデータ層と DDL とドキュメントを再現します。

| 工程 | 主な担当 | 確認するもの |
| --- | --- | --- |
| ER モデルの下書き | AI または人間 | テーブル、列、キー、関連 |
| ER モデルの確定 | 人間 | 要件に照らしたスキーマ |
| DDL、エンティティ、Repository、ドキュメント | 決定的な生成器 | 差分、ビルド、テスト |
| 画面モック、Blazor / WPF の UI | AI | 画面、遷移、CRUD 宣言 |
| モックプロジェクトのデータ層と最終ビルド | 決定的なスキャフォールドと `dotnet build` | ビルド結果 |

生成器そのものは、Roslyn によるコンパイル検証と実 DB を使った統合テスト（[tests/QuickER.Tests](../tests/QuickER.Tests)）で継続的に検証されています。これは、レビュー済みモデルから同じ生成物を再現できることと、生成器の退行を検出できることを意味します。生成された挙動が要件を満たすかどうかのレビューまで肩代わりするものではありません。

## 生成コードの独立性

コード生成ツールには定番の不安があります。生成されたコードが生成器の都合に縛られていて、手を入れようとすると高くつく、というものです。QuickER の生成コードには次の性質があります。

- **UI フレームワーク非依存**：特定の UI ライブラリに依存せず、デスクトップアプリでも Web アプリでも使えます
- **クロスプラットフォーム**：QuickER 本体は Windows 用ですが、生成コードは Windows / Mac / Linux の .NET 上で動きます
- **自己完結**：既定では QuickER のランタイムを、パッケージからではなく生成コードへインラインで含めます（NuGet パッケージ参照に切り替えるモードもあります）
- **partial クラスによる拡張**：検証の追加や表示名の変更は、生成ファイルに触れずに書けます
- **3 層構成への拡張**：リモート用インターフェイスと HTTP + JSON のクライアント / サーバーを追加生成でき、リモートインターフェイスに依存させたコードなら、直接 DB 接続との切り替えも DI の 1 行で済みます

生成されたコードはライセンス上も利用者の成果物であり、制限なく利用、改変、再配布できます。生成メソッドで足りない場面は、生 SQL と partial の拡張点で補えます。

## 守備範囲と試し方

QuickER は .NET 向けの Windows 用ツールとして開発しており、コード生成の対象は現在 C# です。コード生成を使わなくても ER 図の作成ツールとして使え、5 方言の DDL 生成と往復の仕組みはその使い方にも付いてきます。

モデル自体は言語に依存しないテーブルと列と関連です。他の言語への対応で必要になるのはその言語の生成規則と検証であって、モデルの作り直しではありません。

リポジトリには、設計から生成、実行までを通しで実行できる動くサンプル（[samples/ec-order](../samples/ec-order)）が同梱されています。SQLite のファイル DB を使うので、.NET 10 SDK さえあればクローン直後にそのまま動きます。冒頭の「顧客」は、そこではモデルの中にちょうど 1 回だけ書かれています。
