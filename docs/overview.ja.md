# QuickER が ER モデルを正本にする理由

*[English](overview.md) | 日本語*

QuickER は、データ中心の業務アプリケーションを .NET で開発するチームのための Windows ツールです。
レビュー済みの ER モデルを一つ用意すれば、DDL、DB 差分、C# データアクセスコード、リモート API、設計ドキュメント、画面モックを繰り返し生成できます。

なぜ ER モデルを中心に据えるのでしょうか。
業務アプリケーションでは、同じスキーマ情報を何度も記述するからです。
「顧客」を一つ定義すると、その列、キー、関連の情報は、DDL、エンティティクラス、画面にバインドするモデル、設計ドキュメントに現れます。
これらを手作業で記述している限り、変更がすべてに反映されるとは限らず、少しずつ食い違いが生じます。

コードファースト開発は、コードを正本とすることでこの問題に応えました。
DB との同期は保ちやすくなりますが、スキーマのレビューは難しいままです。
正規化の崩れや関連の張り忘れは、クラス定義を追うだけでは見つけにくいからです。
一方、スキーマ全体を見渡すための表現は昔からあります。
テーブルを箱で、関連を線で表し、キーもひと目で確認できる ER 図です。

しかし、図を正本に据えるだけでは不十分です。
実装側の変更を図へ取り込む手段がなければ、図はしだいに実態とずれ、やがて信頼されなくなります。
QuickER は、このよくある失敗を避けるために、二つの条件を設けています。
一つは、モデルとテキスト、モデルと DB を双方向に変換できることです。
もう一つは、モデルから作る成果物を手で書き写さず、生成することです。
生成物はいつでもモデルから作り直せます。
モデルの外で起きた変更も、差分検出によって確認できます。

## ER モデル、テキスト、DB を行き来する

QuickER が保存してバージョン管理するのは、スキーマの構造と意味を表す ER モデルです。
一つの JSON ファイルに、テーブル定義（意味）と座標や色（見た目）を分けて保存します。
Git で差分を確認し、ソースコードと同じようにプルリクエストでレビューできます。
テキストで記述したい場合は、DBML や Mermaid との間でインポートとエクスポートができます。

稼働中の DB とモデルの間でも、スキーマの変更を相互に反映できます。
SQL Server、PostgreSQL、MySQL、Oracle、SQLite の五つの方言に対応しており、DB からスキーマを取り込めます。
反対に、モデルと DB の差分を検出し、DB へ反映するための同期スクリプトも生成できます。
コードファーストで開発してきたシステムなら、最初のモデルは既存 DB から作れます。
その後に生じたずれも、気付かれないまま残るのではなく、差分として確認できます。

定義書にも同じ仕組みを使えます。
Excel の定義書からモデルを作成し、モデルから定義書を出力できます。
開発者以外の関係者には、単一ファイルで完結する HTML の定義書を配布できます。
定義書はモデルから再生成できるため、古くなった箇所を定義書の中から探して直す必要はありません。

## レビュー済みのモデルから生成されるもの

QuickER が自動生成するのは、スキーマだけから機械的に決まるものです。
アプリケーション固有のものは、開発者が実装します。

- **スキーマ定義**：エンティティクラス、列ごとの値オブジェクト（任意）、列定義に基づく検証コードを生成します。
  値オブジェクトを使うと、顧客 ID と商品 ID が別の型になり、取り違えをコンパイル時に検出できます
- **データ操作**：同じインターフェイスを実装する二種類の Repository を生成します。
  一つは軽量な QuickER 版（現在は SQL Server と SQLite に対応）、もう一つは EF Core 版です。
  コードがこのインターフェイスに依存していれば、DI 登録を一行変えるだけで実装を切り替えられます。
  モデルに保存した名前付きクエリは、どちらの実装でも型付きメソッドになります。
  Repository の生成では、単一列の主キーとアプリケーション側での採番を前提とします
- **UI バインディング用モデル**：画面にそのままバインドできる EditModel と、エンティティとの相互変換を行う Mapper を生成します。
  EditModel は画面の入力を文字列として受け取り、型変換できない値をエンティティへ書き込まず、項目ごとのエラーとして保持します。
  正しく変換できた値と変更状態も追跡します。
  Mapper がエンティティとの相互変換を担うため、画面ごとに値の変換やコピー処理を繰り返し書かずに済みます

DDL も五つの方言で生成できます。
モデルの対象 DB は切り替え可能で、変換できる型は自動的に変換し、変換できない型は警告します。
これにより、DDL、エンティティクラス、UI バインディング用モデル、設計ドキュメントの生成元が ER モデルに統一されます。
開発者が手で書くのは、本番の画面とビジネスロジックです。

## AI との分業

新規開発では、取り込める DB がまだありません。
白紙のキャンバスに数十のテーブルを作るだけでも、相応の手間がかかります。
この初期設計を AI チャットが受け持ちます。
「EC サイトの受注管理のテーブルを設計して」と依頼すると、モデルのたたき台が生成され、その後も会話を通じて修正できます。
API キー、ローカル LLM、Codex、Claude Code を使う接続方法については、[AI チャットの設定](ai-chat.ja.md)を参照してください。

AI は、ER モデルから Web 画面のモックも生成します。
生成物は、画面ごとの HTML と共有スタイルを収めた「モックフォルダ」に随時保存されます。
各画面には、遷移先と、読み書きするエンティティが宣言されています。
プレビューで画面遷移を確認し、単一の HTML にまとめて関係者と共有できます。
さらに QuickER は、AI を使わずにモックフォルダから設計ドキュメント（画面一覧、遷移図、画面とエンティティの CRUD 表）を生成します。

追加の工程として、モックフォルダから Blazor Web App または WPF のモックプロジェクトを生成することもできます。
データ層はモデルから機械的に生成し、画面の UI は AI が実装します。
最後に QuickER 自身が `dotnet build` を実行し、実際にビルドできるかを確認します。
エージェント型の接続ではビルドエラーを反復して修正しますが、API キー方式での修正は一回までなので、エラーが残る場合があります。

AI が担うのは ER モデルの作成までではありません。
画面モックと、その UI も AI が生成します。
ただし、どの工程でも出力は検査して保存できる成果物として残ります。
人間は、ER モデルそのものを箱と線で表された図としてレビューします。
モデルのレビューが終われば、データ層、DDL、ドキュメントは同じ入力から毎回同じ内容で生成されます。

| 工程 | 主な担当 | 確認するもの |
| --- | --- | --- |
| ER モデルの下書き | AI または人間 | テーブル、列、キー、関連 |
| ER モデルの確定 | 人間 | 要件に照らしたスキーマ |
| DDL、エンティティ、Repository、ドキュメント | コード生成器 | 差分、ビルド、テスト |
| 画面モック、Blazor / WPF の UI | AI | 画面、遷移、CRUD 宣言 |
| モックプロジェクトのデータ層と最終ビルド | スキャフォールダーと `dotnet build` | ビルド結果 |

コード生成器そのものは、Roslyn によるコンパイル検証と、実際の DB を使う統合テスト（[tests/QuickER.Tests](../tests/QuickER.Tests)）によって継続的に検証されています。
これにより、レビュー済みのモデルから同じ生成物を再現でき、生成器の退行も検出できます。
ただし、生成されたプログラムが要件を満たすかどうかは、別途レビューする必要があります。

## 生成コードの独立性

コード生成ツールには、生成されたコードが生成器の都合に縛られ、手を加えるほど保守が難しくなるという不安がつきまといます。
QuickER の生成コードは、次の性質を備えています。

- **UI フレームワーク非依存**：特定の UI ライブラリに依存せず、デスクトップアプリでも Web アプリでも使えます
- **クロスプラットフォーム**：QuickER 本体は Windows 用ですが、生成コードは Windows、macOS、Linux の .NET 上で動作します
- **自己完結**：既定では QuickER のランタイムを、パッケージ参照ではなく生成コードの一部として埋め込みます。
  NuGet パッケージを参照する方式にも切り替えられます
- **partial クラスによる拡張**：生成ファイルを変更せずに、検証の追加や表示名の変更ができます
- **三層構成への拡張**：リモート用インターフェイスと、HTTP + JSON を使うクライアントおよびサーバーを追加生成できます。
  コードがリモート用インターフェイスに依存していれば、DI 登録を一行変えるだけで直接 DB 接続と切り替えられます

生成コードは、ライセンス上も利用者の成果物です。
制限なく利用、改変、再配布できます。
生成されたメソッドだけでは足りない場合は、生 SQL と partial クラスの拡張点で補えます。

## 対応範囲と試し方

QuickER は .NET 向けの Windows ツールとして開発されており、現在のコード生成対象は C# です。
コード生成を使わない場合も ER 図の作成ツールとして利用でき、五つの方言に対応する DDL 生成と双方向変換の機能も使えます。

モデルそのものは、特定のプログラミング言語に依存しないテーブル、列、関連で構成されます。
別の言語に対応する際に必要なのは、その言語向けの生成規則と検証であり、モデルを作り直す必要はありません。

リポジトリには、設計、生成、実行までを一通り試せるサンプル（[samples/ec-order](../samples/ec-order)）が含まれています。
SQLite のファイル DB を使うため、.NET 10 SDK があれば、クローン直後にそのまま実行できます。
冒頭で挙げた「顧客」は、このサンプルではモデルの中に一度だけ記述されています。
