# QuickER が ER モデルを正本にする理由

*[English](overview.md) | 日本語*

QuickER は、業務アプリケーションの .NET 開発を支援するための Windows 用ツールです。
ER 図の GUI デザイナーと、DB との相互反映、AI との連携機能などを備え、ER モデルを中心に据えた開発が行えます。
ER モデルから DDL、C# コード、画面モック、テーブル定義書などが生成できます。

では、なぜコードや DB ではなく、ER モデルを正本とするのでしょうか。

業務アプリケーションでは、同じスキーマ情報を何度も記述する必要があります。
「顧客」を一つ定義すると、その列、キー、関連の情報は、DDL、エンティティクラス、画面にバインドするモデル、設計ドキュメントに現れます。
これらを手作業で記述していれば、少しずつ食い違いが生じてきます。

コードファースト開発では、コードを正本とすることでこの問題に応えました。
これにより DB との同期は保ちやすくなりましたが、スキーマのレビューには課題が残ります。
正規化の崩れや関連の張り忘れは、クラス定義を追うだけではなかなか見つけにくいものです。
一方で、スキーマ全体を見渡すための表現は昔からあります。
テーブルを箱で、関連を線で表し、キーもひと目で確認できる ER 図です。
図にあらわすことによって、設計の不備が人間の目でも一目で見つけやすくなります。
人間のレビューを通過した図に基づく ER モデルこそ、まさしく正本になるべきものといえます。

ただし、図やモデルは一度作成して終わりというわけにはいきません。
実装側の変更を漏れなく反映しなければ、次第に実態とずれて、やがて誰も信じないものになってしまいます。
QuickER は、このよくある失敗を避けるために、二つの条件を設けています。
一つは、モデルと DB、モデルとテキストを双方向に変換できることです。
もう一つは、モデルから作る成果物を手で書き写さず、機械的に生成することです。
モデルに変更があれば、生成物はいつでもモデルから作り直せます。
モデルの外で起きた変更は、各種の取り込み機能によってモデルに反映できます。

QuickER の狙いは、これらの ER モデルを正本とする開発支援の仕組みを提供することにより、人間の労力を必要最小限に抑え、高品質な業務アプリケーションをより速く、より少ないコストで開発できるようにすることです。

## ER モデル、DB、テキストの往復

ER モデルを正本とするのであれば、モデル定義はテキストで書いて、Git で管理したいと考えるのは自然なことです。
QuickER では、ER 図を 1 つの JSON ファイルとして保存します。
JSON の内部ではモデル定義（意味）と座標や色（見た目）が分かれた構造になっており、モデル定義のみを抜き出して保存することもできます。
これらは、ソースコードと同じように Git でバージョン管理し、プルリクエストで差分を確認してレビューできます。
この他にも、QuickER では、DBML や Mermaid などの他のテキスト形式のデータとの相互のインポートとエクスポートも備えています。
手慣れた形式で作成したデータを取り込み、図で確かめる、という使い分けもできます。

稼働中の DB との間でも、同じようにスキーマの変更を相互に反映できます。
SQL Server、PostgreSQL、MySQL、Oracle、SQLite の 5 つの方言に対応しており、DB からスキーマを取り込めます。
反対に、モデルと DB の差分を検出し、DB へ反映するための同期スクリプトも生成できます。
コードファーストで開発してきたアプリケーションなら、最初のモデルは既存 DB から作れます。

テーブル定義書にも同じ仕組みを使えます。
モデルから Excel の定義書を出力し、手で修正したものを取り込むことができます。
また、参照のみであれば、単一ファイルで完結する HTML の定義書として出力できます。
定義書はモデルからいつでも再生成できるため、古くなった箇所を定義書の中から探して直す必要はありません。

## AI との分業

取り込める DB もデータ元もない、まっさらな新規開発ではどうすればよいでしょうか。
白紙のキャンバスに数十のテーブルを作るのは、相応の手間がかかります。
この初期設計にかかる手間を AI チャット機能が受け持ちます。
「EC サイトの受注管理のテーブルを設計して」と AI に依頼すると、ER 図のたたき台が生成され、その後も会話を通じて修正できます。
AI の利用方式は利用者の環境にあわせて、API キー、ローカル LLM、Codex、Claude Code から選ぶことができます。

また、AI は、ER モデルから Web 画面のモックも生成します。
生成物は、画面ごとの HTML と共有スタイルを収めたモックフォルダに随時保存され、プレビュー画面によって確認し、会話を通じて修正できます。
さらに QuickER によって、モックから単一の HTML や設計ドキュメント（画面一覧、遷移図、画面とエンティティの CRUD 表）を機械的に生成します。
これらを関係者と共有することで、画面イメージも含めて、設計の早い段階で関係者との目線合わせができます。

追加の工程として、モックフォルダから Blazor Web App または WPF のモックプロジェクトを生成することもできます。
データ層はモデルから機械的に生成し、画面の UI は AI が実装します。
最後に QuickER 自身が `dotnet build` を実行し、実際にビルドできるかを確認します。
ただし、生成物の精度は、AI のモデルの能力と方式（API キー／エージェント型）に依存するため、エラーが残る場合があります。
この機能はあくまでも PoC やプロトタイピングのための補助という位置付けです。

以上のような AI 機能の活用は、AI にアプリを丸ごと書かせる開発とは構造が違います。
AI が 1 から書く場合、AI による確率的な出力がコードベースの全層に広がり、人間の確認はコードレビューという形で後から追いかけることになります。
QuickER の流れでは、AI の確率的な工程は ER 図の下書きと、設計の補助となるモックの生成に留まります。
人間はそれぞれの生成物を確認し、必要な修正を加えます。
レビューを通った後は、QuickER が ER モデルに基づくコードを毎回同じ内容で生成します。
ER モデルさえ確かなら、これらの生成コードが日によって崩れることはありません。
AI にすべてをゆだねるのではなく、人間が確認できる場所を設けながら開発を進める、という分業になります。

## 生成コードが引き受ける範囲

レビューを通った ER モデルからは、どのようなコードが出てくるでしょうか。
QuickER が生成するコードは、モデル定義から機械的に決められるものとなります。
アプリケーション固有のものは、開発者が実装する領域として明確に分けられます。
生成コードは次の 3 種に分けられます。

- **スキーマ定義**：エンティティクラス、列ごとの値オブジェクト、列定義に基づく検証コードを生成します。
  値オブジェクトを使うと、顧客 ID と商品 ID が別の型になり、取り違えをコンパイル時に検出できます。
  また、文字列型の主キーとなる値オブジェクトでは、キーとなる値として GUID を生成する機能もあります。
- **データ操作**：同じインターフェースを実装する二種類の Repository を生成します。
  一つは軽量な QuickER 版（現在は SQL Server と SQLite に対応）、もう一つは EF Core 版です。
  抽象化されたインターフェースにより、DI 登録を一行変えるだけで実装を切り替えられます。
  グループ化や集計などのクエリは、ER 図に付随して名前付きクエリとして作成・保存ができます。
  作成した名前付きクエリは、Repository のメソッドとして自動生成されます。
  これ以外にも Repository には生 SQL を実行するための汎用的なメソッドが用意されています。
  また、DBへの直接接続をせずに、Web API 経由でリモートの DB にアクセスするための Repository も生成できます。
  この場合、リモート接続用のインターフェースや、HTTP + JSON を使うクライアントおよびサーバーのコードが追加で生成されます。
  リモート接続への切り替えも、やはり DI 登録を一行変えるだけで済みます。
- **UI バインディング用モデル**：画面に直接バインドできる EditModel と、EditModel とエンティティとの相互変換を行う Mapper を生成します。
  EditModel は画面からの入力値を文字列として受け取り、検証に成功した値を確定値として保持し、失敗した場合はエラー情報を保持します。
  Mapper は、EditModel が保持する確定値と変更状態だけをエンティティに反映するため、不正な入力値がエンティティに入り込むことを防げます。
  また、Mapper が変換処理を担うことで、画面ごとに値の変換やコピー処理を繰り返し書く手間から解放されます。

これらのコードの自動生成により、開発者はデータの定義や操作に関するコードを何度も書く労力から解放されて、本番用の画面デザインやビジネスロジックの実装に集中することができるようになります。

## 生成コードの独立性

コード生成ツールには、生成されたコードがツール側の制限に縛られて、手を加えるほど保守が難しくなるという不安がつきまといます。
その不安に応えるために、QuickER の生成コードは次のような設計になっています。

- **UI フレームワーク非依存**：生成コードは、特定の UI ライブラリに依存せず、デスクトップアプリでも Web アプリでも使えます。
- **クロスプラットフォーム**：QuickER 本体は Windows 用ですが、生成コードは Windows、macOS、Linux の .NET 上で動作します。
- **自己完結**：既定ではランタイム（生成コードの基底クラス・共通部品）がインライン化され、独立した生成コードとして利用できます。
  生成コードを最小限にしたければ、ランタイムを NuGet パッケージとして参照する方式に切り替えることもできます。
- **partial クラスによる拡張**：生成コードとは別のファイルに partial クラスを書くことで、生成コードのファイルを触ることなく、検証の追加や表示名の変更などができます。
  生成コードを更新しても開発者が書いた partial クラスのコードは失われません。

生成されたコードは、ライセンス上も利用者の成果物となり、制限なく利用、改変、再配布できます。
生成された機能では足りなければ、partial クラスで自由に拡張してください。

## 現状とこれから

QuickER は .NET 向けの Windows 用ツールとして開発されており、現在のコード生成対象は C# です。
ER モデル自体は、特定のプログラミング言語に依存しないテーブル、列、関連で構成されており、C# への変換は、そのモデルの上に乗った 1 つの生成機能に過ぎません。
他の言語への対応は、今後の開発で広げていきたい領域です。

また、コード生成を使わない場合でも、ER 図の作成ツールとして、DB やテキストとの相互反映だけでも十分な価値があるものと考えています。
こちらも今後の開発で、より使いやすくしていく余地があります。

QuickER のリポジトリには、ER モデルの設計、コード生成、実行までを一通り試せるサンプル（[samples/ec-order](../samples/ec-order)）が含まれています。
SQLite のファイル DB を使うため、.NET 10 SDK があれば、クローン直後にそのまま実行できます。
まずはこのサンプルで QuickER の機能を体験してみてください。
