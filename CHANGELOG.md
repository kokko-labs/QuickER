# Changelog

*English | [日本語](CHANGELOG.ja.md)*

This file records changes that affect QuickER users. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/) (see [CONTRIBUTING.md](CONTRIBUTING.md) for the versioning rules during 0.x and the release procedure).

## [Unreleased]

### Added

- **Value objects implement `IFormattable`** — `price.ToString("N2")` and the culture-taking overload format the underlying value, and a format specifier in string interpolation, `string.Format`, or a WPF binding's StringFormat now reaches the underlying value. Without a format specifier the result is always `ToString()`, so `ToString()` overrides keep governing unformatted rendering; an underlying value that is not formattable (a string, a byte array, a bool) likewise ignores the format, matching what composite formatting does for any such value

- **The edit-model boilerplate is now driven by a column table** — a generated edit model publishes one `EditModelColumn<TSelf>` per column (its two names, whether input is required, and compiled accessors for the confirmed value and the input string) through the new `EditModelBase<TSelf>.EditModelColumns`, and the required-input check, the input revert, the row-edit snapshot and the duplicate-error mapping are written once on the base class instead of once per column in every class. `EditModelBase.BeginLoad` / `EndLoad`, `GetChildren` / `SetChildren` and `CheckDatabaseUniquenessAsync` are the other new base members the generated code now delegates to. Storage is unchanged (the confirmed-value fields, the input-string fields and the binding setters are exactly what they were), and so is every observable semantic; the generated edit model and mapper shrink by 30-36%, which is roughly 190 fewer lines per edit-model class and 28 fewer per mapper
- **The validation rules a generated value object runs are now public and reusable** — `ValueObjectRules.ValidateRequired`, `ValueObjectStringRules.ValidateMaxLength` and `ValueObjectDecimalRules.Validate` live on the fixed infra (the `QuickER.Runtime` package in package-reference mode) instead of being inlined into every value object, so a generated `ValidateCore` is now one line per rule and a hand-written value object can call the same rules
- **Four general-purpose validation rules to call from `OnValidate`** — `ValueObjectNumberRules.ValidateMaxDigits` (digit count of an integer), `ValueObjectNumberRules.ValidateRange` (closed interval, any `IComparable<T>`), `ValueObjectStringRules.ValidateAsciiAlphanumeric` (ASCII letters and digits plus the symbols you allow) and `ValueObjectStringRules.ValidateEmailAddress` (a practical minimum, deliberately not RFC 5322). Their messages are new `ValueObjectValidationMessages` entries (`DigitsExceeded` / `OutOfRange` / `InvalidCharacters` / `InvalidEmailAddress`)
- **A synchronised table is now described by data rather than by classes of its own** — `SyncTableDescriptor<TEntity, TKey>` carries everything a table contributes (its name, its per-dialect SQL, and how a key, a mirrored version and an unbounded binary column are read and written), and the generated `GeneratedSyncTables` exposes one static descriptor per table plus `All` and a shared `GraphRecorder`. `SyncGraphRecorder` is now a fixed class in `QuickER.Runtime.Sync` that walks a graph once through `EntityBase.EnumerateCascadeChildren`, which yields the same cascade navigations the graph saver's own walk enumerates, instead of a recursive method generated per entity type, so the recording and the saving can no longer drift apart. `EntityBase.EnumerateCascadeChildren` is public for that reason, and `SyncRepositoryBinaryColumns<TEntity, TKey>` is the one implementation of the unbounded-binary copy surface for both the local database and a directly connected server

### Changed

- **A date or time column that carries a sub-second part now shows it** — an edit model derives the input string from the confirmed value with the culture's own format, which stops at whole seconds, so a finer value was displayed truncated; editing any *other* column of the row then committed that truncated instant back over the stored one, because the binding setter rebuilds the confirmed value from the text. The input string now carries the sub-second part when there is one — appended after the seconds with a literal `.` and no trailing zeros — and parses back to the exact tick in every culture. A value with no sub-second part is displayed exactly as before, character for character, so a screen only changes where it was losing precision. `EditModelInputFormat` on the fixed infra is what the generated column table calls for `DateTime`, `DateTimeOffset`, `TimeSpan` and `TimeOnly`; a `date` column keeps its short-date format
- **The in-memory repository enforces the diagram's UNIQUE constraints** — a direct insert, update or bulk insert, and a graph save, are rejected when they would leave two rows holding the same values on a constraint the diagram declares, so a write a real database refuses no longer passes in memory. The rules are the ones the uniqueness pre-check (`CheckUniquenessAsync`) already applied: a tuple containing a null is not compared, and the row being written is excluded by its primary key. A bulk insert is validated in full before any of it is applied, and a graph save is judged by the state it would leave behind — it can free a value on one row and take it on another within the same save, and a violation drops the save whole without publishing any of it. The violation is an `InvalidOperationException`, which is what a duplicate primary key already raises here; a real database reports it through its own provider's exception (`SqlException` with error 2627, for one), and no in-memory type can be that exception, so code that catches a provider exception still has to be exercised against the database. The user-defined checks added through `CollectCustomUniquenessChecks` are not enforced — they are rules of the application rather than constraints the database holds — and neither is seeding through `InMemoryDataStore.Put` / `InMemorySampleData.Seed`
- **A NOT NULL excluded binary column is now required input while the row is new** — with `ExcludeUnboundedBinaryColumns` on, an excluded column stays out of the required-input check, except while the edit model is `RowState.Added`: INSERT keeps every column, so an empty value reaches a NOT NULL column and the database rejects it. That insert always failed; it is now caught in the edit model, with the column named, instead of coming back as a NOT NULL violation. The two-step route (insert, then stream the body in with `Write{Column}Async`) works exactly as before as long as the insert carries an empty value — `ThumbValue.Create([])` with value objects, `[]` without them, which is what the entity of a non-value-object column already starts out with. Nothing changes once the row exists, nor for a nullable excluded column, nor with the option off
- **Breaking: the per-edit-model message and display-name hooks are gone** — generated edit models no longer declare `CustomizeRequiredErrorMessage`, `CustomizeParseErrorMessage`, `CustomizeDuplicateErrorMessage` or `CustomizePropertyDisplayName`, so an existing implementation of one stops compiling. Customize the wording through the matching `EditModelMessages` entry and a display name through `GeneratedDisplayNames.Resolve`, branching on the property name each of them now receives. This is the same move the value-object hooks made: one place per message rather than one place per type, and nothing to re-implement on the generated class after a regeneration. The semantic hooks (`OnValidate`, `OnBeginEdit` / `OnEndEdit` / `OnCancelEdit`, `On{Property}Changing` / `Changed`) are unaffected
- **Breaking: `EditModelMessages.Required`, `ParseFailed` and `DuplicateValue` take the property name first** — `Required` is now `(propertyName, displayName)`, `ParseFailed` is `(propertyName, displayName, inputValue, typeName)`, and `DuplicateValue` is `(propertyNames, displayNames)`. That first argument is the stable key a replacement branches on with `nameof`, which is what lets one resolver do what the per-class hooks used to. The default wording is unchanged, so an application that does not replace these sees no difference
- **Breaking: `MapperBase<TEntity, TEditModel>` owns the load sequence** — `CreateEntity()`, `CreateEditModel(entity)` and `ApplyToEditModel(entity, editModel)` are concrete on the base class instead of abstract, and the generated mapper overrides `LoadColumns` (the column copying) and `CompleteLoad` (the cascade children and the post-load hook) plus two bridges to its `OnEntityCreated` / `OnEditModelCreated` partials. `CreateEntityCore` and `CreateEditModelCore` are gone. Calling code is unaffected — the public surface a caller uses (`CreateEntity`, `CreateEntity(editModel, includeRemoved)`, `CreateEntities`, `CreateEditModel`, `CreateEditModels`, `ApplyToEntity`, `ApplyToEditModel`) is the same, the order of the load is byte-for-byte the same, and the partial hooks still fire in the same places; what breaks is a hand-written mapper that derived from `MapperBase<,>` and overrode the now-non-virtual members
- **Breaking: the per-value-object message and display-name hooks are gone** — generated value objects no longer declare `CustomizeDisplayName`, `CustomizeMaxLengthErrorMessage`, `CustomizeScaleErrorMessage`, `CustomizePrecisionErrorMessage` or `CustomizeValueRequiredErrorMessage`, so an existing implementation of one stops compiling. Customize a display name through `GeneratedDisplayNames.Resolve` and a message through the matching `ValueObjectValidationMessages` entry, branching on the name for a single type (`memberName == nameof(CustomerEntity.Name)`, `displayName == NameValue.DisplayName`). The wording then lives in one place per message rather than one place per type, and nothing has to be re-implemented on the generated class after a regeneration. `OnValidate`, `GetDefinedInstance` and `ConvertCustomInput` are unaffected
- **Breaking: the entity display-name hook is gone** — `EntityBase` no longer declares `CustomizeDisplayName`, so an `override` of it stops compiling, and `DisplayName` simply returns `DefaultDisplayName`. Substitute a display name through `GeneratedDisplayNames.Resolve` instead, branching on the runtime class name it receives (`static (memberName, description) => memberName == nameof(CustomerEntity) ? "Customer" : description ?? memberName;`), or put the wording in the table description, which the default resolver already prefers. This is the same move the value-object and edit-model hooks made: one place for every display name rather than one override per entity class. The diagnostic for an entity whose column is named `DisplayName` no longer mentions the hook either, and such a column no longer suppresses anything beyond the `DefaultDisplayName` override
- **Breaking: every `ValueObjectValidationMessages` entry takes the display name as its first argument** — `MaxLengthExceeded` is now `(displayName, maxLength, actualLength)`, `ScaleExceeded` and `PrecisionExceeded` take `(displayName, …)`, `ValueRequired` takes `(displayName)`, and `InputNotConvertible`'s arguments are reordered to `(displayName, raw)`. This is what makes a single replacement able to vary the wording per type. The default wording is unchanged, so an application that does not replace these sees no difference
- **Breaking: `IRemoteRepository<TEntity, TKey>` declares `CheckUniquenessAsync`** — the uniqueness pre-check used to be declared on each generated `I{Entity}RemoteRepository` (or `I{Entity}Repository`) and implemented on every generated repository class; the declaration now sits on the common runtime surface and the implementation on each back end's repository base class (the dialect, in-memory, EF Core and HTTP client bases). Code that calls the check is unaffected — `I{Entity}Repository` still provides it through inheritance and the signature, the result and the `CollectCustomUniquenessChecks` hook are unchanged, and an existing hand-written hook keeps working untouched. What breaks is a *hand-written implementation* of `IRemoteRepository<,>` or `IRepository<,>` (a test double or an adapter), which now has to provide the member; deriving from a generated base class instead gets it for free. A generated repository now contributes only the constraint table (`{Entity}UniquenessConstraints.Set`) and a two-line bridge to its hook, which is roughly 50 fewer lines per entity per back end
- **DI registration is one line per entity** — `AddGenerated{SqlServer,Sqlite}Repositories` and `AddGeneratedEfCoreRepositories` register the repository as `services.AddScoped<IContract, Implementation>()` and let the container build it from the dependencies the same call registers (the idiom `AddGeneratedInMemoryRepositories` already used), while the keyed overload and `AddGeneratedHttpRemoteRepositories` fold the wiring every entity shares into one local function. The registered lifetimes, the keyed / non-keyed resolution of `ISqlExecutor`, the `TryAddScoped<ISaveHookRegistry>` default and the remote surface forwarding to the same instance are all unchanged
- **Breaking: the per-table sync classes are gone** — `{Entity}SyncTable`, `{Entity}DirectSyncSource` and `Http{Entity}SyncSource` are no longer generated. The fixed classes they used to derive from take a descriptor instead and are constructed directly: `new SyncTable<OrderEntity, int>(local, localSql, source, GeneratedSyncTables.Order)`, `new VersionlessSyncTable<…>`, `new DirectSyncSource<OrderEntity, int>(serverSql, serverRepository, GeneratedSyncTables.Order)`, `new VersionlessDirectSyncSource<…>` and `new HttpSyncServerSource<OrderEntity, int>(httpClient, GeneratedSyncTables.Order)`. `SyncTable<,>`, `VersionlessSyncTable<,>`, `DirectSyncSource<,>`, `VersionlessDirectSyncSource<,>` and `HttpSyncServerSource<,>` are consequently sealed rather than abstract, and `JournalingRepositoryBase<,>` and its two subclasses take the descriptor and the shared `SyncGraphRecorder` as constructor arguments. Nothing changes for code that uses the DI registrations (`AddGeneratedSyncSupport` / `AddGeneratedSyncEngine` / `AddGeneratedDirectSyncSources` / `AddGeneratedHttpSyncSources`), the engine, `ISyncTable`, `ISyncServerSource<,>`, `ISyncBinaryColumns<TKey>`, or the generated `Journaling{Entity}Repository` (still generated, still `(inner, journal)`); what breaks is code that named one of the removed classes or derived from one of the now-sealed ones. The per-table generated code shrinks by roughly 70-80% (779 → 210 lines for the three-table sync fixture)
- **The server-side endpoint mapping is generic** — `RemoteServerEngine.MapCrud<TEntity, TKey, TRepository>` now maps the uniqueness pre-check alongside CRUD and the graph saves, and the new `RemoteServerEngine.MapBinaryColumn<TKey>` maps all three verbs of one unbounded binary column, so a generated `Map{Entity}Endpoints` is left with the named-query handlers and one call per binary column. The startup check for the sync sources walks a table (`SyncSourceServices`) rather than an `if` per table, and names exactly the same sources when one is missing. The routes, the request bodies, the status codes, the 400 / 409 / 500 classification, the `Response.HasStarted` guards, the 404 marker and the `allowUnboundedUploads` opt-in are all unchanged — this is the same wire format written in fewer lines: 26 → 9 generated lines per entity, 57 → 11 per binary column, and 21–71% off the schema-dependent part of the server file depending on the diagram. One consequence is worth naming: the uniqueness check now reads the envelope `Insert` already uses (`RemoteEntityRequest<TEntity>`), so the per-entity `private sealed record {Entity}CheckUniquenessRequest` is gone. Nothing on the wire or in the public API changes with it — the only code that can notice is a hand-written part of the `GeneratedRemoteEndpoints` partial class that named that record
- **Breaking: the generated mapper's `includeRemoved` is now a required argument** — `CreateEntity(editModel, includeRemoved)`, `CreateEntities(collection, includeRemoved)` and `ApplyToEntity(editModel, entity, includeRemoved)` no longer default to `false`, so every call site has to state whether it is building an entity graph to save (`true`) or to display (`false`). Omitting the argument used to leave the deletion-tracked rows out of the graph, and the save then silently kept the rows the user had removed. To migrate, regenerate the code and add `includeRemoved: true` on save paths and `includeRemoved: false` on display paths at the call sites the compiler now flags

## [0.1.0] - 2026-08-30

Initial public release.

### Added

- **Visual ER design** — crow's foot notation, one-to-one / one-to-many / many-to-many, composite primary keys, FK referential actions, comprehensive undo/redo, and a large-diagram canvas UX (zoom / pan / search / minimap)
- **Multi-DB support** — schema import, diff sync, DDL generation, and automatic type conversion on dialect switch, across five dialects (SQL Server / PostgreSQL / MySQL / Oracle / SQLite)
- **C# code generation** — Entity / EditModel / Mapper, plus a 3-way data-access choice: none / the QuickER Repository / the EF Core Repository (the same interfaces, swappable with a single DI registration line). Value objects, named queries, remote contracts and HTTP + JSON services, and a runtime NuGet package reference mode are optional
- **Bidirectional sync** — optionally generates the engine that keeps a local SQLite copy in step with a SQL Server database, over a direct connection or HTTP, with a fast full reload for the first build and for recovery
- **AI chat and mock generation** — create and edit diagrams in conversation (OpenAI API / Anthropic API / an OpenAI-compatible local LLM / Codex / Claude Code / Copilot), generate web screen mockups from the ER model, and optionally scaffold a runnable Blazor or WPF mock project
- **MCP server** — `quicker mcp` exposes diagram editing and code generation to external AI agents over stdio
- **Import/export** — DBML / Mermaid / Excel definition documents / HTML definition documents / schema JSON / PNG / SVG / vector printing
- **CLI** — `quicker generate` / `quicker scaffold` / `quicker reverse` / `quicker mcp`
- **Working samples** — `samples/ec-order` (SQLite, no external database required) and `samples/ec-order-remote` (three-tier over HTTP + JSON)

Distributed as a GUI (Setup.exe and Portable zip, in a full self-contained channel and a lite framework-dependent one) and as NuGet packages (`QuickER.Cli` as a dotnet tool, plus the runtime packages `QuickER.Runtime` / `.SqlServer` / `.Sqlite` / `.EntityFrameworkCore` / `.InMemory` / `.AspNetCore` / `.Sync`).
