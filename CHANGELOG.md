# Changelog

*English | [日本語](CHANGELOG.ja.md)*

This file records changes that affect QuickER users. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/) (see [CONTRIBUTING.md](CONTRIBUTING.md) for the versioning rules during 0.x and the release procedure).

## [Unreleased]

### Added

- **App — PostgreSQL and MySQL connections can ask for TLS** — the connection dialog gains an **Encryption (SSL Mode)** field for those two dialects, offering `Unspecified` / `Disable` / `Prefer` / `Require` / `VerifyCa` / `VerifyFull`, and it is saved per connection profile. It defaults to `Unspecified`, which writes no keyword at all and leaves the decision to the driver, so an existing profile connects exactly as it did — and that matters, because both drivers default to encrypting **without validating the server certificate**, which stops eavesdropping but not a man in the middle. `VerifyCa` or `VerifyFull` is what makes the certificate be checked. SQL Server already exposed the same decision as "Trust the server certificate", and SQLite has no connection to encrypt; Oracle is documented rather than offered a field, because the managed driver switches TLS on through the data source's protocol prefix (`tcps://host:2484/service`) and the listener port rather than through a keyword, and has no equivalent of `Prefer` or `Require`; selecting Oracle in the dialog now says so, since "no field" and "encrypted anyway" are otherwise indistinguishable on screen. `quicker scaffold` takes a connection string as it stands, so `SSL Mode=VerifyFull` — or Oracle's `tcps://` data source — goes straight into `--connection`. What each dialect does by default is now a table in [docs/database.md](docs/database.md)

- **App — A composite primary key keeps its own column order** — the schema import (all five dialects) now reads the column order the `PRIMARY KEY` constraint declared, so `PRIMARY KEY (b, a)` stays `(b, a)`. Previously the key was flattened onto the table's column order, so importing such a table and regenerating DDL silently changed the column order of the backing index. Generated DDL and sync scripts now emit the constraint's own order, the diff sync detects an order-only difference as a primary-key change, and the replace confirmation on re-import treats a diagram that differs only in key order as structurally different. When a table's composite key order differs from its column order, the AI tools' diagram summary adds a `Primary key order:` line. One behavior change follows: in a diagram that carries an imported key order, reordering columns no longer changes the primary key's order (a key whose order has never been stated still follows the column order as before). Viewing and editing that order have their own entries in this release — the properties panel's "Primary key order" card and the `set_primary_key` AI tool. The DBML / Mermaid / Excel documents and the C# reverse import do not carry the order — each of those documents names the limitation

- **App — The AI tools can set a table's primary key** — a new `set_primary_key` tool, available both from the external MCP server and from the built-in chat, takes a table name and a list of columns and replaces that table's primary key with exactly those columns in exactly that order; every other column of the table stops being part of the key. Column order carries meaning here in a way it does not for `set_unique_constraint` — it is the order of the generated `PRIMARY KEY` constraint and of the index behind it — and until now an agent had no way to express it, because `add_column is_primary_key=true` says nothing about order and nothing at all could take a column back out of a key. The listed columns are made NOT NULL, since a key column cannot be null; a column dropped from the key keeps the nullability it had, because dropping it says nothing about whether it may now be null. At least one column is required, so the tool can move or rebuild a key but never leave a table without one — clearing a key outright remains the PK checkbox's job in the editor

- **App — The properties panel can reorder a composite primary key** — a "Primary key order" card sits between the column grid and the unique constraints whenever the selected table has two or more primary key columns, listing the key's columns in order with ↑ / ↓ to move one. Which columns belong to the key is still the PK checkbox's business in the column grid; the card settles only their order, and one move is one undo step — the key's membership, the NOT NULL that comes with it, and the order all travel back together. Until the order is stated explicitly it keeps following the column order in the grid, exactly as before; stating it once — in the card, through `set_primary_key`, or by importing the table from a database — pins it, after which reordering columns in the grid no longer moves the key's columns around and a column ticked PK afterwards joins the key at the end

- **Generated code — Value objects implement `IFormattable`** — `price.ToString("N2")` and the culture-taking overload format the underlying value, and a format specifier in string interpolation, `string.Format`, or a WPF binding's StringFormat now reaches the underlying value. Without a format specifier the result is always `ToString()`, so `ToString()` overrides keep governing unformatted rendering; an underlying value that is not formattable (a string, a byte array, a bool) likewise ignores the format, matching what composite formatting does for any such value

- **Generated code — The edit-model boilerplate is now driven by a column table** — a generated edit model publishes one `EditModelColumn<TSelf>` per column (its two names, whether input is required, and compiled accessors for the confirmed value and the input string) through the new `EditModelBaseCore<TSelf>.EditModelColumns`, and the required-input check, the input revert, the row-edit snapshot and the duplicate-error mapping are written once on the base class instead of once per column in every class. `EditModelBaseCore.BeginLoad` / `EndLoad`, `GetChildren` / `SetChildren` and `CheckDatabaseUniquenessAsync` are the other new base members the generated code now delegates to. Storage is unchanged (the confirmed-value fields, the input-string fields and the binding setters are exactly what they were), and so is every observable semantic; the generated edit model and mapper shrink by 30-36%, which is roughly 190 fewer lines per edit-model class and 28 fewer per mapper
- **Generated code — The validation rules a generated value object runs are now public and reusable** — `ValueObjectRules.ValidateRequired`, `ValueObjectStringRules.ValidateMaxLength` and `ValueObjectDecimalRules.Validate` live on the fixed infra (the `QuickER.Runtime` package in package-reference mode) instead of being inlined into every value object, so a generated `ValidateCore` is now one line per rule and a hand-written value object can call the same rules
- **Generated code — Four general-purpose validation rules to call from `OnValidate`** — `ValueObjectNumberRules.ValidateMaxDigits` (digit count of an integer), `ValueObjectNumberRules.ValidateRange` (closed interval, any `IComparable<T>`), `ValueObjectStringRules.ValidateAsciiAlphanumeric` (ASCII letters and digits plus the symbols you allow) and `ValueObjectStringRules.ValidateEmailAddress` (a practical minimum, deliberately not RFC 5322). Their messages are new `ValueObjectValidationMessages` entries (`DigitsExceeded` / `OutOfRange` / `InvalidCharacters` / `InvalidEmailAddress`)
- **Generated code — The generated base classes can be extended in every output mode** — every base the generated code inherits or implements now comes in two layers, **without exception**: the implementation lives in the fixed runtime as a `*Core` type, and the plain name (`EntityBase`, `EditModelBase<TSelf>`, the value-object bases and a new non-generic `IValueObject` marker, `IRepository<TEntity, TKey>`, `IRemoteRepository<TEntity, TKey>`, `SqlServerRepository<TEntity, TKey>`, `SqliteRepository<TEntity, TKey>`, `EfCoreRepository<TEntity, TKey, TContext>`, `InMemoryRepository<TEntity, TKey>`, `HttpRemoteRepository<TEntity, TKey>`, `MapperBase<TEntity, TEditModel>`) is a `partial` emitted **as source next to the per-type code**, in every output mode including `--use-runtime-packages`. Adding a member or an interface to one of them reaches every generated entity, edit model, value object, repository or mapper at once, and the same file compiles whether the runtime is inlined or referenced as a package — turning the package mode on or off no longer makes you rewrite an extension, which it did when these types were compiled assembly types. For value objects two surfaces reach all of them regardless of value shape: the marker `IValueObject` (`public partial interface IValueObject : IMyInterface { … }` gives every value object that interface, with a default implementation if you write one) and the class root `ValueObjectBase<TSelf, TValue>`, which every value object derives from and which can see `Value` and `TSelf`. The bases for a value shape — `ValueObjectOrderedBase`, `StringBase`, `BooleanBase`, `DateTimeBase`, `BinaryBase`, `GuidKeyBase` — are generated as well, each deriving from that root, so a member meant for one value shape goes on the matching class. A member added to the repository contracts `IRepository<TEntity, TKey>` / `IRemoteRepository<TEntity, TKey>` is callable through any repository reference you resolve from DI — whatever the entity, whatever the back end, and through a decorator too, because a default implementation dispatches virtually and its interface call on `this` lands on the decorator. A member without a body would break every generated repository, so **additions to the contracts must carry a default implementation**. The five backend implementation bases are independent branches with no shared parent, and suit a `protected` helper shared by the handwritten `partial` of each `{Entity}Repository`. The generic contracts `IValueObject<TSelf>`, `IValueObject<TSelf, TValue>` and `IStringMatchValueObject<TSelf>` stay in the runtime and are not extension surfaces, and neither is any `*Core` type: none of them is `partial`, so the extension surface is the only place a member can be added — which is also the only place that works in package-reference mode
- **Generated code — A synchronised table is now described by data rather than by classes of its own** — `SyncTableDescriptor<TEntity, TKey>` carries everything a table contributes (its name, its per-dialect SQL, and how a key, a mirrored version and an unbounded binary column are read and written), and the generated `GeneratedSyncTables` exposes one static descriptor per table plus `All` and a shared `GraphRecorder`. `SyncGraphRecorder` is now a fixed class in `QuickER.Runtime.Sync` that walks a graph once through `EntityBaseCore.EnumerateCascadeChildren`, which yields the same cascade navigations the graph saver's own walk enumerates, instead of a recursive method generated per entity type, so the recording and the saving can no longer drift apart. `EntityBaseCore.EnumerateCascadeChildren` is public for that reason, and `SyncRepositoryBinaryColumns<TEntity, TKey>` is the one implementation of the unbounded-binary copy surface for both the local database and a directly connected server
- **Generated code — EF Core `HasKey` follows the primary key's own column order** — a composite key whose order differs from the table's column order (now representable — see the composite-primary-key entry above) generates `HasKey(e => new { e.B, e.A })` in the key's order. Diagrams whose key order matches their column order — every diagram that existed before this release — generate byte-identical output

### Changed

- **App — A column's data type has to be a plain type expression** — DDL generation and schema-sync script generation write `Column.DataType` into the SQL as it stands, because a type is neither an identifier nor a string literal and there is nowhere to quote it. A type that could not be written safely used to go through untouched; the two generators now refuse the whole output and name the offending `table.column` and the type text. What a type may hold is words (letters, digits, `_`, `$`) separated by single spaces, each optionally followed by parenthesised arguments such as `(max)`, `(50)`, `(10,2)` or Oracle's `(10 BYTE)`, an optional trailing `[]`, or a MySQL value list such as `enum('a','b')`. Every type the five dialect catalogues offer and everything the five schema importers build from a live database passes — `double precision`, `timestamp with time zone`, `TIMESTAMP(6) WITH LOCAL TIME ZONE`, `INTERVAL DAY(2) TO SECOND(6)`, `decimal(10,2) unsigned`, `UNSIGNED BIG INT`, `integer[]` among them. What does not is a type carrying `;`, a quote, a backtick, a backslash, a comment marker (`--`, `/*`, and MySQL's `#`) or a line break, a type with leading or trailing whitespace (what is validated has to be exactly what is written out, and `"\nGO\n"` reads as the word `GO` once trimmed), or a type smuggling a column clause after its first word (`int NOT NULL`, `int DEFAULT 0`, `varchar(50) COLLATE …` — a type is interpolated into the middle of a column definition, so these produce valid DDL that quietly disagrees with what the diagram declares). An empty or whitespace-only type still means "not set" and passes as before. Type *interpretation* is unaffected: a type the dialect catalogue cannot parse is still carried as-is and simply gets no neutral token
- **App — A diagram name containing a line break or a control character is refused by every generator** — a table, column, constraint or query name holding one is reported by C# generation before generation with the place named, instead of producing a file that does not compile; DDL generation and schema-sync script generation refuse the whole output the same way, naming the place (`TABLE 'x'`, `COLUMN 'x'.'y'`, `UNIQUE 'x'.'y'`, `FOREIGN KEY 'x'`). The character set is the C0 controls, DEL, and the three Unicode line separators U+0085, U+2028 and U+2029 — the last three are line breaks to the C# compiler, so a name holding one used to walk out of a `///` comment and become code. Comment folding and identifier escaping stay in place behind this; refusing at the entrance means a single missed one is not enough to matter. Quote characters are deliberately not errors: `"`, `'` and `]` occur in real databases and are handled by escaping. Descriptions are not refused — a line break in one is legitimate, and they are folded where they land in a `--` comment

- **Generated code — Breaking: the fixed runtime base types carry a `Core` suffix** — `EntityBaseCore`, `EditModelBaseCore`, `EditModelBaseCore<TSelf>`, `ValueObjectBaseCore<TSelf, TValue>`, `IValueObjectCore`, `IRemoteRepositoryCore<TEntity, TKey>`, `IRepositoryCore<TEntity, TKey>`, `SqlServerRepositoryCore<TEntity, TKey>`, `SqliteRepositoryCore<TEntity, TKey>`, `EfCoreRepositoryCore<TEntity, TKey, TContext>`, `InMemoryRepositoryCore<TEntity, TKey>`, `HttpRemoteRepositoryCore<TEntity, TKey>` and `MapperBaseCore<TEntity, TEditModel>` are the runtime types; the unsuffixed names now belong to the generated extension surfaces above. The bases for a value shape (`ValueObjectOrderedBase`, `StringBase`, `BooleanBase`, `DateTimeBase`, `BinaryBase`, `GuidKeyBase`) keep their names, because they are generated types rather than runtime ones. Everything you write against keeps its current name: a generated entity still reads `: EntityBase`, a generated edit model `: EditModelBase<TSelf>`, a generated repository contract `: IRepository<CustomerEntity, int>`, a generated repository implementation `: SqlServerRepository<CustomerEntity, int>(…)`, a generated mapper `: MapperBase<CustomerEntity, CustomerEditModel>`, a hand-written value object `: ValueObjectStringBase<ContactMailValue>, IValueObject<ContactMailValue, string>`. What breaks is code that names a runtime type directly — a signature taking `EntityBase` where the runtime declares it (`ISqlExecutor.QueryBySqlAsync<TEntity> where TEntity : EntityBaseCore`), a helper typed as the non-generic `EditModelBase`, an `is IValueObject` test inside your own infrastructure, an implementation that names `IRemoteRepository<,>` / `IRepository<,>` **where the runtime declares it** (`ISyncServerSource<,>.Writer`, say), or a `partial` written against one of these. Rename those to the `Core` form. `IValueObject<TSelf>` and `IValueObject<TSelf, TValue>` keep their names, and `IValueObject<TSelf>` now derives from `IValueObjectCore`
- **Generated code — A date or time column that carries a sub-second part now shows it** — an edit model derives the input string from the confirmed value with the culture's own format, which stops at whole seconds, so a finer value was displayed truncated; editing any *other* column of the row then committed that truncated instant back over the stored one, because the binding setter rebuilds the confirmed value from the text. The input string now carries the sub-second part when there is one — appended after the seconds with a literal `.` and no trailing zeros — and parses back to the exact tick in every culture. A value with no sub-second part is displayed exactly as before, character for character, so a screen only changes where it was losing precision. `EditModelInputFormat` on the fixed infra is what the generated column table calls for `DateTime`, `DateTimeOffset`, `TimeSpan` and `TimeOnly`; a `date` column keeps its short-date format
- **Generated code — The in-memory repository enforces the diagram's UNIQUE constraints** — a direct insert, update or bulk insert, and a graph save, are rejected when they would leave two rows holding the same values on a constraint the diagram declares, so a write a real database refuses no longer passes in memory. The rules are the ones the uniqueness pre-check (`CheckUniquenessAsync`) already applied: a tuple containing a null is not compared, and the row being written is excluded by its primary key. A bulk insert is validated in full before any of it is applied, and a graph save is judged by the state it would leave behind — it can free a value on one row and take it on another within the same save, and a violation drops the save whole without publishing any of it. The violation is an `InvalidOperationException`, which is what a duplicate primary key already raises here; a real database reports it through its own provider's exception (`SqlException` with error 2627, for one), and no in-memory type can be that exception, so code that catches a provider exception still has to be exercised against the database. The user-defined checks added through `CollectCustomUniquenessChecks` are not enforced — they are rules of the application rather than constraints the database holds — and neither is seeding through `InMemoryDataStore.Put` / `InMemorySampleData.Seed`
- **Generated code — A NOT NULL excluded binary column is now required input while the row is new** — with `ExcludeUnboundedBinaryColumns` on, an excluded column stays out of the required-input check, except while the edit model is `RowState.Added`: INSERT keeps every column, so an empty value reaches a NOT NULL column and the database rejects it. That insert always failed; it is now caught in the edit model, with the column named, instead of coming back as a NOT NULL violation. The two-step route (insert, then stream the body in with `Write{Column}Async`) works exactly as before as long as the insert carries an empty value — `ThumbValue.Create([])` with value objects, `[]` without them, which is what the entity of a non-value-object column already starts out with. Nothing changes once the row exists, nor for a nullable excluded column, nor with the option off
- **Generated code — Breaking: the per-edit-model message and display-name hooks are gone** — generated edit models no longer declare `CustomizeRequiredErrorMessage`, `CustomizeParseErrorMessage`, `CustomizeDuplicateErrorMessage` or `CustomizePropertyDisplayName`, so an existing implementation of one stops compiling. Customize the wording through the matching `EditModelMessages` entry and a display name through `GeneratedDisplayNames.Resolve`, branching on the property name each of them now receives. This is the same move the value-object hooks made: one place per message rather than one place per type, and nothing to re-implement on the generated class after a regeneration. The semantic hooks (`OnValidate`, `OnBeginEdit` / `OnEndEdit` / `OnCancelEdit`, `On{Property}Changing` / `Changed`) are unaffected
- **Generated code — Breaking: `EditModelMessages.Required`, `ParseFailed` and `DuplicateValue` take the property name first** — `Required` is now `(propertyName, displayName)`, `ParseFailed` is `(propertyName, displayName, inputValue, typeName)`, and `DuplicateValue` is `(propertyNames, displayNames)`. That first argument is the stable key a replacement branches on with `nameof`, which is what lets one resolver do what the per-class hooks used to. The default wording is unchanged, so an application that does not replace these sees no difference
- **Generated code — Breaking: `MapperBase<TEntity, TEditModel>` owns the load sequence** — `CreateEntity()`, `CreateEditModel(entity)` and `ApplyToEditModel(entity, editModel)` are concrete on the base class instead of abstract, and the generated mapper overrides `LoadColumns` (the column copying) and `CompleteLoad` (the cascade children and the post-load hook) plus two bridges to its `OnEntityCreated` / `OnEditModelCreated` partials. `CreateEntityCore` and `CreateEditModelCore` are gone. Calling code is unaffected — the public surface a caller uses (`CreateEntity`, `CreateEntity(editModel, includeRemoved)`, `CreateEntities`, `CreateEditModel`, `CreateEditModels`, `ApplyToEntity`, `ApplyToEditModel`) is the same, the order of the load is byte-for-byte the same, and the partial hooks still fire in the same places; what breaks is a hand-written mapper that derived from `MapperBase<,>` and overrode the now-non-virtual members
- **Generated code — Breaking: the per-value-object message and display-name hooks are gone** — generated value objects no longer declare `CustomizeDisplayName`, `CustomizeMaxLengthErrorMessage`, `CustomizeScaleErrorMessage`, `CustomizePrecisionErrorMessage` or `CustomizeValueRequiredErrorMessage`, so an existing implementation of one stops compiling. Customize a display name through `GeneratedDisplayNames.Resolve` and a message through the matching `ValueObjectValidationMessages` entry, branching on the name for a single type (`memberName == nameof(CustomerEntity.Name)`, `displayName == NameValue.DisplayName`). The wording then lives in one place per message rather than one place per type, and nothing has to be re-implemented on the generated class after a regeneration. `OnValidate`, `GetDefinedInstance` and `ConvertCustomInput` are unaffected
- **Generated code — Breaking: the entity display-name hook is gone** — `EntityBaseCore` no longer declares `CustomizeDisplayName`, so an `override` of it stops compiling, and `DisplayName` simply returns `DefaultDisplayName`. Substitute a display name through `GeneratedDisplayNames.Resolve` instead, branching on the runtime class name it receives (`static (memberName, description) => memberName == nameof(CustomerEntity) ? "Customer" : description ?? memberName;`), or put the wording in the table description, which the default resolver already prefers. This is the same move the value-object and edit-model hooks made: one place for every display name rather than one override per entity class. The diagnostic for an entity whose column is named `DisplayName` no longer mentions the hook either, and such a column no longer suppresses anything beyond the `DefaultDisplayName` override
- **Generated code — Breaking: every `ValueObjectValidationMessages` entry takes the display name as its first argument** — `MaxLengthExceeded` is now `(displayName, maxLength, actualLength)`, `ScaleExceeded` and `PrecisionExceeded` take `(displayName, …)`, `ValueRequired` takes `(displayName)`, and `InputNotConvertible`'s arguments are reordered to `(displayName, raw)`. This is what makes a single replacement able to vary the wording per type. The default wording is unchanged, so an application that does not replace these sees no difference
- **Generated code — Breaking: the common runtime surface `IRemoteRepositoryCore<TEntity, TKey>` declares `CheckUniquenessAsync`** — the uniqueness pre-check used to be declared on each generated `I{Entity}RemoteRepository` (or `I{Entity}Repository`) and implemented on every generated repository class; the declaration now sits on the common runtime surface and the implementation on each back end's repository base class (the dialect, in-memory, EF Core and HTTP client bases). Code that calls the check is unaffected — `I{Entity}Repository` still provides it through inheritance and the signature, the result and the `CollectCustomUniquenessChecks` hook are unchanged, and an existing hand-written hook keeps working untouched. What breaks is a *hand-written implementation* of `IRemoteRepositoryCore<,>` or `IRepositoryCore<,>` (or of the extension surfaces `IRemoteRepository<,>` / `IRepository<,>` that inherit them) — a test double or an adapter — which now has to provide the member; deriving from a generated base class instead gets it for free. A generated repository now contributes only the constraint table (`{Entity}UniquenessConstraints.Set`) and a two-line bridge to its hook, which is roughly 50 fewer lines per entity per back end
- **Generated code — DI registration is one line per entity** — `AddGenerated{SqlServer,Sqlite}Repositories` and `AddGeneratedEfCoreRepositories` register the repository as `services.AddScoped<IContract, Implementation>()` and let the container build it from the dependencies the same call registers (the idiom `AddGeneratedInMemoryRepositories` already used), while the keyed overload and `AddGeneratedHttpRemoteRepositories` fold the wiring every entity shares into one local function. The registered lifetimes, the keyed / non-keyed resolution of `ISqlExecutor`, the `TryAddScoped<ISaveHookRegistry>` default and the remote surface forwarding to the same instance are all unchanged
- **Generated code — Breaking: the per-table sync classes are gone** — `{Entity}SyncTable`, `{Entity}DirectSyncSource` and `Http{Entity}SyncSource` are no longer generated. The fixed classes they used to derive from take a descriptor instead and are constructed directly: `new SyncTable<OrderEntity, int>(local, localSql, source, GeneratedSyncTables.Order)`, `new VersionlessSyncTable<…>`, `new DirectSyncSource<OrderEntity, int>(serverSql, serverRepository, GeneratedSyncTables.Order)`, `new VersionlessDirectSyncSource<…>` and `new HttpSyncServerSource<OrderEntity, int>(httpClient, GeneratedSyncTables.Order)`. `SyncTable<,>`, `VersionlessSyncTable<,>`, `DirectSyncSource<,>`, `VersionlessDirectSyncSource<,>` and `HttpSyncServerSource<,>` are consequently sealed rather than abstract, and `JournalingRepositoryBase<,>` and its two subclasses take the descriptor and the shared `SyncGraphRecorder` as constructor arguments. Nothing changes for code that uses the DI registrations (`AddGeneratedSyncSupport` / `AddGeneratedSyncEngine` / `AddGeneratedDirectSyncSources` / `AddGeneratedHttpSyncSources`), the engine, `ISyncTable`, `ISyncServerSource<,>`, `ISyncBinaryColumns<TKey>`, or the generated `Journaling{Entity}Repository` (still generated, still `(inner, journal)`); what breaks is code that named one of the removed classes or derived from one of the now-sealed ones. The per-table generated code shrinks by roughly 70-80% (779 → 210 lines for the three-table sync fixture)
- **Generated code — The server-side endpoint mapping is generic** — `RemoteServerEngine.MapCrud<TEntity, TKey, TRepository>` now maps the uniqueness pre-check alongside CRUD and the graph saves, and the new `RemoteServerEngine.MapBinaryColumn<TKey>` maps all three verbs of one unbounded binary column, so a generated `Map{Entity}Endpoints` is left with the named-query handlers and one call per binary column. The startup check for the sync sources walks a table (`SyncSourceServices`) rather than an `if` per table, and names exactly the same sources when one is missing. The routes, the request bodies, the status codes, the 400 / 409 / 500 classification, the `Response.HasStarted` guards, the 404 marker and the `allowUnboundedUploads` opt-in are all unchanged — this is the same wire format written in fewer lines: 26 → 9 generated lines per entity, 57 → 11 per binary column, and 21–71% off the schema-dependent part of the server file depending on the diagram. One consequence is worth naming: the uniqueness check now reads the envelope `Insert` already uses (`RemoteEntityRequest<TEntity>`), so the per-entity `private sealed record {Entity}CheckUniquenessRequest` is gone. Nothing on the wire or in the public API changes with it — the only code that can notice is a hand-written part of the `GeneratedRemoteEndpoints` partial class that named that record
- **Generated code — `[Column]` is emitted whatever `IncludeDataAnnotations` says** — the attribute is the persistence mapping rather than documentation, so it is now applied to every generated column property even with data annotations off; that output gains one line per column, while an output generated with annotations on is byte-for-byte what it was. `IncludeDataAnnotations` from here on governs the documentation and validation attributes alone (`[Table]`, `[Key]`, `[Required]`, `[MaxLength]`, `[DbTableMeta]`, `[DbColumnMeta]`). It is still required for a repository contract, because the runtime reads `[Table]` and `[Key]` through reflection
- **Generated code — Breaking: an unsent local change now stops a sync download, and `SyncResult` says where** — a table's download stops at the first row whose key still holds a journal entry, and every table after it in foreign-key order is left for the next run as well; rows behind the stopping point stay on the server until the entry is settled (decided and re-run, or dropped with `SyncJournal.RemoveTableAsync`). Skipping just that row and carrying on is not available, because the resume point is the highest mirrored version in the table and it would move past the row being protected. `SyncResult.Truncations` / `HasTruncations` report each stop with the table and either the key it stopped at or the table whose stop it waited for. What a run stops for is an unsent journal entry - usually a conflict it has just collected, equally an entry an interrupted upload left behind - so a run that settles every entry reports no truncations and nothing changes for a setup where uploads go through; what does change is that a run with a standing entry now brings down less than it used to, and says so. A versionless table skips the row instead of stopping, since its download re-reads the whole table anyway
- **Generated code — Breaking: the sync engine keeps a second local table, `SyncTableBase<TEntity, TKey>.OnLastWriteWinsUploadedAsync` is gone, and the sync surfaces changed shape** — `SyncJournal.EnsureCreatedAsync` now creates two tables in the local database rather than one: `quicker_sync_journal` as before, and `quicker_sync_ack`, which records per row the version the server stamped on an upload it took (a receipt, not a resume point - nothing derives an anchor from it). The removed hook existed to mirror the version after a last-write-wins upload, which is no longer something an upload does, so an override of it stops compiling with nothing to replace it. Changed signatures: `UploadAsync` on `ISyncTable` and `SyncTableBase<,>` takes a `byte[]? acknowledgedRowVersion` ahead of the cancellation token, and `PropagateDeletesAsync` returns the keys it deleted (`IReadOnlyList<string>`) rather than their count. Additions: `ISyncTable` and `SyncTableBase<,>` take a `DownloadAsync` overload carrying a `SyncDownloadContext` (the table's unsent keys and its outstanding acknowledgements) and returning `SyncDownloadOutcome`; `SyncJournal` gains `RecordAckAsync` / `ReadAcksAsync` / `RemoveAcksAsync` / `RemoveTableAcksAsync`, with `SyncAckRow` as the row type; `SyncUploadOutcome` carries `ServerRowVersion` and the `UploadedWith` factory; `SyncResult` carries `Truncations` / `HasTruncations`; `SyncDownloadTruncation` is new. Unchanged: the four-argument `DownloadAsync` (the table-level surface) still applies every row, and `SyncJournal.RemoveTableAsync` / `RemoveAllAsync` still deal with journal entries alone - dropping unsent local changes says nothing about what the server has already taken. `SyncEngine.UploadAsync` and `DownloadAsync` called separately are now as sound as `SyncAsync`, because the receipts outlive the call that wrote them: a download on its own recognises the echo of every upload whose row has yet to come back down
- **Generated code — Breaking: the generated mapper's `includeRemoved` is now a required argument** — `CreateEntity(editModel, includeRemoved)`, `CreateEntities(collection, includeRemoved)` and `ApplyToEntity(editModel, entity, includeRemoved)` no longer default to `false`, so every call site has to state whether it is building an entity graph to save (`true`) or to display (`false`). Omitting the argument used to leave the deletion-tracked rows out of the graph, and the save then silently kept the rows the user had removed. To migrate, regenerate the code and add `includeRemoved: true` on save paths and `includeRemoved: false` on display paths at the call sites the compiler now flags
- **App — The single-file output mode can be picked with layer folders still checked** — the output-mode radio buttons in the C# generation dialog are always live now, and picking "merge into a single file" clears the "place the generated files into layer folders" checkbox (a single file cannot be split across layers; the implication simply runs both ways, and checking the box still switches the mode to split as before). The radio buttons used to be disabled while the box was checked, so getting back to single-file output meant unchecking it first. Nothing about the generated output changes
- **Generated code — A query no longer compiles an expression tree on every call** — two places used to hand `Expression.Compile()` a fresh tree per call, which builds a dynamic method each time. (1) A generated projection query now keeps its selector in a `private static readonly Expression<Func<TEntity, TResult>>` field on the repository instead of writing the lambda inline in the method body, and the back ends that have to turn it into a delegate (the dialect executors, the in-memory executor, the EF Core fall-back path) ask the new `QuerySelectorCache` for it — C# does not cache an expression tree, so an inline lambda produced a new instance, and a new compilation, on every call. (2) The value side of a predicate is now interpreted wherever it can be: the new `QueryValueEvaluator` reads method calls, value-preserving conversions (a reference upcast, boxing into `object`) and inline arrays directly, on top of the constants and closure reads it already read, and only the remaining shapes fall back to compiling. That second one matters most with value objects on, where every generated query puts `XxxValue.Create(arg)` in value position and so took the compiling fall-back on every single call. Results and exceptions are unchanged — a factory that throws raises the same exception type, not reflection's `TargetInvocationException`, and an instance call on a null receiver still fails as a `NullReferenceException`. Measured against SQLite over 200,000 rows: a projection query repeated 10,000 times went from 5.27 s / 208 MB to 1.60 s / 110 MB, an entity query with a value-object condition from 4.36 s / 188 MB to 1.74 s / 147 MB; a plain full-table materialisation is unchanged. `QuerySelectorCache` and `QueryValueEvaluator` are additions to the `QuickER.Runtime` surface
- **App — The startup update check can be turned off** — the toolbar's language button is now a **Settings** button (⚙), with the language choice moved into a submenu and a new **Check for updates on startup** toggle beside it. Turn it off and the app never contacts GitHub Releases at startup; the setting lives in `gui-settings.json` and defaults to on, so nothing changes unless you change it. The check has always asked before downloading anything, and the Portable edition has never checked at all. The installers and update packages are not Authenticode signed, which is what makes SmartScreen report an unknown publisher — both facts are now stated in the README's Install section
- **App — Breaking: settings and working state moved from `%APPDATA%` to `%LOCALAPPDATA%`** — `gui-settings.json`, `ai-settings.json`, `codegen-settings.json`, `connections.json` and its DPAPI-protected password files, the saved API keys, the auto-save file (`last_diagram.json`) and the crash logs are all read from and written to `%LOCALAPPDATA%\QuickER` now. What lives there is state specific to one machine, and secrets protected with DPAPI under the current user, which a domain roaming profile would copy to other machines where they cannot be decrypted. **There is no migration**: the files under `%APPDATA%\QuickER` are not read, so the display language, saved connections (including their passwords), API keys, code-generation settings and the recovery snapshot all start from their defaults once. To carry them over, copy `%APPDATA%\QuickER` over `%LOCALAPPDATA%\QuickER` before the first launch; the old folder is otherwise safe to delete
- **App — `QUICKER_UPDATE_FEED` only works in a Debug build** — the environment variable that redirects the update feed was meant for end-to-end verification, and in a shipped build it made the update path point wherever the environment said. The branch is now compiled out of Release entirely, so a distributed QuickER only ever reads the feed constant

- **App & generated code — A column type keeps its spelling through a C# reverse round trip** — the dialect-neutral token in `[DbColumnMeta]` carries the meaning of a type only, so several spellings of one meaning collapse onto a single representative: `datetime` came back as `datetime2`, `numeric(10,2)` as `decimal(10,2)`, `ntext` / `text` / `image` as `nvarchar(max)` / `varchar(max)` / `varbinary(max)`, `smallmoney` as `money`. Accepting such an import quietly rewrote the diagram, and the next database sync emitted an `ALTER COLUMN` for every affected column. `[DbColumnMeta]` now also records the original text as `NativeType`, **for those columns only**, and the import adopts it whenever parsing it in the current dialect yields the same type as the token (otherwise the token wins and a warning says so, which is what keeps a hand-edited or cross-dialect file honest). Spelling here means what the database sync means by it — leading and trailing spaces and letter case do not count as a difference — so a diagram whose types are already the representative spelling generates byte-for-byte what it did, and only the attribute's own declaration gains the new property. A generation whose columns do carry a collapsing spelling now reports them in an information diagnostic. A rowversion column is unaffected: it carries no token at all, by design

### Security

- **App — Launching a CLI installed as a `.cmd` shim no longer lets an argument escape the quoting** — on Windows, `codex`, `claude` and `copilot` installed through npm arrive as `.cmd` files, which Windows starts through `cmd.exe`; the command line .NET composes is then parsed a second time by `cmd`, where a quotation mark or an `&` in an argument can end the quoted region and start a command of its own. `codex` already built its own `cmd.exe` command line and refused arguments carrying characters `cmd` interprets; `claude` did not, and its arguments include the system prompt. Both now go through one shared guard: `claude`'s arguments are quoted individually (which is possible because they arrive as a list rather than one joined string) and `%` — the one character `cmd` still acts on inside quotes — is refused, as is a line break, which quoting cannot contain. `copilot` is launched from inside the GitHub Copilot SDK, so QuickER never composes its command line and can only check the resolved path; that residue is written down in `docs/ai-chat.md`
- **App — The Codex chat no longer runs in QuickER's own folder** — a Codex chat thread was started with the application's current directory as its working folder and no sandbox declared, while its approval policy is `never`, so the model could read that folder's contents without being asked. It now gets a throwaway folder under `%TEMP%\QuickER\codex` and declares the `read-only` sandbox, which is what the Claude Code and Copilot chats already did. Mock **project** generation is unaffected and keeps `workspace-write`, since writing to the output folder is the point there
- **App — GitHub Actions are pinned to commit SHAs** — the workflows referenced `actions/checkout@v7` and friends by tag, and a tag can be moved; every action now names a commit, with the version in a trailing comment, and a new Dependabot configuration raises the updates. This changes nothing about the shipped artifacts — it removes a way for a compromised upstream tag to change what the release and publish workflows run

### Fixed

- **App — The AI tools make a primary key column NOT NULL wherever the diagram lives** — `add_column is_primary_key=true is_nullable=true` and `set_column_property is_nullable=true` on a key column used to produce different diagrams depending on which host ran the tool: the in-app chat edits the same view models the editor does, which have always forced a key column to NOT NULL, while the external MCP server writes the file directly and took the flag at face value. The same tool call now normalizes the same way in both, so a diagram edited by an external agent no longer claims a nullable primary key column. Generated DDL is unaffected, because the `PRIMARY KEY` clause makes its columns NOT NULL whatever the diagram says — what changed is that the diagram, the properties panel, the definition documents and the schema diff now agree with it

- **App — An SQLite foreign key that omits its referenced columns now pairs with a composite primary key correctly** — `FOREIGN KEY (a, b) REFERENCES parent` with no column list references the parent's primary key in the key's own column order, but the import used to pair every constituent column with the parent's *first* primary-key column, so such a composite foreign key came back with broken column pairs. Each column is now paired with the primary-key column at the same position. Single-column implicit references were always correct and are unchanged

- **App — PostgreSQL import reads the type a column was actually declared with** — column definitions now come from `pg_catalog` and `format_type()` rather than `information_schema`, which could not express several modifiers. A `numeric(10,-2)` column used to be imported as `numeric(10,2046)`, a spelling PostgreSQL itself rejects, so the diagram could not generate DDL for that table at all; `bit(8)` and `bit varying(16)` lost their length (and applying the truncated `bit` back over the column fails on existing data), `interval day to second(3)` lost its unit, `time(3) with time zone` lost its precision, and an array came back as an internal name — `_int4`, or `_varchar` for `varchar(20)[]`, dropping the length with it. The imported spelling is still QuickER's short vocabulary (`varchar(50)`, `timestamptz(3)`), so a healthy column's type text is unchanged and produces no new diff; a column of the kinds above shows up once as a column change when you re-import into a diagram made by an older version. Because `pg_catalog` is not filtered by column privileges, a table the connecting role has no rights on now imports with its columns instead of silently arriving empty, and a partitioned table is imported as its parent (the partitions themselves are skipped) instead of vanishing
- **App — A foreign key pointing outside the imported scope is reported instead of disappearing** — PostgreSQL imports the `public` schema, MySQL the connected database, Oracle the connecting user's schema; a foreign key whose parent lives elsewhere cannot become a relationship. MySQL used to ignore the referenced schema entirely, so a cross-database key was matched against a same-named table in the connected database — wiring the relationship to the wrong table — and Oracle and PostgreSQL dropped such keys without a word. All three now skip the key and name it in the import warnings
- **App — Oracle stops importing things that are not part of the design** — a `DISABLE`d primary key, unique constraint or foreign key is no longer imported (a disabled constraint enforces nothing, so importing it made the diagram claim a guarantee the database does not provide), and temporary tables and the container tables behind materialized views are excluded, which brings the import in line with the documented "views are not imported"
- **App — Oracle keeps a column's rounding scale and its length unit** — `NUMBER(10,-2)` (round to hundreds) used to be imported as `NUMBER(10)`, which reads as a plain 32-bit integer and loses the rounding; `VARCHAR2(50 CHAR)` used to be imported as `VARCHAR2(50)`, a different type under a multi-byte character set. Both are now carried through, as is a negative scale in PostgreSQL's `numeric(10,-2)` and in the neutral `decimal(10,-2)` token that reverse engineering reads back. Switching such a column to SQL Server, MySQL or SQLite reports it as unconvertible instead of writing DDL those engines cannot run (the first two reject a negative scale outright; SQLite's `DECIMAL` carries no rounding at all)
- **App — Two tables whose names differ only in letter case no longer merge into one** — PostgreSQL and Oracle let `"Dup"` and `dup` coexist through quoted identifiers, and so does MySQL when `lower_case_table_names` is 0 (the default on Linux); the import used to collapse them into a single entity holding both tables' columns. One of them is now imported and the other is named in the import warnings. Which one survives no longer depends on the database's collation, because all three importers now order tables by byte value
- **App — The DB import reports what it could not carry across** — the completion dialog lists the affected objects when a PostgreSQL domain-type column was flattened to its base type, a foreign key pointed outside the imported scope, a table's columns could not be read, a name collided in letter case, a partitioned table was imported without its partitioning, or **a column's data type cannot be written into SQL safely**. That last one matters most: such a type is imported fine but makes DDL generation and schema sync refuse the *whole diagram* later, so naming it at import time is the earliest it can be known — the check runs for all five dialects, since SQLite keeps whatever type text a table was declared with. `quicker scaffold` writes the same list to standard error. An import with nothing to report shows the usual one-line completion message

- **App — Importing C# code says what it drops instead of dropping it silently** — several things the import could not restore left no trace at all. A table whose columns all lack `[DbColumnMeta]` (a small master table typed only in a dialect-specific way the type catalogue cannot parse, such as Oracle's `SDO_GEOMETRY`) was dropped whole, taking its relationships with it; such a table is now imported **with no columns** and named in a warning, so the relationships survive too. A skipped primary key column gets a warning of its own that says the table comes back without one. A relationship whose endpoint column cannot be resolved degrades to having no column pair — the line stays on the diagram while the foreign key disappears from DDL generation and schema diffs — and both that and a relationship whose endpoint table is missing from the file are now named. A `[NavigationReference]` whose endpoint arguments cannot be read is reported rather than ignored, and arguments written as `name:` in an order other than the declared one are now detected instead of being read by position, which silently swapped the two ends of the relationship. Duplicate table names and duplicate column names are reported. A class split into several `partial` declarations inside one file reports how many column properties sit in the parts without `[Table]`, since only the part carrying `[Table]` is read. Deciding what to import no longer requires a `[DbColumnMeta]`-bearing column, just `[Table]` — the attribute the generator puts on entity classes and nothing else
- **App — A referential action written as a number is no longer accepted** — `OnUpdate = "1"` in `[NavigationReference]` passed the enum check and became `Cascade` without a word; the token is matched against the enumeration's names now, so it is reported as unknown and left unspecified like any other token that cannot be read
- **App — Importing C# code no longer copies a many-to-many relationship's metadata onto a one-to-many** — a many-to-many holds no column pair, so its endpoint key degenerated to just the two entities and collided with a one-to-many between the same pair whose columns the import could not resolve. The one-to-many inherited the many-to-many's constraint name and referential actions, and the many-to-many was then added on top, leaving two relationships claiming the same constraint name. Many-to-many relationships are preserved as they always were, but no longer act as a source for filling in unstated fields
- **App — `quicker reverse` creates the output directory** — `--out` pointing into a folder that does not exist failed with a raw `DirectoryNotFoundException` naming the atomic-write temporary file, while `quicker generate` had always created its output directory
- **App — Replacing the open diagram no longer leaks the previous diagram's elements into the change tracker** — opening a file, importing, and the automatic reload on an external change all replace the diagram through a collection `Clear()`, whose Reset notification names nothing it removed, so the old entities, columns, unique constraints and relationships were never detached: the tracker's snapshot dictionary grew by one diagram per replacement (per call, with an MCP client editing the file), and the surviving subscriptions let a stray change to an orphaned element push a ghost command onto the live undo stack and mark a clean document dirty. Every replacement path now runs the same explicit detach the single-element removal path always ran
- **App — An external change arriving mid-drag no longer corrupts the document it lands on** — a table move, a resize, a group drag or a rubber-band selection in progress is now cancelled back to where it started before the reload or the confirmation dialog proceeds. Releasing the mouse after the reload used to push a move command built from the disposed elements, instantly marking the freshly reloaded document dirty with an undo entry that no longer meant anything; and the confirmation dialog could open while the mouse was still captured, so the release never arrived and the first mouse move after closing the dialog committed the table to wherever the pointer happened to be. On the keep-editing path the dragged table returns to its drag-start position — the moved position was never in the undo history, so leaving it standing would have been a change undo could not reach. A dialog that is already open (database sync, query definitions) is not closed; that remains a documented limitation
- **App — Saving can no longer record someone else's write as its own** — the content hash remembered after a save was read back from disk, so an external write landing between the write and that read was recorded as "what I saved" while its change event was discarded by the suspended watcher; from then on no detection path could see that the diagram in memory and the file had diverged, until the next save. The hash is now computed from the JSON text actually written, and the watcher checks the file once more right after resuming, so a write landing in that window is detected like any other external change
- **App — A failing Undo or Redo no longer deletes the operation from history** — a command whose execution threw disappeared from both stacks, leaving no way to retry it or move past it. It is now pushed back onto the stack it came from before the exception continues, so the history still shows it and it can be retried

- **App — Syncing a column description on MySQL no longer wipes the column's other attributes** — MySQL has no statement that changes a comment alone, so the sync goes through `ALTER TABLE ... MODIFY COLUMN`, which re-states the whole column definition. That definition used to be rebuilt from the diagram's type and nullability alone, so every attribute the diagram cannot model was dropped from the live column: its `DEFAULT` (literal or expression), `AUTO_INCREMENT`, its collation, `ON UPDATE CURRENT_TIMESTAMP`, `INVISIBLE`, a spatial `SRID`, and a generated column's expression — and MySQL commits DDL implicitly, so none of it could be rolled back. The same statement also carried the diagram's type across, which quietly applied a type change the user had **not** selected in the diff list. The definition is now reconstructed from `information_schema.COLUMNS` when the script runs and only the trailing `COMMENT` is replaced, so a description sync changes the description and nothing else. The rebuild reads the catalogue of the schema the statement actually targets, so a schema-qualified table takes its own definition rather than that of a same-named table in the connection's default database, and it writes back a `BIT` or binary literal default as the literal it is rather than as a string — a `varbinary` default would otherwise have been silently replaced by the text of its own hex form, and a `binary(n)` default would have stopped the script part way. A column that has disappeared by the time the script runs folds into a no-op; a column that is still there but whose definition cannot be rebuilt fails the script instead of passing silently
- **App — Syncing the column order on MySQL no longer wipes the moved column's attributes or its comment** — `ALTER TABLE ... MODIFY COLUMN ... AFTER` re-states the whole definition just as a comment change does, and it was being rebuilt from the diagram in the same way, so moving a column dropped exactly the attributes listed above. It is now reconstructed from the live catalogue too — with the same schema scoping and literal handling — and the column's existing comment is carried over with it

- **Generated code — The generated repositories now address a schema-qualified table correctly** — a table named `sales.orders` was quoted whole (`[sales.orders]`, `"sales.orders"`), which names a single table whose name literally contains a dot, so every SELECT, INSERT, UPDATE and DELETE against a table outside the default schema failed at run time with "invalid object name". The name is now split on its first `.` and each part quoted on its own (`[sales].[orders]`), which is what the DDL generator has always written. A table name without a dot produces exactly the SQL it did before
- **App & generated code — A table, column or constraint name containing the dialect's quote character no longer breaks the SQL the generated code builds** — a name holding `]` (SQL Server) or `"` (SQLite) closed the quoting early and the rest of the name was read as SQL. Such a name is now escaped by doubling the closing quote, the same rule the DDL generator applies, everywhere the generated runtime builds an identifier: the CRUD statements, the column lists, the `Query()` translation, the Include loader and the binary-column accessors. The same gap existed in the synthesized primary-key constraint name, `PK_{table}`: eight places (SQLite's DDL and the `CREATE TABLE` / `ADD CONSTRAINT` statements of the four sequential-DDL dialects' sync scripts) wrote it into hand-written quotes without escaping, while the UNIQUE and foreign-key names beside them were escaped
- **Generated code — A name containing `"` or `\` no longer produces code that fails to compile** — a table or column name holding either character (which a database import can hand you) was written into `[Table("…")]`, `[Column("…")]`, `[NavigationReference(…)]`, the EF Core `ToTable` / `HasColumnName` calls and the sync descriptors without escaping, so the generated file did not compile. All of these now escape the name, as the description attributes already did. A column name containing `{` or `}` likewise no longer breaks the in-memory sample seeder, whose sample values are interpolated strings
- **App — A schema-sync script no longer breaks when a table name contains `'`** — dropping a primary key or a foreign key whose constraint name is unknown is done through dynamic SQL, and the quoted table name is embedded in a string literal there (`EXEC('…')` on SQL Server, `EXECUTE '…'` inside a PostgreSQL `DO` block, `PREPARE` / `CONCAT` on MySQL, `EXECUTE IMMEDIATE '…'` on Oracle). A single quote in the name closed that literal, so the statement was malformed at best. Each dialect's identifier helper now has `QuoteForDynamicSql`, which quotes the name and then escapes it for the literal, and every such site goes through it

- **App — A PostgreSQL sync script no longer breaks when a table name contains `$$`** — the `DO` blocks that drop a primary key or an unnamed foreign key were dollar-quoted with a fixed `$$` tag, and dollar quoting ends at the tag text itself, so a name holding `$$` closed the block and everything after it became top-level SQL (escaping the literal does not help — it doubles `'`, which has nothing to do with where the block ends). The tag is now chosen after the body is built, deterministically: `$$` while it does not occur in the body, then `$q$`, `$qq$` and so on until it does not. A script for a name without `$$` is byte-for-byte what it was
- **App — A name or description containing a line break no longer breaks out of a SQL comment line** — `--` comments run to the end of the line, so a line break inside a name put the rest of it on a line of its own, where it read as SQL to execute. Every place that writes diagram text into a `--` comment now folds line breaks and control characters to a single space: the many-to-many note of both DDL generators, SQLite's table and column description comments, and the skip and heading comments the sync scripts write — including SQLite's table-rebuild heading, which matters most because the SQLite executor sends the whole script as one command

- **Generated code — A generated XML doc comment no longer breaks on a name containing `<` or a Unicode line separator** — when a table or column carries no description, five generated `///` summaries fall back to naming it (the entity class, its column properties, the value object, the edit model and the in-memory seeder), and two of those wrote the name unescaped. A name holding `<` produced malformed XML (CS1570 once you build with `GenerateDocumentationFile`), and one holding U+2028 walked out of the comment line altogether. All five now go through the same XML escaping the description text already used
- **App — Mermaid and DBML exports no longer break their line structure on a name containing a line break** — both formats put one declaration per line, so a line break inside a table name, a column name or a constraint name split the declaration and the remainder was read as a new one. Names and labels are now folded to a single line on the way out
- **App — A DBML description or constraint name containing a backslash now survives the round trip** — the export escaped `'` but not `\`, so a backslash of your own and one the escaping had added were indistinguishable and the import gave back the wrong text (`a\\b` came back as `a\b`). Backslashes are now doubled on the way out and both escapes are undone in a single pass on the way in
- **App — The Claude Code chat no longer starts a new session on every turn when `claude` was installed through npm** — a `.cmd` shim is launched through `cmd.exe`, and `cmd` cuts the shim's `%*` expansion at the first line break, discarding the rest of that argument *and every argument after it* without an error. QuickER's system prompt is multi-line, so it arrived truncated to its first line and the `--model` and `--resume` that followed it vanished: the conversation could not be continued, the model choice was ignored, and nothing reported a problem. The system prompt now travels in a temporary file passed as `--append-system-prompt-file` — a path holds no line break — and an argument containing one is refused outright rather than silently truncated, on both the `claude` and `codex` launch paths. An installation that resolves to `claude.exe` was never affected, and neither was mock **project** generation through a `.exe`. The same fix removes the truncation of multi-line prompts in mock project generation on shim installations

- **Generated code — A property added to a generated base or to an entity's own `partial` is no longer treated as a column** — the runtime worked out what a column was by exclusion (anything readable and writable that was neither a navigation nor declared on the runtime base), so a read-write property added to the `EntityBase` extension surface, or to a `partial class CustomerEntity` of your own, became a column that does not exist: it went into INSERT / SELECT / UPDATE and failed against a real database with "Invalid column name", while the in-memory backend stayed green. A property is a column only when it carries `[Column]`, which the generator applies to every generated column, so such an added property now stays out of the SQL, out of `HasSameValues` / `GetValueHashCode`, and out of the in-memory column copy. It still rides the JSON path (`ToJson`, `Clone`, the remote transfer), which reads the public properties — add `[JsonIgnore]` to keep it out of that too. A `Query()` predicate that references such a property now fails on the SQL dialect backends with `NotSupportedException` instead of emitting the nonexistent column (the in-memory backend evaluates the predicate as ordinary C#). EF Core is outside this fix: its conventions map every public read-write property, so under `GenerateEfCoreRepositories` an added property still needs `[NotMapped]`. To make an added property a column, give it the standard `[Column("<an existing column>")]` naming a column no generated property already maps: that is the opt-in
- **Generated code — `ValidateUniqueAsync` no longer queries the database for a row marked for removal** — every other read of the validation state skips a removed row (`Validate`, the error collection, and the check among the siblings), but the database check did not, so a duplicate value on a row that was about to be deleted returned `false` with nothing in `CollectErrors`: a save blocked with no error to show for it. A removed edit model now returns `true` without querying. The error store is untouched, so undoing the removal has the next check judge the row again
- **Generated code — A sync run no longer loses the server changes its own upload stepped over** — the upload wrote the version the server had just stamped on the row it sent into the local mirror, and the download's resume point is the highest mirrored version in the table, so that one row's new version stood above every server change still waiting to come down. Those changes were then below the resume point for good: not in that run, not in the next one, not ever. Anything uploaded while the server had unfetched changes could trigger it — one offline edit was enough to lose an unrelated row's update permanently. The version an upload earns is now recorded in `quicker_sync_ack` instead — a per-row receipt that no resume point is derived from — and written to the mirror by the download when the row arrives in version order. The receipt is also what a further edit of that row is replayed against while its echo has yet to come down, so such an edit is not reported as a conflict with a version this same client wrote

- **Generated code — A binary-column upload no longer reserves storage for a length the host is going to refuse** — the `PUT {prefix}/{entity}/{column}` endpoint handed the declared `Content-Length` straight to the write, and a write reserves that length before it reads anything (SQLite allocates a `zeroblob` of exactly that size first). The host's request body size limit, meanwhile, only fires once the body is actually read, so a request that declared a huge length and sent no data at all ran the reservation before the limit could stop it. The declared length is now compared against the limit before the write runs, and an oversized declaration is answered with a 413 carrying the same `RemoteError` body every other classified rejection does. A group mapped with `allowUnboundedUploads: true` - or a host that has lifted the limit - has no limit to compare against, so the declaration passes through as before
- **Generated code — An invalid paging argument on a named query is now a 400 instead of a 500** — the remote endpoint of a query that pages passed `Take` and `Skip` on unchecked, and the query pipeline rejects `take <= 0` and `skip < 0` with `ArgumentOutOfRangeException`, so a value the caller got wrong surfaced as an unhandled server-side failure: HTTP 500, a server log entry and an `OnServerError` call, for something no part of the server got wrong. Any client that can reach the endpoint could raise that alert path at will. Both values are now checked where the request is read - beside the required-field and concurrency-mode checks - and reported as a 400 whose `RemoteError.Type` is "BadRequest". Valid values behave exactly as they did
- **Generated code — A conflict reported under `Collect` no longer has its local row overwritten by the same run's download** — the run reported the disagreement and then applied the server's row over the local one anyway, which left the journal entry describing a row whose content was now the server's; the next run uploaded the server's own values back to it, and the local edit was gone with nothing to show that it had been. The download now stops at the first row whose local change is still unsent, and the tables after it in foreign-key order are left for the next run too (see the Changed entry below)
- **Generated code — An upload interrupted part way no longer leaves journal entries for changes the server already took** — entries were removed in one batch at the end of the run, so a failure anywhere before that left entries for changes that had reached the server. The next run replayed them: a version-guarded update then failed against the row this same client had written, reporting a conflict with nothing to resolve, and a last-write-wins replay put a stale local row back over a newer server one. Each entry is now removed the moment the server takes it
- **Generated code — `SyncConflictPolicy.ServerWins` now restores every row it discards, not just the ones the server happens to have changed** — the documented behaviour was that the local change is discarded and the download overwrites the row with the server's, but the implementation only dropped the run's journal entries and left the rest to the download, which carries a row only when its version has moved since it was last mirrored. A local edit to a row nobody else had touched therefore survived the very run that was told to discard it, and with its entry gone no later run corrected it: the local database silently kept content the caller had explicitly asked to throw away. Each discarded entry's row is now read back from the server and written over the local one, so a row deleted locally comes back as well; a key the server no longer holds has nothing to apply and is left to the delete propagation, which means such a row stays as it is when `PropagateDeletes` is off. The restored row keeps its own mirrored version rather than taking the server's, so the download's resume point does not move past changes this device has not fetched yet. Each applied row is recorded in the acknowledgements instead, which is what a later local edit to it reads its original version from — without that, a row restored under a server version the download has already passed would never be reached again, and editing it would be replayed as a row the server has never seen and reported as a conflict against the device's own copy

- **App — A table created by a schema sync now carries its unique constraints** — the four sequential-DDL dialects (SQL Server, PostgreSQL, MySQL, Oracle) wrote only the primary key into the `CREATE TABLE` of an `AddTable` difference, so a table the DDL generator would have created with its UNIQUE constraints came out without them when the same diagram was applied through a sync instead — silently, with no difference item to notice and no warning to read. The constraint lines of a `CREATE TABLE` (`PRIMARY KEY` then `UNIQUE`, the synthesized `UQ_{table}_{columns}` name included) are now built by one shared helper that the DDL generator and all four sync script builders call, so the two paths cannot drift apart again. SQLite was never affected: its rebuild-based sync already wrote the unique clauses
- **App — A MySQL sync script no longer drops a foreign key nobody asked about** — dropping a foreign key whose constraint name is unknown looks that name up with `SELECT … INTO @fk`, and MySQL leaves a user variable untouched when the query matches no row, so the second and later drops in one script re-used the name left behind by the previous lookup. `@fk` is now set to `NULL` before each lookup, as `@pk` already was on the primary-key side. Two further gaps in the same lookups are closed: both searched the connection's default database whatever schema the table named, so a qualified table found the constraint of a same-named table elsewhere or none at all, and the foreign-key name was written into the `DROP` statement without doubling a backtick it might contain. The foreign-key lookup also orders by constraint name now, so a child and parent joined by two foreign keys drop a predictable one
- **App — A line holding only `GO` or `/` inside a string literal no longer splits a sync script** — SQL Server runs its batches by splitting on a `GO` line and Oracle its statements by splitting on a `/` line, and neither splitter tracked whether it was inside a string literal, a quoted identifier or a block comment. A description carrying such a line (descriptions may contain line breaks) therefore cut a statement in two: a syntax error on SQL Server, and on Oracle — where DDL commits implicitly — a partially applied sync. Both splitters now follow their dialect's literal and comment rules, the way MySQL's already did

- **Generated code — Clearing an edit-model collection no longer leaves the elements it had set aside marked for deletion** — removing an existing element sets it aside as a deletion target and marks it `Removed`, and adding that very instance back cancels the deletion and restores the state it had before. `Clear()` released the tracking list without restoring anything, so after `Remove` → `Clear` → adding the same instance back, the element sat in the collection still marked `Removed` with nothing left to match it against, and the next save deleted the row. `Clear()` now restores each set-aside element to its pre-removal state before releasing the list; everything else it did — resetting the tracking, releasing ownership, the position notifications — is unchanged
- **App — The MCP `generate_ddl` tool no longer writes to an output path that is not a `.sql` file** — the tool wrote the DDL script to whatever path it was handed, so an agent driving the stdio MCP server could overwrite any file of any kind through it. The path must now end in `.sql`, and its parent directory must already exist rather than being created silently — that last part is the rule `create_diagram` already follows (the extension restriction is `generate_ddl`'s own). The write is also atomic now, so an interruption leaves the previous file intact instead of a half-written script. Writing to a `.sql` file is unchanged, its BOM-marked UTF-8 encoding included

- **App — External change detection no longer stops for the rest of the session** — the watcher that notices another program editing the open diagram (the stdio MCP server, an editor, a sync client) did not listen for its own error event, so a burst of changes large enough to overflow the operating system's notification buffer left it silently dead: the file kept changing and QuickER never noticed again, and only reopening the file brought detection back. The watcher now re-establishes itself when that error arrives, and compares the file's content once on the way back up so that a content change made while it was down is reported too (a deletion or rename in that window is not)

- **App — A file saved immediately before the machine loses power no longer comes back empty** — every save writes the new content to a temporary file and swaps that into place, but the write itself only reached the operating system's cache, so the swap could become durable while the content behind it had not. The temporary file is now flushed to disk before the swap. The scope of the guarantee has not widened: whichever of the two contents survives a crash is a complete one, never a half-written file (which of the two survives is still up to the operating system)

- **A failing MCP tool call is now reported as an error rather than as ordinary output** — the MCP servers (`quicker mcp` over stdio, and the built-in chat's own MCP endpoint alike) returned the failure text as a successful result, so an external agent had to read and interpret the message to tell whether, say, `add_entity` had added anything at all. Failures now set the protocol's `isError` flag; the message text itself is unchanged

- **App — Saving no longer overwrites a file another program changed, without asking first** — when the open file changes on disk and you have no unsaved edits, QuickER reloads it by itself; but that reload declines a corrupted file, a document saved in a newer format, and a property whose type does not match, leaving nothing behind but a five-second status message. The document stayed clean and the content QuickER remembered stayed the old one, so the next Ctrl+S wrote over the other program's work without a word — and the check that runs *after* a save compares against what QuickER itself just wrote, so it could never notice. A save that targets the file currently open now compares the file on disk beforehand and asks before overwriting it; cancelling leaves both the file and your unsaved changes as they were. Saving to a new or to a different file is unaffected, and picking the same file through **Save As** counts as the same file, letter case included

- **App — A document saved in a newer format is no longer written back in this version's format without asking** — opening one already warns that data this version cannot represent will be lost, but it is lost only from what QuickER holds in memory: the file keeps it until something overwrites the file. Since the file itself had not changed since it was opened, the comparison above had nothing to report, so the next save quietly rewrote it in the current format. Saving the diagram — Save and Save As — now reads the version of the file it is about to overwrite and asks first if that file is in a newer format (this covers saving the diagram file itself; exports such as JSON export, where you pick the destination each time, are unaffected). Because it is the file that is checked and not what QuickER remembers, the question also comes up after the diagram has been replaced wholesale (the path stays with the document), after restarting QuickER, and when the file was written in a newer format by something else entirely — and it stops once the file is in this version's format

- **App — A diagram file that uses one identifier for two tables or two columns is refused instead of being loaded** — such a file can only come from editing the JSON by hand, and it used to load without complaint and then make saving impossible: Ctrl+S failed every time, the automatic recovery save swallows its own errors and so never succeeded either, and switching the target DBMS with a duplicated column identifier ended the application — its emergency save failing for the same reason, losing everything since the last successful automatic save. Loading now fails with a message naming the tables, the columns and the duplicated identifier, so the file can be fixed by hand; nothing is renumbered automatically. The check sits on the one path the editor, the MCP server, the CLI and the restore of the last session's work all load through. Identifiers of relationships, unique constraints and named queries are not checked, because nothing refers to them

- **App — A diagram file that cannot be read says which kind of problem it has** — a JSON object with the same key twice, and a property whose type does not fit the format, both escaped the classification and reached the caller as a bare failure, so the message could say no more than that the file could not be read; they are reported as invalid JSON now. A document whose `Version` is zero or negative is refused as not being a diagram, rather than being read as a document older than the first release

- **A Codex sign-in URL that is not a web address is no longer handed to the operating system** — the URL returned by `codex app-server` was opened through the shell, which starts whatever application is registered for the URL's scheme, so a `file://` or custom-scheme address would have started something other than a browser. Only `http` and `https` addresses are opened now; anything else is reported in the chat status line instead
