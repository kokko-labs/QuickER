# Changelog

*English | [日本語](CHANGELOG.ja.md)*

This file records changes that affect QuickER users. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/) (see [CONTRIBUTING.md](CONTRIBUTING.md) for the versioning rules during 0.x and the release procedure).

## [Unreleased]

### Breaking changes

#### Code generation dialog & CLI

- **`quicker generate` now resolves column types in the diagram's dialect when `--provider` is omitted** — the default used to be `sqlserver` regardless of the diagram, so a PostgreSQL diagram generated without `--provider` had its types resolved by SQL Server's rules (`timestamptz` became `string`) with only an informational note. The default is now the diagram's target DBMS, falling back to `sqlserver` only when the diagram has none, which is what the MCP `generate_csharp` tool already did. Two cases that used to succeed now fail before generation: a PostgreSQL, MySQL or Oracle diagram generated with the QuickER Repository enabled (`GenerateRepositories`) and no `--repository-dialects`, because the Repository dialect is derived from the provider and only `sqlserver` and `sqlite` are supported (the old default silently produced a SQL Server Repository); and a diagram whose target DBMS names no supported dialect, which now names the diagram's value and asks for `--provider`. Scripts that relied on the old default for a non-SQL Server diagram should pass `--provider sqlserver` explicitly. `scaffold` and `reverse` have no diagram to read and keep `sqlserver` as the default
- **`quicker reverse` no longer overwrites an existing output file without `--force`** — the output is a new schema-only diagram, so overwriting an existing diagram silently dropped its layout, named queries and IDs. When `--out` names a file that already exists, `reverse` now writes nothing and exits with code `2` (the same code `generate` uses when it refuses to overwrite); pass `--force` to overwrite. Previously only a diagram saved in a newer format was protected this way
- **A named query whose type token is a fixed-length string or binary without a length now fails generation** — `fixedstring`, `ansifixedstring` and `fixedbinary` mean nothing without one, and every dialect that needs a length writes them out as a type that does not exist. Give the token a length (for example `fixedstring(10)`), which the diagnostic message now says as well. Variable-length tokens (`string`, `ansistring`, `binary`) are unaffected: a parameter constrains no length, so they keep resolving as before
- **MySQL unsigned integer columns now generate unsigned C# types** — `unsigned` used to be stripped during type resolution, so an `int unsigned` column became `int` and reading a value above the signed range threw `OverflowException`. `tinyint` now becomes `byte`, `smallint` `ushort`, `mediumint` and `int` `uint`, and `bigint` `ulong`, matching what both MySqlConnector and the EF Core provider return (measured against MySQL 8.4). `mediumint` also used to fall through to the "unknown type" case and become `string`; it is now `int`. The property type on generated entities changes for such columns, so code that uses them may need updating. A signed `tinyint(1)` is still `bool`; an unsigned one is not, because MySQL drops the display width from unsigned `tinyint` and the driver returns `byte`

#### Generated code

- **PostgreSQL `time with time zone` columns now generate `DateTimeOffset`, and array columns generate an array of the element type** — `timetz` used to become `TimeSpan` and an array column (`integer[]`, `varchar(20)[]`, `bigint[]`) used to become `string`. Both were types the driver never produces, so such a column could be neither read nor written; because an entity is materialized from all of its columns at once, **one such column made the whole table unusable through EF Core**. The property type on generated entities changes for these columns, so code that uses them may need updating — but no working code can break, because none of it worked at run time.

  | Column type | Before | After |
  |---|---|---|
  | `time with time zone` / `timetz` | `TimeSpan` (read threw `InvalidCastException`) | `DateTimeOffset` |
  | `timestamp(n) with time zone` | `DateTime` (the time zone was dropped) | `DateTimeOffset` |
  | `integer[]` | `string` (read threw `InvalidCastException`) | `int[]` |
  | `bigint[]` | `string` | `long[]` |
  | `varchar(n)[]` | `string` (silently, with no diagnostic) | `string[]` |

  Two limits come with this. Writing a `timetz` value whose offset is not UTC needs the column type spelled out, which QuickER does not generate (EF Core is for connecting to an existing schema); add it in the generated `QuickErDbContext`'s `OnModelCreatingPartial` if you need it. And array columns are left out of edit models and value objects, and the length of an array's elements is not carried into the generated code; generation names the affected columns. A UNIQUE constraint containing an array column is likewise left out of the edit model's duplicate check (the repository still checks it before saving).

#### Import and export

- **A DBML line that cannot be interpreted is now reported instead of being dropped** — every unrecognized top-level line used to be skipped in silence, so a `Table` line that did not match the expected form took its whole table with it. Such a line now fails the import, naming the line and its number. Blocks that only carry information QuickER cannot represent (`Project`, `Enum`, `TableGroup`, `TablePartial`, `Note`, `records`) are still skipped, so files written by other tools keep importing; a relationship written in a form QuickER does not read (the block form `Ref { ... }`) is rejected by name rather than skipped, because skipping it loses the relationship
- **The DBML export now writes standard DBML, and DBML in QuickER's earlier form no longer imports** — dbdiagram.io and the DBML parser (`@dbml/core`) rejected the old output, and standard DBML with its settings after the endpoints did not import into QuickER. A constraint name is now written as a named Ref (`Ref FK_Orders_Customer: Customer.Id < Orders.CustomerId`) instead of a `note` setting, referential actions go in a settings block after the endpoints (`[delete: cascade]`) instead of right after `Ref:`, and a foreign key column no longer carries a `ref` setting without a value, which DBML does not define. Table, column and constraint names that are not made only of ASCII letters, digits and underscores, Japanese names included, are now quoted (`"Order Details"`), because DBML tools reject them bare. A `Ref` line written the old way (settings before the endpoints) now fails the import with its line number; to import such a file, move the settings block after the endpoints and turn `note: 'FK name'` into the Ref's name (`Ref "FK name": …`). A `ref` setting without a value is skipped, so a column's foreign key marker now comes only from the `Ref` line it is the child side of; the export lists a marker on a column that no relationship uses among the information the format drops

### Added

#### Code generation dialog & CLI

- **Generation now names the columns whose C# type fell back to `string`** — a DB type the type catalog cannot parse (`geometry`, `hierarchyid`, `sql_variant` and the like) becomes `string` so that generation keeps going, which the generated code gave no hint of. Such columns are now listed at generation time as "table.column (original type text)" on all five dialects. The generated code itself is unchanged
- **Generation now names the columns declared with a negative scale** — `numeric(10,-2)` (PostgreSQL) and `NUMBER(10,-2)` (Oracle) make the database round values (1234 is stored as 1200), and the generated code carries no precision or scale for such a column: no digit validation on the value object, no Precision/Scale on `[SqlColumnType]`, and no `HasPrecision` in the EF Core model. Neither fact was visible from the generated code. Such columns are now listed at generation time as "table.column (original type text)". This is a note rather than a warning, because a negative scale is written on purpose. The generated code itself is unchanged
- **Generation now warns when a NOT NULL computed column cannot be written on the mirror side** — in a multi-target build (SQL Server as the server, SQLite locally) or with bidirectional sync, the side that does not evaluate the expression gets an ordinary column, and generated code never writes it, so inserting a row there fails on the NOT NULL constraint. The affected columns are now named at generation time, with the two ways out: make the column nullable in the diagram (the mirror then keeps NULL for it) or leave the table out of synchronization. The note the DDL carries next to such a column says the same
- **`quicker generate` now warns when `--provider` differs from the diagram's target DBMS** — generation does not convert column types, so a SQL Server diagram generated with `--provider postgresql` has its types read as written under PostgreSQL's rules. The command still generates, with the exit code unchanged, but now prints a warning on stderr that points to the GUI's target DBMS switch, which converts the types first

#### Generated code

- **A composite primary key's own column order is now recorded in the generated entity's `[DbTableMeta]`** — only for a table whose key order differs from the order the key properties are declared in, as `[DbTableMeta(PrimaryKeyOrder = new[] { "B", "A" })]` with the property names in key order. The generated code of a diagram that states no order, has a single-column key, or keeps the declaration order does not change. It appears only where `[DbTableMeta]` is written, that is, when data annotations are generated. The runtime package `QuickER.Runtime` gains a `PrimaryKeyOrder` property on `DbTableMetaAttribute`

#### Import and export

- **Importing C# code now restores a composite primary key's own column order** — the import reads the `PrimaryKeyOrder` above. An order that does not name exactly the key columns (an unknown property, a column that is not part of the key, a duplicate, or a missing key column) is not adopted: a warning is shown and the key comes back in declaration order. A merge import into an existing diagram keeps the order the current diagram states explicitly when the code states none, as code generated by an older version cannot, as long as the key still consists of the same columns. A table for which the current diagram states no order is imported without one. Until now the round trip put the key back in declaration order, and the next database sync rebuilt the primary key
- **DBML now round-trips a composite primary key's own column order** — a table whose key order differs from its column order is written with the key as a `(col, …) [pk]` index at the top of its `Indexes` block instead of the `pk` column setting, and the import reads that index as the key's columns and order. DBML from other tools that declares the key this way is read as well (the index name is discarded). Column `pk` settings and a `[pk]` index that name different columns, a second `[pk]` index, or a column listed twice in the index are rejected at that line rather than guessed at
- **The Mermaid export now reports that a composite primary key order is lost** — Mermaid has no syntax for the order, so it cannot be carried; the omissions listed when the export finishes include it whenever a table's key order differs from its column order
- **DBML import now reads inline references, `primary key`, and many-to-one `Ref` lines** — these are standard DBML that dbdiagram.io writes all the time, and they used to be skipped in silence, so the primary keys and relationships they declared vanished from an import that reported success. A column setting `ref: > users.id` is read as the `Ref` line with that column on the left; for one-to-one (`-`) the column carrying the `ref` is the foreign key, following DBML's rule, which is the opposite of a `Ref` line. `primary key` is read like `pk`, and a `Ref` line with `>` is read as one-to-many with its sides swapped. An inline reference that cannot be read, such as a schema-qualified one, is reported with its line number

#### AI chat & mock generation

- **AI answers in AI chat and AI mock generation are now shown as formatted Markdown** — headings, emphasis, inline code, code blocks, lists, tables, quotes, horizontal rules and links are formatted once a response ends, and an answer in progress stays as text. A "Markdown" check box in the chat header switches back to the original text, for example to copy it; each window remembers the choice, and it is on by default. Only `http` and `https` links can be clicked (they open in the default browser), images are not loaded and show their alternative text, HTML is shown as written, and an answer nested too deeply to format is shown as text

### Changed

#### Generated code

- **With a schema-qualified table name, the generated unique constraint name now matches the DDL** — for a unique constraint that has no name, the generated entity's `[UniqueConstraint(…, Name = …)]` was synthesized from the raw table name, so for `dbo.Orders` it said `UQ_dbo.Orders_code` where the DDL creates `UQ_dbo_Orders_code`. Importing C# code restores that `Name` as the constraint's own name, so a round trip gave a previously unnamed constraint a different name. **Code generated before this fix still restores the old name**, so regenerate it before importing when you use schema-qualified table names

#### AI chat & MCP

- **A failed response from Claude Code, Codex or GitHub Copilot now says what happened and what to do, in the display language** — these backends showed the raw error text (an exception message or the English text the CLI reported) as the whole message, while the API key connection already explained its failures. A failed response now starts with a summary naming the backend and suggesting to send again and, if it keeps failing, to check the connection status, followed by the original text on a `Details:` line, so the cause stays visible. A failure the backend gives no reason for shows the summary alone. Only an interrupt you asked for completes without a message: a cancellation from anything else is now shown as a failure instead of looking like an interrupt
- **An AI CLI installed as a `.cmd` shim is no longer launched when its path contains `%`, and for Copilot also `!`** — `cmd` would expand such a path as an environment variable (and `!` under delayed expansion, which QuickER cannot turn off for the process the Copilot SDK starts), so the program actually started could differ from the one found on `PATH`. The launch now fails with a message naming the path. Codex and Claude Code are also started with delayed expansion turned off explicitly, so a `DelayedExpansion` setting in the registry no longer applies to them
- **Relationships created by the tools now get the same default constraint name as ones created in the GUI** — the built-in chat's and MCP's `add_relationship` joined the raw table names, so a schema-qualified name produced `FK_dbo.Orders_dbo.Customers` while creating the relationship by hand produced `FK_dbo_Orders_dbo_Customers`. All three now produce the latter. **Constraint names already saved in a diagram do not change.** The synthesized name of an unnamed unique constraint that `get_diagram_summary` shows now matches the DDL as well
- **The ER diagram tools now refuse names and types that the other tools could not reach** — in the built-in chat and over MCP, `add_entity` and `set_entity_property` refuse an empty table name or one that matches another table's name ignoring case (changing only the case of a table's own name is still allowed), `add_column` refuses a column name that matches another column of the same table ignoring case, and `add_column` and `set_column_property` refuse an empty `data_type`. The tools find tables and columns by name ignoring case and take the first match, so a second table or column with such a name could not be edited or removed by any tool, and an empty type stopped DDL generation for the whole diagram. A refused `set_entity_property` or `set_column_property` call changes none of the properties it was given
- **`add_relationship` refuses a second foreign key over the same column pairs** — a relationship between the same parent and child with the same column pairs, in any order, was added again under a different constraint name, so the DDL carried the same foreign key twice. The call now fails and names the existing constraint. Many-to-many relationships and relationships without column pairs are not affected, since neither becomes a foreign key in the DDL
- **`set_query` no longer saves SQL for a query that does not use it, and warns about inputs the chosen implementation ignores** — `sql` given with `implementation` `dsl` or `manual` used to be saved and then never used; it is now dropped, as the GUI's query definition dialog does, with a warning. A `condition` given with `sql` or `manual` (already dropped) now gets a warning too, and so does `implementation` `sql` with no SQL for any dialect, which generates a method to be written by hand in every dialect. The call still succeeds in all three cases
- **Tool results now report what a successful call did not do** — `get_diagram_summary` starts with the target DBMS (`Target DBMS: sqlserver`). `set_column_property` says when it ignored `is_nullable` = `true` on a primary key column, instead of reporting the nullability as updated. `add_relationship` with the columns omitted adds a note when the parent has no primary key or not every key column could be paired with a child column, since the generated DDL then has no foreign key for the relationship or an incomplete one
- **The MCP code generation tools now return English results on any OS language, and warn when `provider` differs from the diagram** — `generate_csharp` shares its messages with the CLI, so on a Japanese Windows the English result carried Japanese lines (the generated file list, the counts, generation diagnostics and settings errors). The results of `generate_csharp` and `generate_ddl` are now in English throughout, like the other tools on the server; the CLI keeps following the OS language. When `provider` names a dialect other than the diagram's target DBMS, the result now begins with a warning that column types were not converted. The message about hand-edited files also now says the list follows it (it said "listed above" while the list came below)
- **Mock generation on Copilot no longer auto-approves a command that references a URL or redirects into a file, even when all of its paths are under the output folder** — the rule for commands with readable paths only checked that every path is under the output folder, so `curl https://… -o .\x.ps1`, `git clone https://… lib\bar` and `dotnet build … > build.log` were approved. Such a command now also has to reference no URL and redirect nothing into a file, which a command without readable paths already had to. A refused command is listed in the progress log. Copilot's own file tools, which the agent uses to write files, are not affected
- **In mock generation, `save_screen` keeps a screen's entity declarations when none of the declarations it receives are valid** — a non-empty `entities` array whose elements were all unusable (an empty name, an element that is not an object, or no valid C/R/U/D letter) was treated like an empty array and cleared the screen's existing CRUD declarations. Such an array now leaves them as they were and the tool result carries a warning saying so. Only an explicit empty array clears them
- **`add_relationship` now warns when the parent columns you name cannot carry a foreign key** — in the built-in chat and over MCP, naming parent columns that are neither the parent's primary key nor one of its unique constraints (a part of a composite key, or an ordinary column) succeeded without a word, and most databases then rejected the `FOREIGN KEY` when the generated DDL was applied. The relationship is still added, since MySQL accepts such a key on indexed columns, but the result now says so and how to fix it

#### DB sync & DDL

- **A difference in nullability on a computed column no longer produces an `ALTER COLUMN`** — the nullability of a computed column follows from its expression, which the diagram does not model and therefore cannot impose on a database. Without this, taking the way out above (making the column nullable in the diagram) would have made the sync offer a meaningless `ALTER COLUMN` against the database the diagram was imported from. Differences in the column's type are still detected
- **The sync confirmation now shows the tables to rebuild and the notes in a scrollable details area** — until now everything was joined into the text of a standard message box, so with many items the OK and Cancel buttons went off the screen, and that happened on the most destructive confirmation of all. The text now holds a summary (how many tables are rebuilt, and against what), and the details area lists every table and every note. A confirmation with nothing to list is still a one-sentence message box

#### Diagram editing

- **A new relationship now pairs the child's primary key column when it is the foreign key** — in an identifying relationship such as order lines keyed by `(OrderId, LineNo)`, `OrderId` is both part of the child's primary key and the foreign key to the order, but primary key columns were never candidates, so the relationship came out without that column pair. A child primary key column is now paired when its name is the one derived from the parent table (`OrderId` / `order_id` for `Orders`), and, for a parent with a composite primary key, when it has the same name as a parent key column (`(TenantId, ProjectId)` → `Tasks(TenantId, ProjectId, TaskId)`). A name that merely equals the parent's single key column (both called `id`) still does not pair a child's primary key, and a self-reference never pairs one. This applies to creating a relationship in the GUI, to `add_relationship` without columns in the built-in chat and over MCP, and to the columns a Mermaid import infers; a name derived from the parent now also wins over a column that only carries a foreign key marker
- **Deleting a table also deletes the named queries defined on it** — this applies to deleting in the GUI, one table or several, and to `remove_entity` in the built-in chat and over MCP. A query left behind belonged to no table, so neither the query definition dialog nor `remove_query` could reach it, and every code generation warned about it. In the GUI, undoing the delete brings the queries back in their original order. Over MCP nothing brings them back; the tool result names the queries it removed

#### Import and export

- **An Excel definition document written in a format this version cannot read is no longer imported** — the document embeds its format version, but the import never looked at it. A document carrying information a future version added is now reported instead of imported, so nothing it could not read is silently dropped (the same stance the diagram file takes towards a newer format). Older documents that carry no version are imported as before
- **Importing Mermaid or DBML into a diagram that is not empty now always asks first** — the import replaces the whole diagram with new tables that are arranged automatically, so even when the file has exactly the same tables and columns, the hand-made layout, colors, memos (and, for Mermaid, descriptions) and the undo history are lost. QuickER used to skip the confirmation when the structure matched and there were no queries or unsaved changes. Re-importing an Excel definition document still skips it when nothing changes, because that import keeps the layout

#### Diagram files

- **A diagram file that leaves a required name or type empty (`null`) is no longer loaded** — a table name, a column name, a column type or a query name written as `null` used to be replaced with a default (an empty name, the type `int`), and saving over the file then made that replacement permanent. Such a file is now refused by name and location instead, in the GUI, the CLI and the MCP server alike, because filling the value in would change what the diagram means. A `null` in an optional string such as a description or a memo is still read as empty text. Only a hand-edited file can carry these, since nothing in QuickER writes one

### Fixed

#### DB sync & DDL

- **A table name with leading or trailing spaces no longer makes DDL and sync disagree about constraint names** — for an unnamed foreign key or primary key, the DDL turned a leading space into `_` (`FK__Orders_…`) while sync trimmed the table name before building the name (`FK_Orders_…`), so a sync could try to drop a constraint that did not exist. DDL, sync, generated code and the tools now all trim the name first and then replace dots and spaces with `_`. Only a diagram whose JSON was edited by hand can have such a name
- **A stale script can no longer be run after recalculating the diff fails** — when a recalculation failed, the previous diff and script stayed and could be run. The same happened when the re-read after a failed run (which follows partial application on MySQL / Oracle) failed because the connection dropped: once the connection came back, the old script could be run again. A failure now clears the diff and the script, and nothing can be run until a recalculation succeeds
- **When running the sync script ends with an exception, the error is now shown and the diff is re-read** — when the run was interrupted by an exception (a dropped connection, for example), it was only reported in the status line and the previous diff and script stayed, so on MySQL / Oracle the same script could be run again after a partial application. As with a failed run, the error is now shown in a dialog and the diff is re-read (if the re-read fails too, nothing can be run until a recalculation succeeds)
- **Other operations are no longer accepted while the diff is recalculated or the script runs** — running during a recalculation sent an old script, and closing with Esc or the button during a run returned to the caller while the DDL kept running outside the dialog. While either is in progress, Recalculate Diff, Execute, Select All, and Deselect All are disabled, and the dialog cannot be closed while the sync script runs (it can be closed during a recalculation)
- **When generating the script fails during a recalculation, the reason now stays in the status line** — it was written and then immediately replaced by the count of differences, so on first opening the dialog (the most common path) the reason never showed
- **Select All and Deselect All no longer regenerate the script once per item** — the plan and script were rebuilt for every item, so the more differences there were, the slower it got, quadratically. They are now rebuilt once per operation

#### Diagram editing

- **A relationship to a table with a composite primary key now pairs each key column with the right child column** — when you create a relationship, or call `add_relationship` from the built-in chat or MCP without columns, or import Mermaid, QuickER pairs every primary key column of the parent with a child column it infers from the names. It looked for a column named after the parent table (`OrderId`) before a column with the key column's own name, so with a composite key the second key column picked the same `OrderId` and was dropped (`Orders(OrderId, Revision)` got a foreign key on `OrderId` alone, which the DDL then rejected), or the first one took the wrong column (`Projects(TenantId, ProjectId)` paired `TenantId` with the child's `ProjectId`). With a composite key, columns named exactly like a key column are now matched first, and a child column already chosen is no longer offered to the next key column. A single-column primary key is paired as before
- **A relationship created by hand no longer takes a constraint name another relationship already uses** — the default name `FK_{child}_{parent}` can be the same for two different pairs of tables when the table names contain `_` (child `A_B` with parent `C`, and child `A` with parent `B_C`, are both `FK_A_B_C`), and the DDL then failed at the second `ADD CONSTRAINT`. A name already used by another constraint in the diagram now gets the child's foreign key column names appended, and then a number, which is what `add_relationship` in the built-in chat and MCP already did. Without a clash the name is the same as before, and undoing the creation is still one step
- **A long description no longer makes the diagram stall while it redraws** — laying out a wrapped description searched for each line break by measuring text up to the whole remaining paragraph, so the cost grew with the square of the description's length (measured at 200px wide: 65 ms for 10,000 characters, 2.3 s for 50,000). The search now brackets the line length first and measures only around it, which is 7 to 47 times faster (measured: 9 ms and 49 ms) and wraps at exactly the same places
- **Typing in a table's memo no longer takes one undo per keystroke** — the memo box committed on every character, so undoing five characters took five presses of Ctrl+Z and the undo history filled up with them. It now commits when you leave the box, like every other field in the property panel, so what you typed is one step. Collapsing the panel still commits what you typed
- **Auto-arranging a large diagram on a grid no longer freezes the window** — "Grid" searches for an arrangement with fewer crossing relationship lines, but the search was exhaustive and grew roughly with the cube of the table count (measured: 6.2 s at 200 tables, 88.7 s at 400; creating a diagram from a database, from the AI or from C# code waits for the arrangement to finish). Pairs that cannot possibly interact are now ruled out before the check, which made it 4 to 9 times faster, and the search has a cap on how many checks it may make: when the cap is reached it keeps the improvements found so far and stops (measured: under 1.5 s at every size). The cap counts checks rather than time, so the same diagram always comes out the same way. Diagrams that stay under the cap (measured up to about 200 tables and 200 relationships) are arranged exactly as before; above it more crossings remain (measured at 400 tables: 223 crossings became 868, total line length +40%, occupied area unchanged)
- **Creating a relationship stops when its starting table leaves the diagram** — after you picked the first table, deleting it, undoing its creation, or opening another diagram (including the automatic reload after an outside change) let you create a relationship from a table that was no longer in the diagram. The line followed no table, and for a deleted table the saved relationship pointed at a table that did not exist. Relationship creation is now cancelled as soon as its starting table leaves the diagram
- **Pairing a new relationship's columns now recognizes more plural table names** — the foreign key column is found by turning the parent table's name into `{singular}_id`, and the singular was guessed by always dropping `es` after `s`, `z`, `ch` or `o`, so `courses` became `cours`, `warehouses` `warehous`, and `purchases` and `responses` likewise. The expected `course_id` was then not found, and pairing fell back to any column marked as a foreign key, which could be the wrong one. Where the ending does not decide whether to drop `es` or only `s`, both spellings are now tried. This applies when you create a relationship, to the `add_relationship` tool of the built-in chat and the MCP server, and to the relationships a Mermaid import creates

#### Diagram files

- **A change written to the open diagram file while QuickER was reading it is no longer missed** — after opening a file, or reloading it because another program changed it, QuickER read the file a second time to record what it had loaded. If an AI agent or another tool wrote to the file between the two reads, QuickER recorded the new contents as the ones it had loaded: the diagram on screen stayed the old one, marked as having no unsaved changes, and the next Save overwrote the other program's change without asking. QuickER now records exactly what it read, so such a change is picked up and reloaded like any other change from outside
- **Opening, importing, and reloading a large diagram after an outside change is faster** — when the whole diagram was replaced, every added relationship reapplied the foreign key marks and edit locks to every column of every table, so the time grew with relationships times tables (measured: 0.26 s for 200 tables and 300 relationships, 1.9 s for 500 tables and 800 relationships). This now happens once at the end of the replacement (measured: 0.05 s and 0.13 s). The resulting diagram is the same as before
- **The confirmation for an outside change no longer stacks** — when the diagram file changes outside QuickER while you have unsaved changes, QuickER asks whether to reload. If the file changed again while that dialog was open, a second confirmation opened on top of it. A change that arrives during the dialog is now checked once against the file after the dialog closes, and you are asked again only if the file changed further (if you chose to reload, the latest content is already loaded and you are not asked). A change notification for content that is already loaded now does nothing (it used to cancel a table drag)
- **Watching the diagram file for outside changes no longer stops for good when its folder is briefly unreachable** — when a network share or USB drive dropped for a moment, the watch could not be restarted and stayed off, so outside changes went unnoticed for the rest of the session. QuickER now keeps retrying (at most every 30 seconds) and resumes watching once the folder is back, picking up any change made while it was off. The status bar says once that watching stopped and once that it resumed
- **Overwriting a diagram file whose `"Version"` is `null`, an object, or an array now asks first** — a version value QuickER cannot read (`"2"` or `2.0`) already made it ask before overwriting, but these three were treated as a file with no version and overwritten without asking. Only a hand-edited file can have one
- **An outside version you chose to keep editing over is no longer ignored after you save** — when the diagram file changed outside QuickER while you had unsaved changes and you chose to continue, QuickER remembered that version so as not to ask about it again. It kept remembering it after you saved, so if the file was later put back to exactly that content (for example by checking out an older commit), QuickER neither asked about the change nor asked before the next Save overwrote it. Saving, opening and reloading now forget it
- **A status bar message no longer disappears right after it appears** — a message is cleared after 5 seconds, but the timer of an earlier message could still clear a newer one that had just been shown

#### Settings

- **Settings written by a newer version are no longer lost when an older one saves** — settings files are saved by writing the whole object back, so any key this version does not know about disappeared on the next save. Unknown keys, including ones nested inside a section, are now carried over (the display language, AI settings and code-generation settings all go through the same store). Keys inside arrays are still not carried over. The connection profiles file (`connections.json`) does not go through this store and is unchanged
- **A momentary read failure no longer resets the settings to their defaults** — saving settings is a read-modify-write, so one failed read wrote the defaults back and took the display language, the update check and the code-generation settings (output path, namespaces, target DBs and the rest) with it. When the file cannot be read, QuickER now starts from the defaults but **does not save over it**, and resumes saving as soon as a read succeeds (the auto-save re-reads the file each time, so in practice the next save recovers on its own)
- **A corrupted settings or connections file is now moved aside before being overwritten** — to `{file name}.corrupt`, once only (a later corruption does not overwrite it, so what remains is the copy closest to the last good state). Previously such a file was simply overwritten with the defaults, leaving nothing to investigate afterwards

#### Distribution

- **Installing an update no longer cuts QuickER off mid-session** — once you accepted an update at startup, QuickER downloaded it in the background and then ended itself the moment the download finished, without the usual shutdown. Changes you made while it downloaded were not written to the recovery file, and the processes started by AI chat and mock generation were left running. QuickER now asks again when the download finishes whether to restart now. Restarting closes QuickER the normal way before the update is applied; choosing Cancel applies the update the next time you close QuickER. Either way the update is applied only after a normal exit

#### Crash handling

- **The crash report no longer disappears while you are reading it** — if another error occurred while the crash report dialog was open, QuickER ended the process on the spot and the report vanished unread. An error that occurs while the dialog is open is now ignored, and QuickER exits after you close the dialog
- **A crash now stops the processes started by AI chat and mock generation before exiting** — a crash skips the normal shutdown, so codex, copilot, claude, and dotnet processes were left running. They are now stopped before the crash report dialog appears; while an AI conversation is running, the dialog can take a few seconds to show
- **The crash log no longer drops part of what went wrong** — an exception that bundles several failures (an unobserved asynchronous failure always takes this form) was logged with only its first failure; every one is now logged. And when two records picked the same file name at the same instant, the later one overwrote the earlier; each is now kept in its own file

#### Startup & restart

- **Restarting after you switch the display language no longer leaves QuickER closed** — the restart launches a new QuickER partway through shutting down, while the old one still held the "already running" marker, so the new one could conclude QuickER was already running and quietly exit. The marker is now released just before the new QuickER is launched
- **Starting QuickER while it is running as administrator now explains why it cannot start** — when a QuickER with different privileges was running, a normal start could not check it and ended without showing anything (only a crash log was written). It now tells you to switch to the window that is already open, or close it and start again
- **Starting QuickER again now brings the window that is already open to the front** — a window behind other windows only flashed in the taskbar

#### Database import & generated code

- **Computed and generated columns are now imported as read-only and left out of generated writes** — a SQL Server computed column, a MySQL / PostgreSQL / SQLite generated column or an Oracle virtual column used to be imported as an ordinary column, so every INSERT / UPDATE the generated repository issued against that table failed at runtime. The import now marks the column and warns that the expression is not carried into the diagram, generated code excludes the column from INSERT / UPDATE on every backend (EF Core mode maps it as store-generated), generated DDL notes next to the column that the expression must be added by hand, and generation reports the excluded columns. A SQLite generated column used to be missing from the import entirely, and a diagram whose primary key is a computed column is now refused at generation time
- **SQL Server tables whose names differ only in letter case no longer merge into one entity** — in a database with a case-sensitive collation, `Dup` and `dup` collapsed into a single entity with both tables' columns mixed together and no warning. One table is now kept and the other is skipped with a warning, the same way the other dialects already behaved
- **SQLite virtual tables (FTS5, R*Tree and the like) are no longer imported as broken ordinary tables** — a virtual table and its shadow tables used to appear as entities full of BLOB columns. They are now excluded from the import, and each virtual table is reported once
- **Disabled constraints are no longer imported as if they were enforced** — a SQL Server foreign key turned off with `NOCHECK CONSTRAINT` used to become a relationship in the diagram even though it enforces nothing. It is now skipped and reported. A key added `WITH NOCHECK` but currently enabled is still imported, because it is enforced from then on. Oracle already skipped its `DISABLE`d constraints, but did so silently; those are now reported the same way
- **SQL Server temporal tables can now be imported and written to** — the history table is excluded and reported instead of arriving as a duplicate entity, and the current table's period columns (`GENERATED ALWAYS AS ROW START / END`) are treated as columns the database produces, so generated code leaves them out of INSERT / UPDATE. Writing to such a table used to be impossible: the period columns were sent like ordinary columns and SQL Server rejected the statement because they are `GENERATED ALWAYS`. Period columns declared `HIDDEN` work the same way, because generated code lists its columns explicitly rather than relying on `SELECT *`
- **A generated mapper no longer fails to compile when a computed column is a NOT NULL value type** — with `datetime2`, `int`, `decimal` and the like, generating edit models produced code that did not compile (CS0266: `System.DateTime?` cannot be converted to `System.DateTime`). An edit model's confirmed value is always `Nullable<T>` for a value type, and the three kinds of column that are only assigned when an input is present (row version, computed, excluded unbounded binary) were missing that unwrap. Row version and excluded binary columns are always `byte[]`, so only a computed column — which can have any type — could reach it. Diagrams without a computed column, and those whose computed columns are reference types, generate byte-identical output
- **A SQLite database whose table name contains a dot can be imported again** — the import quoted such a name as if the dot were a schema qualifier, which made the `PRAGMA` calls a syntax error and failed the whole import
- **A SQLite foreign key whose parent table does not exist is now reported** — SQLite does not check the parent table when a table is created, and such a key used to vanish from the diagram without a word
- **A partitioned MySQL table is now reported the way a PostgreSQL one already was** — the diagram does not model partitioning, so DDL generated from it creates the table unpartitioned; the import now says so instead of staying silent
- **A SQLite primary key that allows NULL is now reported** — in a rowid table, any primary key other than a single column declared exactly `INTEGER` can hold NULL. The import still corrects such a column to NOT NULL (the diagram and the editor always treat a primary key that way), but it now names the columns it adjusted, because existing rows with a NULL key can make a later sync fail while copying the data across. Only the columns that were actually adjusted are named: a key whose columns are already declared `NOT NULL` is left alone
- **A string or binary column with no length is no longer written out for SQL Server, MySQL or Oracle** — switching a diagram to one of those dialects used to produce DDL that MySQL and Oracle refuse to run, while SQL Server quietly created a one-character column. Such a column is now listed as unconvertible, so a length can be given before switching. C# reverse engineering reports the same case per column instead of expanding the token, and generated entities now record the original spelling in `[DbColumnMeta(..., NativeType = "...")]`, so code generated by QuickER still round-trips
- **MySQL `bit(n)` (n greater than 1) and `year` columns now map to `ulong` and `int`** — both used to fall through to the "unknown type" case and become `string`, so reading such a column from generated code threw. `bit(1)` is still `bool`, the counterpart of the `tinyint(1)` convention
- **An Oracle table with more than one `INVISIBLE` column now imports those columns in a fixed order** — Oracle gives such columns no ordinal, so they came after the visible columns in whatever order the database returned them. They now follow the visible columns in the order they were created

#### Code generation dialog & CLI

- **A query that references a deleted column is now reported in the query definition dialog** — references from the sort order, a projection field or a parameter to a column that no longer exists could be confirmed with OK and were only reported at generation time (which skips that query with a warning). The dialog now names the query and the item and keeps OK disabled
- **The query definition dialog now stops a query that code generation always rejects before you confirm it** — it used to leave these rules to generation, so a reserved method name such as `GetById`, a parameter named `Query`, an invalid or duplicate parameter or field name, a result type name used by another query, or paging on a single row was accepted and then reported as an error at every generation. The dialog now runs the generator's own checks and shows the generator's message
- **The "exclude unbounded binary columns" setting is no longer saved while it is hidden** — switching DB access back to "none" or to EF Core hides the row, but a checkbox ticked earlier was still written back to the settings file. Besides the columns QuickER repositories read and write, the setting also drives **whether an EditModel treats such a column as required**, so a hidden tick changed the generated code even in configurations that generate no QuickER repository: a NOT NULL unbounded binary column was left out of the edit model's required inputs (required only on a new row) and its mapper assigned it only when a value was supplied. In those configurations such columns are now required like any other column. While the row is hidden the value is only dropped from the file, not from the screen, so choosing QuickER repositories again brings the original tick back. The sync-support checkbox follows the same rule
- **`--repository-dialects` with a value that names no dialect is now an error** — commas or spaces only produced an empty list, which skipped the "derive a single dialect from the provider" fallback and quietly emitted SQL Server code with exit code 0 even for `--provider sqlite`. A shell variable that failed to expand in CI hits this
- **Interrupting `quicker scaffold` with Ctrl+C during the schema import now exits with code `130`** — the import treated the interruption as an import failure, printed "Failed to import the schema from the database" and exited with `1`, while every other point of the CLI exits with `130`. A timeout raised by the database driver is still reported as an import failure
- **`quicker scaffold` now reports a mistake in `--config` before connecting to the database** — the settings file was read only after the whole schema import, so a mistyped path or an invalid value was found only after a possibly long import. The exit code and message are unchanged; warnings about unknown keys in the settings file now come before the import warnings on stderr
- **The MCP `generate_csharp` tool now reports every settings-file error the same way** — a missing settings file, invalid JSON or a value of the wrong type returned `Error: …` and dropped the warnings already collected, such as unknown keys. These now return `C# code generation failed: …` followed by those warnings, as an unsupported Repository dialect already did

#### Import and export

- **Printing a very large diagram at actual size no longer produces an unusable page** — at actual size the paper is the diagram itself, so a diagram with tables placed far apart asked for a page over 1,000 inches on a side, which no PDF or XPS output can produce (their limit is 200 inches). Such a diagram is now reported with its actual size before the print dialog opens, offering to print it scaled to fit one page instead; cancelling prints nothing. Diagrams within the limit are unaffected (an auto-arranged diagram of 1,000 tables measures 100 x 61 inches)
- **Exporting a very large diagram as PNG no longer fails** — the rasterizer refuses anything past its own size limit, so a diagram big enough simply could not be exported as an image (the error said nothing about size). PNG is now capped at 100 million pixels in total: a diagram above that is scaled down to fit, keeping its aspect ratio, and the completion dialog reports the full size and the size actually saved. SVG has no such cap, so export SVG when you need the full resolution
- **DBML now carries names that contain spaces or symbols** — export writes such a table or column name as a DBML quoted identifier (`"Order Details"`). Without the quotes a table name containing a space did not match the `Table` line's form and the table vanished from the import without a word, while a column name broke at the first space and the rest ran into the type (`Order Date date` became the column `Order` of type `Date date`). Names made only of ASCII letters, digits and underscores are written exactly as before
- **DBML no longer mangles a type that contains a space or brackets** — `double precision` and `integer[]` are now quoted on export, as DBML's own rules require, and the import no longer mistakes the brackets of an unquoted array type for the start of the settings block (which turned `integer[]` into `integer`)
- **A `//` inside a DBML string is no longer treated as a comment** — a description holding a URL used to be cut at `//` and lost. DBML block comments (`/* ... */`), including ones spanning several lines, are now recognized as well, and keywords are accepted in any letter case (a lowercase `ref:` line used to fail to parse)
- **A DBML `Ref:` line written before the table it points at can now be imported** — DBML produced by other tools often groups the Ref lines at the top of the file, and in that order the whole import failed with "referenced table is not defined". Ref lines are now resolved once every table has been read; a line that references a table defined nowhere is still an import error reported with its line number
- **An Excel definition document with more than one foreign key between the same two tables can be read back** — a diagram with, say, a shipping address and a billing address both pointing at the same table exported fine but always failed to import, because duplicates were judged by the pair of table names alone. The check now includes the columns that make up the key; two rows that are identical down to their columns are still rejected
- **Mermaid no longer drops part of a column name that contains a space** — a Mermaid attribute line separates type, name and marker by spaces, so `Order Date` used to lose everything after the space. Such names are now folded to `_` (the same treatment the type already gets) and reported among the information the format cannot carry. If folding would collide with another column in the same table, the name that needs no folding keeps its spelling and the folded one gets a number
- **Importing Mermaid no longer gives several relationships the same constraint name** — a Mermaid relationship line must carry a label, and the import took the label as the constraint name. QuickER writes `relates` for a relationship that has no name, and Mermaid from other tools repeats verbs such as `has`, so after an import several relationships shared one name and the DDL failed at the second `ADD CONSTRAINT` on SQL Server, Oracle and MySQL. A label now becomes the constraint name only when it is a single word without quotes, is not `relates`, appears on no other relationship, and is not the name of a primary key or unique constraint. Any other relationship is left without a name, so it gets the default `FK_{child}_{parent}` from the DDL, unless that name is already taken, for example by a second relationship between the same two tables; then it gets the child's foreign key column names appended, or a number
- **Importing DBML or an Excel definition document no longer gives two unnamed foreign keys the same constraint name** — a `Ref` without a name, or a relationship row with an empty constraint name cell, was imported without a name, so the DDL named it `FK_{child}_{parent}`. Two such relationships between the same two tables (a billing and a shipping customer, for example) therefore got the same name, and the DDL failed at the second `ADD CONSTRAINT` on SQL Server, Oracle and MySQL. The import now applies the same rule as Mermaid: a relationship without a name keeps no name while the default is free, and otherwise gets the child's foreign key column names appended, or a number. Names written in the file are kept as they are
- **Importing C# code no longer gives two unnamed foreign keys the same constraint name** — two `[NavigationReference]` attributes without a `ConstraintName` between the same two tables were both imported without a name, so the DDL named both `FK_{child}_{parent}` and failed at the second `ADD CONSTRAINT` on SQL Server, Oracle and MySQL. Both the CLI's `quicker reverse` and the GUI's merge import now apply the same rule as the other imports. A merge import into a diagram that already holds such a pair, as an earlier import made it, fixes the pair too. Names written in the code, and names a merge import keeps from the current diagram, are kept as they are
- **The DBML export no longer invents a foreign key for a relationship without a column mapping** — such a one-to-one or one-to-many relationship was written with the first column of each table, and since the import takes the columns on a `Ref` line as the foreign key, re-importing it created a foreign key nobody had defined (usually on the child's primary key). It is now left out of the file and reported among the information the format drops, as is a many-to-many relationship to a table that has no columns, which used to make the export fail
- **DBML now carries a type that contains a double quote, and text that ends with a backslash** — a type such as PostgreSQL's quoted `"MyType"` is now quoted on export; written bare, the import took its quotes off and turned it into another type, or read the rest of the line as part of it. A note or index name ending with `\` (`'C:\\'`) followed by another setting no longer swallows that setting, and a composite foreign key whose quoted column names contain `)` no longer fails the import
- **The DBML export now reports computed columns** — DBML cannot mark a column as computed, so such a column comes back as an ordinary one; it is now listed among the information the format drops
- **Mermaid now carries table names that contain a space, and columns without a type** — a table name with a space was written bare, so a relationship line naming it could not be read and the whole import failed. Such names are now written in double quotes (`"Order Details"`), which Mermaid allows, and read back with the quotes removed; names Mermaid accepts bare, Japanese and `dbo.Orders` included, are written exactly as before. A `"`, `%` or `\` cannot appear even inside the quotes, so it is folded to `_` and reported. A column without a type used to be written as `id PK` and came back as a column named `PK` of type `id`; it is now written with the type `_`, which the import reads back as no type
- **Mermaid no longer writes types it cannot read back, and reports the ones it changes** — only spaces, parentheses and commas were folded, so a type such as PostgreSQL's quoted `"MyType"` broke the attribute line on import, and `enum('a','b')` produced invalid Mermaid. Every character Mermaid does not allow in a type is now folded to `_`, and a type the import cannot restore (`nvarchar(max)`, `double precision`) is listed among the information the format drops. Types it already wrote correctly, such as `decimal(10,2)` and `integer[]`, are unchanged
- **The Mermaid export now reports computed columns and a unique constraint hidden behind a foreign key marker** — a column carries one key marker and `FK` comes before `UK`, so a single-column unique constraint on a foreign key column (the one that makes a relationship one-to-one) was dropped without a word. It is now reported, as are computed columns, which come back as ordinary columns
- **Mermaid no longer breaks on a constraint name that contains a space or a symbol** — the export wrote the constraint name bare as the relationship label, so a name such as `FK orders customer` made the line invalid Mermaid, which neither Mermaid nor the import could read. Such a name is now written in double quotes, with a `"` folded to `_`; names Mermaid accepts bare are written as before. Because the import never takes a quoted label as a constraint name, the export now reports relationship constraint names that would not come back as the same name: quoted ones, a name shared by several relationships, and a name equal to `relates` or to a primary key or unique constraint name
- **An Excel definition document can always be read back** — the export writes a relationship whose columns cannot be resolved with both column cells empty, and a table without columns as a detail sheet with no column rows, but the import rejected both, so such a diagram exported fine and then failed to import. Both are now read as they were written; two such relationships between the same tables are not counted as duplicates, and a row with only one of its column cells empty is still an error
- **Re-importing an Excel definition document no longer resets computed columns and the order and names of unique constraints** — the document carries none of these, so a merge import turned computed columns into ordinary ones, put a constraint's columns into table order (`UNIQUE (b, a)` became `(a, b)`), and replaced a constraint's name with the synthesized one. The merge import now takes them from the current diagram: a constraint over the same set of columns keeps its column order and name, and a matching column keeps its computed setting
- **Exporting onto the diagram file that is open is refused** — choosing the open diagram file as the export target (for example with Schema JSON) replaced it with the exported content, and because QuickER then saw its own write as an outside change, a diagram without unsaved changes was reloaded from it and lost its layout. The export now writes nothing and says to use Save for the diagram itself
- **Re-importing an Excel definition document that has lost its target database no longer switches the diagram to SQL Server** — a document saved again by another application (for example Google Sheets) can drop the property that records the target database; the import then fell back to SQL Server and switched the diagram to it without asking, while the column types stayed those of the original database. Such a document now keeps the current diagram's target database
- **The SVG export no longer writes characters XML does not allow** — a control character in a name, a type or a description (a line break pasted from Word is one) made the SVG unreadable to browsers and XML tools. Such characters are now written as a space
- **The date in the print header no longer depends on the system's regional settings** — it is always written as `yyyy/MM/dd HH:mm` in the Gregorian calendar; before, the separator followed the region and a Thai system printed the Buddhist year

#### DB import & connections

- **Saving a connection profile now asks before overwriting a different profile** — the save button picks its target by the profile name, so typing a name that an existing profile already had replaced that profile's server, user and saved password without a word, and with no way back. Overwriting a profile other than the one currently selected now asks first; saving over the profile you loaded is unchanged, and so is saving under a new name (which still creates another profile)
- **A momentary read failure no longer wipes every saved connection profile** — saving, renaming, and deleting re-read `connections.json` before writing it back, so another program holding the file for an instant turned into "read nothing, write nothing back" and every saved profile vanished without a word (only the orphaned secret files remained). Reads now tell "the file is missing", "the file is corrupted" and "the file cannot be read right now" apart: a transient failure is retried as persistently as the write side does, and if it still cannot be read the operation is **cancelled without writing anything** and reported in the status line
- **OK is disabled while a connection test is running** — the test cannot be cancelled, so confirming and closing left it holding the connection on its own, hitting the same database at the same time as the import or sync that started right after
- **The DB Sync dialog no longer restores a last-used connection from a different dialect** — sync fixes the target DB to the diagram's dialect, yet it still copied the host, file path and service name of the last connection into the fields. Those fields mean different things per dialect, so values that could not connect were left in place under a "restored" message
- **Saving with "Save password" ticked but the box empty now clears the tick as well** — no encrypted file is written for an empty password, so only the tick was stored and the dialog showed a password as saved when there was nothing to restore. Overwriting a saved password with an empty box now drops both the encrypted file and the tick
- **A connection profile can now be renamed** — the save button saves the current input under the name in the box, so typing a new name made a copy and left the old profile (and its saved password) behind. A "Rename" button next to it changes only the name of the selected profile, keeping its connection settings and its saved password; renaming onto a name another profile already uses asks first, the same way saving does
- **A saved password that merely could not be read for a moment is no longer deleted silently** — when the encrypted file could not be read or decrypted (another program holding it for an instant, or a file encrypted by another user or machine), it was treated like an unsaved password. Renaming the profile in that state wrote the empty password back and deleted the encrypted file. Renaming no longer touches the password at all. When the password cannot be read, the password box is left empty and the status line says so, and saving over that profile with the box still empty and "Save" ticked is refused (enter the password again, or clear the "Save" tick, and then save). Restoring the last connection reports an unreadable password the same way
- **A failure while writing connection profiles no longer closes the app** — saving, renaming, deleting, and recording the last connection on OK did not catch failures on the write side (a full disk, a failure to write or delete an encrypted file, and so on). The failure is now reported in the status line, and the list is reloaded from the file because the change may have been applied only partly. OK still goes ahead when the last connection cannot be recorded
- **A profile name with spaces before or after it now matches the existing profile of that name** — the lookup used the name with the spaces and the save used it without them, so adding a space slipped past both the overwrite prompt and the overwrite itself and left two profiles with the same name
- **Saving or renaming a profile no longer refills the fields from the saved values** — right after saving a profile without "Save" ticked the password box went blank, and right after renaming, unsaved edits in the fields reverted to the saved values
- **An invalid port is no longer replaced by the default port without a word** — values that were not numbers, or were 0 or less, were treated as the default port, so mistyping `1543z` could connect to a different instance on the default port (and, for sync, run DDL against a different database). Only an empty box now means the default port. A value that is not a number or is outside 1 to 65535 stops OK, the connection test, and saving the profile. Saving the profile now checks the command timeout the same way (until now only saving turned an invalid value into the default without a word)
- **The connection dialog now opens even when `connections.json` has a null list or null entries** — a file edited by hand into `"profiles": null` or similar closed the app as soon as the dialog opened. A null list is read as empty and null entries are skipped (they disappear on the next save)
- **Deleting a connection profile now asks with a warning** — the deletion removes the encrypted file of the saved password too and cannot be undone. It now uses the same level of prompt as overwriting a different profile

#### AI chat & mock generation

- **A second foreign key between the same two tables no longer gets the same constraint name from `add_relationship`** — the built-in chat's and MCP's `add_relationship` always named the relationship `FK_{child}_{parent}`, so the billing and shipping references from `Orders` to `Customers`, which the tool instructions tell the AI to add as separate relationships, both became `FK_Orders_Customers`. The DDL then failed at the second `ADD CONSTRAINT` in every dialect, and `remove_relationship` could never pick one of the two by name. A name already used by another constraint in the diagram now gets the child's foreign key column names appended (`FK_Orders_Customers_ShippingCustomerId`), and then a number if that is taken too. `add_relationship` also accepts an optional `constraint_name`; a name that a foreign key, primary key or unique constraint in the diagram already uses, ignoring case, is rejected. The tool result now reports the name. The first relationship between two tables keeps the name it got before
- **MCP tool calls sent in parallel no longer lose each other's changes** — agents such as Claude Code send several tool calls at once, and each editing tool reads the diagram file, changes it and writes it back. Two calls on the same file could therefore both report success while the later save erased the earlier change, and a call that read the file while another call was saving it could fail with a sharing violation. `quicker mcp` now handles the calls one at a time, the code generation tools included. Two processes writing the same file, such as two servers or the server and the GUI, are still last-write-wins
- **Removing a relationship over MCP now clears the foreign key marker on the child column, as the GUI does** — `remove_relationship`, `remove_entity` and `remove_column` took the relationship away but left the child column marked as a foreign key, so the diagram opened in the GUI or exported to Mermaid and the definition documents still showed an FK on a column nothing referenced. A child column that no longer belongs to any relationship now loses the marker, while a marker on a column that belongs to no relationship, such as one set by a DB import, is kept
- **`set_query` no longer saves a named query that code generation always rejects** — the tool checked the DSL, the raw SQL and the required arguments, but not the rules the generator enforces, so a query named `GetById` (whose method `GetByIdAsync` is a standard repository member), a parameter named `Query` or declared twice, a name that is not a C# identifier, a result type name used by another query, `scalar` with `dsl`, or `paging` on a single row was saved and then skipped with an error at every generation. The tool, in the built-in chat and over MCP, now runs the generator's own checks and refuses such a definition with the generator's message
- **`add_relationship` no longer turns an unknown `relationship_type` into one-to-many** — any value other than exactly `OneToOne` or `ManyToMany` became `OneToMany`, so `onetoone` created a one-to-many relationship and a misspelled value went unnoticed. The value is now matched ignoring case, and any other value is refused with the list of valid ones, in the built-in chat and over MCP
- **Interrupting an AI chat response during a tool call no longer breaks the conversation** — with the API key method, an interrupted tool call left the history inconsistent and every later message failed until "New conversation". The calls that did not run are now recorded in the history as interrupted, so the AI also knows which of its changes reached the diagram
- **The connection tabs, the API key connection settings and "New conversation" are disabled while a response is in progress** — switching tabs mid-response left the window unable to send anything, while the old response kept editing the diagram, and changing the provider, model, API key or endpoint took effect on the running response. Interrupt the response first; the "Interrupt" button stays available
- **A Codex crash or an unanswered interrupt no longer leaves the chat stuck as processing** — when the Codex App Server exits or its connection is lost, the turn now fails with a message, and when an interrupt request goes unanswered or fails while that turn is still running, the server is stopped by force. Both lose the conversation context, which the message states, and the next message starts a new conversation. Mock project generation on Codex now also fails right away instead of waiting out its 30-minute limit
- **A hand-edited `mock.json` with an invalid screen file name no longer ends the application** — opening such a mock folder is now refused as corrupted, and a failure while producing the single-HTML bundle or the design document is reported in the status bar instead
- **A failed save no longer leaves a mock folder that cannot be reopened** — `mock.json`, the screen HTML files and `style.css` were written by truncating the file and then writing it, so a crash or a full disk in the middle of saving `mock.json` left broken JSON, and the whole mock folder could no longer be resumed even though every screen was intact. They are now written in full to a temporary file and then swapped in. A change whose `mock.json` could not be written is also no longer kept in memory, where the next successful save would have written it after all, and the AI receives the failure as the tool's result
- **A hand-edited `mock.json` containing `null` no longer makes later steps fail** — a `null` title, name, description, transition or revision note is read as empty text, and a `null` item in a list is dropped, instead of failing later when saving a screen, resuming, or producing the single-HTML bundle or the design document

- **Resuming a mock no longer loses the note that the ER diagram has changed when the first message fails to send** — the folder's copy of the schema was updated before sending, so after a failed send (for example with no API key set) the next resume no longer told the AI that the diagram had changed. The copy is now updated only after the message has been sent
- **A mock design tool call whose arguments are not a JSON object, or that cannot write to the mock folder, now fails with a clear result** — the AI received the raw text of an internal exception instead
- **Links in the single-HTML mock export now reach the right screen** — a link with a fragment (`OrderDetail.html#items`) became `#OrderDetail#items` and opened the first screen instead, and so did a link to a screen whose name contains a space or non-ASCII characters, or whose case differs from the file name. The fragment is now dropped (the screen opens but does not scroll to the section inside it), and screens are matched after decoding the address and ignoring case. A link within a page (`#items`) also used to jump back to the first screen; it now keeps the current screen shown
- **The mock design document's transition diagram no longer breaks for a screen named `end.html`** — Mermaid read the node id `end` as a keyword. Every node id now starts with `s_` (for example `OrderList` becomes `s_OrderList`), so the ids in an existing `README.md` all change when it is next rewritten; the diagram looks the same
- **Saving a mock screen no longer warns about a link to a screen that another screen has already declared as a transition** — the check counted only the screen's own transitions as announced links, so every later screen whose shared navigation linked to a not-yet-created screen got "Link target … does not exist as a screen and is not declared in the manifest or transitions", even though an earlier screen had declared that transition. The transitions of every screen in `mock.json` now count. A link to a screen that no transition declares is still reported

Every screen file is its own origin, so a screen embedded in another with `<iframe src="Other.html">` could load external resources. The filter now covers every frame (with WebView2 Runtime 122 or later; the Evergreen runtime keeps itself up to date, and an older runtime keeps the previous behavior)
- **An embedded frame no longer changes which screen the mock preview thinks it shows** — moving within an `<iframe>` was treated like moving the whole page, so the screen list selected the embedded screen while the outer one was still shown, and the next refresh of that screen reloaded the wrong page
- **The mock preview no longer sets itself up twice** — opening a mock folder before the preview had finished loading registered every handler twice, so each blocked request and each navigation was handled two times
- **The mock design document now uses LF line breaks throughout** — a screen description or a mock title containing CRLF or a Unicode line separator carried it into `README.md`, and a line break in the title split its heading
- **A runaway AI chat response now stops at 50 tool round trips** — with the API key method, a response that kept calling tools could only be stopped by hand; a response that reaches the limit now ends as a failed turn with a message
- **A tool that already ran is no longer recorded as "not executed" with the API key method** — the activity notification was raised after the tool ran but before its result was recorded, so an exception from the subscriber (the UI) left a synthetic "was not executed" result in the history for a call that had in fact run. The AI would then redo the same operation, adding a table twice. The result is now recorded before the notification, and the notification itself is protected from the subscriber's exceptions
- **Pressing Interrupt right after a Codex response finished no longer loses the conversation** — interrupting a turn that has already completed makes Codex return an error (measured against the real app server: `no active turn to interrupt`), which QuickER treated as a failed interrupt and answered by stopping the App Server. That loses the conversation, so the next message starts a new one. No interrupt is sent when no turn is running, and a failure is no longer answered with a stop if the turn completed while the request was in flight
- **A tool that throws no longer leaves a Codex, Claude Code or Copilot response waiting forever** — the error now goes back to the AI as a failed tool result, and a tool response that cannot be delivered is reported in the status bar
- **The mock design document now survives awkward names** — a screen name containing a line break no longer breaks its heading, entity names differing only in case now share one CRUD column, and a screen file name containing parentheses no longer breaks its link

- **Closing the application now shuts down the AI back ends** — the Codex App Server, the Copilot runtime and a running Claude Code process are disposed on exit, with a three-second cap so a hung shutdown cannot stall the application
- **A failure during shutdown no longer leaves AI child processes running** — closing the application saves the chat and mock-generation settings before disposing the back ends, so one failed save (a full disk, a permission error, a file sitting where the settings folder should be) stopped the shutdown right there and left the Codex App Server, the Copilot runtime and `claude` / `dotnet` child processes behind, with no trace of why. Each step of the shutdown — interrupt, save settings, dispose the back ends, close the window — now runs independently: a failure is written to `%LOCALAPPDATA%\QuickER\shutdown-*.log` (separate from `crash-*.log`, since the application did not crash) naming the step, and the remaining steps still run. The same holds across feature modules: one module failing no longer keeps the others from cleaning up. The application now also exits once the main window closes, rather than once the last window closes: those AI windows hide instead of closing, so a window left behind used to keep the process alive with nothing visible on screen
- **Interrupting Codex just as a turn starts is now reported as an interruption, not an error**
- **Switching or resetting a mock-generation conversation now disposes the previous AI back end** — starting a new conversation, changing the mock folder or switching the connection method used to leave the old session's engine, including a CLI back end's resident child process, alive until the application closed
- **A tool that throws no longer fails the whole turn with the API key method** — the error is now returned to the AI as a failed tool result and the remaining tools still run, the way the Claude Code, Codex and Copilot back ends already behaved. Interrupting still ends the turn as before
- **Reconnecting to Codex now cleans up what the previous connection left behind** — after a dropped connection or a failed start, the exited (or not fully stopped) process, its reader loop and its standard input are still around. They used to be dropped on the floor as a new process was started on top of them
- **Closing the application right after switching a mock-generation conversation now waits for the previous session's engine** — the disposal of a session that has just been detached runs on the thread pool, and shutdown could not see it, so that back end's resident child process was orphaned, and switching several times in a row now waits for every detached session, not just the last one

A single read-only file was enough to make it fail, and a folder that is a reparse point without being a link (such as a OneDrive Files On-Demand folder) was treated as a link and not emptied. Read-only attributes are now cleared before deleting, links are told apart by their target rather than by the reparse-point attribute, and anything that still remains is added to the confirmation shown before the build for Codex and Copilot; if you cancel, the build does not run. The same link check now also lets the pre-build change detection look inside such folders instead of skipping them

The versions are now taken from the ones QuickER builds with (currently 10.0.12, 7.0.3 and 10.0.12), and a SQLite project also references `SQLitePCLRaw.bundle_e_sqlite3` 3.0.5

Both folders are now emptied before they are written again. If the mock folder you chose is one of them, sits inside one, or contains one (for example the `design/mock/` of a previous output), generation stops before writing anything, so the mock folder itself is never deleted

They now say `dotnet build <project name>.sln`

It is now reported like any failed run of the backend, and the log is written whatever happens. An error while starting the final build is reported as a failed build
- **Interrupting mock project generation now also stops the final build** — interrupting only stopped the AI's part of the run; a final build already under way ran to the end
- **Mock project generation with an API key now gives the model the repository's CRUD signatures, and keeps the build output it sends for the fix round to a bounded size** — the summary of the generated data layer listed only the per-table repository contracts, which inherit their CRUD methods (`GetAllAsync`, `GetByIdAsync`, `InsertAsync`, `UpdateAsync`, `DeleteAsync`, `SaveAsync`) from shared base contracts it left out, and it read a `record struct` as a type named `struct`. The base contracts are now included first, so they survive the summary's size limit. The fix round used to receive the whole build output; it now receives up to 8,000 characters with the error lines first
- **A large JPEG, GIF or WebP attachment that QuickER shrinks is now sent as what it is** — shrinking always produces a PNG, but the attachment kept the original type, so the API received PNG data labelled `image/jpeg` (or GIF, WebP) and rejected the message. The type is now taken from the shrunk data. Images that fit without shrinking are sent unchanged
- **Dropping a folder, or a file that cannot be read, on the chat no longer closes the application** — the attachment was read before anything was checked, so a folder, a missing file or a file locked by another program threw an error the window did not handle. These now show a message in the status line, and the other files you dropped are still attached. A file is also checked against a read limit of 32 MB before it is opened, instead of being read whole and then rejected (a multi-gigabyte file used to be loaded into memory first). The limit applies to images before they are shrunk, so **an image file larger than 32 MB is now rejected even if shrinking would have brought it under the 5 MB image limit**. For PDFs and other files the outcome is the same as before
- **API key chat errors are now explained instead of shown raw, and a network timeout is no longer mistaken for an interruption** — a request that timed out was reported like a response you had interrupted (no message at all), and other failures showed the provider SDK's raw text (for Anthropic, the status line followed by the JSON body). A timeout now says so, and HTTP errors from both OpenAI and Anthropic get the same explanation by status (invalid key, rate limit, server error and so on) with the provider's own message as the detail. Interrupting a response still ends it silently
- **Pasting with Ctrl+V while another program holds the clipboard no longer closes the application** — the AI chat and mock generation windows check the clipboard for an image on Ctrl+V, and when another program had the clipboard open the error escaped the key handler. That case, and a clipboard bitmap that cannot be decoded, now count as "no image", so the paste falls through to ordinary text pasting
- **Closing the application now also stops the processes the mock generation window started to check connection status** — the window keeps its own Codex, Claude Code and Copilot engines for the connection checks on its tabs, separate from the conversation, and closing the application did not dispose them, so a Codex App Server or Copilot runtime started for a check could outlive QuickER. They are now disposed as their own shutdown step, so a failure in an earlier step does not skip them. Closing can therefore wait up to 3 seconds longer when a disposal hangs
- **The mock generation window no longer freezes when you switch the connection tab or change the mock folder while a response is in progress** — doing so reset the conversation and detached the running session, so the end of the response never arrived and the window stayed busy: sending, starting a conversation and adding attachments remained disabled, and Interrupt had nothing left to stop. While a response is in progress, the connection tabs are now dimmed and cannot be clicked, and the mock folder box and its Browse button are disabled, until the response ends; the AI chat window already handled tab switches this way

Every such request now gets a JSON-RPC error reply: `-32601` for a method QuickER does not handle, `-32602` for parameters it cannot read, and `-32603` when handling it failed. Notifications still get no reply
- **Cancelling the run that started the Codex app server no longer leaves the connection deaf** — QuickER stopped reading the app server's output as soon as the run that had started it was cancelled (for example a stopped mock generation run), while the app server itself kept running and the connection still looked alive, so every later request waited 30 seconds and timed out. Reading now lasts as long as the connection, and a connection whose output can no longer be read is treated as closed: requests fail at once, and the next request starts a new app server
- **Checking whether you are signed in to Claude Code can no longer leave a `claude` process behind** — the sign-in check runs `claude -p` once; it had no time limit, and closing the application did not stop it, so a check that never returned stayed running after QuickER exited. Closing the application now stops it, and a check that takes longer than 60 seconds is stopped and shown as "could not check the sign-in status", the same as any check that does not finish

The write now falls under the request's 30-second limit and cancellation. A write cut off midway drops the connection, and the next request starts a new app server; a request cancelled while waiting to write leaves the connection alone. Closing the connection now stops the app server before closing its input: closing the input during a stuck write failed, and the app server was never stopped

A call that finds the connection lost now drops it: that call still fails, and the next message starts the runtime again and opens a new conversation. The previous conversation's context is not carried over

- **A Copilot turn that fails while sending no longer reports the failure twice**

A failed write used to escape as a send failure in the status bar; it now ends the turn as a failure in the chat, and the attachments are cleared as with any other failed turn

Empty responses are no longer sent back

- **When the first message of a mock generation conversation fails, the next message starts the conversation again** — the next message used to go out as a revision request, so the AI never received the schema or the screen list, and the message went to a connection that had not been set up

## [0.2.0] - 2026-09-24

Highlights of this release:

- A composite primary key now keeps its own column order across DB import, editing, DDL and generated code
- DB import now carries types and constraints more faithfully, and reports what it could not carry across
- The generated base classes can now be extended with `partial` in every output mode
- Fixed data loss in bidirectional sync, and safety issues in AI CLI launching and mock generation
- Check "Breaking changes" before upgrading (it includes where settings are now stored)

### Breaking changes

#### Distribution & settings

- **Settings and working state moved to `%LOCALAPPDATA%\QuickER`** — the old folder `%APPDATA%\QuickER` is no longer read, so the display language, saved connections (including passwords), API keys, code-generation settings and the recovery snapshot all start from their defaults on first launch. To carry them over, copy the old folder's contents into the new one before the first launch

#### Code generation dialog & CLI

- **The API reference language is now chosen with `ApiDocsLanguage` (CLI: `--api-docs-lang`)** — pick `English` / `Japanese` / `Both`, including a Japanese-only output. The old key `IncludeJapaneseApiDocs` and `--api-docs-ja` are not carried over, so replace them with `"ApiDocsLanguage": "Both"`. If the GUI had the Japanese version turned on as well, choose "Both" again
- **`generate` / `scaffold` and MCP's `generate_csharp` no longer overwrite generated files that were edited by hand** — when a `.g.cs` about to be replaced has been edited since it was generated, the CLI writes nothing, lists the files and exits with code `2`, and `generate_csharp` fails with the same list (the GUI asks instead). Reformatting and line-ending conversion do not count as edits, and files generated before this version are not checked. If a script or CI job rewrites the generated files after generating them, add `--force` (MCP: `force: true`) so regeneration keeps overwriting them. See [docs/code-generation.md](docs/code-generation.md#the-generated-file-header)

#### DB sync & DDL

- **What a column's type and name may contain is now restricted** — DDL generation and schema-sync script generation refuse, naming the place, a type carrying `;`, a quote, a comment marker or a line break, or one smuggling a column clause such as `int NOT NULL`. A line break or control character in a table, column, constraint or query name now stops every generator, including C# generation. Fix the type or the name in the affected diagram

#### Generated code

- **The runtime base types now carry a `Core` suffix** — `EntityBaseCore`, `EditModelBaseCore`, `ValueObjectBaseCore`, `IValueObjectCore`, `IRepositoryCore` / `IRemoteRepositoryCore`, each back end's `…RepositoryCore`, and `MapperBaseCore`. The names the generated code writes (`: EntityBase` and the like) are unchanged. Rename any code of your own that names a runtime type directly — a `where TEntity : EntityBase` constraint, an `is IValueObject` test — to the `Core` form
- **The message and display-name hooks are gone** — the edit model's `Customize…ErrorMessage` / `CustomizePropertyDisplayName`, the value object's `Customize…ErrorMessage` / `CustomizeDisplayName`, and the entity's `CustomizeDisplayName`. Replace wording through `EditModelMessages` / `ValueObjectValidationMessages` and a display name through `GeneratedDisplayNames.Resolve`, branching on the first argument each entry now receives (the property name or the display name) to vary it per type. The default wording is unchanged
- **The mapper's `includeRemoved` argument is now required** — pass `true` when building a graph to save and `false` when building one to display (the old default of `false` left deleted rows out of the save). Code that derived from `MapperBase<,>` by hand and overrode `CreateEntityCore` and the like should move that logic to `LoadColumns` / `CompleteLoad`
- **`CheckUniquenessAsync` is now declared on the common surface `IRemoteRepositoryCore<TEntity, TKey>`** — callers are unaffected. A hand-written test double or adapter implementing a repository contract now has to provide this member
- **With value objects on, same-named columns whose C# types differ are now a generation error** — a diagram where, say, one `payload` column is `varbinary` and another is `varchar` used to unify them into one value object with a warning, which made reading the narrower column throw at run time (or silently changed comparison semantics). Align the column types in the diagram, or rename the columns so they stay apart. A length or precision mismatch alone still warns and unifies as before
- **A column named `row_state` is now a generation error when edit models are generated** — the mapper's state transfer (`entity.RowState = editModel.RowState;`) binds by name, so such a column silently rerouted it to the column property and an edited row was saved as "unchanged". Rename the column in the diagram

#### Generated code

- **CRUD against a schema-qualified table (such as `sales.orders`) no longer fails at run time**
- **A property added through `partial` no longer lands in the SQL as a column** — only a property carrying `[Column]` is treated as a column now. In a configuration that uses EF Core, add `[NotMapped]` to an added property
- **A sub-second part of a date/time column is no longer lost when editing a different column** — the edit model's input string now displays it too
- **A blank input now clears a numeric, date/time, bool or binary column without value objects** — the confirmed value becomes null and the required check decides whether that is acceptable, the same rule the value-object columns already followed. It used to become a conversion error (a binary column, an empty array), so a nullable column could not be set back to NULL from the screen
- **A removed row with an empty required field no longer makes the save throw** — the mapper now skips a removed row's absent non-key values instead of requiring them, so `Validate()` returning true and the save agreeing are one and the same. The key is still required: a delete needs it
- **`AcceptChanges` now cleans up after saved deletions** — a row left in the collection by `MarkRemoved()` leaves the collection instead of coming back as an ordinary row, and a row set aside by `Remove()` becomes Added again, cascade descendants included, so adding the same instance back inserts the whole graph (it used to stay Removed and never be saved). A single cascade child stays Removed on the navigation property; assign null to it after the save
- **A reload during a row edit no longer lets `CancelEdit` roll the loaded values back** — the mapper's load abandons an in-progress row edit, so a cancel arriving afterwards is a no-op instead of restoring the stale pre-load snapshot
- **A value object over MySQL's `tinyint` (`sbyte`) now carries the comparison operators** — it used to derive from the equality-only base, so `OrderBy` on such a column threw at run time
- **A binary value object can now be created from a Base64 string through `TryCreateFrom` / `CreateFrom`** — the same notation the edit models accept. A malformed string is an ordinary conversion error, not an exception
- **A diagram with a column named like `foo_snapshot` next to `foo` generates again** — the generator kept reserving a per-column snapshot member that no longer exists (row-edit snapshots live in one base array), so the legitimate pair was refused as a collision
- **`HasErrors` now raises `PropertyChanged`** — a binding to it (a save button's IsEnabled, say) updates together with the errors, the way `HasChanges` always did
- **An edit-model child collection whose accessor returns null counts as empty** — validation, error collection and accepting changes no longer throw while a lazily initialized collection is still null (the same rule a single child always had)
- **`CreateEntity(editModel, includeRemoved: false)` now leaves a removed single cascade child out as null** — collection elements were filtered, a single child was not
- **A culture clone with a customized `LongTimePattern` renders date/time input strings with its own pattern** — the pattern cache is keyed by the pattern text now, so the clone no longer collapses onto the original culture's cached entry
- **`GetDeclaredInstances()` no longer exposes the registry's internal array** — casting the list back to an array and writing into it can no longer corrupt the shared set
- **Fixed a row whose deletion had been undone still being deleted on save after `Clear()` on an edit-model collection**
- **`ValidateUniqueAsync` no longer queries the database for a row marked for removal**
- **An invalid paging argument on a named query is now a 400 instead of a 500**
- **Fixed the server file's name drifting from the main file's when generating remote services with single-file output**
- **A projection query on a table under bidirectional sync no longer breaks the generated code** — the journaling decorator rebuilt the query methods a second time, the projection's DTO name tripped the build-wide duplicate check, and the delegating method silently vanished (CS0535)
- **A foreign key referencing a column that is not the parent's primary key now joins to that column in EF Core too** — the Fluent configuration emits an explicit `HasPrincipalKey`. EF Core's default silently joined it to the primary key: with matching CLR types, `Include` returned wrong rows; with differing types, the whole DbContext failed model validation. The other backends already joined by the column pair
- **A table without a primary key no longer makes the whole EF Core DbContext throw on first use** — it is excluded from the model (no DbSet, and navigations to it are ignored) and a Warning diagnostic names it: the same line the repository generation already draws for such tables
- **Two named queries on different tables can no longer collide on the server-side request record name** — the record is now named `{Repository}_{Operation}Request` (it is private; nothing on the wire changes)
- **`RepositoryDialects` written in a different letter case (`SQLite`) no longer produces uncompilable output** — the spelling is normalized to the canonical one instead of mixing one dialect's base classes with the other's usings without a diagnostic
- **An IN search on a nullable value-type column now compiles** — the parameter list is lifted to the nullable element type once at the start of the method (`IReadOnlyList<int>` against an `int?` column used to be a CS1929 in the generated code)
- **A named query whose DSL condition cannot type-check no longer breaks the whole generated assembly** — a condition whose emitted C# could never compile (`name > 'M'` ordering a string column, a `CONTAINS` on a numeric column, a fractional literal against an integer-backed value object, a parameter typed by a different column's value object, and the like) is now detected at generation time: the query is skipped with a warning naming the query, the table, the column and the offending operand, and every other query and file generates as before — the same treatment a dangling column reference already received. Nothing that used to compile is newly rejected (an integer column compared with `1.5` still widens to double, for instance). The MCP `set_query` tool still saves such a condition — the file-based server has no dialect type mapper to resolve column types with — and the generation-time warning is where it surfaces (noted in [docs/mcp.md](docs/mcp.md))
- **When repositories are not generated, the dialect selection (`RepositoryDialects`) no longer affects the output** — an EF Core-only run now produces byte-identical output with or without dialect dictionaries; `[SqlColumnType]` attributes and type-unification Info diagnostics used to leak in
- **Ordered comparisons (`<` / `<=` / `>` / `>=`) on a nullable value-object column no longer return NULL rows on the in-memory executor** — value-object comparison operators order null as the smallest value, so only the in-memory backend disagreed with SQL and EF Core (where NULL rows drop out); the emitted condition now carries an explicit "column is not null" premise
- **Equality against a `byte[]` column now matches by content (byte-wise) on the in-memory repository** — `Query()` predicates, DSL equality and uniqueness checks over `byte[]` members are covered; reference comparison combined with the store handing out cloned arrays meant nothing ever matched
- **Raw-SQL parameter matching is now case-sensitive (the same rule the runtime binder uses)** — `@CustomerID` used to match a declared `customerId`, so generation passed and every execution failed; it is now reported as undeclared (warning, that query skipped) plus unused (warning only)
- **A wildcard-less `NOT LIKE 'abc'` no longer matches NULL rows** — it used to fold into a negated equality where the column-side NULL compensation applies, departing from LIKE semantics (a NULL row matches in neither direction); chained prefix `NOT`s now also fold by parity
- **`ValidateUniqueAsync` no longer checks the CLR default (0) when a value-type constraint member has no input** — an unset value-type member cannot carry its unset state onto the entity, so the check now answers true without querying (it is advisory while the required check blocks the save)
- **Named-query definitions that would emit uncompilable code are now diagnosed at generation time** — a parameter named after a C# reserved keyword (`class` and the like), a parameter named `Query` (it hides the repository's `Query()` member), and a projection field named after its result type are generation errors; an IN-list lift variable colliding with a parameter name (`idsValues`) is renamed automatically
- **Numeric literals in DSL conditions accept ASCII digits only** — a full-width digit (`５`) used to pass straight into the C# literal and break compilation; it is now a condition validation error. String literals also escape characters the renderer would turn into real line breaks (U+2028 and friends)
- **Referential actions (ON DELETE) now map to EF Core's DeleteBehavior according to measured behavior** — everything but Cascade used to collapse into `Restrict`; now `SET NULL` → `SetNull`, `NO ACTION` → `NoAction` (client behavior identical to Restrict), and `SET DEFAULT` → `ClientNoAction`. On a SET DEFAULT diagram, deleting a parent through EF used to update tracked children's foreign keys to NULL instead of letting the database apply the default
- **A SQL local variable declared with `DECLARE` in raw SQL is no longer reported as an undeclared parameter** — multi-declarations (`DECLARE @a int, @b int`), initializers, and table variables are recognized; valid queries used to be skipped on the false positive
- **A condition or ordering left on a raw-SQL / manual query is now announced with a warning instead of being silently ignored** — the WHERE / ORDER BY belong to the SQL (or the implementation); generation continues
- **Consecutive blank lines inside a raw SQL verbatim literal are no longer rewritten at generation time** — user SQL containing blank lines inside a SQL string literal used to change silently (blank-line runs outside literals still fold to one, as before)
- **An extremely complex condition (more than 200 ANDs / ORs / NOTs / parentheses combined) is now a validation error instead of a process-killing StackOverflow**
- **A DSL projection that declares a non-nullable field over a nullable value-type column no longer breaks the whole generated assembly** — the combination always fails with CS0266, so the query is skipped with a warning (same treatment as the DSL type check)
- **The raw-SQL single-row body's local (`items`) no longer collides with a parameter of the same name** — it is renamed with a trailing `_` when taken
- **API reference (.g.md) table cells no longer show C# literal escapes (`\"` and the like)** — table-name and description cells now carry the diagram's raw values with only Markdown hardening (pipe escaping, newline folding)
- **An unsupported repository dialect combined with layered output is now reported as a diagnostic instead of an exception** (reachable only through direct library calls)
- **An invalid `RepositoryNamespace` no longer blocks generation in single-dialect non-split layouts where it is unused** — category namespaces are validated only in configurations that actually consume them (split mode, or the non-split multi-dialect layout)
