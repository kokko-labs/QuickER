# Changelog

*English | [日本語](CHANGELOG.ja.md)*

This file records changes that affect QuickER users. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/) (see [CONTRIBUTING.md](CONTRIBUTING.md) for the versioning rules during 0.x and the release procedure).

## [Unreleased]

### Breaking changes

#### Code generation dialog & CLI

- **The inputs that take a path name now reject more forms** — the layer folders, the output subfolders for code and the API reference, the API reference file name, the generated file name, the mock project name and screen file names, and the paths submitted by the API key backend are all checked by the same rules, which reject reserved device names (`CON` and so on), segments longer than 255 characters, whitespace at the start of a segment, a `.` or whitespace at the end of a segment, and segments containing `~` (whitespace around the whole value is still trimmed before the check). The error names the rule that was hit
- **An output file name (`OutputFileName`) that is not a single file name now fails before generation** — when the generated code goes to one file, a name with a folder part such as `sub/Foo.g.cs` was cut silently to `Foo.g.cs`, and a reserved device name (`CON`), a short-name alias (`a~1`) or a name whose derived files (the server implementation `.RemoteServer.g.cs`, the API reference) would pass 255 characters only failed while writing. Such a name now fails with an error naming the rule that was hit, as the API reference file name already did; choose the folder with the output folder and `CodeSubdirectory`. With output split by category the value is not used and is not checked

- **`quicker generate` now resolves column types in the diagram's dialect when `--provider` is omitted** — the default used to be `sqlserver` regardless of the diagram, so a PostgreSQL diagram generated without `--provider` had its types resolved by SQL Server's rules (`timestamptz` became `string`) with only an informational note. The default is now the diagram's target DBMS, falling back to `sqlserver` only when the diagram has none, which is what the MCP `generate_csharp` tool already did. Two cases that used to succeed now fail before generation: a PostgreSQL, MySQL or Oracle diagram generated with the QuickER Repository enabled (`GenerateRepositories`) and no `--repository-dialects`, because the Repository dialect is derived from the provider and only `sqlserver` and `sqlite` are supported (the old default silently produced a SQL Server Repository); and a diagram whose target DBMS names no supported dialect, which now names the diagram's value and asks for `--provider`. Scripts that relied on the old default for a non-SQL Server diagram should pass `--provider sqlserver` explicitly. `scaffold` and `reverse` have no diagram to read and keep `sqlserver` as the default
- **`quicker reverse` no longer overwrites an existing output file without `--force`** — the output is a new schema-only diagram, so overwriting an existing diagram silently dropped its layout, named queries and IDs. When `--out` names a file that already exists, `reverse` now writes nothing and exits with code `2` (the same code `generate` uses when it refuses to overwrite); pass `--force` to overwrite. Previously only a diagram saved in a newer format was protected this way
- **A named query whose type token is a fixed-length string or binary without a length now fails generation** — `fixedstring`, `ansifixedstring` and `fixedbinary` mean nothing without one, and every dialect that needs a length writes them out as a type that does not exist. Give the token a length (for example `fixedstring(10)`), which the diagnostic message now says as well. Variable-length tokens (`string`, `ansistring`, `binary`) are unaffected: a parameter constrains no length, so they keep resolving as before
- **MySQL unsigned integer columns now generate unsigned C# types** — `unsigned` used to be stripped during type resolution, so an `int unsigned` column became `int` and reading a value above the signed range threw `OverflowException`. `tinyint` now becomes `byte`, `smallint` `ushort`, `mediumint` and `int` `uint`, and `bigint` `ulong`, matching what both MySqlConnector and the EF Core provider return (measured against MySQL 8.4). `mediumint` also used to fall through to the "unknown type" case and become `string`; it is now `int`. The property type on generated entities changes for such columns, so code that uses them may need updating. A signed `tinyint(1)` is still `bool`; an unsigned one is not, because MySQL drops the display width from unsigned `tinyint` and the driver returns `byte`

#### Generated code

- **A diagram whose tables or columns give the same generated type name, or the name of a type the generated code already uses, now stops at generation with an error naming them** — a table name is given a suffix such as `Entity`, `EditModel`, `Mapper` or `Repository` only when it does not already end with it, so table `order_edit_model` next to `order` gave `OrderEditModel` twice, and `i_order`, `in_memory_order`, `ef_core_order` and `journaling_order` repeated a repository name of `order`. Table `raw_sql` gave `RawSqlMapper`, a runtime type, and column `sql_parameter` (with value objects) gave `SqlParameterValue`. These used to be generated without a word into code that did not compile. The check now covers every name the generator can emit, whatever the options and the output layout, so such a diagram is refused even where it happened to compile (split output keeps the EF Core and in-memory repositories in their own namespaces, and without Mapper there is no `RawSqlMapper` to clash with)
- **Two tables whose generated names differ only in case, such as `order_item` and `orderitem`, are now refused** — their remote endpoints are routed by these names (`OrderItem` and `Orderitem`), and routing ignores case, so every endpoint of both tables failed with an ambiguous match. The diagram is refused whether or not remote services are generated, so that turning them on later does not break it
- **Entity member names that differ only in case now stop generation with an error** — for example columns `user_id` and `userid` of one table (`UserId` and `Userid`), a column `isadded` next to the inherited `IsAdded`, or a column `orderlines` next to the navigation `OrderLines`. The JSON that reads and writes entities (remote services and SQL Server `Include` loading) matches property names ignoring case, so the generated code compiled but failed at run time with "The JSON property name ... collides with another property". The diagram is refused whatever the options, including where it used to work because neither remote services nor SQL Server `Include` was used. Rename the columns. Edit model members are still compared with case
- **A graph save now takes the children it deleted out of their parent's collection** — after a successful `SaveAsync`, the QuickER repositories, the in-memory repository and the remote client used to leave a child marked with `MarkRemoved()` in its parent's collection, while EF Core removed it. All four now remove it, as `EditModelCollection` does, and the child itself stays `Removed`. A child a save hook skipped stays in the collection, and a single cascade child stays on its navigation, which EF Core used to clear. Code that walked the collection after a save to find the deleted rows no longer sees them; keep your own reference to them before saving
- **EF Core: a raw SQL entity query that leaves out an unbounded binary column is now refused** — with `ExcludeUnboundedBinaryColumns`, `QueryBySqlAsync` on the EF Core repository accepted a SELECT without the excluded columns and left them in their unread state, and the next `UpdateAsync` or graph save wrote that state over the stored value: the blob silently became NULL or empty. EF Core writes every column when it saves an entity, so such a query now throws `InvalidOperationException` naming the missing columns; select them too, or use `SELECT *`. The QuickER repositories are unaffected, since their UPDATE leaves the excluded columns alone
- **A named query whose condition compares an integer column with a number outside the column's type is now skipped with a warning** — such as `tinyint_col = 256`, `smallint_col = 32768` or `unsigned_col = -1`. It used to be generated: C# reported CS0652 and the comparison was always false (or true), and on SQL Server the column-typed parameter raised an overflow exception when the query ran. The check was already there for value object columns and is now the same for plain columns. Hand-written LINQ is not checked; see [Code generation](docs/code-generation.md)
- **A projection whose result type name is already a type of the generated code is now refused** — a generated class or interface (`OrderEntity`, `IOrderRepository`, a value object such as `AmountValue`), a runtime type, or a library type the generated code uses by its simple name (`Task`, `Expression`). It used to produce code that did not compile. The error names the query and the type; the query definition dialog and `set_query` refuse it before saving
- **A DSL string match on a GuidKey column, other than an exact `LIKE` or `=`, is now skipped with a warning** — `CONTAINS`, `STARTSWITH`, `ENDSWITH` and a `LIKE` with `%`. It used to generate a file that failed to compile (CS1929)

- **PostgreSQL `time with time zone` columns now generate `DateTimeOffset`, and array columns generate an array of the element type** — `timetz` used to become `TimeSpan` and an array column (`integer[]`, `varchar(20)[]`, `bigint[]`) used to become `string`. Both were types the driver never produces, so such a column could be neither read nor written; because an entity is materialized from all of its columns at once, **one such column made the whole table unusable through EF Core**. The property type on generated entities changes for these columns, so code that uses them may need updating — but no working code can break, because none of it worked at run time.

  | Column type | Before | After |
  |---|---|---|
  | `time with time zone` / `timetz` | `TimeSpan` (read threw `InvalidCastException`) | `DateTimeOffset` |
  | `timestamp(n) with time zone` | `DateTime` (the time zone was dropped) | `DateTimeOffset` |
  | `integer[]` | `string` (read threw `InvalidCastException`) | `int[]` |
  | `bigint[]` | `string` | `long[]` |
  | `varchar(n)[]` | `string` (silently, with no diagnostic) | `string[]` |

  Two limits come with this. Writing a `timetz` value whose offset is not UTC needs the column type spelled out, which QuickER does not generate (EF Core is for connecting to an existing schema); add it in the generated `QuickErDbContext`'s `OnModelCreatingPartial` if you need it. And array columns are left out of edit models and value objects, and the length of an array's elements is not carried into the generated code; generation names the affected columns. A UNIQUE constraint containing an array column is likewise left out of the edit model's duplicate check (the repository still checks it before saving).

- **Oracle `TIMESTAMP WITH LOCAL TIME ZONE` columns now generate `DateTime`** — they generated `DateTimeOffset`, but ODP.NET returns this type as `DateTime`, so reading failed with `InvalidCastException`. The generated entity's property type changes for such columns, but **nothing that used to work breaks** (reading always failed before). `TIMESTAMP WITH TIME ZONE` still generates `DateTimeOffset`

- **PostgreSQL `interval` columns now generate `TimeSpan`, `inet` columns `System.Net.IPAddress`, and `cidr` columns `System.Net.IPNetwork`** — all three generated `string`, but Npgsql cannot read them as strings, and building an entity reads every column, so **a single such column made the whole table unusable through EF Core**. The generated entity's property type changes for such columns, but **nothing that used to work breaks** (it always failed when run). Reading an `inet` value as `IPAddress` drops its netmask (`/24` and the like), as Npgsql does by default. **`inet` columns are left out of edit models and value objects** (generation names them, as for array columns, and a UNIQUE constraint containing one is left out of the edit model's duplicate check). `interval` and `cidr` work in edit models

- **SQLite `REAL` columns (and other REAL-affinity types such as `FLOAT` and `DOUBLE`) now generate `double`** — `REAL` generated `float` (single precision), but SQLite's REAL holds an 8-byte double, so the generated code dropped the low digits of the value on every read and write. The generated entity's property type changes from `float` to `double` for such columns. Switching the target DBMS now turns SQLite `REAL` into the other dialect's double-precision type (SQL Server `float`, PostgreSQL `double precision` and the like) instead of a single-precision one. A `REAL` column folds to `FLOAT` in the type token, so the generated entity's `[DbColumnMeta]` records the original spelling as `NativeType = "REAL"` and generation names the column in an informational diagnostic (taking the code back yields `REAL`)
- **SQL Server `float(1)` to `float(24)` columns now generate `float`** — SQL Server stores `float(n)` with `n` up to 24 as `real` (single precision) and returns it as `float`, but the type resolution ignored `n` and generated `double`, so `GetAllAsync` / `GetByIdAsync` failed with `InvalidCastException`, and so did EF Core (checked against a real SQL Server). Only `Query()`, which reads through `FOR JSON`, could read such a column, so code that used only `Query()` compiled against `double` and now gets `float`. `float(25)` to `float(53)` and a bare `float` stay `double`. The generated entity records `float(24)` in `[DbColumnMeta]` next to the `float32` type token, and generation names the column in an informational diagnostic. A diagram that says `float(24)` also stops showing an `ALTER COLUMN` against the `real` column the database reports
- **A stored value a value object rejects is now reported as `InvalidOperationException` naming its column on every read** — `GetByIdAsync` / `GetAllAsync`, which call the value object's `Create` directly, and `Query()` on SQL Server and SQLite let the `ValueObjectValidationException` out with only the value object type in it, while the other read paths already wrapped it. Every read now throws `InvalidOperationException` naming the column and the entity property, with the `ValueObjectValidationException` as its inner exception, so the message says where the bad value is. **Code that catches `ValueObjectValidationException` around these reads still compiles but no longer catches the failure**; catch `InvalidOperationException` and look at `InnerException` instead. In the same way, on SQLite a stored Guid, DateTime, TimeSpan or DateTimeOffset whose text is malformed, read into a plain (non value object) property, now throws `InvalidOperationException` with the `FormatException` as its inner exception instead of the bare `FormatException`
- **The in-memory backend now rejects a navigation property in a query condition or ordering** — `Where(c => c.Orders.Any())` matched no row and `Where(o => o.Customer == null)` matched every row without an error, because the in-memory store keeps rows, not graphs, so a navigation read off a stored row is always empty. Such a query now throws `NotSupportedException`, as the QuickER repositories for SQL Server and SQLite already did; filter on the foreign-key column instead. EF Core still translates it
- **`RemoteEntityGraph.CascadeNavigations` was removed from the runtime package `QuickER.Runtime`** — nothing used it any more: the remote client and server now walk a graph through `EntityBaseCore.EnumerateCascadeChildren`, the one cascade traversal every graph operation shares. Code that called it can call `EnumerateCascadeChildren()` on the entity instead
- **`InMemoryCascade`, `IncludeAttacher`, `InMemoryDataStore.InMemoryReadScope` and `InMemoryDataStore.InMemoryWriteScope` are no longer public in the runtime package `QuickER.Runtime.InMemory`** — they are the store's own machinery, and their public constructors and methods read and wrote the store without taking its lock, so code that used them could see or leave a store half written. Nothing outside the in-memory repositories used them. Read and write through the generated repositories (or `InMemoryDataStore.Put` / `Snapshot` / `Find` for seeding and inspection) instead. The same applies to inline output with `LayeredOutput` turned on; other inline output already had them `internal`
- **Class, property and value object names keep the CJK part of a name that mixes it with ASCII letters or digits** — the name conversion dropped a run of kanji or kana that sat next to ASCII letters or digits, so a column `顧客ID` became `Id` and `顧客2` became `_2` (and two columns `注文ID` and `顧客ID` both became `Id`). They now become `顧客Id`, `顧客2` and `注文Id`. Names made only of ASCII letters and digits, and names made only of kanji and kana, do not change. Code that uses a generated name from such a mixed table or column name needs updating
- **A mini DSL `NOT` now matches a row whose column is `NULL` the way C#'s negation does, on every backend** — `NOT qty < 10` on a nullable column used to keep a row whose `qty` is `NULL` in the in-memory backend but drop it in the QuickER Repository, and `NOT (A OR B)` was wrapped as a whole, where SQL's `NOT (UNKNOWN)` drops the row. The generator now pushes `NOT` down to each comparison by De Morgan's laws and negates an ordered comparison on a nullable column as "the column is `NULL`, or not less than", so the rule is one sentence: `NOT` and `<>` mean the same as C#'s negation and match a `NULL` row, and only string matching keeps a `NULL` row out in both directions. A named query that negates an ordered comparison on a nullable column, or negates a parenthesized condition, can return more rows than before on the QuickER Repository (and, with value objects disabled, on EF Core); write `qty IS NOT NULL AND qty >= 10` if the `NULL` rows should stay out
- **A new row's edit model now reads an empty string or an empty byte array as no input** — when the mapper loads an `Added` entity, such a value of a column that is not a value object loads as null. A new row nobody typed into used to pass the required check of a NOT NULL text or binary column and save the entity's initial empty value, two such rows were reported as duplicates of each other, and `ValidateUniqueAsync` compared the empty value with the stored rows. Now the required check stops such a row, blank new rows are not duplicates, and `ValidateUniqueAsync` does not check a text or binary column that is not nullable and has no input. An empty string an `OnEntityCreated` hook sets is read the same way, nullable columns included, so it is now saved as NULL. A stored row's empty values and an excluded unbounded binary column's empty array are loaded as before

#### Import and export

- **A DBML line that cannot be interpreted is now reported instead of being dropped** — every unrecognized top-level line used to be skipped in silence, so a `Table` line that did not match the expected form took its whole table with it. Such a line now fails the import, naming the line and its number. Blocks that only carry information QuickER cannot represent (`Project`, `Enum`, `TableGroup`, `TablePartial`, `Note`, `records`) are still skipped, so files written by other tools keep importing; a relationship written in a form QuickER does not read (the block form `Ref { ... }`) is rejected by name rather than skipped, because skipping it loses the relationship
- **The DBML export now writes standard DBML, and DBML in QuickER's earlier form no longer imports** — dbdiagram.io and the DBML parser (`@dbml/core`) rejected the old output, and standard DBML with its settings after the endpoints did not import into QuickER. A constraint name is now written as a named Ref (`Ref FK_Orders_Customer: Customer.Id < Orders.CustomerId`) instead of a `note` setting, referential actions go in a settings block after the endpoints (`[delete: cascade]`) instead of right after `Ref:`, and a foreign key column no longer carries a `ref` setting without a value, which DBML does not define. Table, column and constraint names that are not made only of ASCII letters, digits and underscores, Japanese names included, are now quoted (`"Order Details"`), because DBML tools reject them bare. A `Ref` line written the old way (settings before the endpoints) now fails the import with its line number; to import such a file, move the settings block after the endpoints and turn `note: 'FK name'` into the Ref's name (`Ref "FK name": …`). A `ref` setting without a value is skipped, so a column's foreign key marker now comes only from the `Ref` line it is the child side of; the export lists a marker on a column that no relationship uses among the information the format drops

#### DB sync & DDL

- **A selected change that needs a change you did not select is now left out of the sync and named in the confirmation** — a foreign key to a new table or column, a primary key change onto a new column, a unique constraint or description on a new column, and a change that makes a column nullable while it stays in the primary key used to run anyway: the sequential dialects failed on the missing object, and SQLite silently skipped the part it could not resolve (a primary key change onto an unselected new column even left a partial primary key and reported success). Such a change is now skipped and the confirmation names it together with what it needs; QuickER does not select the needed change for you. This also covers a foreign key you add or change that refers to the parent's new primary key when that primary key change is not selected (on every dialect). Select the needed change as well to apply it
- **MySQL: a change that only reorders the columns of a referenced composite primary key is no longer run** — MySQL requires a foreign key's columns to follow the order of the referenced key, so re-adding the foreign key after the reorder always failed, and because MySQL commits DDL as it goes, the foreign key was left dropped. Such a primary key change, and a foreign key change that only makes its column order disagree with the key, is now skipped and named in the confirmation. To apply it, also select the removal of the foreign key so that it is dropped first, or change it by hand. This also skips the change where the re-add would in fact succeed: on MySQL 8.0, or on 8.4 with `restrict_fk_on_non_standard_key=OFF`, a non-unique index you created yourself on the referenced columns in the foreign key's order can support it, but QuickER does not import non-unique indexes and cannot tell

#### Bidirectional sync

- **The local sync journal table gained a column, and an existing one has to be recreated** — `quicker_sync_journal` now records which unbounded binary columns each write stored a value in. A local database created by an earlier version keeps the old table, and recording a local change then fails with an SQLite error (nothing is lost silently). Before upgrading, run a sync so the journal is empty, then drop the table (`DROP TABLE quicker_sync_journal`); it is created again on first use. `quicker_sync_ack` and the new `quicker_sync_blob_pending` need nothing
- **`SyncTableBase.CopyBinaryColumnsUpAsync` now takes the columns to send** — the protected `CopyBinaryColumnsUpAsync(TKey, CancellationToken)` became `CopyBinaryColumnsUpAsync(TKey, IReadOnlyList<string> columns, CancellationToken)`, since an upload now sends only the unbounded binary columns a local write stored a value in. Only code that derives its own class from `SyncTableBase` and calls it is affected; pass the columns to copy
- **A local save hook that skips rows the sync engine applies now stops that table's download** — a `BeforeSaveAsync` that returned `false` for a row the engine applied used to lose that row and let the download go on, so such a hook could keep rows out of the local database. The table's download now stops at the skipped row on every run until the hook lets it through (see the Fixed entry). A hook meant to leave the engine's rows alone should return `true` without doing anything while `SyncSession.IsSuppressed` is true

#### Names in a diagram

- **Every name kept in a diagram follows one rule: surrounding spaces are removed, and names that match ignoring letter case are the same name** — this used to hold for table names only. Column names, constraint names (foreign key, primary key, unique constraint), named query names, query parameter names, projection field names and result type names now also lose their surrounding spaces when they enter a diagram, from every route (the properties panel, the AI tools, imports, a diagram file you edited by hand). The spelling, including upper and lower case, is kept. **A diagram file that has such a name with surrounding spaces is read with the spaces removed**, and saving it writes the trimmed name
- **The properties panel no longer accepts a name that another table (or another column of the same table) already has** — typing `orders` over a table next to `Orders`, or a column name that matches another column of the table, puts the old name back and says so in the status bar; nothing is added to Undo. Undo and Redo themselves are not checked. Names were not checked here at all before, so the panel could create two tables with the same name
- **DBML, Mermaid and Excel definition document imports now reject two columns of one table with the same name** — the import stops with an error that names the table and the column (two tables with the same name were already rejected). A database import skips the later of two columns that match ignoring letter case or surrounding spaces and reports it (`quicker scaffold` writes the warning to stderr); the skipped column's key flag, description and foreign keys no longer attach to the column that is kept
- **`set_unique_constraint` rejects a constraint `name` that a foreign key, primary key or unique constraint of the diagram already uses**, as `add_relationship` already did for a foreign key's name. The GUI-side tool of the built-in chat behaves the same
- **DDL generation and schema-sync script generation now refuse a name that the target dialect cannot take** — a table, column, foreign key or unique constraint name longer than the dialect's identifier limit (SQL Server 128 UTF-16 code units, PostgreSQL 63 UTF-8 bytes, MySQL 64 characters, Oracle 128 UTF-8 bytes; SQLite has none), or, on MySQL, one holding a character outside the Basic Multilingual Plane such as an emoji. The error names the place and the limit and nothing is generated. Until now SQL Server, MySQL and Oracle rejected such DDL when it was applied, PostgreSQL silently cut the name at 63 bytes (so two names that differ only after the cut collapsed into one), and MySQL silently replaced the character with `?`. A MySQL table name is also checked against 251 bytes as a file name, so a table named in kanji can have at most 50 characters. Oracle databases running with a `COMPATIBLE` below 12.2 (30-byte names) are not detected; see [Identifier length limits](docs/database.md#identifier-length-limits)
- **The default constraint names QuickER assigns are cut to the dialect's limit when they would be longer** — `PK_{table}`, `FK_{child}_{parent}`, `UQ_{table}_{columns}` and the numbered names that keep them unique now end in `_` and 8 hex digits taken from the full name once they would exceed the limit; a name within the limit is unchanged. This also applies to the unique constraint names written into generated code. A PostgreSQL database created by an earlier version already holds the names PostgreSQL cut, and diff sync treats a foreign key without a name of your own as the same as the one in the diagram, so it adds and drops nothing
- **C# code generation stops with an error that names the names when a diagram holds two tables, or two columns of one table, that match ignoring letter case or surrounding spaces** — including names such as `Äpfel` and `äpfel`, whose C# identifiers differ and which the identifier checks therefore let through. A projection with two fields that match ignoring letter case is rejected too (it used to compile, but a raw-SQL projection lost a value and a remote call threw)

#### AI chat & MCP

- **The ER diagram tools now refuse a missing required argument instead of filling in a default** — in the built-in chat and over MCP, `add_entity` without `table_name` created a table named `NewTable`, `add_column` without `data_type` created an `nvarchar(100)` column (a type PostgreSQL and Oracle do not have), and `add_relationship` without `relationship_type` created a one-to-many relationship. Each now fails and names the argument. A required argument given as `null` is refused the same way
- **Every tool now refuses an argument of the wrong JSON type** — a number where a string is expected, `"true"` where a boolean is expected, an object where an array is expected, an array element that is not an object where objects are expected, a `sql` value that is not a string, and so on. These used to be ignored silently (`is_primary_key: "true"` made a column that is not a primary key, `order_by: {...}` saved an unordered query), and a non-object element in `set_query`'s `parameters`, `order_by` or `fields` returned a raw .NET error. This applies to the built-in chat and to all MCP tools, including `generate_csharp` and `generate_ddl`. An optional argument given as `null` still counts as omitted
- **`quicker mcp` no longer reads `appsettings.json` from the folder it is started in** — the server used the .NET host's default configuration, which loaded that file from the working folder (usually the agent's project) and watched it for changes, so a malformed `appsettings.json` there stopped the server from starting and a large project tree held a recursive file watcher. Nothing in QuickER read those settings

#### DB import & connections

- **DB import no longer imports external tables (Oracle and SQL Server)** — an Oracle `ORGANIZATION EXTERNAL` table and a SQL Server external table (`is_external` in `sys.tables`) used to be imported as an ordinary entity, although their data lives outside the database and the generated DDL and schema sync cannot recreate them. They are now left out and named in the import warnings, like PostgreSQL's foreign tables. Importing such a database again into a diagram that already has the table lists the table among the tables that would disappear in the replacement confirmation

### Added

#### Code generation dialog & CLI

- **Generation now names the columns whose C# type fell back to `string`** — a DB type the type catalog cannot parse (`geometry`, `hierarchyid`, `sql_variant` and the like) becomes `string` so that generation keeps going, which the generated code gave no hint of. Such columns are now listed at generation time as "table.column (original type text)" on all five dialects. The generated code itself is unchanged
- **Generation now names the columns declared with a negative scale** — `numeric(10,-2)` (PostgreSQL) and `NUMBER(10,-2)` (Oracle) make the database round values (1234 is stored as 1200), and the generated code carries no precision or scale for such a column: no digit validation on the value object, no Precision/Scale on `[SqlColumnType]`, and no `HasPrecision` in the EF Core model. Neither fact was visible from the generated code. Such columns are now listed at generation time as "table.column (original type text)". This is a note rather than a warning, because a negative scale is written on purpose. The generated code itself is unchanged
- **Generation now warns when a NOT NULL computed column cannot be written on the mirror side** — in a multi-target build (SQL Server as the server, SQLite locally) or with bidirectional sync, the side that does not evaluate the expression gets an ordinary column, and generated code never writes it, so inserting a row there fails on the NOT NULL constraint. The affected columns are now named at generation time, with the two ways out: make the column nullable in the diagram (the mirror then keeps NULL for it) or leave the table out of synchronization. The note the DDL carries next to such a column says the same
- **`quicker generate` now warns when `--provider` differs from the diagram's target DBMS** — generation does not convert column types, so a SQL Server diagram generated with `--provider postgresql` has its types read as written under PostgreSQL's rules. The command still generates, with the exit code unchanged, but now prints a warning on stderr that points to the GUI's target DBMS switch, which converts the types first

#### Generated code

- **Generated type names that differ only in case are reported as a warning** — for example `UserIdValue` from column `user_id` and `UseridValue` from column `userid` of another table. The generated code works as it is; the warning names both types and the columns they come from, so that a name spelled differently in different places can be noticed
- **A composite primary key's own column order is now recorded in the generated entity's `[DbTableMeta]`** — only for a table whose key order differs from the order the key properties are declared in, as `[DbTableMeta(PrimaryKeyOrder = new[] { "B", "A" })]` with the property names in key order. The generated code of a diagram that states no order, has a single-column key, or keeps the declaration order does not change. It appears only where `[DbTableMeta]` is written, that is, when data annotations are generated. The runtime package `QuickER.Runtime` gains a `PrimaryKeyOrder` property on `DbTableMetaAttribute`
- **DB import now marks a column the database numbers and refuses given values for, and generated code leaves it out of writes** — SQL Server `IDENTITY` and PostgreSQL and Oracle `GENERATED ALWAYS AS IDENTITY` columns. They used to come in as ordinary columns, and the generated INSERT / UPDATE sent a value to them and failed at run time. Import marks such a column and names it in an import warning, and generated code puts `[IdentityColumn]` on a non-key marked column and leaves it out of INSERT, bulk insert and UPDATE (SELECT still reads it; EF Core gets `ValueGeneratedOnAddOrUpdate()`). A primary key column stays in the writes, because the generated repositories write the key, and generation warns about it when it generates repositories (the GUI's code import keeps this mark from the current diagram). A NOT NULL marked column that the QuickER Repository for SQLite cannot write (as the only dialect or as the mirror of a multi-target build) is named in a generation warning too. The diagram has no numbering definition (seed and increment), so DDL and schema sync create an ordinary column, with a comment next to it on SQL Server, PostgreSQL and Oracle asking you to add the property by hand. C# import reads `[IdentityColumn]` back into the mark, and Mermaid and DBML export report the mark as lost. MySQL and SQLite cannot have such columns, so switching the target DBMS to one of them removes the mark (the confirmation lists the columns, and a single undo brings them back), and generating for one of these two dialects with the CLI's `--provider` or MCP's `provider`, when it differs from the diagram, names the marked columns in a warning. The runtime package `QuickER.Runtime` gains `IdentityColumnAttribute`. Generated code for a diagram without marked columns does not change. See [code generation](docs/code-generation.md#columns-the-database-numbers)
- **The generated mappers now take a save back into the edit model with `mapper.AcceptSaved(editModel, entity)`** — and `mapper.AcceptSaved(editModels, entities)` for a collection. Call it after a successful save in place of `editModel.AcceptChanges()`. A row the save wrote is read back from its entity, so the new row version, values the database produced and values a Before hook set reach the edit model, and the next save updates the right row with the right version; with `AcceptChanges()` the edit model kept the version it was loaded with, and saving it again failed as a conflict. A row a Save hook skipped keeps its state, and a child deletion a hook skipped stays pending, where `AcceptChanges()` marked them as saved. Without the EF Core repositories, an excluded unbounded binary column goes back to not fetched, so the next save leaves the stored blob alone; with them, the edit model keeps the blob, which the EF Core repositories write with every save. `AcceptChanges()` itself is unchanged

#### Import and export

- **Importing C# code now restores a composite primary key's own column order** — the import reads the `PrimaryKeyOrder` above. An order that does not name exactly the key columns (an unknown property, a column that is not part of the key, a duplicate, or a missing key column) is not adopted: a warning is shown and the key comes back in declaration order. A merge import into an existing diagram keeps the order the current diagram states explicitly when the code states none, as code generated by an older version cannot, as long as the key still consists of the same columns. A table for which the current diagram states no order is imported without one. Until now the round trip put the key back in declaration order, and the next database sync rebuilt the primary key
- **DBML now round-trips a composite primary key's own column order** — a table whose key order differs from its column order is written with the key as a `(col, …) [pk]` index at the top of its `Indexes` block instead of the `pk` column setting, and the import reads that index as the key's columns and order. DBML from other tools that declares the key this way is read as well (the index name is discarded). Column `pk` settings and a `[pk]` index that name different columns, a second `[pk]` index, or a column listed twice in the index are rejected at that line rather than guessed at
- **The Mermaid export now reports that a composite primary key order is lost** — Mermaid has no syntax for the order, so it cannot be carried; the omissions listed when the export finishes include it whenever a table's key order differs from its column order
- **DBML import now reads inline references, `primary key`, and many-to-one `Ref` lines** — these are standard DBML that dbdiagram.io writes all the time, and they used to be skipped in silence, so the primary keys and relationships they declared vanished from an import that reported success. A column setting `ref: > users.id` is read as the `Ref` line with that column on the left; for one-to-one (`-`) the column carrying the `ref` is the foreign key, following DBML's rule, which is the opposite of a `Ref` line. `primary key` is read like `pk`, and a `Ref` line with `>` is read as one-to-many with its sides swapped. An inline reference that cannot be read, such as a schema-qualified one, is reported with its line number

#### AI chat & mock generation

- **AI answers in AI chat and AI mock generation are now shown as formatted Markdown** — headings, emphasis, inline code, code blocks, lists, tables, quotes, horizontal rules and links are formatted once a response ends, and an answer in progress stays as text. A "Markdown" check box in the chat header switches back to the original text, for example to copy it; each window remembers the choice, and it is on by default. Only `http` and `https` links can be clicked (they open in the default browser), images are not loaded and show their alternative text, HTML is shown as written, and an answer nested too deeply to format is shown as text

#### Bidirectional sync

- **Code generation warns about a fixed-length string primary key on a synchronized table** — SQL Server pads an `nchar(n)` / `char(n)` value with spaces, so a row created locally comes back under the padded key after a sync, and a local child row keeps both rows apart. When sync support is generated, such a key is named with a warning that recommends a variable-length type (`nvarchar` / `varchar`)
- **Two conflict reasons for writes the server refuses over a foreign key** — `SyncConflictReason.ParentMissingOnServer` (a row whose parent the server no longer has) and `SyncConflictReason.DeleteRefusedOnServer` (a delete of a row the server still holds while other tables refer to it, typically because another device added a row pointing at it). They are reported only after a write has failed, by looking up the state the failure follows from, and the run carries on with the next row instead of stopping
- **`SyncConflictReason.UniqueValueTakenOnServer`** — a write the server refuses because another row there already holds one of its unique values. Like the two foreign-key reasons, it is looked up only after a write has failed. `Collect` and `LocalWins` report it and keep the entry (`LocalWins` does not take the value away from the other row); `ServerWins` settles it by putting the server's row back, in a versioned run and in a last-write-wins run alike
- **`SyncDownloadTruncation.MissingParentTableName`** — names the parent's table when the download stops at a row whose parent cannot be brought in: the parent's table is outside the run's scope, the parent holds an unsent local delete the run is not discarding, or the server does not have the parent either. It is null when the row stopped for another reason
- **`SyncResult.LocalRowChanges`** — the local rows a `SyncAsync` changed on its own rather than by applying a server change: the rows whose unsent changes a `ServerWins` run discarded (`DiscardedByServerWins`), the rows read again from the server because a downloaded row needed a unique value they held (`ReloadedForUniqueValue`), and the rows a `ServerWins` run removed before the download because the server does not have them (`RemovedBeforeDownload`). The counts alone did not say which rows. A `SyncAsync` that throws hands the rows it had changed so far on in the exception's `Data` under `SyncEngine.LocalRowChangesDataKey`

### Changed

#### DB import & connections

- **Import warnings are now listed by kind, in the GUI and in `quicker scaffold`** — each kind of warning gets one heading with the count, followed by one line per place. A table left out of the diagram (a view, a virtual table, a history table and so on) is listed by name under its heading; a definition that was imported in a reduced form keeps its one-sentence description. The sentences are now the same in the GUI's import details and in `quicker scaffold`'s stderr, where the heading starts with `Warning:` and each place is indented with `  - `. Scripts that matched the old one-line warnings in stderr need updating; the exit code and the generated files are unchanged
- **DB import now names the objects it leaves out of the diagram** — views (all five DBMSs), materialized views (PostgreSQL, Oracle), foreign tables (PostgreSQL), partitions (PostgreSQL, with the parent table they belong to) and temporary tables (Oracle) used to be skipped without a word. A foreign key that references a table the import left out (a PostgreSQL partition, an SQLite virtual table or view) is now reported as such; SQLite used to report it as referencing a table outside the imported scope
- **DB import now names the parts of a column or table it imports in a reduced form** — default values (all five DBMSs), automatic numbering that also accepts given values (MySQL `AUTO_INCREMENT`, PostgreSQL `serial` and `GENERATED BY DEFAULT AS IDENTITY`, Oracle `GENERATED BY DEFAULT AS IDENTITY`, SQLite `AUTOINCREMENT`), a MySQL column's own collation when it differs from the table default, MySQL `INVISIBLE`, `ON UPDATE` and `SRID`, SQL Server partitioned tables and alias types (`CREATE TYPE … FROM`), and names with spaces around them, which are imported without the spaces. The diagram models none of these, so generated DDL leaves them out; they used to be dropped without a word
- **DB import no longer imports a table whose name contains a dot, and names it** — the diagram reads the first dot of a table name as the separator between a schema and a table, so such a table was read as another one: the generated QuickER Repository reported that the table does not exist, and DDL and schema sync created another table, or failed when that schema did not exist. On SQL Server this covers a table in `dbo` whose name contains a dot and every table in a schema whose name contains a dot; a dotted table name in another schema reads back as the same table and is still imported. A foreign key that references such a table is reported as a foreign key to a table the import left out

#### Code generation dialog & CLI

- **The code generation dialog now lists value object warnings in a scrollable box** — with value objects on, the warnings found during generation were put into the body of a standard confirmation, which does not scroll, so a diagram that raised a warning per column pushed the buttons off the screen. The confirmation now shows the question at the top and every warning in a scrollable list below it, as the confirmation before overwriting edited files already did

#### Generated code

- **A graph save that deletes rows now writes in three stages, and its save hooks fire in that order** — the new and updated rows come first, in graph order, then the deletions, then the rows held back because they take a value a deleted row still holds. Before, a deletion ran where the walk reached it, so a deletion that came first among the roots or in a collection ran before the other rows were written, and its hooks fired first. Every backend uses the new order, so a hook that relied on a deletion running before the writes next to it now sees the writes first. A save that deletes no row keeps graph order
- **The generated EF Core `DbContext` declares each unique constraint as a unique index** — `OnModelCreating` now has a `HasIndex(...).IsUnique()` line for every unique constraint of the diagram, so EF Core runs a deletion that frees a unique value before the update or insert that takes it. Nothing is created in the database: the schema still comes from the generated DDL, and Migrations and `EnsureCreated` are not used. Only diagrams with unique constraints get different code
- **`GetByIdAsync`, `DeleteAsync` and the unbounded binary column accessors now refuse a null key with `ArgumentNullException` on every implementation** — for `GetByIdAsync` and `DeleteAsync`, the QuickER repositories threw `InvalidOperationException`, the EF Core repository returned `null` / `false`, and the HTTP client sent the request and failed with `RemoteRepositoryException` (400). The stream accessors (`Read{Column}Async` / `Write{Column}Async`) failed the same ways, and the sync journaling decorator's write failed with `NullReferenceException` for a value-object key. Every implementation, the sync journaling decorator included, now throws `ArgumentNullException` with `ParamName` `id` before it reads, writes, deletes, records or sends anything; the file overloads (`Read{Column}ToFileAsync` / `Write{Column}FromFileAsync`) refuse it before they touch a file. The EF Core repository still throws `NotSupportedException` from the stream accessors. Code that relied on EF Core's `null` / `false` for a null key has to check the key first
- **`Query().ExecuteDeleteAsync` now refuses a query with `Skip` or `Take`** — the paging was ignored, so `Take(1).ExecuteDeleteAsync()` deleted every row the conditions matched. It now throws `NotSupportedException` before any statement runs, on every backend. Narrow the rows with a condition, or fetch the page and delete those rows
- **The names a named-query parameter cannot use have changed** — the members that a generated method body calls are now qualified with `this.`, so parameters named `Query` and `QueryBySqlAsync` are now allowed (a parameter named like the sync decorator's `_inner` now compiles too). In their place, a parameter whose name with the first letter capitalized is `ToString`, `Equals`, `GetHashCode`, `GetType`, `MemberwiseClone`, `ReferenceEquals`, `EqualityContract`, `PrintMembers` or `Deconstruct` (`toString` included) is refused: it collided with a member of the remote request record and the generated code did not compile. It is refused even when remote services are not generated. A `dsl` projection also refuses a parameter named like the field that holds its selector (`_` plus the method name starting in lower case plus `Selector`), which hid the field. `set_query`, the query definition dialog and code generation all apply the same rule. Generated query method bodies now use `this.`, as in `this.Query()`
- **A `decimal` column written without a precision (SQL Server, MySQL) now records the default precision and scale in the generated entity's `[DbColumnMeta]`, along with the original spelling** — a bare `decimal` means `decimal(18,0)` on SQL Server and `decimal(10,0)` on MySQL, but the type token recorded a bare `decimal` with no precision, so taking the generated code back into a diagram warned that the type token could not be expanded (the column's type did come back correctly). The token is now `decimal(18,0)` / `decimal(10,0)`, the original spelling is recorded as `NativeType = "decimal"`, and generation names the column in an informational diagnostic. Taking the code back yields `decimal` with no warning. Switching a SQL Server bare `decimal` to MySQL now gives `decimal(18,0)` instead of listing it as unconvertible
- **With a schema-qualified table name, the generated unique constraint name now matches the DDL** — for a unique constraint that has no name, the generated entity's `[UniqueConstraint(…, Name = …)]` was synthesized from the raw table name, so for `dbo.Orders` it said `UQ_dbo.Orders_code` where the DDL creates `UQ_dbo_Orders_code`. Importing C# code restores that `Name` as the constraint's own name, so a round trip gave a previously unnamed constraint a different name. **Code generated before this fix still restores the old name**, so regenerate it before importing when you use schema-qualified table names
- **The in-memory sample data now keeps every key, UNIQUE constraint and foreign key of the diagram** — the seeder built each value from the column's type alone, so the default `AddGeneratedInMemoryRepositories()` could seed a store that broke the diagram: a UNIQUE column got the same value on several rows (after which any update or save of those rows failed with a unique-constraint violation even when the value was not touched), an unsigned integer key or a key shorter than its sample text collapsed the three rows into one, and a string foreign key, or one referring to a UNIQUE column, pointed at no parent row. A key or UNIQUE column now gets a different value on every row (a short string keeps its row number and loses the end of the column name), a foreign-key column takes the value of the column it refers to on the same row, and an entity whose key or UNIQUE constraint cannot take three different values (a NOT NULL bool, for one) is seeded with fewer rows, as is a child that refers to it. The seeded values change accordingly
- **Writing an unbounded binary column from a stream now fails when the stream does not yield exactly `length` bytes** — `Write{Column}Async` ignored a `length` passed with a seekable stream, SQL Server stored the whole of a non-seekable stream regardless of `length`, and SQLite, which sets aside `length` bytes first, filled the tail of a short stream with zeros and reported success. A `length` that differs from what is left in a seekable stream, and a stream that ends before `length` or goes on past it, now throw `ArgumentException` (`ParamName` is `length`) on SQL Server, SQLite and the in-memory backend, and the stored value stays as it was. Omitting `length` for a seekable stream works as before
- **SQL Server `BulkInsertAsync` now stores `null` as NULL in a column that has a DEFAULT** — `SqlBulkCopy` puts the column's DEFAULT in place of a `null` unless told otherwise, so a bulk insert stored the default where `InsertAsync` stores NULL. `SqlBulkCopyOptions.KeepNulls` is now always on. QuickER's DDL emits no DEFAULT, so this only changes tables imported from an existing database
- **SQLite: a date and time stored as text with an offset is now read as UTC on every path** — the driver's typed read behind `GetByIdAsync` / `GetAllAsync` converts `2024-01-15 10:00:00+09:00` to 01:00 UTC, while `Query()`, a value object column and raw SQL converted the same text to local time, so one row came back with two different values. Every path now reads it the way the driver does: text with an offset becomes UTC (`DateTimeKind.Utc`), text without one stays `Unspecified`. QuickER itself never writes an offset, so this only changes values written by other tools
- **A synchronous write to the stream a binary download hands to its read function now follows the host's rule on synchronous I/O** — `DeferredOctetStreamBody.Write` blocked a thread on an asynchronous write, so a hand-written read function that wrote synchronously worked even with `AllowSynchronousIO` off (the default) and tied up a thread for each write. It now writes to the response body synchronously, so under the default it throws (the download answers 500) as any synchronous write to the response does. Write with `WriteAsync`, or turn `AllowSynchronousIO` on. The generated endpoints only write asynchronously and are unaffected
- **SQL Server: `Query()` without `Include` now reads with a plain SELECT instead of FOR JSON** — a fetch with no `Include` has nothing to nest, yet `ToListAsync` / `FirstOrDefaultAsync` (and a projection that falls back to reading whole entities) had the database build a JSON document and then parsed it. It now reads the rows the way `GetAllAsync` does. In our measurement, reading 200,000 rows of a 24-column table went from 2.2 s and 1.9 GB allocated to 0.76 s and 0.49 GB, and 20,000 rows from 229 ms to about 85 ms; fetching a single row takes the same time and allocates a little more (about 17 KB instead of 11 KB for that table), as `GetByIdAsync` does. A query with `Include` still uses FOR JSON, which reads the parent and its children in one statement
- **The in-memory backend's prefix and suffix match (`StartsWith` / `EndsWith`) on a plain string column now compares ordinally** — a query condition such as `name LIKE 'a%'` and a hand-written `Where(x => x.Name.StartsWith("a"))` compared with the current culture, which ignores characters such as the soft hyphen and treats a precomposed character (`が`) as equal to its decomposed form, so the in-memory backend could return rows the SQL backends do not. It now compares ordinally whatever the current culture is, the same as `Contains` and value-object columns

The data in the old location is not moved and stays where it is (in the installed version it stays inside `current` until the next update removes it; it is only the preview's cache, so it can be deleted)

The name is now refused before generation starts, with a message saying why

This covers `add_entity`, `add_column`, `set_entity_property`, `set_column_property`, `add_relationship` with `constraint_name` and `set_unique_constraint`, in both the MCP server and the built-in chat, and the note appears once, in the call that introduced the name

A failure the backend gives no reason for shows the summary alone. Only an interrupt you asked for completes without a message: a cancellation from anything else is now shown as a failure instead of looking like an interrupt

The launch now fails with a message naming the path. Codex and Claude Code are also started with delayed expansion turned off explicitly, so a `DelayedExpansion` setting in the registry no longer applies to them
- **Relationships created by the tools now get the same default constraint name as ones created in the GUI** — the built-in chat's and MCP's `add_relationship` joined the raw table names, so a schema-qualified name produced `FK_dbo.Orders_dbo.Customers` while creating the relationship by hand produced `FK_dbo_Orders_dbo_Customers`. The tools find tables and columns by name ignoring case and take the first match, so a second table or column with such a name could not be edited or removed by any tool, and an empty type stopped DDL generation for the whole diagram. A refused `set_entity_property` or `set_column_property` call changes none of the properties it was given

- **The MCP code generation tools now return English results on any OS language, and warn when `provider` differs from the diagram** — `generate_csharp` shares its messages with the CLI, so on a Japanese Windows the English result carried Japanese lines (the generated file list, the counts, generation diagnostics and settings errors). The results of `generate_csharp` and `generate_ddl` are now in English throughout, like the other tools on the server; the CLI keeps following the OS language. When `provider` names a dialect other than the diagram's target DBMS, the result now begins with a warning that column types were not converted. The message about hand-edited files also now says the list follows it (it said "listed above" while the list came below)
- **Mock generation on Copilot no longer auto-approves a command that references a URL or redirects into a file, even when all of its paths are under the output folder** — the rule for commands with readable paths only checked that every path is under the output folder, so `curl https://… -o .\x.ps1`, `git clone https://… lib\bar` and `dotnet build … > build.log` were approved. Such a command now also has to reference no URL and redirect nothing into a file, which a command without readable paths already had to. A refused command is listed in the progress log. Copilot's own file tools, which the agent uses to write files, are not affected

- **`add_relationship` now warns when the parent columns you name cannot carry a foreign key** — in the built-in chat and over MCP, naming parent columns that are neither the parent's primary key nor one of its unique constraints (a part of a composite key, or an ordinary column) succeeded without a word, and most databases then rejected the `FOREIGN KEY` when the generated DDL was applied. The relationship is still added, since MySQL accepts such a key on indexed columns, but the result now says so and how to fix it

#### DB sync & DDL

- **On SQL Server, changing a primary key no longer picks up a table with the same name in another schema, and constraint names containing `]` work** — to drop the old primary key, sync looked up the constraint by table name alone, so with `dbo.Orders` and `other.Orders` it could take the other table's constraint name and fail (or drop the wrong one). It also wrapped the name it read in `[` `]` without escaping, so a primary key name containing `]` broke the statement. Sync now looks up exactly the table it changes and quotes the name it reads with `QUOTENAME`. Dropping a foreign key whose name is not known works the same way
- **On PostgreSQL, changing a primary key now works when the constraint name contains `"`** — sync read the old primary key name and wrapped it in `"` without escaping, so a name containing `"` (QuickER itself names the primary key of table `a"b` as `PK_a"b`) broke the statement and the sync failed. The name read is now quoted with `quote_ident`. Dropping a foreign key whose name is not known works the same way
- **On Oracle, DDL and sync scripts with multi-line descriptions now run correctly in SQL*Plus** — a description was written as one string literal with its line breaks kept, and SQL*Plus reads input line by line even inside a literal, so the statement was cut at the line break and the following lines were run as separate statements. `&` was also treated as a substitution variable. A description that contains a line break, a carriage return or `&` is now written as a PL/SQL block that joins those characters with `CHR(n)`, so no raw line break or `&` is left in the output. Other descriptions are written as before. Scripts run by QuickER itself were not affected
- **A difference in nullability on a computed column no longer produces an `ALTER COLUMN`** — the nullability of a computed column follows from its expression, which the diagram does not model and therefore cannot impose on a database. Without this, taking the way out above (making the column nullable in the diagram) would have made the sync offer a meaningless `ALTER COLUMN` against the database the diagram was imported from. Differences in the column's type are still detected
- **The sync confirmation now shows the tables to rebuild and the notes in a scrollable details area** — until now everything was joined into the text of a standard message box, so with many items the OK and Cancel buttons went off the screen, and that happened on the most destructive confirmation of all. The text now holds a summary (how many tables are rebuilt, and against what), and the details area lists every table and every note. A confirmation with nothing to list is still a one-sentence message box
- **Dropping a table or column now also drops the foreign keys that lose an end, even when their removal is not selected** — removing a foreign key is unselected by default, so dropping a parent and its child table together failed when the parent came first in import order, a dropped referenced column was refused, and on SQLite a foreign key pointing at a dropped table or column was left behind. Such foreign keys are now dropped first (on SQLite the remaining child table is rebuilt without them)
- **A column that joins the new primary key is made `NOT NULL` as part of the primary key change** — it no longer depends on selecting that column's own change, so a primary key change no longer fails on SQL Server because a new key column is still nullable
- **Changing the columns of a named unique constraint is now one change, unselected by default** — the drop and the add used to be separate items, and selecting the add alone (the default) failed because the name was already in use. A constraint that keeps its name (or whose generated name `UQ_{table}_{columns}` matches the database's name) but changes columns now shows as one change that drops and re-adds it
- **A computed column's type change can now be selected only on PostgreSQL** — the diagram does not hold the expression, and the other dialects cannot change the type without it (SQL Server rejects the change, and a SQLite rebuild drops the expression). On those dialects and on MySQL the difference is shown for information only. Its nullability is never compared
- **On SQLite and Oracle, a unique constraint on exactly the primary key's columns is no longer compared, and the DDL and the tables the sync creates leave it out** — SQLite does not keep such a constraint, so the difference never went away, and Oracle rejects it (ORA-02261); the primary key already guarantees uniqueness. A comment in the DDL and the sync script says the constraint was left out. On Oracle, a sync that moves the primary key onto the columns of a unique constraint the database already has fails unless that unique constraint is dropped first
- **On SQL Server, a `SET DEFAULT` foreign key on a NOT NULL referencing column is now named** — SQL Server cannot create it when the column has no DEFAULT constraint (error 1762). The diagram does not carry column defaults, so the DDL adds a comment before the foreign key, and the sync lists the foreign keys it adds or recreates in the confirmation dialog. It does not stop the sync, because the foreign key is created when the column has a DEFAULT constraint
- **On SQL Server, the DDL adds a comment before a foreign key whose string ends differ in length** — SQL Server cannot create such a foreign key (error 1753)
- **On Oracle, the DDL and the sync script add a comment for an `ON DELETE SET DEFAULT` they leave out** — Oracle has no `SET DEFAULT`, so the foreign key is created as `NO ACTION` without the clause (`ON UPDATE` already had such a comment)
- **A composite foreign key whose column pairs differ only in order is no longer a difference on any dialect** — the pairs map parent columns to child columns and their order carries no meaning. Oracle does not keep the declared order (it returns the pairs in the referenced key's order), so the comparison showed a foreign key change after every import. On SQL Server and MySQL, which require that order, the DDL now writes the pairs in the order of the referenced key (the primary key, or else a unique constraint), so a diagram in any order applies. A foreign key the sync adds or recreates is still written in the diagram's order
- **On MySQL, altering a column now keeps the column attributes the diagram does not model** — the `MODIFY` used to be built from the diagram, dropping `DEFAULT`, `AUTO_INCREMENT`, the collation and character set, `ON UPDATE`, `INVISIBLE` and `SRID`. It is now rebuilt from the live catalog at execution time, like description and column-order sync, and changes only the type and the nullability. When a kept attribute does not fit the new type, the change fails with a MySQL error. A column that no longer exists at execution time makes the change fail instead of doing nothing
- **A sync that changes the kind of type of a column with a default value is now shown in the confirmation dialog on every dialect except SQLite (SQL Server, PostgreSQL, MySQL and Oracle)** — the sync keeps the database's default, so when it does not fit the new type, the sync fails on PostgreSQL and Oracle, the sync fails with error 1067 on MySQL (on MySQL and Oracle, the statements before it stay applied), and an insert that uses the default fails on SQL Server
- **On SQLite, a table name with a dot is now named** — SQLite reads `a.b` as table b in an attached database a, so it fails unless that database is attached. The DDL adds a comment before the table, and the sync lists such tables in the confirmation dialog
- **A foreign key you add or change now warns when its referenced columns are not exactly a primary key or a unique constraint after the sync** — and on SQL Server and MySQL the check also requires the same column order, so reordering a referenced composite primary key warns there instead of failing without one
- **Changing a primary key now drops and re-adds only the foreign keys that rely on the old primary key** — foreign keys referencing a unique constraint are no longer dropped and re-added (on MySQL, a foreign key referencing only the leading columns of the old primary key is still handled, because the old key's index can be the one supporting it)
- **MySQL: dropping a foreign key also drops a non-unique index with the same name, unless another foreign key needs it** — MySQL creates such an index for a foreign key that has no suitable one and keeps it after the foreign key is dropped, so re-creating a foreign key of the same name on other columns failed (error 1061) and left it dropped. An index you created yourself with the same name as the foreign key is dropped too, because the catalog cannot tell the two apart
- **A column type whose length or precision is written with digits other than ASCII (such as full-width `varchar(５０)`) is now refused by DDL generation and DB sync, with the column named** — such a type was let through, so the DDL was generated and the database refused it. The type catalogs, type mappers and the comparison of type notations no longer read these digits as numbers either

#### Diagram editing

- **The status bar now warns when you enter a name that the target database would refuse** — a table, column, foreign key or unique constraint name longer than the dialect's identifier limit, or on MySQL holding a character outside the Basic Multilingual Plane. The name is accepted as typed; Undo, Redo and loading a file do not warn. Switching the target database also lists such names in the confirmation dialog, next to the columns whose types change
- **A new relationship now pairs the child's primary key column when it is the foreign key** — in an identifying relationship such as order lines keyed by `(OrderId, LineNo)`, `OrderId` is both part of the child's primary key and the foreign key to the order, but primary key columns were never candidates, so the relationship came out without that column pair. A child primary key column is now paired when its name is the one derived from the parent table (`OrderId` / `order_id` for `Orders`), and, for a parent with a composite primary key, when it has the same name as a parent key column (`(TenantId, ProjectId)` → `Tasks(TenantId, ProjectId, TaskId)`). A name that merely equals the parent's key column when it is a lone `id` still does not pair a child's primary key, whether the parent's key has one column or several: each table's `id` is that table's own key, so for `Projects(TenantId, Id)` → `Tasks(TenantId, Id, ProjectId)` the parent's `Id` pairs with `ProjectId`. A self-reference never pairs a child's primary key. This applies to creating a relationship in the GUI, to `add_relationship` without columns in the built-in chat and over MCP, and to the columns a Mermaid import infers; a name derived from the parent now also wins over a column that only carries a foreign key marker
- **Deleting a table also deletes the named queries defined on it** — this applies to deleting in the GUI, one table or several, and to `remove_entity` in the built-in chat and over MCP. A query left behind belonged to no table, so neither the query definition dialog nor `remove_query` could reach it, and every code generation warned about it. In the GUI, undoing the delete brings the queries back in their original order. Over MCP nothing brings them back; the tool result names the queries it removed
- **Ctrl+clicking a table while creating a relationship now cancels the creation** — the starting table used to stay pending, so the next plain click after a multi-selection silently created a relationship. To create one, start again from a relationship button

#### Import and export

- **Exports, generated code, mock output, and saved API keys and connection passwords are now written atomically** — the target used to be truncated and then written, so a crash partway left the existing file with partial content. The write now goes to a temporary file in the same folder and is then swapped in, so the target holds either the complete old content or the complete new content. Two differences are visible. While it writes, a `name.<GUID>.tmp` file appears briefly in the target folder. If the target is a symbolic link to a file, the link itself is replaced by a regular file instead of the file it points to
- **Re-importing from a database or an Excel definition document now matches names that differ only in letter case** — the merge import kept a table or column only when its name matched exactly, so MySQL on Windows (which returns table names in lower case) turned the diagram's `Orders` into a new table `orders`: its layout and memo were lost and the named queries on it were listed for removal. A name that differs only in case now matches when it is unique on both sides ignoring case, and the imported spelling replaces the diagram's. Where names differing only in case exist side by side, an exact match is taken first, and a name that stays ambiguous is still treated as new
- **An Excel definition document written in a format this version cannot read is no longer imported** — the document embeds its format version, but the import never looked at it. A document carrying information a future version added is now reported instead of imported, so nothing it could not read is silently dropped (the same stance the diagram file takes towards a newer format). Older documents that carry no version are imported as before
- **Importing Mermaid or DBML into a diagram that is not empty now always asks first** — the import replaces the whole diagram with new tables that are arranged automatically, so even when the file has exactly the same tables and columns, the hand-made layout, colors, memos (and, for Mermaid, descriptions) and the undo history are lost. QuickER used to skip the confirmation when the structure matched and there were no queries or unsaved changes. Re-importing an Excel definition document still skips it when nothing changes, because that import keeps the layout

#### Diagram files

- **Leading and trailing spaces are removed from table names** — a table name such as `Orders ` (easy to type by accident) was kept as written, so DDL and the generated code created and referred to `"Orders "` while DB sync, which trims table names, looked for `"Orders"` and failed. A table name now loses its leading and trailing spaces as soon as it enters the diagram: a diagram file that has such a name loads without them (and saves that way), and so does a table imported from a database whose name really has them. In the GUI, the name box keeps showing the spaces until the diagram is reopened. Column and constraint names are unchanged, because DDL and sync already agree on them
- **A diagram file that leaves a required name or type empty (`null`) is no longer loaded** — a table name, a column name, a column type or a query name written as `null` used to be replaced with a default (an empty name, the type `int`), and saving over the file then made that replacement permanent. Such a file is now refused by name and location instead, in the GUI, the CLI and the MCP server alike, because filling the value in would change what the diagram means. A `null` in an optional string such as a description or a memo is still read as empty text. Only a hand-edited file can carry these, since nothing in QuickER writes one

#### Bidirectional sync

- **A table whose download stops part way no longer holds back the tables after it** — every later table used to wait for the next run, with `SyncDownloadTruncation.TruncatedByTableName` naming the table that stopped it. The later tables now go on in the same run: a row that points at a parent behind the stopping point brings the parent in from the server first, or stops its own table when the parent cannot be had, so no row goes in without its parent. This also ends a run that stopped at the same row forever: when the server moved a child to another parent, deleted the old parent and created a new one with the same unique value, the stale local child kept the old parent, the new parent collided with it, and the child table that would have fixed the child was never downloaded. `TruncatedByTableName` is kept so that code using it still compiles, and is now always null
- **A `DateTime` primary key is written to the journal without its kind** — the key text was the round-trip form with its kind (`Z`, or the local offset), but neither database keeps the kind, so the text never matched the row read back: an offline insert of such a row was discarded as if the row were gone, and a later edit missed its receipt and came back as a false `DuplicateOnServer`. The text now leaves the kind out (the public `SyncKeyText.WithoutDateTimeKind` does the same to a text). Texts an earlier version wrote into the journal, the receipts and the owed blob copies are rewritten at the start of every run, so a local database kept from an earlier version goes on working as it is. A `DateTimeOffset` key is unchanged, because its offset is part of the value

#### Settings

- **Choosing the display language that is already shown no longer asks to restart** — after choosing another language and declining the restart, choosing the original language again asked for a restart that changed nothing. The menu check still shows the language used at the next start

### Fixed

#### DB sync & DDL

- **Dropping a column with a DEFAULT constraint now works on SQL Server** — the sync dropped the column alone, which SQL Server refuses while a DEFAULT constraint depends on it (error 5074), so the whole sync failed. The column's DEFAULT constraint is now dropped first. A CHECK constraint or an index of your own on the column still makes the drop fail, and the sync is rolled back
- **Dropping a column of a primary key or of a unique constraint now gives the same result in every database** — when only the column drop was selected, SQL Server refused the drop (error 5074), Oracle refused it for a multi-column constraint, PostgreSQL silently dropped the primary key or the unique constraint, MySQL narrowed it to the remaining columns, and SQLite applied the narrower primary key you had not selected. A unique constraint that uses the dropped column is now dropped with it, and the confirmation names each one; it is not re-created on the remaining columns. A column of the primary key is dropped only when the primary key change that removes it is selected too; otherwise the drop is left out of the script and the confirmation names it
- **Renaming a table in the diagram no longer fails when the new table keeps the old table's unique constraint names (SQL Server, PostgreSQL, Oracle)** — the sync script added the new table before dropping the old one, and these databases keep constraint names unique across a schema, so the new table's unique constraint collided with the old one. Tables are now dropped before tables are added. On MySQL and Oracle, where DDL is committed implicitly, the old table stays dropped if adding the new one fails; running the sync again adds it
- **A description made only of spaces no longer shows up as a difference right after its DDL is applied** — the DDL skipped such a description, but the comparison treated it as a real description, so the next comparison always showed one difference. A description made only of spaces now counts as no description in the DDL, the comparison and the sync script alike, and syncing it removes the description from the database
- **On MySQL, adding a column no longer sets its description unless the description item is selected** — the added column got its description in the `ADD COLUMN` statement even when the description item was not selected; on the other dialects only the description item writes it. The description is now written only by the description item, on MySQL as well
- **Changing the columns of a named unique constraint and adding an unnamed one on its old columns no longer fails the sync** — unique constraints were paired by their columns alone, so the new unnamed constraint matched the database's constraint, and adding the named constraint on its new columns failed because the database still used that name (SQL Server, PostgreSQL, MySQL and Oracle). A unique constraint you named in the diagram is now paired with the database's constraint of the same name first, so the change becomes a recreate of the named constraint plus an added unnamed constraint. A constraint without a name in the diagram is still paired by its columns
- **On MySQL, a description with emoji no longer shows up as a difference after it is synced** — MySQL saves each character outside the Basic Multilingual Plane in a description as `?`, so the comparison always found the diagram's emoji and the database's `?` different, and syncing again changed nothing. The comparison now treats such a description as the `?` form MySQL stores. The sync confirmation names each description that loses characters this way, and the DDL writes a note before it
- **Two unnamed relationships between the same pair of tables no longer get the same foreign key name** — both were named `FK_{child}_{parent}`, so the DDL failed on the second one. The second now gets the child's column names appended (`FK_Orders_Customers_ShipCustomerId`), the same name the imports already gave such a relationship, and DB sync and its comparison use the same names, so a database built from the DDL shows no foreign key differences. The diagram itself is not changed: the relationships stay unnamed. Such relationships come from older versions, hand-edited files, or a relationship whose name was cleared, because creating one in QuickER already picks a unique name. A many-to-many relationship, or one with no column pairs, does not take the default name, because the DDL creates no foreign key for it: the real foreign key between the same tables keeps `FK_{child}_{parent}`, as earlier versions named it
- **Selecting items in the DB Sync dialog for a large SQLite database no longer lags** — the plan is rebuilt on every checkbox change, and for each table to rebuild it searched every foreign key and, for each one, the whole table list again; with 500 tables to rebuild and 800 foreign keys this took about a second per click. Foreign keys are now resolved once per plan (about 5 ms for the same case)
- **Comparing against a database with tables or columns whose names differ only in letter case no longer fails** — PostgreSQL's quoted identifiers let `"Dup"` and `dup` exist side by side and the import brings both back, but the comparison indexed names ignoring case and stopped with a duplicate-key error, so the DB Sync dialog could not work with that database at all. Names are now paired with an exact match first, then ignoring case only where that is unique on both sides; a name that stays ambiguous shows up as an addition or a removal instead of being paired by position
- **SQLite: a sync no longer leaves foreign key checks turned off on the pooled connection** — the sync turned foreign key checks off outside the transaction and returned the connection to the pool that way, so a connection opened later with the same connection string could skip the checks (the bundled SQLite checks them by default). The sync now restores the setting it found
- **SQLite: a rebuild no longer fails when a view refers to the rebuilt table** — since SQLite 3.26 the `RENAME` at the end of a rebuild re-checks every view, so it failed once the old table was dropped (even an unrelated broken view made every rebuild fail). The rebuild now turns on `PRAGMA legacy_alter_table` while it runs, and a sync that really breaks a view (one that refers to a dropped column) rolls back and names the view
- **SQLite: child rows without a parent that already exist no longer make every sync fail** — the foreign key check after the sync looked at the whole database. It now fails only when the sync adds violations
- **MySQL: altering a column's type no longer clears or replaces its comment** — the `MODIFY` took the comment from the diagram even when the description change was not selected. It now keeps the comment in the database
- **Oracle: altering only a column's type no longer fails** — `MODIFY` always added `NULL` or `NOT NULL`, which Oracle rejects when the column already has that setting (ORA-01442 / ORA-01451). The clause is now added only when nullability changes
- **SQL Server: altering the type of a primary key column now succeeds** — the key was left in place, so `ALTER COLUMN` always failed with Msg 5074. The primary key is now dropped and added back with the same columns around the change (named `PK_{table}`)
- **MySQL: altering the type of a column on either end of a foreign key now succeeds when both ends get the same type** — MySQL rejects the change while the foreign key exists, and sync did not drop it. The foreign key is now dropped and re-added around the change
- **Sync no longer drops a foreign key it cannot add back when the change leaves its two ends with different types** — altering only one side dropped the foreign key, changed the column, and then failed to re-add it, which on MySQL left the foreign key missing. Such a foreign key is now left in place, so the column change fails without changing anything, and the execution confirmation names it
- **MySQL: changing the primary key now works when a foreign key of the same table relies on the old key's index, or when the old key column is `AUTO_INCREMENT`** — both failed (errors 1553 and 1075). The foreign key is dropped and re-added around the change, and `AUTO_INCREMENT` is removed from the old key column (the diagram does not model it, so it is not added back)
- **A foreign key whose child table or column is dropped in the same sync is no longer re-added** — changing a referenced primary key while dropping the child table failed because sync tried to re-add the foreign key to the dropped table
- **An unnamed relationship no longer shows a foreign key difference after its DDL has been applied** — the DDL names an unnamed foreign key `FK_{child}_{parent}`, but the diff compared the empty name, so every sync listed the foreign key as added (selected by default) and dropped, and running it with the default selection failed because the name already existed. The diff now matches by the same default name
- **A foreign key whose referential actions, column pairs, or referenced table alone changed is now one "recreate" item** — it was listed as a drop (unselected) and an add (selected) under the same name, so running with the default selection failed on the duplicate name, and on SQLite the rebuilt table kept the old and the new foreign key side by side. The new `AlterForeignKey` item drops and re-adds the foreign key, and like the other alter items it is unselected by default
- **SQLite: changing a column's type no longer drops its unique constraint or reorders a composite primary key** — when the diagram's column IDs differ from the database's (always the case for a diagram drawn or opened in the GUI), the rebuild replaced the database's column with the diagram's, so a unique constraint on that column silently disappeared from the rebuilt table and a composite primary key could come back in a different order. The rebuild now keeps the database's column and copies only the type, nullability, and computed flag from the diagram
- **SQLite: a rebuild no longer changes the primary key unless the primary key change is selected** — selecting only a column type change, or a new column that the diagram marks as part of the primary key, changed the primary key even though the primary key change was left unselected. Only the selected primary key change now decides the primary key
- **SQLite: changing a referenced primary key now warns about foreign keys that would lose their candidate key** — the other dialects warned before running, but on SQLite the sync just failed with `foreign key mismatch` and rolled back. The execution confirmation now shows the same warning
- **SQLite: the rebuild warning now also lists `WITHOUT ROWID`, `STRICT`, `DEFERRABLE INITIALLY DEFERRED`, and `ON CONFLICT`** — a rebuild dropped them without any warning
- **A table name with leading or trailing spaces no longer makes DDL and sync disagree about constraint names** — for an unnamed foreign key or primary key, the DDL turned a leading space into `_` (`FK__Orders_…`) while sync trimmed the table name before building the name (`FK_Orders_…`), so a sync could try to drop a constraint that did not exist. DDL, sync, generated code and the tools now all trim the name first and then replace dots and spaces with `_`. Only a diagram whose JSON was edited by hand can have such a name
- **A stale script can no longer be run after recalculating the diff fails** — when a recalculation failed, the previous diff and script stayed and could be run. The same happened when the re-read after a failed run (which follows partial application on MySQL / Oracle) failed because the connection dropped: once the connection came back, the old script could be run again. A failure now clears the diff and the script, and nothing can be run until a recalculation succeeds
- **When running the sync script ends with an exception, the error is now shown and the diff is re-read** — when the run was interrupted by an exception (a dropped connection, for example), it was only reported in the status line and the previous diff and script stayed, so on MySQL / Oracle the same script could be run again after a partial application. As with a failed run, the error is now shown in a dialog and the diff is re-read (if the re-read fails too, nothing can be run until a recalculation succeeds)
- **Other operations are no longer accepted while the diff is recalculated or the script runs** — running during a recalculation sent an old script, and closing with Esc or the button during a run returned to the caller while the DDL kept running outside the dialog. While either is in progress, Recalculate Diff, Execute, Select All, and Deselect All are disabled, and the dialog cannot be closed while the sync script runs (it can be closed during a recalculation)
- **When generating the script fails during a recalculation, the reason now stays in the status line** — it was written and then immediately replaced by the count of differences, so on first opening the dialog (the most common path) the reason never showed
- **Select All and Deselect All no longer regenerate the script once per item** — the plan and script were rebuilt for every item, so the more differences there were, the slower it got, quadratically. They are now rebuilt once per operation
- **A column whose type is written as another spelling of the same type no longer shows a type change that survives the sync** — a database does not remember a declaration as written (SQL Server returns `numeric(18,0)` as `numeric(18)`, `datetime2(7)` as `datetime2`, and `rowversion` as `timestamp`; Oracle returns `TIMESTAMP` as `TIMESTAMP(6)` and `INTEGER` as `NUMBER(*,0)`; PostgreSQL returns `timestamp` as `timestamp(6)` and `numeric(18,0)` as `numeric(18)`; MySQL returns `decimal(12)` as `decimal(12,0)` and a bare `decimal` as `decimal(10,0)`), so the spelling in the diagram or the type list disagreed with the imported one and the difference stayed after running the sync. Types are now compared after bringing both sides to the spelling the database returns. Types that differ in meaning (`datetime2(3)` and `datetime2`) are still a difference
- **Switching to SQL Server or Oracle now lists lengths and precisions beyond the target's limits as unconvertible, and switching to SQL Server or MySQL lists a `decimal` without a precision as well** — SQL Server's `nvarchar(5000)`, `varchar(9000)`, `decimal(50,2)`, `datetime2(9)` and `nchar(max)`, Oracle's `NVARCHAR2(4000)` (what the common SQL Server `nvarchar(4000)` turns into), `NUMBER(39)` and `TIMESTAMP(10)`, and MySQL's `datetime(7)` and `decimal(66,2)`, were written out as types the DDL then failed on, and Oracle's `NUMBER` or PostgreSQL's unconstrained `numeric` became a bare `decimal` (`decimal(18,0)` on SQL Server, `decimal(10,0)` on MySQL), a column that quietly rounds away the fractional part. Oracle's `NUMBER(*,2)` (no precision limit, a scale of 2) was written out for PostgreSQL as a bare `numeric` that drops the rounding to two places, and is now listed too. Oracle's limits for strings and `RAW` are those of `MAX_STRING_SIZE = STANDARD`, the default, so a column beyond them is listed even for an `EXTENDED` database
- **Oracle: a foreign key with `ON UPDATE` or `ON DELETE SET DEFAULT` in the diagram no longer leaves a foreign key difference after every sync** — Oracle has neither, and the sync creates the foreign key without the clause, so after importing again it came back as `NO ACTION` and every diff offered to recreate it (running only the add failed with `ORA-02275` on the duplicate name). Those settings in the diagram are now compared as `NO ACTION`
- **Oracle: switching the target DBMS now handles `NUMBER(*)` and `NUMBER(*,s)` as declared** — `NUMBER(*)` (a floating number, like a bare `NUMBER`) was read as an integer, and a number with a scale but no precision lost its scale when written out for Oracle, becoming a bare `NUMBER`
- **MySQL: an `enum` / `set` column longer than 200 characters no longer stops DDL generation and sync** — the 200-character limit on a type was applied to value lists too, so a single real `enum` with a dozen or so values made the whole diagram's DDL and sync script be refused. Value lists have no length limit
- **A data type followed by `AS` (a generated column), `AUTO_INCREMENT`, `AUTOINCREMENT`, `INVISIBLE`, `VISIBLE` or `CONSTRAINT` is now refused by DDL generation and sync** — `int AS (price)` or `int AUTO_INCREMENT` appends a column clause to the type, produces valid DDL, and turns a column the diagram says is neither computed nor auto-numbered into a generated or auto-numbered one in the database (the generated code's INSERT then fails at run time). Like `NOT NULL`, it is refused with the column named
- **Oracle: a sync script run by hand in SQL*Plus no longer runs each statement twice** — every statement was followed by a `/` line, and SQL*Plus runs the previous statement again on `/`, so the second `CREATE TABLE` or `ALTER TABLE … ADD` stopped the script with ORA-00955 / ORA-01430. Ordinary statements now end with `;` only, and a `/` line follows only a PL/SQL block, as in the generated DDL. QuickER's own sync splits a script by the same rules as SQL*Plus, so it was not affected, and a script that still has a `/` after an ordinary statement also runs each statement once
- **Oracle: switching the target DBMS no longer turns a fixed-length string of maximum length into a one-character column** — a `nchar(max)` / `char(max)` type was written as a bare `NCHAR` / `CHAR`, which Oracle creates as one character long. Oracle has no fixed-length type of unlimited length, so such a column is now listed as one that cannot be converted
- **MySQL: `SET DEFAULT` on a foreign key is no longer written out as if it worked** — InnoDB accepts `ON DELETE SET DEFAULT` / `ON UPDATE SET DEFAULT` and stores it, but deleting or updating the parent row then fails, exactly as with `NO ACTION`. The DDL and the sync script now leave the clause out with a comment saying so, and the diff compares the setting as `NO ACTION`, as it already did for Oracle. A database that already has such a declaration behaves the same as before and shows no difference
- **PostgreSQL: changing a column to a type of another family now works** — a sync from `varchar` to `integer`, `text` to `date` or `integer` to `boolean` failed with 42804, because PostgreSQL converts without `USING` only where an assignment cast exists. Such a change is now written with `USING column::new_type`. A change to a string type is still written without it, so shortening a `varchar(n)` below an existing value fails instead of cutting the value off
- **MySQL: switching the target DBMS now keeps the range of unsigned and signed integers** — `unsigned` was ignored, so an `int unsigned` column became a 32-bit integer on SQL Server and PostgreSQL, too narrow for its values, and a signed `tinyint` (-128 to 127) became SQL Server's `tinyint` (0 to 255). Integers are now converted to a type that holds the whole range: `smallint unsigned` to a 32-bit integer, `int unsigned` to a 64-bit one, `bigint unsigned` to `decimal(20,0)`, and a signed `tinyint` to a 16-bit one. Generated code for such columns now records the original spelling in `[DbColumnMeta(..., NativeType = "int unsigned")]`, so taking the code back yields the same type; the property's C# type (`uint` and so on) does not change
- **SQL Server: descriptions of a table written without a schema now go to the same table as `CREATE TABLE`** — the table was created in the connecting login's default schema, but its description was always written to `dbo`, so for a login whose default schema is not `dbo` the description failed and the whole sync rolled back. The description now takes the schema from `SCHEMA_NAME()` (a `DECLARE @default_schema sysname = SCHEMA_NAME();` line appears in the DDL and before each description statement of the sync script). Tables written with a schema are unchanged
- **SQLite: switching the target DBMS now converts multi-word type names** — a column typed `double precision` or `character varying(20)` (common in databases made by other tools and in DBML) was listed as unconvertible, although generated code typed it correctly. Such names are now read the same way by both
- **Syncing a diagram whose table or column names differ from the database's only in letter case now reaches the real table** — the diff pairs such names, but the script wrote the diagram's spelling in quotes, so on Oracle a table created without quotes (stored as `ORDERS`) could not be reached from a diagram's `Orders` (ORA-00942), and dropping its old primary key quietly found nothing; PostgreSQL had the same problem with tables stored in lower case. The script now writes the database's spelling for every table and column it paired. Tables and columns that exist only in the diagram are still created with the diagram's spelling, and the diagram itself is not changed
- **MySQL: dropping a unique constraint whose index is the only one supporting a foreign key no longer fails** — the drop failed with error 1553 and left the earlier statements applied. The foreign key is now dropped and re-added around it
- **MySQL: a foreign key between string columns of different lengths no longer blocks changing one end's length** — MySQL allows `varchar(50)` and `varchar(100)` on the two ends, but sync treated them as a type mismatch and did not drop and re-add the foreign key, so a change crossing the 255-byte boundary failed (error 1832)
- **On SQL Server and PostgreSQL, altering a column no longer resets its collation to the database default** — the type was changed without `COLLATE`, so a collation set on the column was lost. The collation is now read back at execution time and written again (on PostgreSQL only when it differs from the type's default)
- **On SQL Server, changing the type of a column with a DEFAULT constraint no longer fails** — `ALTER COLUMN` with the constraint still in place was refused with error 5074. The constraint is now dropped, the type changed, and the constraint added back with the same name and definition
- **On PostgreSQL, the sync can now move the primary key of a table with a dot in its name (such as `sales.orders`) and drop its foreign keys whose name is unknown** — the constraint name lookup was fixed to the `public` schema, so the old primary key of such a table was not found and the sync failed. The lookup now targets the same table as `ALTER TABLE` (`to_regclass`), and does nothing when the table does not exist
- **PostgreSQL and Oracle: a foreign key between string columns that differ only in length no longer blocks moving the referenced primary key** — these databases also allow different lengths on the two ends, but sync treated them as a type mismatch and did not drop and re-add the foreign key, so dropping the primary key was blocked by it. On Oracle this applies only when the length unit (`CHAR` / `BYTE`) is the same on both ends
- **When a column change leaves one foreign key with mismatched types, no foreign key is dropped any more** — the column change fails anyway, and dropping the others (another foreign key on the same column, or one on a parent column it refers to) left them dropped on MySQL. The same check now also applies when a primary key change re-adds a foreign key whose column type changes
- **Two foreign keys on the same column pair no longer interfere with each other** — explicitly dropping one of them made SQL Server keep the other one in place, so the column change it needed failed, and on SQLite changing one of them dropped both
- **SQLite: a table selected for removal is no longer rebuilt first** — it was rebuilt and then dropped, which did nothing but take time and warn about losing attributes
- **SQLite: a change the rebuild cannot apply is no longer reported as done** — a unique constraint on a column dropped in the same sync, for example, was dropped from the rebuild silently, the sync succeeded, and the same difference came back next time. It now stays in the script with a comment saying it was skipped
- **SQLite: the warning about attributes a rebuild drops is more accurate** — it no longer counts `NOT DEFERRABLE INITIALLY DEFERRED` or a foreign key's `ON DELETE SET DEFAULT`, which a rebuild keeps, and it no longer misses a keyword written right after a string literal or comment (`DEFAULT'a'COLLATE NOCASE`)
- **A table or column whose type QuickER would refuse to write can now be dropped by sync** — the type check also looked at the columns of tables and columns being dropped, whose types are never written, so such a table could not be removed
- **A primary key column is no longer reported as changing from `NOT NULL` to `NULL`** — a diagram that left a primary key column marked nullable produced a change that could not run; nullability is now compared as it takes effect (a primary key column is `NOT NULL`)
- **Smaller fixes in the comparison** — table, column and constraint names containing `|`, `>` or `,` no longer make two different foreign keys look the same; a long description is no longer cut in the middle of a surrogate pair; a dropped unique constraint no longer warns about a foreign key that the same sync removes; and two unnamed foreign keys between the same tables are re-added under the names the DDL gives them
- **Unique constraints and foreign keys now line up with their columns when names contain a letter such as the Kelvin sign** — the comparison paired tables and columns ignoring letter case, but built the keys for unique constraints and foreign keys by lowering the letters, and a few letters lower to the same letter as a different one (the Kelvin sign `K`, U+212A, and `k`). So after renaming such a column, the unique constraint on it showed no change while the column itself was added and removed; renaming a foreign key from `FK_K` to `FK_k` showed no change; and changing the type of `k` showed a warning that the foreign key on the Kelvin sign column would end up with mismatched types. Every name in the comparison now follows the same rule
- **The column order notice in DB Sync (SQL Server, PostgreSQL, Oracle) names a table the way the database spells it** — when the diagram spelled the table with different letter case, the notice used the diagram's spelling while every other item for that table used the database's
- **The `Generated at` line at the top of the DDL now uses the Gregorian calendar on every system** — it followed the system's culture, so on a Thai system the year came out in the Buddhist calendar (2569). It is now always `yyyy-MM-dd HH:mm:ss` in the Gregorian calendar
- **A negative scale (`numeric(10,-2)`, `NUMBER(10,-2)`) is now written with an ASCII minus sign on every system** — switching the target DBMS and importing from Oracle formatted the scale with the system's culture, so on a Swedish system it came out as `numeric(10,−2)` (U+2212), which the database rejects
- **On a Turkish system, the SQLite rebuild warning no longer misses `AUTOINCREMENT`, `DEFERRABLE INITIALLY DEFERRED`, `WITHOUT ROWID` and `STRICT`** — the case-insensitive matching followed the system's culture, where `I` and `i` are not the upper and lower case of each other, so these keywords written in lower case were not found
- **SQL Server: DB sync and code generation no longer stop with an error on a column type whose length or precision has full-width digits** — `float(２４)`, `decimal(１０,２)` and `datetime2(３)` matched the pattern for a number but could not be read as one, so the comparison of type notations threw `FormatException`

#### Diagram editing

- **Pressing Delete in the column list of the property panel now removes the column the same way as the row's delete button** — the list removed the selected column directly, so the removal could not be undone, the diagram did not count as changed (an automatic reload after an outside change could drop it without asking), and a unique constraint kept the removed column. Delete now runs the same command as the row's delete button: it can be undone in one step, and a unique constraint that uses the column is removed with it. With no column selected, Delete in the list does nothing, and while you edit a cell it deletes a character as before
- **Undoing a relationship that used a column you had marked as a foreign key by hand no longer clears that mark** — once a column becomes a relationship's child column, the relationship takes charge of its foreign key mark, so undoing the relationship's creation, or undoing a change of the column pair that picked the column, removed the mark you had set yourself and the diagram no longer matched what it was before. Undo now restores the mark as it was. Deleting the relationship still clears the mark, as before
- **Switching the target DBMS or importing no longer applies to a diagram that changed while its confirmation was open** — the switch and the imports (Excel definition documents, Mermaid, DBML, a database, C# code) prepared their result from the diagram before asking, and applied it after. If the diagram changed while the confirmation was open (an automatic reload after an outside change, or an edit by the built-in chat), the switch changed the dialect of the new diagram without converting its columns, and an import replaced the new diagram with a result built from the old one, discarding the change (after a reload, the next save would then overwrite the outside change). Confirming now does nothing in that case and says so: the switch in the status bar, an import in a dialog. Run it again
- **A relationship to a table with a composite primary key now pairs each key column with the right child column** — when you create a relationship, or call `add_relationship` from the built-in chat or MCP without columns, or import Mermaid, QuickER pairs every primary key column of the parent with a child column it infers from the names. It looked for a column named after the parent table (`OrderId`) before a column with the key column's own name, so with a composite key the second key column picked the same `OrderId` and was dropped (`Orders(OrderId, Revision)` got a foreign key on `OrderId` alone, which the DDL then rejected), or the first one took the wrong column (`Projects(TenantId, ProjectId)` paired `TenantId` with the child's `ProjectId`). With a composite key, columns named exactly like a key column are now matched first, and a child column already chosen is no longer offered to the next key column. A single-column primary key is paired as before
- **A relationship created by hand no longer takes a constraint name another relationship already uses** — the default name `FK_{child}_{parent}` can be the same for two different pairs of tables when the table names contain `_` (child `A_B` with parent `C`, and child `A` with parent `B_C`, are both `FK_A_B_C`), and the DDL then failed at the second `ADD CONSTRAINT`. A name already used by another constraint in the diagram now gets the child's foreign key column names appended, and then a number, which is what `add_relationship` in the built-in chat and MCP already did. Without a clash the name is the same as before, and undoing the creation is still one step
- **A long description no longer makes the diagram stall while it redraws** — laying out a wrapped description searched for each line break by measuring text up to the whole remaining paragraph, so the cost grew with the square of the description's length (measured at 200px wide: 65 ms for 10,000 characters, 2.3 s for 50,000). The search now brackets the line length first and measures only around it, which is 7 to 47 times faster (measured: 9 ms and 49 ms) and wraps at exactly the same places
- **Typing in a table's memo no longer takes one undo per keystroke** — the memo box committed on every character, so undoing five characters took five presses of Ctrl+Z and the undo history filled up with them. It now commits when you leave the box, like every other field in the property panel, so what you typed is one step. Collapsing the panel still commits what you typed
- **Auto-arranging a large diagram on a grid no longer freezes the window** — "Grid" searches for an arrangement with fewer crossing relationship lines, but the search was exhaustive and grew roughly with the cube of the table count (measured: 6.2 s at 200 tables, 88.7 s at 400; creating a diagram from a database, from the AI or from C# code waits for the arrangement to finish). Pairs that cannot possibly interact are now ruled out before the check, which made it 4 to 9 times faster, and the search has a cap on how many checks it may make: when the cap is reached it keeps the improvements found so far and stops (measured: under 1.5 s at every size). The cap counts checks rather than time, so the same diagram always comes out the same way. Diagrams that stay under the cap (measured up to about 200 tables and 200 relationships) are arranged exactly as before; above it more crossings remain (measured at 400 tables: 223 crossings became 868, total line length +40%, occupied area unchanged)
- **Creating a relationship stops when its starting table leaves the diagram** — after you picked the first table, deleting it, undoing its creation, or opening another diagram (including the automatic reload after an outside change) let you create a relationship from a table that was no longer in the diagram. The line followed no table, and for a deleted table the saved relationship pointed at a table that did not exist. Relationship creation is now cancelled as soon as its starting table leaves the diagram
- **Pairing a new relationship's columns now recognizes more plural table names** — the foreign key column is found by turning the parent table's name into `{singular}_id`, and the singular was guessed by always dropping `es` after `s`, `z`, `ch` or `o`, so `courses` became `cours`, `warehouses` `warehous`, and `purchases` and `responses` likewise. The expected `course_id` was then not found, and pairing fell back to any column marked as a foreign key, which could be the wrong one. Where the ending does not decide whether to drop `es` or only `s`, both spellings are now tried. Likewise, a name ending in `ies` used to become only `y` (`movies` became `movy`), so `movie_id` was never found; both `y` and dropping only the `s` are now tried. This applies when you create a relationship, to the `add_relationship` tool of the built-in chat and the MCP server, and to the relationships a Mermaid import creates
- **Redoing (Ctrl+Y) the removal of a unique constraint while a relationship that references it is selected no longer closes the app** — when a foreign key referenced only the columns of a unique constraint and that constraint went away, the column pairing field dropped the column from its choices. A column dropped from the choices also lost its selection, which was then treated as your own edit, so the column pair disappeared and the app closed partway through. Undo (Ctrl+Z) and the built-in chat's tools could do the same when they changed the constraint. A column you picked now stays among that row's choices even after it stops being a primary key or part of a unique constraint, so the pair stays as long as the column exists, and removing the constraint can be undone in one step. Such a column is not offered to rows you add afterwards
- **Reordering columns no longer lists the same column twice in the column choices of a unique constraint or a relationship** — the choices followed a reorder by removing and inserting only, so each move added another copy of a column (moving B to the front of `A, B, C` gave `B, A, C, B, C`). The choices now follow the column order without duplicates, and the column you picked stays selected when you reorder
- **Buttons and check boxes you reach with Tab or other keys can now be pressed with Space** — to pan the diagram (drag while holding Space), Space was taken for the whole window, so outside text boxes neither the toolbar buttons nor the check boxes in the property panel (such as PK in the column list) could be pressed with Space. When you move to a button, check box, combo box, list item or grid cell with Tab or another key, Space now presses that control. Right after you click a button with the mouse, and right after you come back from another window, Space still pans, so that looking around with Space and a drag after pressing a toolbar button does not press that button again. Space on the canvas pans as before
- **The resize pointer now appears at the right edge of a table** — a table can be widened by dragging its right edge, but the pointer kept its normal shape there, so the place to grab was hard to find. The pointer now changes to the left-right resize arrow over the right edge of a table (not while you pan with Space)
- **Dragging a table no longer turns into a rubber-band selection** — when a press on the blank area of the diagram never got its release (for example, the button was released outside the diagram), the unfinished selection stayed armed, and a later drag of a table could start a rubber-band selection that took the drag away from the table. Each press now discards an unfinished selection
- **Pressing a relationship line or its label and moving the mouse slightly no longer starts a rubber-band selection** — the press selected the relationship, and moving the mouse a few pixels then started a rubber-band selection that replaced the selection, so the relationship you had just selected was deselected. A press on a relationship (including the area around its line where you can click it) now selects it as before and does not start a rubber-band selection
- **Columns are reordered only by a drag that starts on a row header** — in a table's column list, a drag that started in a cell and then moved over a row header reordered the columns
- **Turning PK or FK on or off for a column in the compact view now resizes the table** — the compact view shows only PK and FK columns, but the table kept its previous height, so relationship lines, the minimap, and auto-arrange used the old height (creating a relationship in the compact view was enough to cause it)
- **Undoing the deletion of tables puts the tables and their relationships back where they were** — undo added them to the end of the diagram, which changed the order of the tables in the saved file and in the generated DDL, and which table is drawn on top
- **Turning NULL on or off for a column that is not in the primary key can now be undone** — toggling the NULL check box in the column list was not recorded, so Ctrl+Z could not revert it, and it did not count as an unsaved change either (the automatic reload after the file changed outside the app, New, and Open discarded it without asking). When the NULL setting changes because the column joins or leaves the primary key, it still goes back together with the primary key in one undo
- **One undo after changing a relationship to many-to-many now also restores its referential actions** — changing to many-to-many resets the delete and update actions to their defaults, and that reset was recorded as a separate step, so the first Ctrl+Z restored only the type and the column pairs and left the actions at their defaults
- **Undoing the addition of a table, column, or relationship now clears the selection of it** — after undoing an add, paste, or duplicate, the property panel kept showing the removed table. Editing it there was recorded neither in the undo history nor as an unsaved change, and redo (Ctrl+Y) brought the table back with those unrecorded edits. Text being typed when you undo is no longer written to the removed table
- **Search no longer selects a table that was deleted or reloaded** — with the search box open, pressing Enter after deleting a table or reloading the diagram selected a table that was no longer in the diagram, and deleting it after a reload also removed the named queries of the table with the same name. Enter now finds the matches again in the current diagram before moving on
- **Undoing the deletion of a relationship puts it back where it was** — undo added it to the end, so when two unnamed foreign keys joined the same pair of tables their default constraint names swapped, and the next DDL or database sync showed both foreign keys being dropped and re-created
- **Changing the title color of several tables with another spelling of the same color no longer marks the diagram as changed** — a lowercase color code or surrounding spaces counted tables that already had that color as changed, which added an undo step and an unsaved change
- **Arranging, undoing, redoing, deleting many tables at once, and dragging a group no longer freeze a large diagram** — the minimap and the canvas size were rebuilt every time a position or width changed, so a single undo of an arrangement took about 18 seconds on a 500-table diagram. They are now rebuilt once at the end of each operation, which takes about 0.3 seconds on the same diagram. Toggling the NULL display, renaming a column, and adding a column also no longer trigger unrelated recalculations
- **Undoing the deletion of a single table brings the table back selected** — the restored table was drawn with its selection frame, but the property panel was empty and the delete button was disabled. The table that was selected just before the deletion is selected again. Undoing the deletion of several tables now also reselects the table you last selected before the deletion, rather than the first one
- **Undoing the addition or duplication of a table also removes the named queries defined on it** — queries defined after the addition stayed behind where no dialog could open them, and every code generation warned about them. Redo puts the queries back in their original position
- **The minimap now shows table moves and title color changes right away** — right after a table was moved, the relationship line still pointed at its previous position, and a title color change did not appear until some other change happened. Changing the color of several selected tables at once rebuilds the minimap only once
- **The key-column and unique-constraint column editors no longer drift from the diagram** — switching a relationship without column pairs to many-to-many kept a half-filled row, which came back when switching back to one-to-many, and a constraint row whose selection had dropped from the display could not be removed with ×. When a row is removed and the rows below move up, each new selection is now added to the candidates before it is applied
- **SVG export and printing no longer split an emoji where a description wraps** — a line break could fall inside an emoji (a character stored as two UTF-16 units), which left a blank (SVG) or a replacement mark (printing) on both lines

#### Diagram files

- **The auto-saved diagram is no longer restored with the record of a different file** — the auto-save writes the diagram (`last_diagram.json`) and the record of the file it belongs to (`gui-settings.json`) separately. When only the record failed to be written, or QuickER stopped between the two writes, the next start opened one diagram with the path of the previous file and no unsaved changes, and Save overwrote the previous file with the other diagram without asking. The record now carries the hash of the diagram written with it, and when the two do not match at startup the diagram is restored as untitled with unsaved changes and the status bar says so (Save then asks where to save). A record written by an earlier version has no hash and is restored as before
- **Files whose name is 219 to 255 characters long can now be saved** — a save first writes a temporary file in the same folder, named after the target plus 37 characters, so a long name pushed the temporary name past the 255-character limit and saving the diagram, an export, generated code or mock output always failed. The temporary name now keeps the start of the original name and is cut to fit
- **Saving where a file cannot be replaced in place (such as a folder synchronized to the cloud) now keeps the target's attributes and access control** — the move used instead of the replacement dropped the hidden and system attributes and the access control list (ACL). They are now copied back after the move (if they cannot be, the save still succeeds; the ACL is copied on Windows only)
- **A change written to the open diagram file while QuickER was reading it is no longer missed** — after opening a file, or reloading it because another program changed it, QuickER read the file a second time to record what it had loaded. If an AI agent or another tool wrote to the file between the two reads, QuickER recorded the new contents as the ones it had loaded: the diagram on screen stayed the old one, marked as having no unsaved changes, and the next Save overwrote the other program's change without asking. QuickER now records exactly what it read, so such a change is picked up and reloaded like any other change from outside
- **Opening, importing, and reloading a large diagram after an outside change is faster** — when the whole diagram was replaced, every added relationship reapplied the foreign key marks and edit locks to every column of every table, so the time grew with relationships times tables (measured: 0.26 s for 200 tables and 300 relationships, 1.9 s for 500 tables and 800 relationships). This now happens once at the end of the replacement (measured: 0.05 s and 0.13 s). The resulting diagram is the same as before
- **The confirmation for an outside change no longer stacks** — when the diagram file changes outside QuickER while you have unsaved changes, QuickER asks whether to reload. If the file changed again while that dialog was open, a second confirmation opened on top of it. A change that arrives during the dialog is now checked once against the file after the dialog closes, and you are asked again only if the file changed further (if you chose to reload, the latest content is already loaded and you are not asked). A change notification for content that is already loaded now does nothing (it used to cancel a table drag)
- **Watching the diagram file for outside changes no longer stops for good when its folder is briefly unreachable** — when a network share or USB drive dropped for a moment, the watch could not be restarted and stayed off, so outside changes went unnoticed for the rest of the session. QuickER now keeps retrying (at most every 30 seconds) and resumes watching once the folder is back, picking up any change made while it was off. The status bar says once that watching stopped and once that it resumed
- **Overwriting a diagram file whose `"Version"` is `null`, an object, or an array now asks first** — a version value QuickER cannot read (`"2"` or `2.0`) already made it ask before overwriting, but these three were treated as a file with no version and overwritten without asking. Only a hand-edited file can have one
- **An outside version you chose to keep editing over is no longer ignored after you save** — when the diagram file changed outside QuickER while you had unsaved changes and you chose to continue, QuickER remembered that version so as not to ask about it again. It kept remembering it after you saved, so if the file was later put back to exactly that content (for example by checking out an older commit), QuickER neither asked about the change nor asked before the next Save overwrote it. Saving, opening and reloading now forget it
- **A status bar message no longer disappears right after it appears** — a message is cleared after 5 seconds, but the timer of an earlier message could still clear a newer one that had just been shown

#### Settings

- **Removing a model from the history no longer closes the app when the AI settings file cannot be written** — when `ai-settings.json` could not be written (read-only, for example), the AI chat and mock generation connection settings let the exception through and the UI's handler for unhandled exceptions closed the app. When the file could not be read, the model looked removed although nothing was saved, and saving the connection settings was silently dropped. The × in the history now removes the model only when the change is saved and otherwise shows the reason in the status; saving the connection settings and recording the model of a successful turn also tell you when they could not be saved
- **After a failed backup of a corrupted settings file, the next save no longer copies the repaired settings over the backup** — when moving the corrupted file aside (to `{file name}.corrupt`) failed, the save went on, but the corrupted flag stayed set and the next save without a fresh read copied the now healthy file to the backup. The flag is cleared once the file is written
- **Load Settings in the code generation dialog now reads a CLI `quicker.json` written in PascalCase** — the CLI reads settings keys case-insensitively, but QuickER read only the camelCase keys it writes itself, so loading a `quicker.json` such as `{"RootNamespace": …}` threw every key away and silently reset the dialog to its defaults. Keys are now read case-insensitively in every settings file, and saving such a file writes each key once in camelCase. The CLI-only `OutputFileName` is not read, because it names a file without a folder
- **Turning "check for updates on startup" on or off, or choosing a display language, now tells you when the setting cannot be saved** — a settings file that was read-only, or that could not be read at that moment, left the menu showing the new choice while the file kept the old one, so the next start behaved differently from what the menu showed (and the language switch offered to restart into the language it had not saved). The menu now goes back to the saved value and an error explains why
- **A settings file with an explicit `null` no longer keeps the code generation dialog from opening** — a hand-edited `"repositoryDialects": null` made the dialog fail every time it was opened, for as long as the file stayed, and `"codeSubdirectory": null` made OK fail. A `null` for a setting that has no "empty" meaning is now read as "not specified" and gets its default, in every settings file (display language, AI and code-generation settings); the rest of the file is read as before
- **Settings written by a newer version are no longer lost when an older one saves** — settings files are saved by writing the whole object back, so any key this version does not know about disappeared on the next save. Unknown keys, including ones nested inside a section, are now carried over (the display language, AI settings and code-generation settings all go through the same store). Keys inside arrays are still not carried over. The connection profiles file (`connections.json`) does not go through this store and is unchanged
- **A momentary read failure no longer resets the settings to their defaults** — saving settings is a read-modify-write, so one failed read wrote the defaults back and took the display language, the update check and the code-generation settings (output path, namespaces, target DBs and the rest) with it. When the file cannot be read, QuickER now starts from the defaults but **does not save over it**, and resumes saving as soon as a read succeeds (the auto-save re-reads the file each time, so in practice the next save recovers on its own)
- **A corrupted settings or connections file is now moved aside before being overwritten** — to `{file name}.corrupt`, once only (a later corruption does not overwrite it, so what remains is the copy closest to the last good state). Previously such a file was simply overwritten with the defaults, leaving nothing to investigate afterwards
- **The display language menu no longer shows a check that differs from the saved language** — choosing the current language again removed its check, and a failed save left both languages checked. Clicking no longer toggles the check, which now only shows the saved language

#### Distribution

- **Installing an update no longer cuts QuickER off mid-session** — once you accepted an update at startup, QuickER downloaded it in the background and then ended itself the moment the download finished, without the usual shutdown. Changes you made while it downloaded were not written to the recovery file, and the processes started by AI chat and mock generation were left running. QuickER now asks again when the download finishes whether to restart now. Restarting closes QuickER the normal way before the update is applied; choosing Cancel applies the update the next time you close QuickER. Either way the update is applied only after a normal exit

#### Crash handling

- **The crash report no longer disappears while you are reading it** — if another error occurred while the crash report dialog was open, QuickER ended the process on the spot and the report vanished unread. An error that occurs while the dialog is open is now ignored, and QuickER exits after you close the dialog
- **A crash now stops the processes started by AI chat and mock generation before exiting** — a crash skips the normal shutdown, so codex, copilot, claude, and dotnet processes were left running. They are now stopped before the crash report dialog appears; while an AI conversation is running, the dialog can take a few seconds to show
- **The crash log no longer drops part of what went wrong** — an exception that bundles several failures (an unobserved asynchronous failure always takes this form) was logged with only its first failure; every one is now logged. And when two records picked the same file name at the same instant, the later one overwrote the earlier; each is now kept in its own file

#### Startup & restart

- **Restarting after you switch the display language no longer leaves QuickER closed** — the restart launches a new QuickER partway through shutting down, while the old one still held the "already running" marker, so the new one could conclude QuickER was already running and quietly exit. The marker is now released just before the new QuickER is launched
- **Choosing to restart for an update now brings QuickER back even when the update cannot be applied** — QuickER closes and leaves applying the update, and the restart, to the updater. When the updater could not be started, a restart asked for by switching the display language fell back to launching QuickER directly, but one asked for by the update's "restart now" did not, so QuickER stayed closed. Both now fall back the same way
- **Starting QuickER while it is running as administrator now explains why it cannot start** — when a QuickER with different privileges was running, a normal start could not check it and ended without showing anything (only a crash log was written). It now tells you to switch to the window that is already open, or close it and start again
- **Starting QuickER again now brings the window that is already open to the front** — a window behind other windows only flashed in the taskbar

#### Database import & generated code

- **A save hook that writes an unbounded binary column no longer leaves a stale row version on the saved entity** — the QuickER repository for SQL Server wrote back the version the save's own statement returned, so when an After hook wrote a blob of a saved row with `WriteBinaryColumnAsync`, the database held a newer version and the next save of the same instance failed as a conflict. The versions of the rows the save wrote are now read again before the commit and written back after it. A hook that writes a saved row with `ExecuteSqlAsync` still makes the next save of that instance report a conflict, since the SQL may have changed any column: read the row again before saving it
- **A failed unbounded binary write from a save hook on SQLite no longer leaves a half-written column** — the write set aside the declared length and copied into it, so a stream that ended early or failed left zeros and part of the data, which the save committed when the hook caught the exception. The write now runs inside a savepoint and rolls back to it when it fails
- **A blob a save hook writes in a synchronised graph save is now uploaded** — the journaling decorator recorded a graph save from the graph before it ran, so an unbounded binary column an After hook wrote through its context went unrecorded: it was never sent to the server, and the next download put the server's value back over it. The write is now recorded inside the save's transaction, so the entry commits or rolls back with the save. A hook running while the engine applies a download still writes without a record
- **A row a local save hook skips while the sync engine applies it is no longer lost** — the engine applied a batch with one save and counted every row as applied, so a row a `BeforeSaveAsync` returned `false` for was left out while the rows after it went in, and the resume point moved past it: the row never came down again, and a row `ServerWins` was putting back lost its journal entry and kept the local edit. The table's download now stops at the skipped row, reported in `SyncResult.Truncations` with the new `SyncDownloadTruncation.SkippedBySaveHook`, and the row comes down once the hook lets it through; a row `ServerWins` puts back keeps its entry. To find the row, a table whose local repository runs a save hook for its entity applies the downloaded rows one at a time, each in its own local transaction, which makes its downloads several times slower. `SyncTable` and `VersionlessSyncTable` take the hooks as a new optional `localSaveHooks` constructor argument, which the generated registration fills in; a table built without them throws when a hook skips one of its rows
- **A remote save now carries back what the server set on the rows** — the Insert, Update and Save responses carried only the row versions, so a value a server-side save hook set (an audit column, a key it assigned) and a value the server's EF Core repository read back after the save (a value the database generated) stayed on the server's copy. The client kept its old values, and the next save of the same entity wrote them back over the server's. The responses now carry the column values of the saved rows, which the client writes back; a Save response matches them to the rows by position, so a key a hook assigned reaches the right row. Excluded unbounded binary columns are not carried
- **A remote service whose server uses the EF Core repository no longer wipes excluded unbounded binary columns** — with `ExcludeUnboundedBinaryColumns`, the client sends an update with the excluded columns not fetched, as its update guard requires, and the server's EF Core repository wrote every column, so the stored blobs silently became NULL or empty. The server's reads also returned the blobs, so fetching a row, editing it and updating it always failed the client's guard, and `GetAllAsync` sent every blob. While serving a remote request, the EF Core repository now leaves the excluded columns of an updated row as they are stored, and the server returns entities with them not fetched, as a server using a QuickER repository does. An insert still writes the values that were sent, a named-query projection that references an excluded column still carries its value, and a direct EF Core repository still reads and writes every column
- **A graph save that deletes a row and adds a row with the same unique value now succeeds in the QuickER repositories** — when the new row came first in the collection or in the list of roots, it was inserted before the deletion and the unique constraint refused it. This includes an edit model collection, which places the rows removed with `Remove()` after the others. EF Core and the in-memory repository already saved it; a remote service whose server uses a QuickER repository failed the same way. Every backend now writes a new row that takes the primary key or a unique value of a row the same save deletes after the deletion, with the rows below it (see the three-stage order under Changed). Removing a row and adding one with the same key in the same save now replaces the row on every backend, whichever comes first; before, all three failed (a primary-key violation in the QuickER and in-memory repositories, a tracking conflict in EF Core). Where no row with that key exists, the new row is kept (the QuickER and in-memory repositories used to leave no row), and EF Core reports the deletion of the missing row as `NotFound`, the known asymmetry of a no-row delete
- **A graph save that moves rows away from a parent and deletes that parent now succeeds** — the QuickER repositories deleted the parent first when it came first among the roots or in a collection, so the foreign key refused the deletion, or a cascading deletion took the moved rows with it and their update then matched no row (`SaveConflictException` with `NotFound`). EF Core failed the same way whatever the order: an entity it had not loaded looked as if it had always pointed at its new parent. A remote service failed like its server. The updates now run before the deletion on every backend, and the EF Core repository reads the stored foreign keys of the rows it updates before saving. An updated row that takes a unique value of a row the same save deletes is now written after the deletion too: it failed in the QuickER repositories when it came first, and in EF Core when the deleted row had children
- **`Query().CountAsync` and `AnyAsync` now apply `Skip` and `Take`** — they counted every row the conditions matched, so `Take(1).CountAsync()` could return 3 and `Skip(3).AnyAsync()` could return `true` when no row was left to fetch. They now count the rows `ToListAsync` would fetch for the same query, on every backend
- **The EF Core repository now inserts a row whose key is `0`** — EF Core treated an integer primary key as one the database generates and left out a key of `0`, so inserting or graph-saving a row with key `0` failed. The generated `DbContext` now configures a single-column integer primary key with `ValueGeneratedNever()`, so the key is sent as the application set it, as the QuickER repositories do. A primary key marked as an identity column and a `Guid` primary key keep EF Core's convention (EF Core generates a `Guid` when the key is `Guid.Empty`), and a key of value-object type was not affected
- **The in-memory repository now honors a cancelled token** — only `BulkInsertAsync` checked it, so an insert, update, delete, graph save, bulk delete or read called with a cancelled token ran to the end. Every operation now throws `OperationCanceledException` before it reads or writes, as the database repositories do. The EF Core graph save also stops before its save hooks run when the token is already cancelled; it used to run the Before hooks first
- **A new child row of an edit model that is marked for deletion before it was ever saved is now left out of the save** — the mapper put it into the entity graph as a row to delete, so a row whose key was still empty failed the conversion, and a row with a key made the save delete a row that did not exist. The row is now dropped, and accepting the save takes it out of its collection
- **Two tables joined by relationships in both directions now generate when their navigation names would clash** — for example a one-to-one relationship from `customers` to `profiles` and another from `profiles` to `customers` gave `customers` two members named `Profile`, and generation stopped with a duplicate member error. All the relationships between the two tables are now named after their foreign-key columns in that case (`customer.Profile` and `customer.ProfileByCustomer`). Diagrams whose names did not clash, such as two one-to-many relationships in opposite directions, keep their names
- **Two foreign keys that join the same child column to the same parent column now stop generation with an error naming both constraints** — this used to be reported as a duplicate navigation member, which did not say that the foreign key itself was defined twice. Delete one of them
- **The generated `Read{Column}ToFileAsync` now replaces the file the same way the application saves** — it moved the temporary file into place without flushing it to disk, so a power loss could leave a short file, the target lost its attributes and access control, and a collision with another process failed at once. The temporary file is now flushed to disk, an existing target is replaced (moved over where that is not available), and a collision is retried a few times. The temporary file is named the same way as the application's saves, so a target whose name is 219 to 255 characters long can also be written
- **`NOT col LIKE 'abc'` (a `LIKE` without wildcards) no longer returns the rows where the column is `NULL`** — a string match never matches a `NULL` row in either direction, but the positive form was read as `=` and an outer `NOT` turned it into `<>`, which does match them. The two forms now behave alike on every backend
- **Generated query code no longer raises compiler warnings** — an `IN` on a nullable value object column (CS8604), a projection field declared non-null over a nullable string or value object column (CS8601), and the `cref` in the `[DbColumnMeta]` documentation that did not resolve when only the SQLite repository was generated (CS1574)
- **A skipped projection query no longer holds its result type name** — a later valid query that used the same name failed the whole generation as a duplicate of a DTO that was never emitted
- **Raw SQL checks** — `;WITH cte AS (…)` is no longer reported as multiple statements, `]]` and `""` inside a quoted identifier no longer end the identifier early, and the argument name in `EXEC proc @Name = @param` is no longer counted as an undeclared parameter
- **A parameter named `QueryBySqlAsync` is now refused** like `Query` and `await`, because it hid the method the generated raw SQL code calls
- **An `IN` on a nullable column of a value type the generator does not recognize (PostgreSQL `cidr`) with a list of another type is now skipped with a warning** instead of throwing `InvalidCastException` in the in-memory backend

- **A named query with an empty or whitespace-only SQL no longer generates a method that runs blank SQL** — `set_query` saved the blank text and the generator wrote an implementation for it (SQLite silently returned no rows), instead of leaving the method to be written by hand as the "no SQL for any dialect" warning says. The tool now treats a blank `sql` value as no SQL and does not save it (the GUI dialog already did), and the generator does the same for a diagram file that holds one
- **An error in the SQL for a dialect that is not generated no longer drops the whole named query** — even with correct SQL Server SQL, an undeclared parameter in the PostgreSQL, MySQL or Oracle SQL removed everything from the contract method to the SQL Server implementation. Errors in the SQL of dialects that get no implementation in this generation (dialects QuickER does not implement, dialects not selected for the repositories, or every dialect when QuickER repositories are not generated) are now warnings only, and the query is generated
- **Strings in generated code now keep every character** — an unpaired surrogate in a simple DSL condition string, in raw SQL, or in a name or description in the diagram became U+FFFD in the generated (UTF-8) file, so the compared value, the SQL or the column name silently differed from the diagram. Such characters and control characters are now written as `\uXXXX` escapes
- **Named-query diagnostics now name what you wrote** — fixed: the projection nullability diagnostic named the C# property instead of the database column, an unsupported LIKE pattern pointed at the column, an unexpected `@p` or `'x'` was shown as `p` or `x`, a condition written with LIKE was reported as CONTAINS and the like, a parameter whose type could not be resolved was also reported as undeclared in the SQL, and truncating a long string could split an emoji
- **A string match (CONTAINS and the like) on a value-object column whose value is not a string is now refused before generation** — on a PostgreSQL `cidr` column, for example, the generated code did not compile. As with other type mismatches, a warning is reported and only that query is skipped
- **Names that C# cannot use are now refused before a named query is saved** — `__arglist` and the like as a parameter or field name, and `extension`, `file`, `record`, `required` or `scoped` as a projection's result type name, produced code that did not compile
- **A raw SQL's `DECLARE`d local variable is matched ignoring letter case** — `DECLARE @Total INT; ... SELECT @total` was reported as an undeclared parameter and the whole query was left out of generation, although SQL Server treats the two as the same variable. Parameters you declare on the method are still matched exactly, because the driver binds them that way
- **Computed and generated columns are now imported as read-only and left out of generated writes** — a SQL Server computed column, a MySQL / PostgreSQL / SQLite generated column or an Oracle virtual column used to be imported as an ordinary column, so every INSERT / UPDATE the generated repository issued against that table failed at runtime. The import now marks the column and warns that the expression is not carried into the diagram, generated code excludes the column from INSERT / UPDATE on every backend (EF Core mode maps it as store-generated), generated DDL notes next to the column that the expression must be added by hand, and generation reports the excluded columns. A SQLite generated column used to be missing from the import entirely, and a diagram whose primary key is a computed column is now refused at generation time
- **SQL Server tables whose names differ only in letter case no longer merge into one entity** — in a database with a case-sensitive collation, `Dup` and `dup` collapsed into a single entity with both tables' columns mixed together and no warning. One table is now kept and the other is skipped with a warning, the same way the other dialects already behaved
- **SQLite virtual tables (FTS5, R*Tree and the like) are no longer imported as broken ordinary tables** — a virtual table and its shadow tables used to appear as entities full of BLOB columns. They are now excluded from the import, and each virtual table is reported once
- **Disabled constraints are no longer imported as if they were enforced** — a SQL Server foreign key turned off with `NOCHECK CONSTRAINT` used to become a relationship in the diagram even though it enforces nothing. It is now skipped and reported. A key added `WITH NOCHECK` but currently enabled is still imported, because it is enforced from then on. Oracle already skipped its `DISABLE`d constraints, but did so silently; those are now reported the same way
- **SQL Server temporal tables can now be imported and written to** — the history table is excluded and reported instead of arriving as a duplicate entity, and the current table's period columns (`GENERATED ALWAYS AS ROW START / END`) are treated as columns the database produces, so generated code leaves them out of INSERT / UPDATE. Writing to such a table used to be impossible: the period columns were sent like ordinary columns and SQL Server rejected the statement because they are `GENERATED ALWAYS`. Period columns declared `HIDDEN` work the same way, because generated code lists its columns explicitly rather than relying on `SELECT *`
- **A generated mapper no longer fails to compile when a computed column is a NOT NULL value type** — with `datetime2`, `int`, `decimal` and the like, generating edit models produced code that did not compile (CS0266: `System.DateTime?` cannot be converted to `System.DateTime`). An edit model's confirmed value is always `Nullable<T>` for a value type, and the three kinds of column that are only assigned when an input is present (row version, computed, excluded unbounded binary) were missing that unwrap. Row version and excluded binary columns are always `byte[]`, so only a computed column — which can have any type — could reach it. Diagrams without a computed column, and those whose computed columns are reference types, generate byte-identical output
- **A SQLite database whose table name contains a dot can be imported again** — the import quoted such a name as if the dot were a schema qualifier, which made the `PRAGMA` calls a syntax error and failed the whole import
- **A SQLite foreign key whose parent table does not exist is now reported** — SQLite does not check the parent table when a table is created, and such a key used to vanish from the diagram without a word
- **A partitioned MySQL table is now reported the way a PostgreSQL one already was** — the diagram does not model partitioning, so DDL generated from it creates the table unpartitioned; the import now says so instead of staying silent
- **A SQLite primary key that allows NULL is now reported** — in a rowid table, any primary key other than a single column declared exactly `INTEGER` can hold NULL. The import still corrects such a column to NOT NULL (the diagram and the editor always treat a primary key that way), but it now names the columns it adjusted, because existing rows with a NULL key can make a later sync fail while copying the data across. Only the columns that were actually adjusted are named: a key whose columns are already declared `NOT NULL` is left alone
- **A string or binary column with no length is no longer written out for SQL Server, MySQL or Oracle** — switching a diagram to one of those dialects used to produce DDL that MySQL and Oracle refuse to run, while SQL Server quietly created a one-character column. Such a column is now listed as unconvertible, so a length can be given before switching. C# reverse engineering reports the same case per column instead of expanding the token, and generated entities now record the original spelling in `[DbColumnMeta(..., NativeType = "...")]`, so code generated by QuickER still round-trips
- **MySQL `bit(n)` (n greater than 1) and `year` columns now map to `ulong` and `int`** — both used to fall through to the "unknown type" case and become `string`, so reading such a column from generated code threw. `bit(1)` is still `bool`, the counterpart of the `tinyint(1)` convention
- **An Oracle table with more than one `INVISIBLE` column now imports those columns in a fixed order** — Oracle gives such columns no ordinal, so they came after the visible columns in whatever order the database returned them. They now follow the visible columns in the order they were created
- **SQL Server's `datetime2` / `time` / `datetimeoffset` columns now import their fractional-second precision** — the precision was not read, so `datetime2(3)` came in as `datetime2` (7 digits), and a sync from that diagram that changed, say, the column's nullability quietly widened its precision to 7. The default precision of 7 is still written without parentheses. **In a diagram imported by an earlier version, columns whose precision is not 7 show up as a type change in the next sync**. Import the diagram again, or change the types in the diagram to match the database's declarations
- **Oracle `INTEGER`, `SMALLINT` and `NUMBER(*,0)` columns now import as integer columns** — Oracle stores them as a `NUMBER` with no precision and a scale of 0, but the import wrote a bare (floating) `NUMBER`, so DDL generated from that diagram made a column that accepts fractions. They now import as `NUMBER(*,0)`. **In a diagram imported by an earlier version, such columns show up as a type change in the next sync**
- **An Oracle length with a unit, such as `VARCHAR2(50 CHAR)`, is now read as the maximum length in generated code** — the unit left the maximum length empty, so `[MaxLength]`, EF Core's `HasMaxLength` and the value object length check were missing. In a diagram imported from a database with `NLS_LENGTH_SEMANTICS=CHAR`, every string column has this form
- **Oracle `NUMBER(*,s)` (no precision limit, a scale of s) now keeps its scale in the generated code's type token** — the token dropped the scale and wrote `decimal`, so taking the generated code back into a diagram produced a bare (floating) `NUMBER`, and a column imported from `INTEGER` (`NUMBER(*,0)`) lost its integer constraint. The token is now `decimal(*,s)`, which goes back to Oracle as the original spelling. Taking it into another dialect warns and keeps the token text, as for any type that dialect cannot write out
- **A query condition that does not read a column is now evaluated before it reaches the database** — the common "no filter when null" form `x => filter == null || x.Name == filter` sent `filter == null` to SQL Server and SQLite as a comparison of two parameters, and a null made it unknown for every row, so the query returned the wrong rows (only the rows whose name was NULL) without an error. A part of the condition that reads no column, such as a closure variable, a constant or a comparison between them, is now evaluated first, and `&&` / `||` stop at the left operand when it decides the result, as C# does. `flag || x.IsActive` used to fail with `NotSupportedException` and now works
- **`StartsWith` / `EndsWith` / `Contains` on a fixed-length SQL Server column (`nchar(n)`, `char(n)`) now match** — the pattern was bound with the column's fixed-length type, so it was padded with blanks and stopped matching. Note that SQL Server returns such a value padded with blanks, so `EndsWith` compares against the padded value, as C# does on the value it reads back
- **`.Date` on a SQLite date-time column now matches** — `x.At.Date == day` matched no row and `>=` dropped the boundary day, because the column side was written as `'YYYY-MM-DD'` and the parameter as `'YYYY-MM-DD HH:MM:SS'`. The date parts (`Year`, `Hour`, `Date` and so on) of a SQLite `DateTimeOffset` column are now taken in the offset the value was stored with; they used to be converted to UTC first, so `2024-01-01 05:00 +09:00` did not count as year 2024 or hour 5
- **A query condition can now read a nullable column through `.Value`** — `x.ShippedAt != null && x.ShippedAt.Value.Year == 2024` failed with `NotSupportedException`
- **`Contains` / `StartsWith` / `EndsWith` with a `char` argument now work** — they failed with an `ArgumentNullException` that claimed the argument was null
- **`string.IsNullOrEmpty` / `IsNullOrWhiteSpace` now give the C# result on SQL Server and SQLite** — on SQL Server, `IsNullOrEmpty` also matched values made only of blanks, and on both dialects `IsNullOrWhiteSpace` treated tabs, line breaks and full-width spaces as content
- **A SQL Server query no longer fails when a column, a property or a navigation is named like a keyword** — `Query()` on a table with a column named `group`, or `Include(x => x.Order)`, was a syntax error, and a column name containing `]` broke the statement
- **A SQL Server `Query()` now returns the same values as `GetByIdAsync` / `GetAllAsync`, with or without `Include`** — every query read through FOR JSON, which writes a `float` with 16 significant digits and a `real` with 8, so `0.1 + 0.2` came back as `0.3`, the largest `double` as infinity, and a `real` such as `10.0001545` as `10.000154`. FOR JSON also leaves out a NULL, so a column the entity declares non-null (a `string`, for one) that holds NULL in the database kept its initializer (`""`) instead of coming back `null`. A query without `Include` now reads with a plain SELECT, and a query with `Include` reads its `float` and `real` columns in SQL Server's lossless text form and treats a missing column as NULL, so both come back as stored, for the parent and every included child
- **`Include` no longer leaves a navigation empty when the primary key and the foreign key have different CLR types** — on SQLite and in the in-memory backend, a `long` primary key (`INTEGER`) referred to by an `int` foreign key (`INT`) never matched, so `Include` returned empty collections and null parents without an error, and the in-memory `ExecuteDeleteAsync(cascadeDelete: true)` left the children behind. The in-memory backend also reads each related table once per `Include` instead of once per entity
- **Updating a row of a table with no column to update no longer fails** — a table made only of its key and columns an update leaves out (a row version, computed columns, excluded binary columns) produced `UPDATE … SET WHERE …`, a syntax error, so `UpdateAsync` and a graph save of such a row always failed on SQL Server and SQLite. The update now assigns the key to itself, which keeps the existence check, the row-version guard and the returned version working. On SQL Server, a key set to the value it already holds does not run `ON UPDATE CASCADE`, so no child row is rewritten
- **An EF Core graph save no longer deletes or writes entities outside the cascade** — `SaveAsync` registered every entity reachable through any navigation, including parent references, so deleting one order line loaded together with its order deleted the order and the line's siblings as well, two loaded orders that carried separate instances of the same customer failed with "another instance with the same key is already being tracked", and an edited parent was written although only the child was saved (and kept its `Updated` state). The EF Core repository now saves only the entities the cascade reaches from the root, as the QuickER repositories do. With `cascadeSave: false`, a removed root's descendants are now deleted first when `cascadeDelete` is true, as the QuickER repositories do, instead of leaving them to violate the foreign key
- **EF Core's `QueryBySqlAsync` now works on SQLite and Oracle** — a column that is not a value object was handed to its property in the driver's storage type, so on SQLite (an `int` column comes back as `long`) and Oracle (`NUMBER` comes back as `decimal`) every raw-SQL entity query failed. The value is now converted to the property's type, as the QuickER repositories already did
- **EF Core value-object columns now use the column's own length and precision** — the generated `QuickErDbContext` left `HasMaxLength` / `HasPrecision` out for value-object columns, so EF Core treated them as `nvarchar(max)` and `decimal(18,2)`: a condition on `.Value` was compared through a cast to that type (rounding a column with more than 2 decimal places), and its parameters were declared with that precision. The generated configuration now carries the column's length and precision for value-object columns too, and the `.Value` translation casts to the column's own type
- **EF Core saves now work under a retrying execution strategy** — with `EnableRetryOnFailure` (and any other strategy that retries), a save with save hooks and a cascading `ExecuteDeleteAsync` always failed because they open their own transaction. Both now run inside the strategy and start over on every attempt; with save hooks, Before and After run once per attempt
- **An EF Core update that matches no row for a reason other than concurrency is no longer reported as a concurrent change or retried for ever** — when a trigger or row-level security discarded an update of a table without a rowversion column, `UpdateAsync` and `SaveAsync` threw a `SaveConflictException` saying someone else had changed the row, and with `ConcurrencyMode.ForceOverwrite` they retried until cancelled. Such an update is now reported as a missing row, as the QuickER repositories do, and a save that keeps being rejected as a concurrency conflict gives up after 10 attempts
- **A `binary(n)` primary key now works in the in-memory backend, and in SQLite's `Include`** — a `byte[]` key was compared by reference, so the in-memory store could not find a row by a key read back from it (`GetByIdAsync` returned null, a second insert of the same key went through, and updating a fetched entity found no row), `Include` on SQLite and in memory left the navigation empty, and an in-memory `Where(x => keys.Contains(x.Hash))` over a list of byte arrays matched nothing. Keys are now compared by their bytes
- **Oracle: a partitioned table is now reported, and materialized view log tables are no longer imported** — a partitioned table was imported without the warning PostgreSQL and MySQL give, although DDL generated from the diagram creates it unpartitioned; it is now reported the same way. A materialized view log (`MLOG$_…`) is a change record kept for refreshing a view, not a table of the design, and is now skipped like the materialized view's own container table
- **Oracle: a foreign key to another schema on a table that was not imported is no longer reported** — when one of two tables whose names differ only in letter case was skipped, the skipped table's foreign keys to other schemas were still listed as skipped foreign keys, naming a table that is not in the diagram
- **PostgreSQL: two tables with a foreign key of the same name to another schema are now both reported** — PostgreSQL names foreign keys per table, but the import reported a skipped foreign key once per name, so the second table's key was dropped without a word. PostgreSQL and MySQL also no longer report a foreign key of a table that was itself skipped because its name differs from another only in letter case
- **The HTTP client's `SaveAsync` over a list no longer throws `NullReferenceException` for a null element** — a direct connection skips a null element and the server already did, but the client read it before sending and after the save. It is now skipped as well
- **The HTTP client's `CheckUniquenessAsync(null)` now throws `ArgumentNullException`, as a direct connection does** — it sent the null to the server and failed with a `RemoteRepositoryException` (400) instead
- **An HTTP client upload over the server's size limit now fails with `RemoteRepositoryException` (413) instead of a connection error** — the server rejects such an upload without reading the body and closes the connection, so the reset that reached the client while it was still sending usually discarded the 413 (almost always for a 31 MB upload) and `Write{Column}Async` threw `HttpRequestException`. The upload now carries `Expect: 100-continue` and sends the body only once the server has accepted the headers. Behind a proxy that does not answer `100 Continue`, each upload waits up to the handler's `Expect100ContinueTimeout` (1 second by default) before sending the body
- **The HTTP client's blob transfer no longer reads a response that did not come from the endpoint as success** — any 2xx was taken as success, so behind an authentication proxy that sends an expired session to its sign-in page, `Read{Column}Async` wrote that HTML page to the destination and returned `true`, and `Write{Column}Async` returned `true` for a write that never reached the server. A download now succeeds only on 200 with `application/octet-stream`, and an upload or setting to `NULL` only on 204; any other success response throws `RemoteRepositoryException` and the download writes nothing. The blob copy of bidirectional sync over HTTP follows the same rule
- **An HTTP client upload from a stream that does not yield exactly `length` bytes now fails with `ArgumentException` without changing the stored value, as a direct connection does** — a stream that ended early failed with `HttpRequestException`, and one that went on past `length` could have its first `length` bytes stored. The body is now read with the same check as the direct path, which refuses a stream that goes on past `length` before the last of the body is sent. A seekable stream sent again to follow a redirect is read again from where the first send began
- **Raw SQL results can now be read as an enum, `DateOnly` or `TimeOnly`** — `ExecuteScalarSqlAsync<TEnum>`, a single-value projection to an enum, and a projection DTO with an enum property always failed with `InvalidCastException`; an enum is now read from a number or from a member name. `DateOnly` and `TimeOnly` were not treated as single values, and a `DateTime` or `TimeSpan` the driver returns for a date or time column (as SQL Server does) could not become one. A `DateTime` with a time of day and a `TimeSpan` outside one day are refused rather than cut down. The same conversion applies when a value object is created from such a value
- **An edit model's `ValidateUniqueAsync` no longer puts the result of a check on values that changed while it ran** — when a confirmed value was edited (or another check started) while the query was out, the duplicates found for the old values were registered on the new ones, and a value that had become a duplicate passed as unique. Such a check now registers nothing and returns `false`, meaning the current values were not confirmed unique; run it again
- **A `TimeOnly` value with seconds keeps its seconds in an edit model's input text** — a value on a whole minute is still shown in the short form, but a value with seconds was shown without them, so editing another field and saving wrote the time back cut down to the minute. It is now shown in the culture's long time format
- **`EditModelCollection.RemoveRange` rejects a count that overflows past the end** — an `index + count` above `int.MaxValue` passed the range check, removed elements up to the end, and then threw. It now throws `ArgumentOutOfRangeException` before removing anything
- **SQLite tables whose names differ only in non-ASCII letter case no longer replace one another** — SQLite folds only ASCII letters, so `Äpfel` and `äpfel` can both exist; the import kept only the last one without a word and tied foreign keys and indexes of the dropped one to the one it kept. As on the other dialects, the first one is now imported and the other is reported. A foreign key whose `REFERENCES` spells the table with different ASCII case (`REFERENCES ORDERS` for `orders`) is still resolved, as SQLite does
- **SQLite: reading an unbounded binary column on its own can no longer return another row's blob** — `Read{Column}Async` looked up the row's rowid and then opened the blob in two separate statements. A row deleted in between by another connection, followed by an insert that reused its rowid (SQLite hands out the highest rowid again once that row is gone), made the read return the new row's blob. The lookup and the read now run in one read transaction
- **SQL Server `BulkInsertAsync` now follows the connection string's `Command Timeout`** — `SqlBulkCopy` has a timeout of its own (30 seconds) that the connection string does not reach, so a bulk insert gave up after 30 seconds whatever `Command Timeout` said. It now takes the connection's command timeout
- **SQLite: a Guid stored as a 16-byte BLOB, and a hand-written entity's `DateOnly` / `TimeOnly` column, can now be read through `Query()` and raw SQL** — `GetByIdAsync` read a BLOB Guid but `Query()`, a value object column and raw SQL failed on it, and a `DateOnly` / `TimeOnly` property (which QuickER does not generate, but a hand-written entity passed to `QueryBySqlAsync` or a repository can have) failed to read on every path
- **`ApplyDdlAsync` rejects a negative `commandTimeout` before it opens a connection** — the check ran after the connection opened, so on SQLite a call with a bad argument left an empty database file behind, and on SQL Server an unreachable server reported a connection error instead of the argument. The exception's `ParamName` is now `commandTimeout`
- **An in-memory graph save no longer deletes a row someone else inserted while its After hooks ran** — a save that deleted a row which did not exist when it reached it removed whatever stood under that key when it published, including a row another writer had inserted in the meantime; for a type with a rowversion column the save failed with a `SaveConflictException` (`Modified`) instead. Such a delete now does nothing, as a real database's `DELETE` affected no rows at the moment it ran
- **An in-memory cascading `ExecuteDeleteAsync` over a cyclic cascade now fails even when no row matches** — a self-referencing table (or any cascade that loops back) was rejected with `NotSupportedException` only when the condition matched at least one row, and quietly returned `0` otherwise. It is now rejected before any row is read, as the SQL Server and SQLite repositories already did
- **In-memory reads no longer copy excluded blobs, and bulk writes check UNIQUE constraints in linear time** — every read copied the whole row through a JSON round trip and only then dropped the excluded binary columns, so reading a row holding a 20 MB blob allocated about 70 MB. Reads now copy the columns they return and leave excluded columns unread. `BulkInsertAsync` and a graph save checked each row they wrote against every other row, which took seconds at ten thousand rows; they now index the rows once
- **EF Core: raw SQL and a save hook's `ExecuteSqlAsync` now follow the command timeout configured on the DbContext** — both create their command from the connection, so a timeout set with `CommandTimeout(...)` in the provider options never reached them and they ran with the connection's default (30 seconds on SQL Server). They now use the configured value, so raw SQL that used to run longer than it is now stopped at that timeout; with none configured nothing changes
- **EF Core: `GetByIdAsync` and `DeleteAsync` send the key as a parameter** — the key was written into the SQL as a literal, so EF Core compiled a new query, and the database cached a new plan, for every key value. In the runtime package, an error message that lists a table's columns no longer puts them in SQL Server's square brackets, and the metadata no longer compiles a row materializer that EF Core never uses
- **EF Core: a graph save of 10 or more rows that each need resolving no longer fails** — EF Core reports one failing statement at a time, and the attempt limit counted every resolved row, so a `SaveAsync` with `insertWhenUpdateMissing` over 10 or more rows another user had deleted, or a `ForceOverwrite` save over 10 or more rows whose versions had moved on, always failed with a `SaveConflictException` blaming a trigger or row-level security. The limit now applies per row, and only once the row is found to be still there, so a row that is gone on the last attempt is reported as gone (`NotFound`, or `false` from `UpdateAsync`) rather than as an exhausted retry
- **EF Core: a save with save hooks no longer runs a statement twice under SQL Server MARS** — after a statement matched no row, the save retried inside the same transaction and relied on EF Core's automatic savepoint to undo the statements that had already run. EF Core turns savepoints off when `MultipleActiveResultSets=True` (and `AutoSavepointsEnabled` can turn them off), so the retry sent those statements again: an inserted row failed with a primary-key violation and a deleted row failed with `NotFound`. Each attempt now has a transaction of its own; Before still runs once, and After once, after the attempt that succeeded
- **EF Core: a cascading `ExecuteDeleteAsync` whose condition reads a navigation now deletes the matching rows** — the condition was evaluated again for each statement after the descendants were gone, so `Where(o => o.OrderLines.Any())` deleted every line of the matching orders, left the orders in place and returned only the line count. The keys of the matching rows are now read first and the deletes go by those keys, 500 keys at a time so that neither SQL Server's limit of 2,100 parameters per statement nor a database below compatibility level 130 matters. A cyclic cascade is now refused before any statement runs, instead of after the deletes of the navigations ahead of the cycle had run and been rolled back
- **EF Core: delete hooks now run children first and also for added descendants** — a deleted root's hooks ran before its descendants', and an `Added` descendant (which has no row to delete) got no delete hook, unlike the QuickER repositories and the in-memory repository. EF Core now runs them in the same order and for the same rows
- **EF Core: `SaveConflictException.NotFound` names the operation that matched no row** — a graph save that deleted a row that was already gone reported "The record to update was not found". `SaveConflictException.NotFound` gains an overload that takes the operation, and the EF Core repository passes it
- **A value object string match in a hand-built expression tree is now translated** — a predicate built with `Expression.Call` and a method taken from the value object type itself (`typeof(NameValue).GetMethod("Contains", ...)`) was not recognized as a string match: the QuickER repositories and EF Core failed to translate it, and a `null` argument was not rejected up front with `ArgumentNullException`. Such a method is now recognized the same way as the one the compiler picks, on every backend
- **EF Core: a string match whose receiver is a value object variable now runs** — `Where(c => term.Contains(c.Name))`, with `term` a value object, failed with "No mapping exists from object type" because the variable was sent as the value object rather than its raw value. It now takes the column's conversion
- **EF Core: the LIKE pattern of a value object string match follows a non-Unicode column** — for a column configured as non-Unicode (`IsUnicode(false)` or `HasColumnType("varchar(...)")`), the pattern, its escape character and a string argument were written as Unicode text, so SQL Server converted the column to compare it and could not use its index. They are now written as non-Unicode text for such a column; the SQL for other columns is unchanged
- **EF Core on Oracle: a value object string match with a null pattern no longer matches every row** — Oracle concatenates NULL as if it were empty, so a `null` passed to `Contains` / `StartsWith` / `EndsWith` in a predicate run on the DbContext directly turned the pattern into `'%%'` and matched every row (`SqlQuery.Where` rejects a `null` pattern up front, so the repositories' `Query()` was not affected). The pattern is now tested for NULL on Oracle, so it matches no row, as on the other databases; an empty string still matches every row
- **EF Core: a non-Unicode string column is configured as non-Unicode** — the generated Fluent configuration gave a SQL Server `varchar` column (and Oracle's `VARCHAR2` and the like) only its length, so EF Core took it for `nvarchar` and sent searches and updates against it with `nvarchar` parameters and `N'…'` literals. SQL Server then converted the column to compare it, which can keep its index from being used. Such a column is now configured with `IsUnicode(false)`
- **EF Core: a value object string match emits `ESCAPE` on a provider QuickER does not recognize** — a provider other than SQL Server, Oracle, MySQL, SQLite and PostgreSQL was given no `ESCAPE` clause, so on a database with no default escape character the escaped `%` and `_` matched as a backslash followed by the wildcard. Only PostgreSQL, whose default escape character is the backslash, now goes without it
- **The remote server no longer answers a request whose client disconnected part-way through the body as a fault** — a connection reset while the server was reading the request body was classified as a bad request (400, or 500 for a binary upload, which also logged a server error and called `OnServerError`), and writing that answer to the dead connection could throw again. Which of these happened depended on how busy the server was. Such a request is now left without a response, logs nothing and raises no hook, and the server drops the connection at once. A body the client stopped sending by closing its side of the connection is recorded as a 400 bad request, as Kestrel itself classifies it; Kestrel has already closed the response side by then, so nothing reaches the client, and nothing is logged as a server error
- **The remote server answers a request its host timed out with 504** — with the `RequestTimeouts` middleware, the failure the timeout caused was taken for a client that had gone away, so the request ended without an answer: a JSON call came back as an empty 200 that the client could not read, and an upload got no response at all while Kestrel logged an error. The failure is now handed back to the middleware, which answers 504, and the client raises a `RemoteRepositoryException` with that status
- **Binary uploads work on a host that buffers request bodies** — on a host that calls `EnableBuffering` (for logging or signature checks), the request body became seekable with the length buffered so far, and every non-empty upload failed with 500 because that length did not match the declared `Content-Length`. The body is now read forward for exactly the declared length
- **A client that cancels during a database query is no longer recorded as a server failure** — the database driver reports the cancellation of its command in its own type (SqlClient throws a `SqlException`), so each abandoned request on a SQL Server backed server was logged as an error and raised `OnServerError`. Once the client has gone, a database exception now counts as a disconnect and is logged at Debug level only; any other failure is still a 500
- **An `OnServerError` hook attached through endpoint metadata no longer replaces the 500** — a hook that threw escaped the error handler, so the client got a bare 500 without the `RemoteError` body or correlation id. The hook's failure is now logged as a separate entry and the 500 body is always written
- **A binary upload with an unreadable key is answered with 400 before its length is checked** — a request without `Content-Length` got 411, and one whose declared length was over the limit got 413, even when its `?id=` key could not be read. The key is now read first, so such a request gets the 400 for the key; this also changes the answer when a request is both oversized and carries a malformed key, which used to be 413
- **A binary download whose read function flushes before writing can still answer 404** — flushing the stream before anything was written started the response, so a read function that then returned `false` (no row) could no longer switch it to the 404 marked "NotFound". A flush before the first write now does nothing
- **A single-file output for two repository dialects compiles when the repository namespace is not inside the root namespace** — with `RepositoryNamespace` set to, for example, `Data.Repos` and `RootNamespace` to `MyApp`, the dialect blocks (`namespace Data.Repos.SqlServer`) lost their `using MyApp;` and the file failed to compile with hundreds of errors, while generation reported nothing. The using is now kept whenever a block cannot see the namespace as an enclosing one
- **Value objects over MySQL unsigned integers now have comparison operators** — a value object whose value is `ushort`, `uint` or `ulong` (`smallint unsigned`, `int unsigned`, `bigint unsigned` and the like) derived from the equality-only base, so it had neither `<` / `>` nor `IComparable`, and a named query comparing such a column with `<` or `>` was skipped with a warning. These value objects now derive from `ValueObjectOrderedBase` like the signed ones; existing code keeps compiling
- **A column whose property name equals its class name is now reported at generation time** — a column `order_entity` on the table `orders` gave the `OrderEntity` class a property of the same name, and the generated code failed to compile (CS0542). Generation now stops with an error naming the column, as it already did for two members with the same name
- **Two relationships between the same pair of tables no longer stop generation** — navigation properties were named after the table at the other end only, so a second relationship (an order's ship-to and bill-to customers, say) gave both classes two members with the same name, and generation stopped with an error that renaming columns could not fix. When two or more relationships join the same parent table and child table, every relationship between them is now named after its foreign-key column: `order.ShipCustomer` / `order.BillCustomer` on the child, `customer.OrdersByShipCustomer` / `customer.OrdersByBillCustomer` on the parent. A table that references itself twice works the same way. Navigation names in diagrams with one relationship per pair of tables do not change
- **A named query no longer produces code that does not compile, without a word, in four more cases** — the same list parameter used for `IN` on two columns of different value-object classes declared one local variable twice; an `int32` list used for `IN` on a value-object column over `bigint` (a common shape for an `int32` token against a `bigint` key) could not convert the elements; an integer literal outside the range of the column (`Tiny < 300` on a value object over `tinyint`, `Qty = 3000000000` on one over `int`, a 20-digit literal on any column) was emitted as is; and a parameter named `await` broke the raw-SQL single and count methods, which are `async`. The first two now generate working code, an out-of-range literal skips that query with a warning like other type mismatches, and `await` is rejected as a parameter name the way `Query` already was (in generation, in the query dialog and in the MCP `set_query` tool). Each of these broke the build of every repository in the generated file, not only the query
- **Raw SQL with line breaks keeps its exact value in the generated code** — the SQL was embedded as a verbatim string with its line breaks written out, and the generator rewrites line breaks to the generating machine's convention, so a line break inside an SQL string literal became CRLF or LF depending on the OS, and a LINE SEPARATOR or FORM FEED became a line break. SQL with line breaks is now written as one verbatim string per line joined with the original line-break characters written as escapes; single-line SQL is generated exactly as before
- **An edit model's `ValidateUniqueAsync` checks every constraint it can, and a user-defined check sees the whole row** — the entity built for the check carried only the primary key and the constraint columns, so a check added through `CollectCustomUniquenessChecks` read every other column as its default value. And when a value-type constraint column had no input, the method returned `true` without querying at all, so an unrelated constraint that was really violated went unreported and the database findings of the previous call were cleared. Every confirmed value now goes onto the entity; a constraint that includes a value-type column with no input, or a column the edit model does not have (an array or `inet` column), is left unchecked, and the other constraints are checked as usual. The runtime package `QuickER.Runtime` gains a protected overload of `EditModelBaseCore.CheckDatabaseUniquenessAsync` that takes the properties to leave unchecked
- **`Read{Column}ToFileAsync` no longer empties an existing file when there is nothing to read** — it opened the destination with `File.Create` before the row was even found, so reading a missing row or a NULL value returned `false` and left a zero-byte file, and a failed read left a truncated one. It now reads into a temporary file in the same folder and moves it over the destination only when the read returns `true`; on `false`, an exception or a cancellation the temporary file is deleted and an existing file is untouched. The runtime package `QuickER.Runtime` gains `UnboundedBinaryColumns.ReadToFileAsync`, which the generated method calls
- **The API reference (`.g.md`) keeps its tables intact and shows a usage example that compiles** — a description containing NEL, FORM FEED, LINE SEPARATOR or PARAGRAPH SEPARATOR became a real line break in a table cell and split the row, because only CR and LF were folded; every character the generator treats as a line break is now folded. The usage example took the first table even when it had no repository (a composite primary key), so it called `GetByIdAsync` on a repository that does not exist; it now uses the first table that has one
- **SQLite: a write that returns rows no longer fails with "database is locked" while another connection reads** — the provider retries a locked database only on a statement's first step, and an `INSERT`, `UPDATE` or `DELETE` with `RETURNING` outside a transaction commits on a later step, so passing one to the raw SQL methods failed at once whenever another connection held a read. The generated SQLite `SqlConnectionFactory` now sets SQLite's busy timeout to the connection string's `Default Timeout` on every open, so the statement waits for the reader as other writes do. While SQLite waits, the cancellation token is not observed, and a connection factory of your own does not get the timeout; see [Code generation](docs/code-generation.md)
- **EF Core: a table whose name in the diagram has a schema (`sales.Orders`) is now the same table the QuickER Repository uses** — the generated `QuickErDbContext` passed the whole name to `ToTable`, which does not split it, so EF Core read and wrote the table `[sales.Orders]` in the default schema instead of `[sales].[Orders]`. It now emits `ToTable("Orders", "sales")`, splitting at the first dot as the rest of QuickER does; a table without a schema is generated as before

#### Bidirectional sync

- **A refresh that leaves out a table whose local rows refer to the tables it empties is now refused before it deletes anything** — a refresh narrowed with `SyncRefreshOptions.Mode` (`Versioned` leaves the versionless tables out) or `ExcludedEntityTypes`, or one with a table excluded where the engine was put together, emptied the tables it covers without looking at the tables it left out. A local row of such a table that referred to an emptied row was deleted with it under `ON DELETE CASCADE`, unsent edit and all, and the next sync reported the edit as discarded; under the default foreign key the emptying failed every time and the tables emptied before it stayed empty. The run now throws `SyncRefreshScopeException`, naming each referring table and the table it refers to; a table left out that holds no such row still does not stand in the way. A refresh whose emptying fails for another reason no longer drops the records of what the server has accepted, so editing a row it had uploaded is no longer reported as changed on the server
- **A table with a `decimal` primary key whose value is below 1e-5 in magnitude can now be synced** — the key was written to the journal in exponent form (`1E-06`), which it could not read back, so uploading such a row failed with `FormatException` on every run. Keys are now written in fixed-point form, and keys an earlier version wrote in exponent form are rewritten at the start of the next run
- **A second row holding NULL in a unique column no longer stops a sync against SQL Server** — a SQL Server UNIQUE constraint compares NULL as a value and refuses a second row with the same NULL, but the uniqueness pre-check of the QuickER Repository for SQL Server (`CheckUniquenessAsync`) skipped any value tuple containing NULL. The engine could not explain the refused upload and threw it on every run. The pre-check now follows the SQL Server rule, so such an upload is reported as `UniqueValueTakenOnServer` (settled under `ServerWins`), and `ValidateUniqueAsync` on an edit model reports the second NULL as a duplicate. The QuickER Repository for SQLite, EF Core and the in-memory store still skip a tuple containing NULL
- **Writing to the local database while a sync runs no longer loses the write** — the run read the unsent changes once, before downloading, so a row created during the download was deleted by the same run's delete propagation (and its journal entry was then discarded, losing the row on both sides), and a row edited during the download was overwritten by the batch. The journaling repositories and the engine now share a lock on the local database: a local write waits for at most one download batch (or one table's delete propagation, or a whole refresh), and the engine reads the unsent changes again under that lock right before acting on them. The lock covers one process; another process writing the same database file is not covered
- **Two sync runs over the same local database no longer overlap** — `SyncAsync`, `RefreshAsync`, `UploadAsync` and `DownloadAsync` called at the same time used to run side by side and could report false conflicts or apply the same rows twice. The one that arrives later now waits
- **Journaling a bulk insert or a graph save is much faster** — every row was recorded with its own auto-committed INSERT, so recording 10,000 rows took several hundred times as long as the insert itself. The rows are now recorded as multi-row inserts of 100 rows each (`SyncJournal.RecordManyAsync`)
- **A change that was followed by a failed write is no longer lost on upload** — the replay sent only what the newest journal entry said, and the journal records an intent before the write it describes, so the newest entry could describe a write that never landed. An edit followed by a delete that a foreign key refused was dropped without reaching the server, and a delete followed by a reinsert that failed left the row on the server. The operation sent is now decided from whether the local row is there and from every entry recorded about it
- **`SyncAsync` now rejects a `DownloadBatchSize` of zero or less before it changes anything** — it was checked only when the download started, after the upload (and a `ServerWins` run's reading back of the server's rows) had already changed the databases
- **A foreign key on the server or in the local database no longer stops every sync run** — three arrangements failed on every run until the journal was edited by hand: a row edited here whose row and parent were deleted on the server (delete propagation kept the row and removed its parent), a `ServerWins` run over a row the server had moved to a parent added since (the row was put back before its new parent had come down), and a `LocalWins` or last-write-wins run that sent a row whose parent the server had deleted. Delete propagation now keeps the parents of the rows it keeps, `ServerWins` puts rows back table by table right after each table's download, and a write the server refuses for a missing parent is reported as `ParentMissingOnServer`. Deleting here a row another device has since pointed a new row at on the server is reported as `DeleteRefusedOnServer`, and the download stops at that new row instead of failing on the local foreign key
- **Carrying unbounded binary columns no longer clears or loses blobs** — a run with `IncludeUnboundedBinary` sent every such column of an edited row, so editing a row whose blob had never come down here cleared the server's blob; a download whose blob copy failed never brought that blob down again, because the row had already moved the resume point; and a blob upload that failed left the next run reporting a conflict against this device's own write. Only the columns a write stored a value in are sent now, owed copies are recorded and made by the next run that carries the columns, and the receipt is recorded before the blobs are sent
- **A NOT NULL unbounded binary column of a value-object entity no longer stops the download** — a row read for a run arrives without the column, which then held nothing and failed the local insert on every run. The engine fills such a column with an empty value when it inserts a row, on either side
- **Sync support compiles for a table whose primary key is a `TimeSpan`, and a cycle of foreign keys no longer puts a child before its parent** — the key text was written with `ToString(CultureInfo.InvariantCulture)`, which `TimeSpan` does not have, so a SQL Server `time` primary key produced code that did not compile; it is now written with the invariant `"c"` format (and a `TimeOnly` key, which no built-in dialect produces, with `"O"`, since the default dropped the seconds). When the tables referred to each other in a cycle, everything left was emitted in declaration order, so a table outside the cycle that referenced one inside it could come before its parent; now one table on the cycle is taken at a time, so download applies parents first
- **Delete propagation no longer fails on a local foreign key, and removes a chain of rows in one run** — it removed the rows the server dropped in key order, so a parent whose key sorts before its child's in the same table, a row an unsent local row still refers to, a row a child left stale by a stopped download refers to, and a row referred to by a table outside the run (a versionless table in a versioned run, or a table in `ExcludedEntityTypes`) made the local foreign key throw, and the run stopped there every time. It now removes only the rows no local row refers to, and repeats until nothing more can go, so parents and children the server deleted all go in one run. A referring table the local database does not have is skipped. Rows that refer to each other in a cycle stay, as before
- **A row whose parent is not here yet no longer fails on the local foreign key** — the download applies rows in version order, so a parent changed after its child comes after it, in a later batch or above the run's ceiling, and in a self-referencing table a child could come before its parent; the rows `ServerWins` puts back and the rows of `RefreshAsync` had the same problem, and a `ServerWins` run that discarded a local delete applied the parent's new children before the parent. The missing parent is now read from the server and applied first, and its own parents the same way. When it cannot be had (see `MissingParentTableName` above), the download stops at the row, and `ServerWins` leaves the row and its entries as they are. `ServerWins` no longer counts an unsent delete in a table outside the run's scope as discarded, so a row pointing at that deleted parent is held back too
- **A versionless table now reports the rows its download held back** — a row with an unsent change, or a parent that could not be had, was skipped without a word, so a later table's row pointing at it failed on the local foreign key and no conflict explained why. The table is now reported as truncated at the first row it skipped
- **In a last-write-wins run, `ServerWins` now settles the writes the server refuses** — a write refused for a missing parent (`ParentMissingOnServer`), a delete refused because other rows refer to it (`DeleteRefusedOnServer`) or a value another row holds (`UniqueValueTakenOnServer`) was only reported, so in a versionless table, which a versioned run does not touch, such a row could never be settled. These three are now settled by putting the server's row back, as in a versioned `ServerWins` run; other conflicts and the other policies are unchanged
- **Writes within one table are retried when the server refuses one for a foreign key** — the writes of a table were replayed in the order they were first recorded, so in a self-referencing table, renaming a row and moving it under a row created later, or deleting a parent and its child with the parent's entry first, was refused on every run. A write refused for a foreign key is now set aside and sent again after the rest of the table's writes, for as long as each pass sends at least one; what is still refused after that is reported
- **Deleting a row and creating another with the same unique value is now uploaded in an order the server accepts** — the new row went first and the server refused it while the old row still held the value. An upsert that collides with a value on the server, and the upserts that refer to it, are now sent after the table's deletes
- **A row the server dropped no longer blocks a downloaded row that takes its unique value** — delete propagation ran only after the download, so the new row collided with the old local copy and the batch failed. Delete propagation now runs before the download as well, and a batch that still fails stops the download at the colliding row instead. A `ServerWins` run likewise removes the local rows it is discarding that the server does not have before it puts the server's rows back
- **A local row still holding a unique value a downloaded row needs is brought up to date first** — the download sees each row at its latest version only, so when the server moved a value to another row and then changed the original row again, a device that had not synced in between stopped at the same row on every run. The local row holding the value is now read from the server (or removed when the server no longer has it, nothing refers to it and the run propagates deletes) before the batch is applied again. A row with an unsent change keeps the value, and two rows the server swapped values between still stop the download until `RefreshAsync`
- **SQL Server: the key-ordered download of a versionless table with a `varchar` key no longer skips rows** — the key to resume after was sent as `nvarchar`, and comparing it with a `varchar` column under a SQL_ collation follows different rules from the `ORDER BY`, so rows at a page boundary could be skipped. The key is now cast to the column's own type
- **A local write that fails no longer leaves its journal entry behind** — the journal records the intent before the write, and a write that then threw (a foreign key refused it, a save hook's `AfterSaveAsync` threw, a stream given to `Write{Column}Async` ended early) kept its entry. The next run uploaded content the local database never committed: a `LocalWins` or last-write-wins replay put an older row or blob back over another writer's newer one, a device whose blob copy had failed overwrote the server's blob with an empty one, and a write that changed nothing moved the server's version on and raised a false `ModifiedOnServer` on another device. The journaling repository now takes back the entries a write recorded when that write throws, under the same lock and before the exception reaches the caller; earlier entries for the same row stay. A process that ends between recording and writing still leaves its entries, which the upload settles as before. Should taking the entries back fail too, the failure is put in the write exception's `Data` under `JournalingRepositoryBase<TEntity, TKey>.JournalCleanupFailureKey`
- **A delete made through a graph save no longer disappears when the deleted object carries no version** — a stub made from the key alone, or an object kept since before the row's last download, carries no version (or an older one), so the delete was recorded without one, and the upload took the row for one the server never had and dropped the delete: the row stayed on the server, together with any blob written to it here. A delete of a versioned table now records the later of the entity's version and the version of the local row, read before it goes (one more SELECT per such delete). The new descriptor property `SyncTableDescriptor<TEntity, TKey>.LocalRowVersionSql` holds the query
- **A row deleted and created again under the same key is no longer a false `DuplicateOnServer`** — the new row has no mirrored version, so the upload inserted it, and the server, which still had the row the delete removed, refused it. It is now sent as an update guarded by the version the delete recorded; a change made on the server in the meantime is reported as `ModifiedOnServer`, as for any edit. A row that never reached the server before being deleted and created again is inserted as before
- **A row the server is given for the first time now gets every blob** — with `IncludeUnboundedBinary`, an upload sends only the unbounded binary columns a local write stored a value in, which is right for an update but not for an insert: a row a `LocalWins` or last-write-wins edit puts back after the server deleted it, and a row whose earlier entries a `ServerWins` run dropped and that was edited here again, were created on the server with their blobs empty. Every column is now sent when the upload inserts the row, and if sending them fails, the next run still sends them all
- **An overwrite without the version guard no longer hides another writer's blob** — `LocalWins` and a last-write-wins run overwrite the server's row without its version guard, which leaves the server's blobs in place, and the row that came back down was recognised as this device's own echo, so a newer blob another device had written never came down. The columns the overwrite did not send are now recorded as owed copies, and the next run that carries the columns brings the server's blobs down (a column written here since keeps the local value)
- **An owed blob copy of a row the server has deleted no longer stops every run** — reading the blob of a row the server no longer has came back empty, and writing that into a NOT NULL column failed on every run. Such a copy is now dropped, and the row is left to delete propagation
- **A row a save hook skipped or gave its key is journaled as it was saved** — the journal entries of a graph save are written before its hooks run. A row a `BeforeSaveAsync` returned `false` for was not written, yet its entry uploaded the row's current content, over another device's newer row or as a write that changed nothing but moved the server's version on and raised a false `ModifiedOnServer` elsewhere. A hook that gave a new row its key left the entry under the old key, so the upload dropped it and the next delete propagation removed the row on both sides. Once the save has succeeded, the entries are now checked against it under the same lock: a skipped row's entry is taken back, and an entry whose row took another key is moved to that key
- **A table class of your own receives the keys still unsent** — the engine read what is unsent only through internal members, so a table implementing just `ISyncTable` found `SyncDownloadContext.PendingKeyTexts` empty and overwrote the local edit of a row whose conflict the same run had just reported. The context now carries the unsent keys as of the start of the table's download (a copy: an edit made after that is not covered)

#### Code generation dialog & CLI

- **Switching the code generation dialog between one file and split output now converts the output path** — the one path box holds a file path for one file and a folder path for split output, but switching kept the text as it was, so a folder such as `C:\App\Generated` became a file named `Generated` next to it, and a file such as `C:\out\Foo.g.cs` became a folder named `Foo.g.cs`. Switching to split output now takes the file's folder, and switching back adds the file name used last for one file (or the default name) to the folder. Turning on layered output, which implies split output, converts the same way; an empty path stays empty
- **Code generation now runs even when the dialog cannot save its settings** — the settings are saved when you click OK, and a failure to write them (a file in the place of the settings folder, for example) escaped as an unhandled error, so nothing was generated and QuickER went into its crash handling. The failure is now reported with its cause, and generation goes ahead with the settings in the dialog. The same report appears when the existing settings file could not be read and was therefore left as it was
- **Code generation no longer stops on a namespace option the output does not use** — the CLI and MCP checked every namespace option that could be used, so an invalid `RuntimeNamespace` stopped generation in runtime-package mode (which writes no runtime files), and an invalid `RootNamespace` stopped layered output (which takes every namespace from the layer folders or the per-category options). Only the options the planned files actually take their namespace from are checked now; an option that is used is still rejected as before. The code generation dialog follows the same rule: it checked every namespace field on screen and always required the root namespace, so an invalid Runtime namespace in runtime-package mode, or an empty or invalid root namespace with layered output, kept OK from going through (and an empty root namespace hid the file preview)
- **A query that references a deleted column is now reported in the query definition dialog** — references from the sort order, a projection field or a parameter to a column that no longer exists could be confirmed with OK and were only reported at generation time (which skips that query with a warning). The dialog now names the query and the item and keeps OK disabled
- **The query definition dialog now stops a query that code generation always rejects before you confirm it** — it used to leave these rules to generation, so a reserved method name such as `GetById`, a parameter named `Query`, an invalid or duplicate parameter or field name, a result type name used by another query, or paging on a single row was accepted and then reported as an error at every generation. The dialog now runs the generator's own checks and shows the generator's message
- **The "exclude unbounded binary columns" setting is no longer saved while it is hidden** — switching DB access back to "none" or to EF Core hides the row, but a checkbox ticked earlier was still written back to the settings file. Besides the columns QuickER repositories read and write, the setting also drives **whether an EditModel treats such a column as required**, so a hidden tick changed the generated code even in configurations that generate no QuickER repository: a NOT NULL unbounded binary column was left out of the edit model's required inputs (required only on a new row) and its mapper assigned it only when a value was supplied. In those configurations such columns are now required like any other column. While the row is hidden the value is only dropped from the file, not from the screen, so choosing QuickER repositories again brings the original tick back. The sync-support checkbox follows the same rule
- **`--repository-dialects` with a value that names no dialect is now an error** — commas or spaces only produced an empty list, which skipped the "derive a single dialect from the provider" fallback and quietly emitted SQL Server code with exit code 0 even for `--provider sqlite`. A shell variable that failed to expand in CI hits this
- **Interrupting `quicker scaffold` with Ctrl+C during the schema import now exits with code `130`** — the import treated the interruption as an import failure, printed "Failed to import the schema from the database" and exited with `1`, while every other point of the CLI exits with `130`. A timeout raised by the database driver is still reported as an import failure
- **`quicker scaffold` now reports a mistake in `--config` before connecting to the database** — the settings file was read only after the whole schema import, so a mistyped path or an invalid value was found only after a possibly long import. The exit code and message are unchanged; warnings about unknown keys in the settings file now come before the import warnings on stderr
- **The MCP `generate_csharp` tool now reports every settings-file error the same way** — a missing settings file, invalid JSON or a value of the wrong type returned `Error: …` and dropped the warnings already collected, such as unknown keys. These now return `C# code generation failed: …` followed by those warnings, as an unsupported Repository dialect already did
- **Undoing or redoing a column rename now takes the named queries' conditions with it** — renaming a column rewrites the mini DSL conditions that refer to it, but undoing the rename left the conditions on the new name, so the queries referred to a column that no longer existed. Undo and redo now rewrite the conditions back and forth with the column name (the queries themselves stay outside the undo history, as before). A rename to a name the mini DSL cannot read (one with a space or a symbol, starting with a digit, or spelled like a keyword such as `and`) no longer rewrites the conditions into a syntax error that renaming back could not repair; they are left as they are and work again once the name comes back. A rename that touches no condition no longer marks the queries as changed
- **The query definition dialog no longer loses or corrupts parts of a query** — saving a raw-SQL query kept only its SQL Server and SQLite SQL, so SQL for PostgreSQL, MySQL or Oracle added through the MCP `set_query` tool disappeared as soon as any query was edited in the dialog; it is now kept. Setting a parameter or projection field that took its type from a column back to "(none)" kept the column's database type (`nvarchar(50)`) as the type token, which generation cannot resolve; it now goes back to the token typed before the column was chosen, or, for a row loaded with a column, the column's type as a neutral token (empty when the type has no token). Choosing a new column for an ORDER BY row whose column had been deleted now clears the error and enables OK
- **Importing C# code into the current diagram no longer crashes when two primary-key properties map to the same column name** — the parser lets duplicate `[Column]` names through with a warning, but carrying the current diagram's primary-key order over looked the key columns up by name, which threw and sent the app to its crash handling. Such a table now simply keeps the order the code gives

#### Import and export

- **Re-importing from a database or an Excel definition document now asks when only a computed column or a foreign key marker changes** — the check that skips the confirmation when the structure is unchanged did not look at whether a column is computed or carries a foreign key marker, so an import that changed only those replaced the diagram without asking, although the computed setting changes the generated `INSERT` and `UPDATE` and a hand-set foreign key marker was silently dropped
- **Printing a very large diagram at actual size no longer produces an unusable page** — at actual size the paper is the diagram itself, so a diagram with tables placed far apart asked for a page over 1,000 inches on a side, which no PDF or XPS output can produce (their limit is 200 inches). Such a diagram is now reported with its actual size before the print dialog opens, offering to print it scaled to fit one page instead; cancelling prints nothing. Diagrams within the limit are unaffected (an auto-arranged diagram of 1,000 tables measures 100 x 61 inches)
- **Exporting a very large diagram as PNG no longer fails** — the rasterizer refuses anything past its own size limit, so a diagram big enough simply could not be exported as an image (the error said nothing about size). PNG is now capped at 100 million pixels in total: a diagram above that is scaled down to fit, keeping its aspect ratio, and the completion dialog reports the full size and the size actually saved. SVG has no such cap, so export SVG when you need the full resolution
- **DBML now carries names that contain spaces or symbols** — export writes such a table or column name as a DBML quoted identifier (`"Order Details"`). Without the quotes a table name containing a space did not match the `Table` line's form and the table vanished from the import without a word, while a column name broke at the first space and the rest ran into the type (`Order Date date` became the column `Order` of type `Date date`). Names made only of ASCII letters, digits and underscores are written exactly as before
- **DBML no longer mangles a type that contains a space or brackets** — `double precision` and `integer[]` are now quoted on export, as DBML's own rules require, and the import no longer mistakes the brackets of an unquoted array type for the start of the settings block (which turned `integer[]` into `integer`)
- **A `//` inside a DBML string is no longer treated as a comment** — a description holding a URL used to be cut at `//` and lost. DBML block comments (`/* ... */`), including ones spanning several lines, are now recognized as well, and keywords are accepted in any letter case (a lowercase `ref:` line used to fail to parse)
- **A DBML `Ref:` line written before the table it points at can now be imported** — DBML produced by other tools often groups the Ref lines at the top of the file, and in that order the whole import failed with "referenced table is not defined". Ref lines are now resolved once every table has been read; a line that references a table defined nowhere is still an import error reported with its line number
- **An Excel definition document with more than one foreign key between the same two tables can be read back** — a diagram with, say, a shipping address and a billing address both pointing at the same table exported fine but always failed to import, because duplicates were judged by the pair of table names alone. The check now includes the columns that make up the key; two rows that are identical down to their columns are still rejected
- **Mermaid no longer drops part of a column name that contains a space** — a Mermaid attribute line separates type, name and marker by spaces, so `Order Date` used to lose everything after the space. Such names are now folded to `_` (the same treatment the type already gets) and reported among the information the format cannot carry. If folding would collide with another column in the same table, the name that needs no folding keeps its spelling and the folded one gets a number
- **Importing Mermaid no longer gives several relationships the same constraint name** — a Mermaid relationship line must carry a label, and the import took the label as the constraint name. QuickER writes `relates` for a relationship that has no name, and Mermaid from other tools repeats verbs such as `has`, so after an import several relationships shared one name and the DDL failed at the second `ADD CONSTRAINT` on SQL Server, Oracle and MySQL. A label now becomes the constraint name only when it is a single word without quotes, is not `relates`, appears on no other relationship, and is not the name of a primary key or unique constraint. Any other relationship is left without a name, so it gets the default `FK_{child}_{parent}` from the DDL, unless that name is already taken, for example by a second relationship between the same two tables; then it gets the child's foreign key column names appended, or a number
- **Importing DBML or an Excel definition document no longer gives two unnamed foreign keys the same constraint name** — a `Ref` without a name, or a relationship row with an empty constraint name cell, was imported without a name, so the DDL named it `FK_{child}_{parent}`. Two such relationships between the same two tables (a billing and a shipping customer, for example) therefore got the same name, and the DDL failed at the second `ADD CONSTRAINT` on SQL Server, Oracle and MySQL. The import now applies the same rule as Mermaid: a relationship without a name keeps no name while the default is free, and otherwise gets the child's foreign key column names appended, or a number. Names written in the file are kept as they are
- **Importing C# code no longer gives two unnamed foreign keys the same constraint name** — two `[NavigationReference]` attributes without a `ConstraintName` between the same two tables were both imported without a name, so the DDL named both `FK_{child}_{parent}` and failed at the second `ADD CONSTRAINT` on SQL Server, Oracle and MySQL. Both the CLI's `quicker reverse` and the GUI's merge import now apply the same rule as the other imports. A merge import into a diagram that already holds such a pair, as an earlier import made it, fixes the pair too. Names written in the code, and names a merge import keeps from the current diagram, are kept as they are
- **The DBML export no longer invents a foreign key for a relationship without a column mapping** — such a one-to-one or one-to-many relationship was written with the first column of each table, and since the import takes the columns on a `Ref` line as the foreign key, re-importing it created a foreign key nobody had defined (usually on the child's primary key). It is now left out of the file and reported among the information the format drops, as is a many-to-many relationship to a table that has no columns, which used to make the export fail
- **DBML now carries a type that contains a double quote, and text that ends with a backslash** — a type such as PostgreSQL's quoted `"MyType"` is now quoted on export; written bare, the import took its quotes off and turned it into another type, or read the rest of the line as part of it. A note or index name ending with `\` (`'C:\\'`) followed by another setting no longer swallows that setting, and a composite foreign key whose quoted column names contain `)` no longer fails the import
- **The DBML export now reports computed columns** — DBML cannot mark a column as computed, so such a column comes back as an ordinary one; it is now listed among the information the format drops
- **Mermaid now carries table names that contain a space, and columns without a type** — a table name with a space was written bare, so a relationship line naming it could not be read and the whole import failed. Such names are now written in double quotes (`"Order Details"`), which Mermaid allows, and read back with the quotes removed; names Mermaid accepts bare, Japanese and `dbo.Orders` included, are written exactly as before. A `"`, `%` or `\` cannot appear even inside the quotes, so it is folded to `_` and reported. A column without a type used to be written as `id PK` and came back as a column named `PK` of type `id`; it is now written with the type `_`, which the import reads back as no type
- **Mermaid no longer writes types it cannot read back, and reports the ones it changes** — only spaces, parentheses and commas were folded, so a type such as PostgreSQL's quoted `"MyType"` broke the attribute line on import, and `enum('a','b')` produced invalid Mermaid. Every character Mermaid does not allow in a type is now folded to `_`, and a type the import cannot restore (`nvarchar(max)`, `double precision`) is listed among the information the format drops. Types it already wrote correctly, such as `decimal(10,2)` and `integer[]`, are unchanged
- **The Mermaid export now reports computed columns and a unique constraint hidden behind a foreign key marker** — a column carries one key marker and `FK` comes before `UK`, so a single-column unique constraint on a foreign key column (the one that makes a relationship one-to-one) was dropped without a word. It is now reported, as are computed columns, which come back as ordinary columns
- **Mermaid no longer breaks on a constraint name that contains a space or a symbol** — the export wrote the constraint name bare as the relationship label, so a name such as `FK orders customer` made the line invalid Mermaid, which neither Mermaid nor the import could read. Such a name is now written in double quotes, with a `"` folded to `_`; names Mermaid accepts bare are written as before. Because the import never takes a quoted label as a constraint name, the export now reports relationship constraint names that would not come back as the same name: quoted ones, a name shared by several relationships, and a name equal to `relates` or to a primary key or unique constraint name
- **An Excel definition document can always be read back** — the export writes a relationship whose columns cannot be resolved with both column cells empty, and a table without columns as a detail sheet with no column rows, but the import rejected both, so such a diagram exported fine and then failed to import. Both are now read as they were written; two such relationships between the same tables are not counted as duplicates, and a row with only one of its column cells empty is still an error
- **Re-importing an Excel definition document no longer resets computed columns, the order and names of unique constraints, or the order of a composite primary key** — the document carries none of these, so a merge import turned computed columns into ordinary ones, put a constraint's columns into table order (`UNIQUE (b, a)` became `(a, b)`), replaced a constraint's name with the synthesized one, and put a primary key whose order you had set back into column order, so re-importing an unchanged document asked to replace the diagram and the next DB sync rebuilt the primary key. The merge import now takes them from the current diagram: a constraint over the same set of columns keeps its column order and name, a matching column keeps its computed setting, and a primary key with the same set of column names keeps the order the current diagram set (the rule the merge import of C# code already used)
- **Exporting onto the diagram file that is open is refused** — choosing the open diagram file as the export target (for example with Schema JSON) replaced it with the exported content, and because QuickER then saw its own write as an outside change, a diagram without unsaved changes was reloaded from it and lost its layout. The export now writes nothing and says to use Save for the diagram itself
- **Re-importing an Excel definition document that has lost its target database no longer switches the diagram to SQL Server** — a document saved again by another application (for example Google Sheets) can drop the property that records the target database; the import then fell back to SQL Server and switched the diagram to it without asking, while the column types stayed those of the original database. Such a document now keeps the current diagram's target database
- **The SVG export no longer writes characters XML does not allow** — a control character in a name, a type or a description (a line break pasted from Word is one) made the SVG unreadable to browsers and XML tools. Such characters are now written as a space
- **The date in the print header no longer depends on the system's regional settings** — it is always written as `yyyy/MM/dd HH:mm` in the Gregorian calendar; before, the separator followed the region and a Thai system printed the Buddhist year

#### DB import & connections

- **Saving a connection profile now asks before overwriting a different profile** — the save button picks its target by the profile name, so typing a name that an existing profile already had replaced that profile's server, user and saved password without a word, and with no way back. Overwriting a profile other than the one currently selected now asks first; saving over the profile you loaded is unchanged, and so is saving under a new name (which still creates another profile)
- **A momentary read failure no longer wipes every saved connection profile** — saving, renaming, and deleting re-read `connections.json` before writing it back, so another program holding the file for an instant turned into "read nothing, write nothing back" and every saved profile vanished without a word (only the orphaned secret files remained). Reads now tell "the file is missing", "the file is corrupted" and "the file cannot be read right now" apart: a transient failure is retried as persistently as the write side does, and if it still cannot be read the operation is **cancelled without writing anything** and reported in the status line
- **OK is disabled while a connection test is running** — the test cannot be cancelled, so confirming and closing left it holding the connection on its own, hitting the same database at the same time as the import or sync that started right after
- **The DB Sync dialog no longer restores a last-used connection from a different dialect** — sync fixes the target DB to the diagram's dialect, yet it still copied the host, file path and service name of the last connection into the fields. Those fields mean different things per dialect, so values that could not connect were left in place under a "restored" message
- **Saving with "Save password" ticked but the box empty now clears the tick as well** — no encrypted file is written for an empty password, so only the tick was stored and the dialog showed a password as saved when there was nothing to restore. Overwriting a saved password with an empty box now drops both the encrypted file and the tick
- **A connection profile can now be renamed** — the save button saves the current input under the name in the box, so typing a new name made a copy and left the old profile (and its saved password) behind. A "Rename" button next to it changes only the name of the selected profile, keeping its connection settings and its saved password; renaming onto a name another profile already uses asks first, the same way saving does
- **A saved password that merely could not be read for a moment is no longer deleted silently** — when the encrypted file could not be read or decrypted (another program holding it for an instant, or a file encrypted by another user or machine), it was treated like an unsaved password. Renaming the profile in that state wrote the empty password back and deleted the encrypted file. Renaming no longer touches the password at all. When the password cannot be read, the password box is left empty and the status line says so, and saving over that profile with the box still empty and "Save" ticked is refused (enter the password again, or clear the "Save" tick, and then save). Restoring the last connection reports an unreadable password the same way
- **A failure while writing connection profiles no longer closes the app** — saving, renaming, deleting, and recording the last connection on OK did not catch failures on the write side (a full disk, a failure to write or delete an encrypted file, and so on). The failure is now reported in the status line, and the list is reloaded from the file because the change may have been applied only partly. OK still goes ahead when the last connection cannot be recorded
- **A failure while saving a connection no longer pairs it with the saved password of another connection** — the password of the last connection is kept in one file whatever the server, and a profile's in a file named after the profile, so when `connections.json` was written but the encrypted password file was not, the new server was restored with the old server's password and connecting sent it there. The old encrypted file is now removed before `connections.json` is written and the new one is written after it, so a failure at any step leaves the connection without a saved password (enter it again) instead. The trade-off: if `connections.json` itself cannot be written, the profile keeps its old settings but loses its saved password. Deleting or replacing a profile no longer leaves its encrypted password file behind when that file cannot be removed, and a failure to record the last connection on OK is now reported instead of being dropped
- **A profile name with spaces before or after it now matches the existing profile of that name** — the lookup used the name with the spaces and the save used it without them, so adding a space slipped past both the overwrite prompt and the overwrite itself and left two profiles with the same name
- **Saving or renaming a profile no longer refills the fields from the saved values** — right after saving a profile without "Save" ticked the password box went blank, and right after renaming, unsaved edits in the fields reverted to the saved values
- **An invalid port is no longer replaced by the default port without a word** — values that were not numbers, or were 0 or less, were treated as the default port, so mistyping `1543z` could connect to a different instance on the default port (and, for sync, run DDL against a different database). Only an empty box now means the default port. A value that is not a number or is outside 1 to 65535 stops OK, the connection test, and saving the profile. Saving the profile now checks the command timeout the same way (until now only saving turned an invalid value into the default without a word)
- **The connection dialog now opens even when `connections.json` has a null list or null entries** — a file edited by hand into `"profiles": null` or similar closed the app as soon as the dialog opened. A null list is read as empty and null entries are skipped (they disappear on the next save)
- **Deleting a connection profile now asks with a warning** — the deletion removes the encrypted file of the saved password too and cannot be undone. It now uses the same level of prompt as overwriting a different profile
- **The replacement confirmation no longer appears when an import differs from the current diagram only in the order of tables or relationships** — the signature that decides whether to ask sorted names with the current culture, so two names the culture treats as equal (a precomposed and a decomposed character, or a name with and without a soft hyphen) kept the order they came in. Names are now sorted ordinally

#### AI chat & MCP

- **`remove_relationship` can now remove a relationship that has no stored constraint name** — when two such relationships ran in the same direction between the same tables, no `constraint_name` matched either of them. They are now picked by the name the generated DDL gives the foreign key, and `get_diagram_summary` and the candidate list show that name followed by `(default name)`. In the built-in chat and over MCP
- **An editing tool call that changes nothing no longer rewrites the diagram file** — for example, `set_column_property` with `is_nullable: true` on a primary key column (which is ignored), or setting a value the diagram already has. The rewrite changed the file's timestamp and made the GUI reload the diagram or ask about an external change
- **The MCP tools no longer fail at once when another process is saving the same diagram** — a read that collided with the GUI's or another server's save failed with "being used by another process". It is now retried briefly, as settings files already were. The GUI's open and reload share the same read
- **`create_diagram` no longer overwrites a diagram that another process creates at the same moment** — it checked that the file did not exist and then wrote it with a call that replaces an existing file
- **A diagram saved by a newer QuickER that this version cannot read is no longer reported as "not valid JSON"** — the MCP tools now say that a newer version of QuickER saved it. A `Version` below 1 is reported with its value instead of as a missing `Version`
- **`set_query` no longer refuses a definition because of SQL it does not use** — with `implementation` = `dsl` or `manual`, an unknown dialect key or a non-string value in `sql` refused the save, although that SQL is not saved. These are now warnings, and they still refuse the save with `implementation` = `sql`
- **`set_query` now warns about SQL and ordering that the generated code does not use** — SQL for `postgresql`, `mysql` or `oracle` (the code generator implements raw SQL only for `sqlserver` and `sqlite`, so the method becomes a contract to write by hand), and `order_by` with `implementation` = `sql` or `manual`. Both are still saved, as in the GUI
- **`set_query` refuses the same dialect given twice in `sql`** — keys that differed only in letter case, such as `sqlserver` and `SqlServer`, kept one and dropped the other without a word
- **`set_query` reports declared parameters as unused when a DSL query has no condition** — the generated method took the parameters and returned every row, with no warning
- **A named query whose table is no longer in the diagram can be removed, and no longer blocks a result type name** — `list_queries` showed such a query under `(unknown entity)`, but `remove_query` matched by table name and could not reach it, and its result type name kept new projections from using the same name although code generation skips the query. `remove_query` now removes it by `query_name` when `table_name` names no table
- **Multi-line tool responses now use LF line breaks only** — the named-query tools mixed LF and CRLF within one response on Windows, and `get_diagram_summary` used CRLF in the built-in chat but not over MCP

#### AI chat & mock generation

- **A saved API key that cannot be read is no longer deleted silently** — a key saved by another user or on another PC, or a damaged file, was treated as empty, so clearing the Save check box or saving the connection settings deleted the encrypted file. When the key cannot be read, a note now appears under the key box, and the saved key is neither overwritten nor deleted until you enter a new one
- **Creating a new mock folder no longer overwrites a `mock.json` another process created in the meantime** — the file was checked for and then written, so a `mock.json` created in between was overwritten. It is now created with a write that does not replace an existing file, and an existing one gives the same error as before
- **The mock project's `design/mock/` no longer includes temporary files left by an interrupted write** — files such as `mock.json.<GUID>.tmp` left in the mock folder were copied as they were
- **Mock generation on Copilot now auto-approves writes and reads under an output folder at the root of a drive** — with an output folder such as `D:\`, the check compared paths against `D:\\` and approved nothing, so every file the agent tried to write was refused
- **A mock project name with spaces around it is no longer refused** — the generate button checked the name as typed while generation uses it with the spaces removed, so ` MockApp` could not be generated
- **The API key backend of mock generation no longer reads a screen file outside the mock folder** — the screen names in `mock.json` were checked when the folder was opened, but the screens read as material for the AI were not, so a `mock.json` changed afterwards to name an absolute path or `..` made the backend send that file to the AI. Such a name is now skipped
- **The mock preview no longer lets a page save files to the Downloads folder** — a script in the AI's HTML could start a download (for example a `run.bat` it made itself), which was saved to Downloads and could be opened from WebView2's download list. All downloads in the preview are now cancelled. A blocked request also no longer slips through when its blocking response cannot be created: the response is made once when the preview starts, and if it cannot be, the preview is not used
- **The mock project's final verification build no longer goes ahead without asking when the AI has hidden a folder's contents from QuickER** — the check for build settings the AI added skipped any folder it could not list, so an AI that denied QuickER the right to list the output folder made every change disappear from the check, and a `.csproj.user` it had written ran during the build. A folder that cannot be listed, the output folder itself included, is now always shown in the confirmation (the output folder as `.`)
- **An error during a Claude Code turn other than a cancellation no longer leaves the claude process running** — the process was stopped only when the turn was cancelled; it is now stopped whenever the turn or the login check does not finish normally
- **The revision times in the mock resume prompt and the file names of pasted images now use the Gregorian calendar whatever the current culture is** — with Thai, for example, they were written in the Buddhist calendar (2569 for 2026)

Two calls on the same file could therefore both report success while the later save erased the earlier change, and a call that read the file while another call was saving it could fail with a sharing violation. `quicker mcp` now handles the calls one at a time, the code generation tools included. ## [0.2.0] - 2026-09-24

Highlights of this release:

- A composite primary key now keeps its own column order across DB import, editing, DDL and generated code
- DB import now carries types and constraints more faithfully, and reports what it could not carry across
- The generated base classes can now be extended with `partial` in every output mode
- Fixed data loss in bidirectional sync, and safety issues in AI CLI launching and mock generation

### Breaking changes

#### Distribution & settings

- **Settings and working state moved to `%LOCALAPPDATA%\QuickER`** — the old folder `%APPDATA%\QuickER` is no longer read, so the display language, saved connections (including passwords), API keys, code-generation settings and the recovery snapshot all start from their defaults on first launch. To carry them over, copy the old folder's contents into the new one before the first launch

#### Code generation dialog & CLI

- **The API reference language is now chosen with `ApiDocsLanguage` (CLI: `--api-docs-lang`)** — pick `English` / `Japanese` / `Both`, including a Japanese-only output. The old key `IncludeJapaneseApiDocs` and `--api-docs-ja` are not carried over, so replace them with `"ApiDocsLanguage": "Both"`. If the GUI had the Japanese version turned on as well, choose "Both" again
- **`generate` / `scaffold` and MCP's `generate_csharp` no longer overwrite generated files that were edited by hand** — when a `.g.cs` about to be replaced has been edited since it was generated, the CLI writes nothing, lists the files and exits with code `2`, and `generate_csharp` fails with the same list (the GUI asks instead). Reformatting and line-ending conversion do not count as edits, and files generated before this version are not checked. If a script or CI job rewrites the generated files after generating them, add `--force` (MCP: `force: true`) so regeneration keeps overwriting them. See [docs/code-generation.md](docs/code-generation.md#the-generated-file-header)

#### DB sync & DDL

- **What a column's type and name may contain is now restricted** — DDL generation and schema-sync script generation refuse, naming the place, a type carrying `;`, a quote, a comment marker or a line break, or one smuggling a column clause such as `int NOT NULL`. A line break or control character in a table, column, constraint or query name now stops every generator, including C# generation. Fix the type or the name in the affected diagram

#### Generated code

- **The runtime base types now carry a `Core` suffix** — `EntityBaseCore`, `EditModelBaseCore`, `ValueObjectBaseCore`, `IValueObjectCore`, `IRepositoryCore` / `IRemoteRepositoryCore`, each back end's `…RepositoryCore`, and `MapperBaseCore`. The names the generated code writes (`: EntityBase` and the like) are unchanged. Rename any code of your own that names a runtime type directly — a `where TEntity : EntityBase` constraint, an `is IValueObject` test — to the `Core` form
- **The message and display-name hooks are gone** — the edit model's `Customize…ErrorMessage` / `CustomizePropertyDisplayName`, the value object's `Customize…ErrorMessage` / `CustomizeDisplayName`, and the entity's `CustomizeDisplayName`. Replace wording through `EditModelMessages` / `ValueObjectValidationMessages` and a display name through `GeneratedDisplayNames.Resolve`, branching on the first argument each entry now receives (the property name or the display name) to vary it per type. The default wording is unchanged
- **The mapper's `includeRemoved` argument is now required** — pass `true` when building a graph to save and `false` when building one to display (the old default of `false` left deleted rows out of the save). Code that derived from `MapperBase<,>` by hand and overrode `CreateEntityCore` and the like should move that logic to `LoadColumns` / `CompleteLoad`
- **`CheckUniquenessAsync` is now declared on the common surface `IRemoteRepositoryCore<TEntity, TKey>`** — callers are unaffected. A hand-written test double or adapter implementing a repository contract now has to provide this member
- **With value objects on, same-named columns whose C# types differ are now a generation error** — a diagram where, say, one `payload` column is `varbinary` and another is `varchar` used to unify them into one value object with a warning, which made reading the narrower column throw at run time (or silently changed comparison semantics). Align the column types in the diagram, or rename the columns so they stay apart. A length or precision mismatch alone still warns and unifies as before
- **A column named `row_state` is now a generation error when edit models are generated** — the mapper's state transfer (`entity.RowState = editModel.RowState;`) binds by name, so such a column silently rerouted it to the column property and an edited row was saved as "unchanged". Rename the column in the diagram
- **A named query can no longer take the name of a remote operation** — `SaveMany`, `Ping`, `SyncCeiling` / `SyncChanges` / `SyncKeys` / `SyncPage`, in any letter case; and two queries whose names differ only in case are now rejected as duplicates. The remote endpoints put both on the same route (routes ignore case), so every call to either answered 500. Rename the query in the diagram

#### Bidirectional sync

- **The generated sync classes and interfaces changed shape** — the per-table sync classes (`{Entity}SyncTable` / `{Entity}DirectSyncSource` / `Http{Entity}SyncSource`) are no longer generated; construct the fixed classes instead, passing a descriptor from `GeneratedSyncTables` (no change needed if you use the DI registrations). `SyncTableBase.OnLastWriteWinsUploadedAsync` is gone, and the signatures of `ISyncTable.UploadAsync` and `PropagateDeletesAsync` changed. The local database gains an acknowledgement table, `quicker_sync_ack` (created by `SyncJournal.EnsureCreatedAsync`)
- **A sync download now stops at a row with an unsent local change** — so as not to overwrite it with the server's content. `SyncResult.Truncations` reports where it stopped; resolve the conflict, or drop the entry with `SyncJournal.RemoveTableAsync`, then run the sync again

### Fixed

#### Diagram editing & files

- **The open file's external changes are no longer missed or overwritten without asking** — saving now compares the disk content beforehand and asks if it changed externally, and asks as well before writing back over a file saved in a newer format — including when a Schema JSON export targets one. Also fixed: watching stopped after a burst of changes, and an external write landing right after a save could be missed
- **An external change arriving mid-drag no longer corrupts the diagram or the undo history** — an in-progress move, resize or rubber-band selection is now cancelled back to where it started. A dialog that is already open is not closed
- **A diagram file with a duplicated table or column identifier is now refused instead of being loaded** — it used to load but could not be saved, and switching the target DBMS ended the application. The message names the table, the column and the duplicated identifier. A file that cannot be loaded now also reports what kind of problem it has (invalid JSON, for one)
- **A file saved immediately before a power loss no longer comes back empty**
- **Fixed memory use growing and stray items appearing in the undo history each time a diagram was reopened or imported**
- **A failing Undo or Redo no longer removes the operation from history**

#### DB import

- **PostgreSQL import now reads a column's actual declared type** — `numeric(10,-2)`, the length of `bit(8)`, the unit of `interval`, and an array's element type are now imported correctly. A table whose connecting role has no column privileges no longer imports with zero columns, and a partitioned table no longer disappears whole. Affected columns show up once as a change when re-imported into an older diagram
- **Oracle import no longer imports a `DISABLE`d constraint, a temporary table or a materialized view, and now keeps `NUMBER(10,-2)` and `VARCHAR2(50 CHAR)`** — switching a column with a negative scale to SQL Server, MySQL or SQLite reports it as unconvertible
- **A foreign key pointing outside the imported scope, and two same-named tables differing only in letter case, are now handled correctly** — MySQL used to wire an out-of-scope foreign key to a same-named table by mistake, and PostgreSQL / Oracle / MySQL mixed the columns of same-named tables. Both cases are now skipped with a warning instead
- **The DB import now lists at completion what it could not carry across** — a flattened domain type, an out-of-scope foreign key, unreadable columns, a name collision, a lost partition, and a type that cannot be written into DDL. `quicker scaffold` writes the same list to standard error
- **An SQLite composite foreign key that omits its referenced columns is now imported with the correct column pairs**

#### DB sync & DDL

- **Syncing a description or a column order on MySQL no longer wipes the column's other attributes** — `DEFAULT`, `AUTO_INCREMENT`, the collation and the like are now rebuilt from the live definition. A type change you had not selected is no longer applied along with it either
- **A MySQL sync script no longer drops a foreign key nobody asked about**
- **A table created by a schema sync now carries its UNIQUE constraints** (SQL Server / PostgreSQL / MySQL / Oracle)
- **A sync script is no longer split apart by a description containing a line holding only `GO` or `/`** (SQL Server / Oracle)
- **A name containing a symbol or a line break no longer breaks the output** — a table or column name carrying a quote character, `'`, `$$`, `"`, `\`, `<` or a line break used to break DDL, sync scripts, generated code, XML doc comments, and the DBML / Mermaid output. A backslash in DBML now survives the round trip too

#### C# code import

- **What could not be imported is no longer silently dropped** — a table whose columns cannot be restored at all is now kept with zero columns, and dropping a primary key column or a relationship endpoint is now named in a warning. Also fixed: a referential action written as a number was misread, and a many-to-many relationship's metadata could carry over onto a one-to-many
- **A column's type spelling no longer changes across a C# code import round trip** — a type that collapses onto another spelling, such as `datetime` or `numeric`, now also records the original spelling in `[DbColumnMeta]`, and import restores it. It used to be rewritten, and the next DB sync then emitted a needless `ALTER COLUMN`

#### Generated code

- **CRUD against a schema-qualified table (such as `sales.orders`) no longer fails at run time**
- **A property added through `partial` no longer lands in the SQL as a column** — only a property carrying `[Column]` is treated as a column now. In a configuration that uses EF Core, add `[NotMapped]` to an added property
- **A sub-second part of a date/time column is no longer lost when editing a different column** — the edit model's input string now displays it too
- **A blank input now clears a numeric, date/time, bool or binary column without value objects** — the confirmed value becomes null and the required check decides whether that is acceptable, the same rule the value-object columns already followed. It used to become a conversion error (a binary column, an empty array), so a nullable column could not be set back to NULL from the screen
- **A removed row with an empty required field no longer makes the save throw** — the mapper now skips a removed row's absent non-key values instead of requiring them, so `Validate()` returning true and the save agreeing are one and the same. The key is still required: a delete needs it
- **`AcceptChanges` now cleans up after saved deletions** — a row left in the collection by `MarkRemoved()` leaves the collection instead of coming back as an ordinary row, and a row set aside by `Remove()` becomes Added again, cascade descendants included, so adding the same instance back inserts the whole graph (it used to stay Removed and never be saved). A single cascade child stays Removed on the navigation property; assign null to it after the save
- **A reload during a row edit no longer lets `CancelEdit` roll the loaded values back** — the mapper's load abandons an in-progress row edit, so a cancel arriving afterwards is a no-op instead of restoring the stale pre-load snapshot
- **A value object over MySQL's `tinyint` (`sbyte`) now carries the comparison operators** — it used to derive from the equality-only base, so `OrderBy` on such a column threw at run time
- **A binary value object can now be created from a Base64 string through `TryCreateFrom` / `CreateFrom`** — the same notation the edit models accept. A malformed string is an ordinary conversion error, not an exception
- **A diagram with a column named like `foo_snapshot` next to `foo` generates again** — the generator kept reserving a per-column snapshot member that no longer exists (row-edit snapshots live in one base array), so the legitimate pair was refused as a collision
- **`HasErrors` now raises `PropertyChanged`** — a binding to it (a save button's IsEnabled, say) updates together with the errors, the way `HasChanges` always did
- **An edit-model child collection whose accessor returns null counts as empty** — validation, error collection and accepting changes no longer throw while a lazily initialized collection is still null (the same rule a single child always had)
- **`CreateEntity(editModel, includeRemoved: false)` now leaves a removed single cascade child out as null** — collection elements were filtered, a single child was not
- **A culture clone with a customized `LongTimePattern` renders date/time input strings with its own pattern** — the pattern cache is keyed by the pattern text now, so the clone no longer collapses onto the original culture's cached entry
- **`GetDeclaredInstances()` no longer exposes the registry's internal array** — casting the list back to an array and writing into it can no longer corrupt the shared set
- **Fixed a row whose deletion had been undone still being deleted on save after `Clear()` on an edit-model collection**
- **`ValidateUniqueAsync` no longer queries the database for a row marked for removal**
- **An invalid paging argument on a named query is now a 400 instead of a 500**
- **Fixed the server file's name drifting from the main file's when generating remote services with single-file output**
- **A projection query on a table under bidirectional sync no longer breaks the generated code** — the journaling decorator rebuilt the query methods a second time, the projection's DTO name tripped the build-wide duplicate check, and the delegating method silently vanished (CS0535)
- **A foreign key referencing a column that is not the parent's primary key now joins to that column in EF Core too** — the Fluent configuration emits an explicit `HasPrincipalKey`. EF Core's default silently joined it to the primary key: with matching CLR types, `Include` returned wrong rows; with differing types, the whole DbContext failed model validation. The other backends already joined by the column pair
- **A table without a primary key no longer makes the whole EF Core DbContext throw on first use** — it is excluded from the model (no DbSet, and navigations to it are ignored) and a Warning diagnostic names it: the same line the repository generation already draws for such tables
- **Two named queries on different tables can no longer collide on the server-side request record name** — the record is now named `{Repository}_{Operation}Request` (it is private; nothing on the wire changes)
- **`RepositoryDialects` written in a different letter case (`SQLite`) no longer produces uncompilable output** — the spelling is normalized to the canonical one instead of mixing one dialect's base classes with the other's usings without a diagnostic
- **An IN search on a nullable value-type column now compiles** — the parameter list is lifted to the nullable element type once at the start of the method (`IReadOnlyList<int>` against an `int?` column used to be a CS1929 in the generated code)
- **A named query whose DSL condition cannot type-check no longer breaks the whole generated assembly** — a condition whose emitted C# could never compile (`name > 'M'` ordering a string column, a `CONTAINS` on a numeric column, a fractional literal against an integer-backed value object, a parameter typed by a different column's value object, and the like) is now detected at generation time: the query is skipped with a warning naming the query, the table, the column and the offending operand, and every other query and file generates as before — the same treatment a dangling column reference already received. Nothing that used to compile is newly rejected (an integer column compared with `1.5` still widens to double, for instance). The MCP `set_query` tool still saves such a condition — the file-based server has no dialect type mapper to resolve column types with — and the generation-time warning is where it surfaces (noted in [docs/mcp.md](docs/mcp.md))
- **When repositories are not generated, the dialect selection (`RepositoryDialects`) no longer affects the output** — an EF Core-only run now produces byte-identical output with or without dialect dictionaries; `[SqlColumnType]` attributes and type-unification Info diagnostics used to leak in
- **Ordered comparisons (`<` / `<=` / `>` / `>=`) on a nullable value-object column no longer return NULL rows on the in-memory executor** — value-object comparison operators order null as the smallest value, so only the in-memory backend disagreed with SQL and EF Core (where NULL rows drop out); the emitted condition now carries an explicit "column is not null" premise
- **Equality against a `byte[]` column now matches by content (byte-wise) on the in-memory repository** — `Query()` predicates, DSL equality and uniqueness checks over `byte[]` members are covered; reference comparison combined with the store handing out cloned arrays meant nothing ever matched
- **Raw-SQL parameter matching is now case-sensitive (the same rule the runtime binder uses)** — `@CustomerID` used to match a declared `customerId`, so generation passed and every execution failed; it is now reported as undeclared (warning, that query skipped) plus unused (warning only)
- **A wildcard-less `NOT LIKE 'abc'` no longer matches NULL rows** — it used to fold into a negated equality where the column-side NULL compensation applies, departing from LIKE semantics (a NULL row matches in neither direction); chained prefix `NOT`s now also fold by parity
- **`ValidateUniqueAsync` no longer checks the CLR default (0) when a value-type constraint member has no input** — an unset value-type member cannot carry its unset state onto the entity, so the check now answers true without querying (it is advisory while the required check blocks the save)
- **Named-query definitions that would emit uncompilable code are now diagnosed at generation time** — a parameter named after a C# reserved keyword (`class` and the like), a parameter named `Query` (it hides the repository's `Query()` member), and a projection field named after its result type are generation errors; an IN-list lift variable colliding with a parameter name (`idsValues`) is renamed automatically
- **Numeric literals in DSL conditions accept ASCII digits only** — a full-width digit (`５`) used to pass straight into the C# literal and break compilation; it is now a condition validation error. String literals also escape characters the renderer would turn into real line breaks (U+2028 and friends)
- **Referential actions (ON DELETE) now map to EF Core's DeleteBehavior according to measured behavior** — everything but Cascade used to collapse into `Restrict`; now `SET NULL` → `SetNull`, `NO ACTION` → `NoAction` (client behavior identical to Restrict), and `SET DEFAULT` → `ClientNoAction`. On a SET DEFAULT diagram, deleting a parent through EF used to update tracked children's foreign keys to NULL instead of letting the database apply the default
- **A SQL local variable declared with `DECLARE` in raw SQL is no longer reported as an undeclared parameter** — multi-declarations (`DECLARE @a int, @b int`), initializers, and table variables are recognized; valid queries used to be skipped on the false positive
- **A condition or ordering left on a raw-SQL / manual query is now announced with a warning instead of being silently ignored** — the WHERE / ORDER BY belong to the SQL (or the implementation); generation continues
- **Consecutive blank lines inside a raw SQL verbatim literal are no longer rewritten at generation time** — user SQL containing blank lines inside a SQL string literal used to change silently (blank-line runs outside literals still fold to one, as before)
- **An extremely complex condition (more than 200 ANDs / ORs / NOTs / parentheses combined) is now a validation error instead of a process-killing StackOverflow**
- **A DSL projection that declares a non-nullable field over a nullable value-type column no longer breaks the whole generated assembly** — the combination always fails with CS0266, so the query is skipped with a warning (same treatment as the DSL type check)
- **The raw-SQL single-row body's local (`items`) no longer collides with a parameter of the same name** — it is renamed with a trailing `_` when taken
- **API reference (.g.md) table cells no longer show C# literal escapes (`\"` and the like)** — table-name and description cells now carry the diagram's raw values with only Markdown hardening (pipe escaping, newline folding)
- **An unsupported repository dialect combined with layered output is now reported as a diagnostic instead of an exception** (reachable only through direct library calls)
- **An invalid `RepositoryNamespace` no longer blocks generation in single-dialect non-split layouts where it is unused** — category namespaces are validated only in configurations that actually consume them (split mode, or the non-split multi-dialect layout)

#### Bidirectional sync

- **Fixed sync losing server changes or local edits** — an uploaded row's new version could step over an unfetched change, so that change never came down again. Also fixed: the same run's download overwriting the local edit of a row it had just reported as a conflict, and an upload interrupted part way causing a false conflict or overwriting with a stale value
- **`SyncConflictPolicy.ServerWins` now restores a discarded row's content from the server** — a local edit to a row nobody else had touched used to survive being discarded
- **Delete propagation and acknowledgement matching no longer miss rows on tables with a decimal primary key** — the key-to-text conversion now normalizes the scale (no trailing zeros); SQL Server returns `1.50` rescaled to the declared scale while the local SQLite mirror returns `1.5` as written, so the same row counted as two different keys
- **A table name with two schema qualifiers (the `dbo.sync.orders` shape) is now quoted in sync SQL by the same rule as CRUD and DDL (split at the first dot only)**

#### AI chat & mock generation

- **Fixed the Claude Code chat starting a new session on every turn with `claude` installed through npm** — a multi-line system prompt was cut short, taking the `--resume` / `--model` arguments after it with it
- **The AI tools now make a primary key column NOT NULL through every host** — only the external MCP server used to be able to write a nullable primary key column into the diagram
- **Generating a mock project into an output folder that already holds a project now asks before overwriting**
- **Mock project generation now handles interruption, timeout and app exit correctly** — an interruption under Claude Code is now reported as an interruption, and the final verification build is aborted after 10 minutes. Closing the app now interrupts the AI chat and mock generation child processes too
- **Fixed the mock project artifact check and log display** — the check now looks only inside the generated project folder and no longer fails on an unreadable subfolder. The log display no longer slows down during a long generation

#### CLI & MCP

- **A failed MCP tool call is now returned as an error (`isError`)**
- **`quicker reverse` now creates the output folder**
- **`quicker reverse` no longer overwrites a diagram saved in a newer format** — it writes nothing and exits with code `2`; add `--force` to overwrite it anyway
